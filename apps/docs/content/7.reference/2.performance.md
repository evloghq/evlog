The cost of logging depends on the fields you collect, serialization, redaction, output, and delivery. The repository includes microbenchmarks for those operations, but an event-construction measurement is not an end-to-end request cost or a delivery guarantee.

## evlog vs alternatives

The [comparison suite](https://github.com/evloghq/evlog/blob/v3/packages/evlog/bench/comparison/vs-alternatives.bench.ts) gives every logger the same work: build the record, serialize it to one JSON line, and write that line to the same no-op stream. evlog reaches the stream through a drain, as a deployed application does. Within a group every logger writes the same fields. Delivery to a backend is not part of any row.

### Results

Microseconds per call, lower is better. Median of three runs, `NODE_ENV=production`, on an Apple M4 Pro with evlog 3 (beta), pino 10.4, LogLayer 9.4 over pino, LogTape 2.4 and winston 3.19. Every minimum was within 5% of its median, except winston's, within 11%.

Node.js 24.22 (LTS):

| Work | evlog | pino | LogLayer | LogTape | winston |
| --- | ---: | ---: | ---: | ---: | ---: |
| One record, 5 fields | 0.67 | 0.59 | 0.98 | 3.14 | 2.84 |
| One request record | 1.22 | 1.02 | 1.80 | 4.09 | 5.18 |
| A request record with an error | 1.99 | 1.80 | 2.61 | 5.71 | 4.65 |
| Redact two paths in a request record | 3.15 | 1.40 | | | |

Node.js 26.7:

| Work | evlog | pino | LogLayer | LogTape | winston |
| --- | ---: | ---: | ---: | ---: | ---: |
| One record, 5 fields | 0.57 | 0.62 | 1.03 | 3.31 | 3.20 |
| One request record | 0.98 | 0.84 | 1.71 | 4.57 | 5.64 |
| A request record with an error | 1.21 | 2.25 | 3.21 | 6.13 | 4.64 |
| Redact two paths in a request record | 3.36 | 1.21 | | | |

On these rows evlog is 2.3 to 5.8 times faster than LogTape and winston, and 1.3 to 2.7 times faster than LogLayer over pino. Against pino it ranges from 1.2 times slower to 1.9 times faster, depending on the row and the Node.js version. consola, with a reporter that serializes its log object, takes 0.57 µs for one record on Node.js 24. It has no equivalent for the other rows.

### Where evlog is slower, and why

- **A request record, against pino.** evlog creates a request logger, checks every `set()` payload for `Error` objects so they are logged with their name, message and stack, and calls the drain through a promise so a failing drain cannot break the request. pino serializes the record it is given and writes it.
- **Redacting paths, against pino.** evlog copies the whole event and checks every key against the paths. pino only visits the paths you configure. evlog's default redaction in production, which also masks emails, card numbers and other built-in patterns in every string, takes 3.17 µs for the same request on Node.js 24. No other logger here scans values by default, so that row has no counterpart.

Moving from several records per request to one accumulated event changes how many lines you write, not the cost of each line. The [log cost guide](/reference/cost) separates event-based and byte-based billing and lets you use your own traffic assumptions.

## What affects event construction?

`log.set()` merges fields into the pending context. `emit()` selects severity, applies sampling and configured redaction, and prepares the final event. With JSON console output enabled, serialization runs during output. A drain can serialize again for its own protocol.

The amount and shape of data matter: nested objects, error stacks, redaction patterns, and plugin hooks exercise different paths. Timing a small event without output does not price a large event with custom enrichment and export.

## When evlog might not win

A [Pino transport](https://github.com/pinojs/pino/blob/main/docs/transports.md) can run in a worker, separating transport processing from the calling thread. Initial record serialization still happens in the logger. Winston formats and transports, or a Consola reporter, may already implement the exact output your application needs. Keeping that configuration can be preferable to migrating it.

There is no supported claim here that evlog wins every other workload. Measure throughput and application latency with your destination, payloads, and delivery policy. Include queued work and final flushing, not just the time it takes to enqueue an event.

## What it costs on one real request

Measure the complete path you deploy:

1. Run a representative handler with `enabled: false` to establish a baseline without logging.
2. Enable event construction, the redaction rules and enrichers you use, and the actual output configuration.
3. Exercise successes, errors, and the largest expected context. Record request latency distributions as well as throughput.
4. Include batching, retries, queue limits, and shutdown or background-delivery behavior. Confirm records reach the destination.

Do not add means from unrelated microbenchmarks and label their sum a measured request cost. Work may overlap, take different branches, or happen asynchronously. Network delivery and backend indexing need their own measurements.

## Bundle size

An emitted entry-point file is not the size of the application bundle that imports it. Shared chunks and selected exports contribute to the final size. The server core, `evlog/http`, framework integrations, and drain adapters also target different uses.

Build the entry points you plan to import and measure the resulting bundle. For a comparison with another library, keep the bundler, target, minification, compression, versions, and imported capabilities consistent. A server bundle cannot establish which browser logger is smaller.

## Detailed benchmarks

| Suite | Question it helps answer |
| --- | --- |
| `bench/core/` | How do context size, merging, emission, and errors affect construction? |
| `bench/comparison/` | What does each logger cost to write the same JSON line? |
| Other files under `bench/` | What do the corresponding enrichers, middleware, sampling, or pipeline operations cost? |

Read each setup before interpreting a result: silent output, disabled drains, and reused fixtures can change the work included. [Sampling](/learn/sampling) and [Configuration](/reference/configuration) describe the controls you should match to your application.

## Methodology & trust

### Can you trust these numbers?

The [benchmark source](https://github.com/evloghq/evlog/tree/main/packages/evlog/bench) is available for inspection. A trustworthy comparison also needs equivalent work, versioned inputs, and reproducible output. The comparison suite writes the same fields to the same stream for every logger; check a library's output line before adding it to a group.

When publishing a run, record the commit, dependency versions, runtime, CPU, operating system, warmup and measurement settings, payload, redaction, and destination. Repeat it to expose variation. State whether the number measures construction, serialization, queued delivery, or completed delivery.

### Run it yourself

From a checkout with dependencies installed, run the suite once rather than leaving it in watch mode:

```bash [Terminal]
cd packages/evlog
pnpm exec vitest bench --run
pnpm exec vitest bench --run bench/comparison/
pnpm exec tsx bench/scripts/size.ts
```

Vitest writes benchmark results to `bench/results.json`. Keep that output with the run metadata when sharing a measurement. The size script measures its declared imports, so inspect them before applying the result to your own bundle.
