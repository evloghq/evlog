evlog 3 removes the APIs deprecated in 2.x, changes a few defaults, and raises the Node.js floor to 22. This page lists each breaking change with the code to change and its upgrade status.

Every entry gives what changed, who is affected, a before and after snippet, and the upgrade status. The status says what `npx @evlog/cli@latest upgrade` does with the change:

- **auto**: the command rewrites the code for you.
- **report**: the command lists the lines it cannot rewrite, and you change them.
- **manual**: nothing is rewritten. You change the code yourself.

::callout{icon="i-lucide-construction" color="warning"}
`npx @evlog/cli@latest upgrade` is planned and not released yet. Until it ships, make the changes by hand with the snippets below.
::

## Node 22 or later

**Who:** every project.

`engines.node` is now `>=22.0.0` in every published package: `evlog`, `@evlog/cli`, `@evlog/nuxthub`, `@evlog/telemetry` and `@evlog/signals`. Before, `evlog`, `@evlog/nuxthub` and `@evlog/telemetry` declared `>=18.0.0`, `@evlog/signals` declared `>=20.0.0`, and `@evlog/cli` already declared `>=22.0.0`.

Nuxt 4.6.1 declares `^22.22.3 || ^24.15.0 || >=26.0.0`, so Nuxt projects should run one of those ranges.

```diff
 "engines": {
-  "node": ">=18.0.0"
+  "node": ">=22.0.0"
 }
```

**Upgrade status:** manual.

## Browser entry removed

**Who:** projects that import from `evlog/browser`.

The entry was deprecated in 2.x and re-exported `evlog/http` under other names. It is removed. The types follow the rename: `BrowserDrainConfig` is now `HttpDrainConfig`, and `BrowserLogDrainOptions` is now `HttpLogDrainOptions`.

```diff
- import { createBrowserDrain, createBrowserLogDrain } from 'evlog/browser'
+ import { createHttpDrain, createHttpLogDrain } from 'evlog/http'
```

**Upgrade status:** auto (the import path and the four renames).

## Credential aliases removed

**Who:** projects that pass `token` to the Axiom drain or `sourceToken` to the Better Stack drain, set the matching environment variables, or set `evlog.axiom.token` in the Nuxt module.

The drains and the Nuxt module read the API key from `apiKey` only. A project that still sets only the old name has no key, so the drain logs a missing-key error and sends nothing. `applyDeprecatedAlias` is no longer exported from `evlog/toolkit`.

| Removed | Use |
| --- | --- |
| Axiom `token` option | `apiKey` |
| `AXIOM_TOKEN` / `NUXT_AXIOM_TOKEN` | `AXIOM_API_KEY` / `NUXT_AXIOM_API_KEY` |
| Better Stack `sourceToken` option | `apiKey` |
| `BETTER_STACK_SOURCE_TOKEN` / `NUXT_BETTER_STACK_SOURCE_TOKEN` | `BETTER_STACK_API_KEY` / `NUXT_BETTER_STACK_API_KEY` |
| Nuxt `evlog.axiom.token` | `evlog.axiom.apiKey` |

```ts
// before
createAxiomDrain({ token: process.env.AXIOM_TOKEN, dataset: 'logs' })
createBetterStackDrain({ sourceToken: process.env.BETTER_STACK_SOURCE_TOKEN })

// after
createAxiomDrain({ apiKey: process.env.AXIOM_API_KEY, dataset: 'logs' })
createBetterStackDrain({ apiKey: process.env.BETTER_STACK_API_KEY })
```

**Upgrade status:** auto for the options and the Nuxt option. Report for the environment variables, which you rename in your `.env` files and deployment settings.

## PostHog events drain removed

**Who:** projects that call `createPostHogEventsDrain()` or import `PostHogEventsConfig`.

Both were deprecated in 2.x. Use the main drain in events mode, which takes the same options. `sendToPostHogEvents()` and `sendBatchToPostHogEvents()` are unchanged.

```diff
- import { createPostHogEventsDrain } from 'evlog/posthog'
- initLogger({ drain: createPostHogEventsDrain({ eventName: 'server_request' }) })
+ import { createPostHogDrain } from 'evlog/posthog'
+ initLogger({ drain: createPostHogDrain({ mode: 'events', eventName: 'server_request' }) })
```

**Upgrade status:** auto.

## Logger storage moved

**Who:** custom framework integrations and adapters that import `createLoggerStorage` from `evlog/toolkit`.

`createLoggerStorage` is exported from `evlog/toolkit/storage` only. That entry has exported it since 2.x. The main toolkit no longer pulls in `node:async_hooks`, so framework integrations built on it stay edge-safe.

```diff
- import { createLoggerStorage, defineFrameworkIntegration } from 'evlog/toolkit'
+ import { defineFrameworkIntegration } from 'evlog/toolkit'
+ import { createLoggerStorage } from 'evlog/toolkit/storage'
```

**Upgrade status:** auto.

## eve redactMessage

**Who:** projects that set `redactMessage` on the eve hook.

::callout{icon="i-lucide-clock" color="neutral"}
Not merged on the v3 branch yet. The replacement lands in a later beta. Today `redactMessage` still works and logs a deprecation warning.
::

The planned replacement is the `message` option. `redactMessage: true` maps to `message: 'omit'`, and `redactMessage: false` maps to `message: 'preview'`.

```ts
// before
export default defineEvlogHook({ redactMessage: true })

// after (planned, later beta)
export default defineEvlogHook({ message: 'omit' })
```

**Upgrade status:** set when the change lands.

## Error status fields

**Who:** code that reads `statusCode`, `statusText` or `statusMessage` on an `EvlogError`, and drains or saved queries that read those fields from logged events.

Two changes, both made so that `status` and `message` are the only fields.

First, the `statusCode`, `statusText` and `statusMessage` getters on `EvlogError` are removed. Read `status` for the HTTP status and `message` for the text. A removed field returns `undefined`, and TypeScript reports it. Errors thrown by h3 and Nuxt keep their own `statusCode`, and evlog still reads it from them.

```diff
 const error = createError({ message: 'Payment failed', status: 402 })
-error.statusCode    // 402
-error.statusMessage // 'Payment failed'
+error.status        // 402
+error.message       // 'Payment failed'
```

Second, a logged error carries `status` only. Before, the same error also logged `statusCode`, `statusText` and `statusMessage`, which repeated the other two fields. Trimmed, the logged `error` of `createError({ status: 402, message: 'Payment failed' })` changes like this:

```diff
 "error": {
   "name": "EvlogError",
   "message": "Payment failed",
   "stack": "...",
-  "statusCode": 402,
-  "statusText": "Payment failed",
-  "statusMessage": "Payment failed",
   "status": 402
 }
```

**Upgrade status:** auto on a known `EvlogError` type. Report otherwise.

## Logged error guidance

**Who:** drains and saved queries that read `error.data.why` or `error.data.fix` from a logged event.

A logged `EvlogError` carries `code`, `why`, `fix` and `link` once, at the top of `error`. Its `data` is now only the payload passed to `createError({ data })`, and it is left out when there is none. Before, the logged `data` repeated the guidance fields:

```diff
 "error": {
   "name": "EvlogError",
   "message": "Payment failed",
   "code": "PAYMENT_DECLINED",
   "status": 402,
   "why": "Card declined by issuer",
   "fix": "Try another card",
-  "data": { "retryAfter": 30, "code": "PAYMENT_DECLINED", "why": "Card declined by issuer", "fix": "Try another card" }
+  "data": { "retryAfter": 30 }
 }
```

The HTTP response is unchanged. Its `data` still carries the guidance fields, and `parseError()` reads them on the client. This holds when h3 wraps the error too. Change `error.data.why` to `error.why` in your drains and queries.

**Upgrade status:** manual.

## Status is optional

**Who:** code that reads `error.status` as a number, alert or sampling rules that match on it, and projects that log errors outside HTTP, such as agent turns, jobs, cron tasks and CLI scripts.

`status` is optional on `EvlogError`, on `createError()` options, and on error catalog entries (`defineErrorCatalog`, `defineError`). Core no longer defaults it to 500. An error that never reaches an HTTP response has no `status`, and the logged event leaves the field out:

```json
{ "name": "EvlogError", "message": "Export job stalled", "stack": "...", "why": "No progress for 5 minutes", "fix": "Retry the export" }
```

Every HTTP boundary still answers 500 for an error without a `status`. That covers the Nuxt and Nitro error handlers, h3, Next, Hono, Express, Fastify, Elysia, NestJS, SvelteKit and `parseError()`. Before this change, the same export error also logged `status: 500`.

**Upgrade status:** manual. Check code that reads `error.status` as a number, and any alert or sampling rule that matched on it.

## Changed defaults

**Who:** anyone who sends logs to `evlog/otlp`, PostHog (logs or events mode), HyperDX or Sazabi. HyperDX and Sazabi are built on the OTLP encoder, so they follow the same defaults.

OTLP records now default to the compact shape, with OpenTelemetry semantic conventions on:

- `recordShape` defaults to `'compact'`. The body is a one-line summary such as `POST /api/checkout (500)`, and nested fields become dotted attributes such as `user.id`. In PostHog events mode, nested properties are flattened the same way.
- `semanticConventions` defaults to `true`. Records also carry `http.request.method`, `url.path`, `http.response.status_code`, `exception.*` and `gen_ai.*`, and the resource carries `deployment.environment.name`. The evlog field names stay.

For the same 100 events, the OTLP request shrinks from 151,235 to 140,250 bytes as JSON (2,804 to 2,198 gzipped), and from 76,839 to 63,925 bytes as protobuf.

To keep the 2.x output:

```ts
createOTLPDrain({ recordShape: 'json', semanticConventions: false })
createPostHogDrain({ recordShape: 'json' })
```

**Upgrade status:** auto. The command writes the 2.x values explicitly, so your output does not change until you remove them.

## Nitro entry points

**Who:** projects that import `evlog/nitro`. The entry now serves Nitro 3.

`evlog/nitro` is the Nitro 3 module, and the nitropack (Nitro 2) module moves to `evlog/nitro/v2`. `evlog/nitro/v3` is removed. Nitro 2 stays supported in evlog 3.

```diff
 // Nitro 3
-import evlog from 'evlog/nitro/v3'
-import { useLogger, createError, evlogErrorHandler } from 'evlog/nitro/v3'
+import evlog from 'evlog/nitro'
+import { useLogger, createError, evlogErrorHandler } from 'evlog/nitro'

 // nitropack (Nitro 2)
-import evlog from 'evlog/nitro'
-import { useLogger } from 'evlog/nitro'
+import evlog from 'evlog/nitro/v2'
+import { useLogger } from 'evlog/nitro/v2'
```

The Nuxt module needs no change: `evlog/nuxt` still runs on Nuxt 4's nitropack.

**Upgrade status:** auto. The command rewrites the nitropack imports first, then the Nitro 3 ones, so no import is moved twice.

## Nitro and Nuxt error body

**Who:** client code that reads `statusCode` or `statusMessage` from the JSON body of an error response.

The error body from the Nitro, Nuxt and SvelteKit error handlers carries the status in `status` and the text in `message`. The `statusCode`, `statusText` and `statusMessage` fields are gone. `url`, `error: true` and `data` are unchanged, and `why`, `fix` and `link` stay under `data`.

```diff
 {
   "url": "/api/checkout",
   "status": 402,
-  "statusCode": 402,
-  "statusText": "Payment failed",
-  "statusMessage": "Payment failed",
   "message": "Payment failed",
   "error": true,
   "data": { "why": "Card declined", "fix": "Use another card" }
 }
```

`parseError()` already reads `status` and `message`, so client code that goes through it needs no change. Client code that reads the JSON directly should read `status` and `message`.

**Upgrade status:** manual.

## CLI peer range

**Who:** projects that install `@evlog/cli` next to `evlog`.

On the v3 branch, `@evlog/cli` is `1.0.0-beta.0`. Its peer range is `evlog ^2.31.0 || >=3.0.0-beta.0`, so the CLI installs next to evlog 2.31 or later, and next to evlog 3 betas. The CLI and the library now have separate version lines, so check both versions in your lockfile after you upgrade.

**Upgrade status:** manual.

## Two majors in one process

**Who:** projects where a dependency still loads evlog 2 while your app loads evlog 3.

Each major keeps its own process-wide state: the logger configuration, the drain and the redaction. `initLogger()` in your app does not configure a 2.x copy loaded by a dependency, and the other way round. When both majors load, evlog prints this warning:

```txt
[evlog] Multiple major versions of evlog are loaded in this process (2.x, 3.x). They cannot share request scope or logger configuration: events emitted through the other copy will be undrained and unredacted, and useLogger() may throw. Deduplicate evlog to a single major.
```

To find the 2.x copy, run `pnpm why evlog`. It lists every path that pulls evlog into the tree. With npm, `npm ls evlog --all` shows the same information.

`3.0.0-beta.0` stored its config under the 2.x registry key, so the two copies shared state without the warning ever firing. The fix is planned for `3.0.0-beta.1`, which is not published yet. If you are on `3.0.0-beta.0`, move to `3.0.0-beta.1` once it is out.

**Upgrade status:** manual. Deduplicate the dependency so one major is installed.

## What is not changing

- **Datadog, Loki, ClickHouse and FS** keep their 2.x options and behavior in evlog 3.
- **Sentry** keeps its 2.x options. Issue creation stays opt-in through `issues`.
- **Axiom and Better Stack** lose only the credential aliases above. Their other options stay.
- **Nitro 2** stays supported through `evlog/nitro/v2`.
