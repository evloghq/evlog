Your app has dozens of routes, jobs, and server actions, and you cannot say which of them will be able to tell you why they broke. The observability score is a single number out of 100 that answers that: how much of your code would leave evidence if it failed tonight. Think of it as logging coverage with a grade attached.

`evlog map` computes it in seconds. It reads your source on disk, finds every entry point, checks each one for wide-event coverage, and produces the score plus a ranked list of fixes. Nothing is executed and no traffic is needed.

## Score any project, evlog or not

You do not have to adopt evlog to run this. `evlog map` is static analysis over your source, so it works on any codebase, including one that has never imported evlog:

```bash [Terminal]
npx @evlog/cli map
```

If evlog is not installed, the scan still runs and the score still appears. The wide-event check simply reports that evlog is missing and points you at [wide events](/learn/wide-events), so a low score on a non-evlog project is not an error: it is your baseline. The report tells you exactly which entry points are dark and what adding coverage would look like, which makes `map` a reasonable first command to run before you decide on a logging library at all.

## What the score measures

Each entry point starts at 100 and loses the weight of every requirement it fails. The weights, from [Scoring](/cli/scoring):

| Requirement | Weight |
| --- | --- |
| `wide-event` | 40 |
| `audit` | 25 |
| `structured-errors` | 20 |
| `page-error-handling` | 20 |
| `context` | 15 |
| `error-handling` | 15 |

The global score is a weighted average across entry points, where money and auth routes count double and pages count half. A check that does not apply, such as audit on a route that touches nothing sensitive, costs nothing.

## Logging coverage, section by section

The **COVERAGE** block groups entry points the way you think about your app, so you can see at a glance which layer is blind. This is a real run against the Next.js example app:

::code-collapse
```text [evlog map]
█▀█ ▀▀█   score /100              evlog-nextjs-example · Next.js
█▀█   █   ▰▰▰▰▰▰▰▰▰▰▰▰▰▰▰▰▰▱▱▱    5 entry points scanned
▀▀▀   ▀   good                    ▆▆█▁█

COVERAGE
● API handlers       ▰▰▰▰▰▰▰▰▰▱   92  1 of 3 have gaps
● Pages              ▰▰▰▰▰▰▰▰▱▱   80  1 swallows fetch errors
● Money & auth       ▰▰▰▰▰▰▰▰▱▱   75  missing audit trails

FIX FIRST
1. POST   /api/checkout $ — moves money with no audit trail
   app/api/checkout/route.ts:3 · evlog.dev/use-cases/audit/overview
2. PAGE   / — swallows fetch errors — users see a blank page
   app/page.tsx:1 · evlog.dev/learn/lifecycle

✓ Already solid: /api/error · /api/health
▲ 87 → 100 by fixing the 2 above

────────────────────────────
how this score works → evlog.dev/cli/scoring
▸ evlog map --all every entry point · evlog map <file> inspect one
  --min-score 80 CI gate
```
::

The score alone hides the shape. Here the handlers are fine at 92, but the one page that fetches data swallows errors, and the money route lacks an audit trail. A flat low row would mean no instrumentation at all.

## Where to spend the fixes

**FIX FIRST** names at most three entry points, ranked by what they touch: money, auth, and PII come before a health check. The `▲ 87 → 100` line is the payoff: fixing exactly those two lands you at 100, which is why you start there rather than anywhere else. Run `evlog map <file>` on each one to see the suggested shape before editing.

## The score is deterministic

The same code yields the same score, on any machine, every time. The rule engine parses your source with an AST and applies a versioned rule set, so nothing depends on timing, traffic, or environment. That is what makes the number usable as a gate rather than a vibe.

## Gate it

A score you cannot regress is a score worth keeping. Commit `evlog.map.json` and pass `--baseline` in CI, and any refactor that quietly drops a `log.set` fails the build exactly like a broken snapshot test. `--min-score <n>` sets an absolute floor. Full setup on [CI](/cli/ci).

## Limits / cost

The score is cheap to run but young: the rule set is still being refined, and a release that sharpens a rule can change a verdict on code you did not touch. Pin the CLI version if you gate a pull request on the number. Sensitivity flags (money, auth, PII) are heuristics over imports and route paths, and `evlog map <file>` always shows the reason for a flag, so a wrong call is visible rather than silent. Only five frameworks have adapters today.
