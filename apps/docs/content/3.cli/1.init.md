`evlog map` tells you which entry points are dark. `evlog init` is what you run before that. It does the setup the framework guide describes, in the project you are standing in.

```bash [Terminal]
npx evlog init
```

On a terminal it reads your project, asks what it cannot infer, and shows you the plan before touching anything:

```text [Interactive]

│

│  Axiom, Sentry
```

The production picker is a fuzzy search (type `ax` for Axiom) and takes more than one destination: the same event fans out to each. Extras are grouped and only list what your project can actually use, with the evidence that put them there.

## What it does

1. **Reads your project** with the same analysis [`evlog map`](/cli/map) runs: framework, installed packages, errors you repeat, entry points with no audit trail. That is what the offers are built from.
2. **Installs `evlog`** with the package manager your lockfile implies, unless it is already there. `--no-install` prints the command instead of running it.
3. **Registers the integration**: the Nuxt module, the Nitro module, or the Next.js instrumentation files.
4. **Writes `evlog.config.ts`** with your service name and destinations, dev and production branched in one place, plus batching, enrichers and sampling when you asked for them. The app reads it at runtime, and [`evlog config`](/cli/config) shows what the CLI reads from it.
5. **Teaches your AI agents**, if you let it. The evlog conventions as a block in `AGENTS.md`, and the [agent skills](/reference/agent-skills) via `npx skills add`. Same thing [`evlog agents`](/cli/agents) does; the writes are planned alongside the wiring so you confirm once. Skills already installed are left for `npx skills update`. If the skills CLI fails, the wiring and the block stay and the run exits 1. `--no-agents` skips it.
6. **Runs `evlog doctor`** before it finishes, so the run answers "did it work" instead of telling you to go and check.

Everything it writes is reported line by line, including the parts that were already in place.

If a file cannot be written, the run stops there with `cli.WRITE_FAILED` and exits 1. The error names that file and the ones written before it, under `--json` too. Fix the path or its permissions and run `evlog init` again: what is already in place is left alone.

## It only offers what it can back up

An option that does not apply is not shown, and one that is shown says why:

| Offer | Appears when |
| --- | --- |
| Error catalog | The scan found the same `createError` in more than one file |
| Audit actions | `map` flagged sensitive entry points with no `log.audit()` |
| AI SDK logging | `ai` is a dependency |
| Auth identity | `better-auth` is a dependency |
| Batching and retry | A production destination was picked — there is nothing to batch otherwise |
| Vite plugin | The framework is Vite-based |

Passing one of these as a flag against a project that cannot use it drops it and says so, rather than wiring something inert.

## Non-interactive

Prompts are skipped, and every answer comes from flags and defaults, whenever anything suggests nobody is watching:

| Condition | Why |
| --- | --- |
| `--yes` | You said so |
| `--json` | The payload is the contract; half a TUI in front of it helps nobody |
| stdin or stdout is not a TTY | Piped, redirected, or spawned by a tool |
| `CI` is set to anything but `false` / `0` | A workflow runner has no keyboard |

```bash [Terminal]
evlog init --yes --prod-drain axiom,sentry --extras pipeline,enrichers
evlog init --yes --extras sampling --sampling high
evlog init --json --drain none          # plan and result as JSON, nothing to read
```

::callout{icon="i-lucide-bot" color="neutral"}
**Written for agents too.** The non-interactive path can express every choice the prompts can, so an agent reproduces exactly what a human just did, and it can never end up waiting on a keystroke that is not coming. An unknown `--drain` or `--extras` value stops the run rather than falling back to a default, because silently wiring the wrong destination is worse than a failed command.
::

## It will not overwrite your code

`init` appends; it never rewrites. Concretely:

- A config file is patched **at the exact offsets** of the node it is adding to. Your comments, quote style, and formatting survive. Nothing is reprinted from an AST.
- A file that already exists is left alone and reported as already present. There is no `--force`.
- Anything it cannot do safely becomes a **manual step** with the snippet to paste and the reason it stopped. A `modules` key built from a variable is the common case: there is no correct place to splice a string into an array the CLI cannot see.
- An `evlog.config.ts` you already have is read, never rewritten. A setting the run picked that your file lacks, a drain for instance, becomes a manual step. The service it names, under `service` or `env.service`, becomes the default answer, so the plan shows the name your events carry.

Which makes it safe to run twice. The second run reports what is already wired and writes nothing:

```text [Output]
· nuxt.config.ts already registers evlog/nuxt
· evlog.config.ts already exists
· .env.example already lists the adapter keys
```

Use `--dry-run` first if you would rather see the plan before anything is touched.

## Your settings land in evlog.config.ts

Whatever you answered, service name, destinations, enrichers, sampling, is written to one file at the root of the app, the same one the CLI reads:

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createFsDrain } from 'evlog/fs'

/**
 * Settings for checkout, read by the app and by the evlog CLI.
 * https://evlog.dev/cli/config
 */
export default defineEvlog({
  service: 'checkout',
  // Local NDJSON under .evlog/logs, in development only.
  drain: process.env.NODE_ENV === 'production' ? undefined : createFsDrain(),
})
```

The framework files only point at it. The Nuxt and Nitro modules find the file on their own, and options you pass to the module override it. On Next.js, Hono, Express, Fastify and Effect the generated `evlog.ts` imports it, and on eve the extension file does.

## Per framework

### Nuxt

Adds `'evlog/nuxt'` to `modules`. `useLogger` and `parseError` are auto-imported from there, and `createError` is imported from `evlog`.

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxt/ui', 'evlog/nuxt'],
})
```

### Nitro

Adds the import and the module call, picking the subpath that matches your Nitro major and the evlog major installed: `evlog/nitro` for Nitro 3 and `evlog/nitro/v2` for `nitropack` on evlog 3, `evlog/nitro/v3` and `evlog/nitro` on evlog 2. Creates `nitro.config.ts` when there is none.

```typescript [nitro.config.ts]
import { defineConfig } from 'nitro'
import evlog from 'evlog/nitro'

export default defineConfig({
  modules: [evlog()],
})
```

### Next.js

Creates `instrumentation.ts` and `lib/evlog.ts`, under `src/` when your app lives there, since Next only loads the one that matches. `lib/evlog.ts` starts the logger and builds the handler wrapper from the config:

```typescript [lib/evlog.ts]
import { toLoggerConfig } from 'evlog'
import { createEvlog } from 'evlog/next'
import { createInstrumentation } from 'evlog/next/instrumentation/create'
import config from '../evlog.config'

/** Loaded by instrumentation.ts when the server starts. */
export const { register, onRequestError } = createInstrumentation({
  ...toLoggerConfig(config),
  captureOutput: true,
})

export const { withEvlog, useLogger, log, createError } = createEvlog(config)
```

`init` writes the config import relative to the file it creates, so `src/lib/evlog.ts` imports `../../evlog.config`.

Wrapping handlers stays yours: Next has no ambient request logger, so each route opts in with `withEvlog()`. `init` prints the snippet.

### TanStack Start

Writes the Nitro v3 config with `experimental.asyncContext` enabled. Without it `useRequest()` returns nothing and you get an install that looks complete and logs no business context.

The `evlogErrorHandler` middleware on your root route is a manual step: `__root.tsx` is a component file, and splicing into it is guesswork.

### Hono

Creates `src/evlog.ts` (or `evlog.ts` when there is no `src/`), since Hono has no config file to append to. It starts the logger from `evlog.config.ts` and exports a middleware built from the same file.

Registering it stays yours: your app entry is application code, so `init` prints the two lines to paste.

```typescript [src/evlog.ts]
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { evlog } from 'evlog/hono'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

/** Register once, before your routes: `app.use(evlogMiddleware)`. */
export const evlogMiddleware = evlog(toMiddlewareOptions(config))
```

The config import is relative to the file `init` creates, so a root-level `evlog.ts` imports `./evlog.config`.

### Express

Same shape as Hono: `src/evlog.ts` starts the logger from the config and exports an `evlogMiddleware` built from `evlog/express`, and the `app.use(evlogMiddleware)` line is left for you to paste before your routes.

### Fastify

`src/evlog.ts` re-exports the `evlog` plugin next to an `evlogOptions` object read from the config, so the registration is one line in your entry file: `await app.register(evlog, evlogOptions)`.

### Effect

Detected from the `effect` dependency, for Effect 4 apps served by `HttpRouter`. An app that also lists Next.js, Hono or another framework keeps that framework, and an Effect 3 app (`@effect/platform`) is not detected, since `evlog/effect` needs Effect 4.

`src/evlog.ts` exports the two [`evlog/effect`](/integrate/frameworks/effect) layers built from the config. Providing them to your server layer stays yours, so `init` prints the lines:

```typescript [src/evlog.ts]
import { toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { initLoggerLayer, routerLayer } from 'evlog/effect'
import config from '../evlog.config'

/** Provide to the server layer: it starts the logger when the layer builds. */
export const EvlogInit = initLoggerLayer(toLoggerConfig(config))

/** Provide to the HttpRouter routes: one wide event per request, read with `yield* EvlogLogger`. */
export const EvlogRouter = routerLayer(toMiddlewareOptions(config))
```

### eve

Detected from an `eve` dependency at 1.0 or later next to an agent: `agent/`, or `agents/<name>/agent/` in an agent workspace. It installs `evlog` and [`@evlog/eve`](/use-cases/eve), from the `beta` tag until evlog 3 is stable, and mounts the extension in each agent from the config:

```typescript [agent/extensions/evlog.ts]
import evlog from '@evlog/eve'
import config from '../../evlog.config'

/** One wide event per agent turn, with the settings in evlog.config.ts. */
export default evlog(config)
```

It also writes `instrumentation/evlog.ts` in each agent, the same file as `evlog setup eve`, which puts each turn's trace and span ids on its event. A workspace gets one `evlog.config.ts` at its root and a mount in every member; a member with its own `package.json` is not part of the workspace, for eve or for `init`. Each member's mount sets its own `service`, its eve name: the turns of `agents/support/` report as `support`.

An agent often ships inside a web app. When the project is also a Next.js, Nuxt or other app `init` supports, both are set up from the same `evlog.config.ts`: the agent's mount and, for Next.js, `lib/evlog.ts`, or for Nuxt the `evlog/nuxt` module. `--framework eve` sets up only the agent, and `--framework next` only the app. An `evlog.config.ts` you already have is reused. The app and the agent are two services: the app keeps the one the config names, and the agent's mount sets `<service>-agent`, which the report shows beside it (`eve + next · service web · agent web-agent`):

```typescript [agent/extensions/evlog.ts]
import evlog from '@evlog/eve'
import config from '../../evlog.config'

/** One wide event per agent turn, with the settings in evlog.config.ts. */
export default evlog({
  ...config,
  // The agent's own service, apart from the app's.
  service: 'web-agent',
})
```

A mount that is already there and sets no `service` gets the line to add. An `evlog: {}` block in `nuxt.config.ts` stays where it is: it configures the Nuxt app only, and `evlog.config.ts` is shared by the Nuxt app and the agent. A web app whose eve integration sets `eveRoot` runs its agent from somewhere else; `init` sets up the app and prints the `evlog init --cwd` that sets up the agent.

Nothing an agent already has is rewritten:

- A file under `extensions/` that imports `@evlog/eve`, as `<name>.ts` or `<name>/extension.ts`, counts as the mount. Under a name other than `evlog`, the report says the logs tool is `<name>__logs`.
- An `extensions/evlog.ts` or `instrumentation/evlog.ts` that does something else is left alone, and the lines to add are printed.
- Other extensions and instrumentation files are not touched.

eve 1.0 and `@evlog/eve` require Node 24. When `engines.node`, or `.nvmrc` or `.node-version` without it, allows an older version or says nothing, `init` prints the `engines` line to add. An agent on eve before 1.0 is not set up: `init` says why, and sets up the web app around it if there is one.

#### The agent's own logs

`@evlog/eve` gives the agent an `evlog__logs` tool that reads its own wide events: a signed-in caller reads its own session, a schedule every turn, an anonymous caller nothing. Locally it reads `.evlog/logs`, which the development drain writes, so it works as soon as the agent runs. An interactive run asks whether to keep it; `--no-agent-logs` hides it, which writes `logs: { ...config.logs, access: () => false }` into the mount.

On Vercel the tool reads the project's runtime logs through a Vercel Connect connector, which `init` never picks for you. When the project is linked (`.vercel/project.json`), an interactive run lists the team's connectors that can read runtime logs and asks which to use, offers to create one, or skips. The connector it uses is written to `evlog.config.ts` as `logs: { vercel: { connector } }` and attached to the project the way [`evlog setup vercel`](/cli/logs) does, after showing what the attachment grants. With `--yes`, `init` does not contact Vercel and points at `npx evlog setup vercel` instead.

## Destinations

Two questions rather than one list: nobody sends local development traffic to Axiom, and nobody reads production logs off the box's filesystem. `--drain` sets the development drain (`fs` or `none`); `--prod-drain` takes one or more hosted destinations.

| Id | Destination | Needs |
| --- | --- | --- |
| `fs` | Local files under `.evlog/logs` (dev default) | nothing |
| `axiom` | Axiom | `AXIOM_DATASET`, `AXIOM_API_KEY` |
| `otlp` | Any OpenTelemetry collector | `OTEL_EXPORTER_OTLP_ENDPOINT` |
| `posthog` | PostHog | `POSTHOG_API_KEY` |
| `sentry` | Sentry | `SENTRY_DSN` |
| `better-stack` | Better Stack | `BETTER_STACK_API_KEY` |
| `datadog` | Datadog | `DATADOG_API_KEY`, `DATADOG_SITE` |
| `hyperdx` | HyperDX | `HYPERDX_API_KEY` |
| `sazabi` | Sazabi | `SAZABI_INTAKE_URL` |
| `loki` | Grafana Loki | `LOKI_ENDPOINT` |
| `clickhouse` | ClickHouse | `CLICKHOUSE_ENDPOINT`, and the `evlog_events` table created first |
| `none` | Pretty console output only | nothing |

With one destination on each side, the generated config picks the drain in one line:

```typescript [evlog.config.ts]
export default defineEvlog({
  service: 'checkout',
  drain: process.env.NODE_ENV === 'production' ? createAxiomDrain() : createFsDrain(),
})
```

Picking several production destinations fans the same event out to each. The generated config branches on the environment in one place, so "which drain runs where" is never something to reconstruct:

```typescript [evlog.config.ts]
const drains = process.env.NODE_ENV === 'production'
  ? [pipeline(createAxiomDrain()), pipeline(createSentryDrain())]
  : [createFsDrain()]
```

Every framework branches on `process.env.NODE_ENV`, not `import.meta.dev`: Nitro inlines it as a literal in its production build, and `process.env` type-checks in a fresh Nuxt project before `nuxi prepare` has run.

Batching wraps the network sends only, because buffering a local file write adds latency to the one loop where you want the event on screen immediately.

::callout{icon="i-lucide-key" color="neutral"}
**`init` never asks for a secret.** It prints which environment variables the drain reads and leaves them to you. A setup command that prompts for an API token is one that writes a credential into a file it chose, and the answer lands in your shell history on the way there.
::

## Extras

| Id | What you get |
| --- | --- |
| `enrichers` | Pick from user agent, geo, request size, trace context (`--enrichers`) |
| `pipeline` | Batching and retry instead of one HTTP call per request |
| `sampling` | A rate profile, see below (`--sampling`) |
| `error-catalog` | A typed catalog seeded with the errors you already repeat |
| `audit-catalog` | Typed audit actions for the sensitive routes with no trail |
| `ai` | Token usage, tool calls and cost on AI SDK generations |
| `better-auth` | The signed-in user on every event |
| `vite` | The Vite plugin that strips `log.debug()` from production builds |

An extra that does not apply is dropped and reported, not refused, so `--extras vite,enrichers` does the right thing across a monorepo of mixed apps.

### Sampling presets

Named by the traffic your app takes. Info is what moves: it is the bulk of the volume and the bulk of the bill, and warnings only give way at the top, where halving them still leaves the shape.

| Id | Info | Warnings | For |
| --- | --- | --- | --- |
| `all` | everything | everything | The right answer until volume or cost says otherwise |
| `low` | 50% | 100% | A small app that has started to repeat itself |
| `medium` | 25% | 100% | Steady traffic with a bill worth watching |
| `high` | 10% | 100% | Info is most of what you are paying for |
| `very-high` | 1% | 50% | Trends rather than individual requests |

**Errors are kept at 100% in every tier.** A sampling config that drops errors hides the only events anybody reads at three in the morning. The generated config states it explicitly so the invariant is visible where somebody would otherwise wonder.

**`debug` is never sampled, and never appears in the config.** An unspecified level is kept in full, and debug events only exist because somebody turned them on to chase something: a 5% sample of the logs you switched on to investigate a problem is a 5% chance of seeing the line you needed. Production builds strip `log.debug()` anyway, so there is rarely volume there to sample.

```typescript [evlog.config.ts]
export default defineEvlog({
  service: 'shop',
  sampling: {
    rates: { info: 10, warn: 100, error: 100 },
  },
})
```

### Catalogs are seeded, not scaffolded

`error-catalog` does not write a template with the names filled in. It writes the errors your code already repeats, with the prose you already wrote:

```typescript [server/utils/errors.ts]
export const shopErrors = defineErrorCatalog('shop', {
  /** Currently written inline in server/api/checkout.post.ts, server/api/refund.post.ts */
  CARD_DECLINED: {
    status: 402,
    message: 'Card declined',
    why: 'The issuer refused it',
    fix: 'TODO: what they should do about it',
  },
})
```

`audit-catalog` works the same way, naming an action per entry point `map` flagged as sensitive and untracked. Both land as a to-do list with the types already written, so the migration is a find and replace rather than a design exercise.

## Monorepos

Run from a workspace root and `init` sets up the apps rather than the root package, which serves no traffic. It lists the workspace packages that have a detectable framework. A shared `utils` package has no entry points to instrument, and asks which to wire:

```bash [Terminal]
evlog init                            # pick from the list
evlog init --yes --apps apps/web,apps/api
```

Each app keeps its own service name, taken from its `package.json`.

An `evlog.config.ts` at the workspace root is where settings shared by every app belong. Each app's config then `extends` it and leaves out what the root already sets, so a drain configured once at the root reaches every app:

```typescript [apps/shop/evlog.config.ts]
import { defineEvlog } from 'evlog'
import base from '../../evlog.config'

export default defineEvlog({
  extends: base,
  service: 'shop',
})
```

A config extends one level. When the root config already extends a preset of its own, `init` writes nothing for the app and prints its settings as a manual step instead.

## The local drain

The filesystem drain, and only that one, is **gated to development** in `evlog.config.ts`:

```typescript [evlog.config.ts]
export default defineEvlog({
  service: 'api',
  // Local NDJSON under .evlog/logs, in development only.
  drain: process.env.NODE_ENV === 'production' ? undefined : createFsDrain(),
})
```

A drain that writes files writes them on whatever box serves the request. Turning one on in production without being asked is not a decision a setup command should make for you. Every hosted destination is generated without the guard, because that is what you picked it for.

The directory it writes to is `.evlog/logs`, and evlog gitignores it on first write. It is also what [`evlog doctor`](/cli/doctor) looks for.

An app set up by an earlier version of `init` has `server/plugins/evlog-drain.ts` and `evlog-enrich.ts`. They keep working, and the new config leaves `drain` or `enrich` out while they exist, so no event is sent twice.

## Flags

| Flag | What it does |
| --- | --- |
| `--yes`, `-y` | Skip every question and take the defaults |
| `--framework <name>` | Override detection (`nuxt`, `nitro`, `next`, `tanstack-start`, `hono`, `express`, `fastify`, `effect`, `eve`) |
| `--service <name>` | Service name on every wide event (default: the one your `evlog.config.ts` sets, else your package name, unscoped) |
| `--drain <id>` | Development drain: `fs` (default) or `none` |
| `--prod-drain <a,b>` | Production destinations — see the table above |
| `--extras <a,b>` | Comma-separated, see Extras |
| `--enrichers <a,b>` | `user-agent`, `geo`, `request-size`, `trace-context` (default: all) |
| `--sampling <id>` | `all`, `low`, `medium` (default), `high`, `very-high` |
| `--apps <a,b>` | Workspace packages to set up (monorepo root only) |
| `--dry-run` | Print the plan, write nothing |
| `--no-agent-logs` | eve: hide the agent's `evlog__logs` tool |
| `--no-install` | Do not run the package manager; print the command instead |
| `--no-agents` | Skip all of it: no `AGENTS.md` block, no agent skills |
| `--cwd <dir>` | Set up another app in the workspace |
| `--json` | The plan and result as JSON on stdout (implies non-interactive) |
