`evlog logs` reads the events the [file system drain](/integrate/adapters/self-hosted/fs) wrote and shows them the way you would want to read them: one line per request, the thing that mattered at the end of it, and one request in full when you have its id. It reads files; it never touches the app.

```bash [Terminal]
evlog logs
```

```text [Output]
6 events · .evlog/logs

08:00:00  GET    /api/health                                 200      2ms
10:00:00  POST   /api/checkout                               402    412ms  ✗ Error: Payment processing failed · Card declined by issuer
10:30:00  GET    /api/reports                                200    1.2s   report.id=r-1
11:00:00  POST   /api/refund                                 200     80ms  audit billing.refund user:usr_42 → invoice:inv_1 success
11:30:00  GET    /api/items                                  500     30ms
11:45:00  GET    /api/items                                  warn   700ms  user.id=usr_7

evlog logs errors — the 2 that failed · evlog logs <requestId> — one request in full · evlog logs slow — worst first
```

The newest event is at the bottom, like `tail`. Nothing is written: the fs drain writes on every request and this reads what it wrote, both the compact and the `pretty: true` layout, across the dated files. The files are read one event at a time, so memory does not grow with the log: a view keeps the `--limit` events it shows, and `stats` one duration per event for the percentiles.

## Six views

| Command | Shows |
| --- | --- |
| `evlog logs` | The last 50 events, oldest first |
| `evlog logs errors` | Events that failed: a `5xx` status, an `error` or `fatal` level, or an `error` block |
| `evlog logs slow` | Events over 500ms, worst first (`--over 1s` to move the bar) |
| `evlog logs <requestId>` | Every event carrying that id, in full: request, error with `why`, `fix` and `link`, audit record, then the business fields. The first block of a UUID is enough. A complete id shows only the events carrying it whole, so `wrun_1:turn_1` does not pull in `turn_10` |
| `evlog logs sessions` | One summary per AI session (`gen_ai.conversation.id`), latest first: turns and how each ended, failed tool calls, model and tool calls, tokens with cache reads, the provider-reported cost, the slowest turn and the latest failure. Working time (the turns' durations summed) and elapsed time (first turn's start to last event) are kept apart. Each token count sums the turns that reported it, with `turnsReporting` next to it, and a field no turn reported is left out, not written as 0 |
| `evlog logs stats` | The shape of the traffic: per route, count, errors, p50 and p95, routes with the most errors first; then counts by status class and by level |

## Filters

Filters compose with any view.

| Flag | What it does |
| --- | --- |
| `--since <when>` | Only events after: a duration back from now (`15m`, `2h`, `3d`) or a date (`2026-10-01`, `2026-10-01T09:00`) |
| `--until <when>` | Only events before, same spellings. Without it a read stops at now, so an event stamped ahead of the clock is left out; `--follow` has no end |
| `--level <a,b>` | Only these levels: `trace`, `debug`, `info`, `warn`, `error`, `fatal` |
| `--path <path>` | Only requests on this exact path |
| `--status <n>` | Only this status (`404`) or class (`4xx`) |
| `--where <clause>` | Only events where a field matches, see below; repeat the flag for several clauses, all must hold |
| `--session <id>` | Only one AI conversation: the events whose `gen_ai.conversation.id` is `<id>`, such as an eve session's turns |
| `--over <duration>` | For `slow`: what a request has to exceed (default `500ms`) |
| `--limit <n>` | Most events to show (default 50), or sessions for `sessions` |
| `--expect <a,b>` | Refuse to answer from another store or environment: `files`, `vercel`, `production`, `preview`, `development`. `--expect production` on local files exits 1 instead of printing an empty list |
| `--dir <path>` | Read another directory (default: the project's `.evlog/logs`; in a workspace with no logs at the root, every `apps/*/.evlog/logs` and the like, merged by time with the app in a column) |
| `--source vercel` | Read the linked Vercel project's runtime logs instead of files, see [below](#a-vercel-deployment) |
| `--url <endpoint>` | Read the [memory drain](/integrate/adapters/self-hosted/memory)'s dev endpoint instead of files: a JSON array of events, or `{ "events": [...] }` |
| `-f`, `--follow` | Keep reading as the app writes, like `tail -f`; `Ctrl-C` stops |
| `--json` | The events as JSON on stdout |
| `--cwd <dir>` | Another project in the workspace |

An event delivered twice under the same `idempotencyKey`, for example by a drain write that was retried, shows once. Events without one are never merged.

A time, level, status or limit that cannot be read stops the command (exit 2) rather than silently widening the query.

`--dir` and `--limit` can be set once for the project in [`evlog.config.ts`](/cli/config), as `logs.dir` and `logs.limit`. The flag wins when both are set.

```bash [Terminal]
evlog logs errors --since 1h
evlog logs slow --over 2s --path /api/reports
evlog logs --status 5xx --level error,fatal --limit 20
evlog logs -f --path /api/checkout
```

### `--where`: any field on the event

A clause is a dotted field, an operator, and a value. Numbers compare as numbers, everything else as text, and the field can sit anywhere in the event, which is the point of a wide event: the business fields are there to be queried.

A value is a number when it spells one exactly: `5000`, `-3`, `12.5`. Leading zeros, an exponent, or more digits than a 64-bit float holds keep it as text, so `zip=00123` and a 19-digit id match only themselves. The same reading applies to a field that arrived as text. `>`, `>=`, `<` and `<=` against a number never match a field that is not one.

| Clause | Matches when |
| --- | --- |
| `user.id=usr_42` | the field equals the value (`true`/`false` and numbers are read as such) |
| `audit.outcome!=success` | the field differs |
| `payment.amount>5000` | greater; also `>=`, `<`, `<=` |
| `error.message~declined` | the field matches the regular expression, case-insensitive; an object is matched as JSON |
| `audit` | the field is present |
| `!error` | the field is absent |

```bash [Terminal]
evlog logs --where 'payment.amount>5000' --where audit.outcome=failure
evlog logs errors --where 'error.why~card declined'
evlog logs stats --where user.plan=pro
evlog logs -f --where '!error' --where 'durationMs>1000'
```

Quote the whole clause whenever it carries `>`, `<` or `!`, which the shell reads as redirection or history before `evlog` ever sees them, and whenever the value has a space: `'payment.amount>5000'`, `'!error'`, `'error.why~card declined'`.

## For agents

`--json` returns one envelope: where it read (`origin`: `files`, `url` or `vercel`, and the environments), the time range read (`window`), the view, how many events matched and how many are shown, `coverage`, and the events. A tool that failed and recovered leaves a `warn` event with an `error` block, so `errors` lists it even with a 200 status.

```bash [Terminal]
evlog logs errors --since 2026-11-20 --until 2026-11-21 --json
```

```json
{
  "schemaVersion": 2,
  "sources": [".evlog/logs"],
  "origin": { "kind": "files", "environments": ["development"] },
  "window": { "since": "2026-11-20T00:00:00.000Z", "until": "2026-11-21T00:00:00.000Z" },
  "view": "errors",
  "count": 1,
  "matched": 1,
  "coverage": { "complete": true },
  "events": [ { "requestId": "wrun_A:turn_1", "level": "warn", "status": 200, "eve": { "outcome": "completed", "failedCalls": 1 }, "error": { "message": "Refund service timed out" } } ]
}
```

`coverage.complete` is `false`, with `reasons`, when the read was cut short: Vercel cut lines, or more lines were left past the 10,000 read. An empty result then says nothing about the events it did not reach. `slow --json` adds `over`, the threshold in milliseconds, so "nothing was slow" is always "nothing over N ms".

`sessions --json` carries `sessions` and `sessionsMatched` in place of `events`. `stats --json` carries `stats` (`total`, `errors`, `byRoute`, `byStatus`, `byLevel`) in place of `events`. With `--follow --json`, each new event is one JSON line on stdout, since a stream has no end. The [`analyze-logs` skill](/reference/agent-skills) calls `evlog logs` first and falls back to reading the files only when the CLI is not available.

## A workspace, and a running app

Run from a monorepo root with no `.evlog/logs` of its own, it reads every app that has one (`apps/*`, `packages/*`, `examples/*`, `services/*`), merges the events by time, and shows the app in a column. `--cwd apps/web` reads one app; `--dir` reads one directory.

An app on the [memory drain](/integrate/adapters/self-hosted/memory) (Cloudflare Workers, where there is no file system) has no files to read, but it can expose `readMemoryLogs()` on a dev route. Point `--url` at it; every view and filter works the same, and `-f` polls it once a second. A failed poll is a gap rather than the end, since the app restarting under a follower is normal; if the endpoint stays quiet the run says so once and keeps trying.

```bash [Terminal]
evlog logs errors --url http://localhost:8787/_evlog/logs
```

## A Vercel deployment

On Vercel, evlog prints one JSON line per event, and Vercel keeps those lines as the project's runtime logs. `--source vercel` reads them back, so a deployment needs no drain for `evlog logs` to work on it.

Set it up once, from the project directory:

```bash [Terminal]
npx evlog setup vercel
```

It runs `vercel link` if the directory is not linked yet. When the team already has a Vercel connector that holds an API key, such as the `vercel/mcp` one an agent's Vercel MCP connection rides, it offers to reuse it; otherwise it creates a Vercel Connect connector named `vercel/evlog`. Pick **API Key** when it asks how to connect, and paste a [Vercel access token](https://vercel.com/account/tokens) scoped to the team: Connect stores it, and evlog only ever receives it for the length of a read. A token scoped to your personal account, or one that has expired, gets a 403 on every read; replace the key in the connector's settings. Setup then attaches the connector to the project for production, preview and development, and reads the last hour through it to check. Each step is skipped when it is already done, so running it again is safe. A reused connector is read through once `evlog.config.ts` names it as `logs: { vercel: { connector: 'vercel/mcp' } }`, which setup prints; `--connector vercel/mcp` picks it without asking. A connector's UID is what code passes to Connect, so rename it only together with every caller. The connector shows in the project's Connect tab, where it can be revoked.

To check each step without changing anything, run it with `--check`. It reports the link, the OIDC token, the connector, its attachment, the token exchange, a read of the last hour and, for an eve agent, the trace instrumentation, each on its own line. A connector whose stored key gets a 403 fails on the read, not on the token: Connect issuing a token does not prove the key behind it may read runtime logs. It exits 1 when a stage fails and names what to run, and says which of those steps is interactive.

```bash [Terminal]
npx evlog setup vercel --check
```

```bash [Terminal]
evlog logs --source vercel
evlog logs errors --source vercel --since 2h
evlog logs --source vercel --session wrun_01M7NNNW
```

No token goes in an env var or in your code. The CLI asks Vercel for the linked project's OIDC token with your `vercel login`, exchanges it for a short-lived token from the connector, and takes the team, project and environment from the OIDC token itself, so a read never reaches another project. Connect only issues the token to a project the connector is attached to.

`logs: { source: 'vercel' }` in `evlog.config.ts` makes Vercel the default for a project whose logs live there; `--source files`, `--dir`, `--url` and `-f` still read local files. Every run prints what it read above the events, such as `Vercel prj_… (production) · 2026-11-19 12:00 → 2026-11-20 12:00 UTC`.

Without `--since`, it reads the last day, which is Pro's log retention; Hobby keeps an hour. It reads at most the newest 10,000 log lines, and `--session` narrows them on Vercel's side first. When lines are left, or Vercel cut a line to its size limit so it no longer parses as an event, the output says so under the header and in `notes` with `--json`. `--follow`, `--dir` and `--url` do not apply and stop the command.

## What it will not do

- **It reads local files, a dev endpoint, and Vercel runtime logs.** A remote drain (Axiom, Datadog, …) has its own query language and UI; this command does not wrap them.
