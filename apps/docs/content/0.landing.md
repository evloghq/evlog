  #nuxt
  ```ts [server/api/checkout.post.ts]
  export default defineEventHandler(async (event) => {
    const log = useLogger(event)
    const { cartId } = await readBody(event)

    const cart = await db.findCart(cartId)
    log.set({ cart: { items: cart.items.length, total: cart.total } })

    const charge = await stripe.charge(cart.total)
    log.set({ stripe: { chargeId: charge.id } })

    if (!charge.success) {
      throw createError({
        status: 402,
        message: 'Payment failed',
        why: charge.decline_reason,
        fix: 'Try a different payment method',
      })
    }

    return { orderId: charge.id }
  })
  ```

#headline
FAQ
#title
Before you install
#body
  ::accordion{type="single"}
    ::accordion-item{label="I already use pino. What actually changes?"}
    evlog supplies a context accumulator and integrations that finish the request event. `log.set()` adds fields during the operation, and the emitted event carries its outcome and error together. Pino can also emit a completed object once, with accumulation managed by your application. `createError()` adds `why` and `fix`, and a [catalog](/learn/catalogs) gives recurring failures a stable code. Call signatures, serializers, and output configuration need an explicit migration. See [the comparison for your stack](/reference/vs-other-loggers#choose-the-comparison-for-your-stack).
    ::
    ::accordion-item{label="My app is already in production. Is it too late?"}
    No, and you do not have to guess where to start. `evlog map` reads your source and scores every entry point on the context it will hand you when it breaks, then names the ones to fix first. It needs no traffic, no agent, and no deploy, so you get that list before the next incident instead of during it. Day one or year three, the work is the same list. See [adding it to an app already in production](/cli/map#adding-it-to-an-app-already-in-production).
    ::
    ::accordion-item{label="Do I have to change where my logs go?"}
    No, and you keep the platform you already pay for. evlog produces the events, a drain ships them: Axiom, Datadog, Sentry, Better Stack, PostHog, Loki, ClickHouse, OTLP, or the filesystem. Changing provider is a drain swap, not an architecture change, because your handlers never name a destination. If you are building the platform rather than buying one, that same pipeline is where you plug in. See [how a drain keeps the destination out of your code](/integrate/adapters/overview#send-events-without-naming-a-destination-in-your-code).
    ::
    ::accordion-item{label="Will it cost me more to ship these logs?"}
    It usually costs less. One request leaves one event instead of four lines, which measures **56% fewer bytes and 75% fewer events** on the checkout shape in the [log cost guide](/reference/cost), because the level, timestamp, host and request bindings stop repeating on every line. Which of those two numbers moves your bill depends on your provider: most charge per GB ingested, so you save on bytes, while a provider that also bills per million events indexed rewards the event count instead. Then [sampling](/learn/sampling) drops what you were never going to read and force-keeps errors and slow requests. Price it against your own traffic on [which number moves your bill](/reference/cost#which-number-moves-your-bill).
    ::
    ::accordion-item{label="How much work is it to adopt?"}
    You migrate one handler at a time. `log.info()` behaves like `console.log`, so nothing breaks on the first commit. Two calls are worth learning: `log.set()`, which adds context to the event in flight, and `createError()`, which attaches a `why` and a `fix` to an error instead of a bare stack. See [how much of this you need on day one](/start/quick-start#how-much-of-this-do-you-need-on-day-one), or [what evlog is](/start/introduction) if you want the shape before the code.
    ::
    ::accordion-item{label="What does it cost at runtime?"}
    The core package has **zero runtime dependencies**. Execution cost depends on context size, redaction, output, and delivery. A silent construction benchmark excludes console serialization and remote export, so it cannot establish a fixed cost per production request. Follow [what it costs on one real request](/reference/performance#what-it-costs-on-one-real-request) to measure the complete path on your runtime.
