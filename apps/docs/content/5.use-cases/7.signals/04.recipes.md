Every signal below is a question a rule cannot answer from the fields alone. They ship in the package's demo catalog and run against fixtures with `pnpm --filter @evlog/signals demo -- --mock`, or against the real model with `AI_GATEWAY_API_KEY` set. Copy the ones that match your traffic and change the `when` to your paths.

| Signal | Hook | Question | Why a rule cannot |
| --- | --- | --- | --- |
| `fault` | enrich, cached | Who is responsible: user, us, upstream | A Stripe timeout and a null deref are both a 500 |
| `severity` | enrich | noise, watch or page | Urgency depends on what failed and for whom |
| `retryable` | enrich, cached | Would a retry succeed | Transient and permanent errors share status codes |
| `slow-cause` | enrich | database, upstream, compute | Reading the timings takes a human |
| `silent-failure` | keep | 200, but the customer left empty-handed | Sampling only keeps what a predicate can name |
| `webhook-ignored` | keep | Acknowledged but not acted on | The provider only sees the 200 |
| `validation-bug` | keep | The rejected input was valid | Looks identical to bad input |
| `turn-resolved` | enrich | The agent did what was asked | A sampled LLM-as-judge misses the rest |
| `turn-looping` | keep | Repeated a tool call without progress | Loops hide in successful turns |
| `turn-off-script` | keep | Did something nobody asked for | Same |
| `audit-review` | keep | This action deserves a reviewer | Risk is in the combination, not one field |
| `job-flaky` | enrich | Succeeded only because it retried | The retry hides the cause |

## Label every failure

Three signals on the error path, all answered in one call per event. `fault` splits the error budget between the client, the code and the dependencies, which is the first question in every incident review. `severity` and `retryable` turn the same 5xx into a rubric and a retry hint:

```typescript [signals/errors.ts]
import { defineSignal } from '@evlog/signals'

const errorName = (e: Record<string, unknown>) => (e.error as { name?: string } | undefined)?.name ?? 'none'

export const fault = defineSignal({
  name: 'fault',
  when: e => (e.status ?? 0) >= 400,
  ask: 'Who is responsible for this failure?',
  choice: {
    user: 'Bad input, expired session, missing permission, client mistake',
    us: 'A bug, a misconfiguration or a validation error in our own code',
    upstream: 'A third-party dependency failed, timed out or rate-limited us',
  },
  cacheKey: e => e.error ? `${e.method} ${e.path} ${e.status} ${errorName(e)}` : undefined,
})

export const severity = defineSignal({
  name: 'severity',
  when: e => (e.status ?? 0) >= 500,
  ask: 'How urgent is this failure for the on-call engineer?',
  score: ['noise', 'watch', 'page'],
})

export const retryable = defineSignal({
  name: 'retryable',
  when: e => (e.status ?? 0) >= 500,
  ask: 'Would the same request most likely succeed if retried in a few seconds?',
  criteria: { true: 'Timeout, connection reset, rate limit, transient upstream error', false: 'Bug, bad data, missing resource' },
  cacheKey: e => e.error ? `${e.path} ${errorName(e)}` : undefined,
})
```

With `fault` on every error, `GROUP BY signals.fault.value` over a week tells you whether to spend the next sprint on validation messages, on your own bugs, or on a dependency's SLA. `cacheKey` on the error name means an outage costs one call, not one per request.

## Explain a slow request

`slow-cause` runs on requests over two seconds and names the component to blame from the timings your handlers logged. It answers the question a trace answers, before anyone opens one:

```typescript [signals/slow-cause.ts]
export const slowCause = defineSignal({
  name: 'slow-cause',
  when: e => (e.durationMs ?? 0) > 2_000,
  ask: 'What dominated the duration of this request?',
  choice: {
    database: 'Query time, lock waits, many round trips',
    upstream: 'A third-party API or another service',
    compute: 'Serialization, rendering, large payloads, CPU work',
    unknown: 'Nothing in the event explains the time',
  },
})
```

The `unknown` option is deliberate. Without it the model picks the least wrong of three, and you lose the signal that your events do not carry the timings they should.

## Rescue the 200 that lied

The three keep signals. Each one runs on successful responses that head sampling drops at 95%, and promotes the ones where success was not what the customer got:

```typescript [signals/silent.ts]
export const silentFailure = defineSignal({
  name: 'silent-failure',
  when: e => e.status === 200 && e.path === '/api/checkout',
  ask: 'The request returned 200, but the customer did not get what they came for',
  criteria: { true: 'No order or confirmation, a fallback path, an empty or partial result', false: 'Order created and confirmed' },
  keep: v => v.value && v.confidence > 0.8,
})

export const webhookIgnored = defineSignal({
  name: 'webhook-ignored',
  when: e => e.status === 200 && (e.path ?? '').startsWith('/api/webhooks/'),
  ask: 'The webhook was acknowledged but not acted on',
  criteria: { true: 'Unhandled event type, skipped, no side effect recorded', false: 'The event was processed' },
  keep: v => v.value && v.confidence > 0.85,
})

export const validationBug = defineSignal({
  name: 'validation-bug',
  when: e => e.status === 400,
  ask: 'The rejected input was actually valid and our validation is wrong',
  keep: v => v.value && v.confidence > 0.85,
})
```

`validation-bug` is the one to watch. A validator that rejects `hugo+test@example.com` returns the same 400 as one that rejects `notanemail`, and both go to the same dashboard. The signal reads the rejected value and the reason, and keeps the ones where the reason is wrong.

Keep signals run before the sampling decision and wait for the verdict, so scope them tightly with `when`. The checkout path, not every 200.

## Judge agent turns

`evlog/eve` emits one wide event per agent turn with `method: 'EVE'` and the tools it called. LLM-as-judge pipelines sample a few percent of turns and miss the rest. A signal reads every turn:

```typescript [signals/agent.ts]
const isTurn = (e: Record<string, unknown>) =>
  e.method === 'EVE' && typeof (e.eve as { turnId?: string } | undefined)?.turnId === 'string'

export const turnResolved = defineSignal({
  name: 'turn-resolved',
  when: isTurn,
  ask: 'The agent accomplished what the user asked for in this turn',
})

export const turnLooping = defineSignal({
  name: 'turn-looping',
  when: isTurn,
  ask: 'The agent repeated the same tool call without making progress',
  keep: v => v.value && v.confidence > 0.85,
})

export const turnOffScript = defineSignal({
  name: 'turn-off-script',
  when: isTurn,
  ask: 'The agent took an action the user did not ask for',
  keep: v => v.value && v.confidence > 0.85,
})
```

`turn-resolved` as a rate over time is the metric. `turn-looping` and `turn-off-script` keep the turns worth reading. See [eve](/use-cases/eve) for the event shape they read.

## Flag an audit action for review

[Audit events](/use-cases/audit/overview) carry the actor, the action, and the target. Risk is in the combination: an export by an admin at 10:00 is routine, the same export by a support agent at 03:00 is not. One signal, one reviewer queue:

```typescript [signals/audit.ts]
export const auditReview = defineSignal({
  name: 'audit-review',
  when: e => typeof e.audit === 'object' && e.audit !== null,
  ask: 'This action deserves a human review',
  criteria: {
    true: 'Privilege change, bulk deletion, export of personal data, action outside business hours by a non-admin',
    false: 'Routine self-service action',
  },
  keep: v => v.value && v.confidence > 0.8,
})
```

## Catch the job that only passed on retry

A retried job that succeeds is green on every dashboard, and the cause of the first failure is still in production:

```typescript [signals/jobs.ts]
export const jobFlaky = defineSignal({
  name: 'job-flaky',
  when: e => typeof e.operation === 'string' && ((e.retries as number | undefined) ?? 0) > 0,
  ask: 'The job only succeeded because it retried, and the underlying cause is still there',
})
```

## More that fit the shape

`first-seen` (is this error new for this route), `user-impact` (none, degraded, blocked), `owner` (which team should look), `known-error` (which catalog entry is this, from your own `why` and `fix`), `frustration` on support conversations, `did-succeed` on session events.

## Not a fit

- Secret or PII detection. Sending a value to a model to ask whether it is a secret is the leak you were trying to prevent. Use [redaction](/learn/redaction).
- Paging. Never page on a probability. `severity` ranks what to read first, and an alert rule on `status` and `durationMs` decides who wakes up.
- Anything adversarial as a single verdict. A model that can be asked can be prompted.
- Anything numeric. A decision model returns a distribution over options, not a number. Compute it in the handler and log it.
