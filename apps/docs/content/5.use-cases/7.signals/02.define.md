You have a question you ask yourself every time you open a failed request: was this us or them, is it worth paging, would a retry have fixed it. `defineSignal` writes that question down once. The shape of the answer follows the shape of the input: `ask` alone is yes/no, `ask` + `choice` picks one option, `ask` + `score` positions the event on a rubric.

## The three shapes

A yes/no signal is the shortest form. `criteria` is optional and tells the model what each answer looks like, which raises confidence on borderline events:

```typescript [signals/retryable.ts]
import { defineSignal } from '@evlog/signals'

export const retryable = defineSignal({
  name: 'retryable',
  when: e => (e.status ?? 0) >= 500,
  ask: 'Would the same request most likely succeed if retried in a few seconds?',
  criteria: {
    true: 'Timeout, connection reset, rate limit, transient upstream error',
    false: 'Bug, bad data, missing resource',
  },
})
```

A choice signal names its options, each with the description the model matches against. The column's `value` is one of the keys, so it is the shape to reach for when you plan to `GROUP BY` the answer:

```typescript [signals/fault.ts]
export const fault = defineSignal({
  name: 'fault',
  when: e => (e.status ?? 0) >= 400,
  ask: 'Who is responsible for this failure?',
  choice: {
    user: 'Bad input, expired session, missing permission, client mistake',
    us: 'A bug, a misconfiguration or a validation error in our own code',
    upstream: 'A third-party dependency failed, timed out or rate-limited us',
  },
})
```

A score signal takes ordered levels, lowest first. The column carries the most likely level as `value` and the probability-weighted position as `score`, so `severity.score > 1.5` reads as "closer to page than to watch":

```typescript [signals/severity.ts]
export const severity = defineSignal({
  name: 'severity',
  when: e => (e.status ?? 0) >= 500,
  ask: 'How urgent is this failure for the on-call engineer?',
  score: ['noise', 'watch', 'page'],
})
```

| Shape | Input | `value` | Extra fields |
| --- | --- | --- | --- |
| Boolean | `ask`, optional `criteria` | `boolean` | |
| Choice | `ask` + `choice` (at least two) | one of the option names | |
| Score | `ask` + `score` (at least two levels) | one of the level names | `score: number`, `0` to `levels - 1` |

Every verdict carries `confidence`, the probability of `value`. `name` is the column under `event.signals`: letters, digits and dashes, unique across the signals you register.

## Scope with `when`

`when` is a plain predicate over the event. It runs before anything else, and no model call happens when it returns `false`. It is what keeps a signal cheap: `fault` above costs nothing on the 99% of requests that succeed.

The event a signal sees is the wide event in `enrich`, or the accumulated request context plus `status`, `path`, `method` and `durationMs` in `keep`. The fields evlog sets are typed. Everything your handlers logged with `log.set()` is there too, as `unknown`, so narrow it before reading:

```typescript
when: e => e.status === 200 && (e.payment as { provider?: string } | undefined)?.provider === 'stripe'
```

`when` is required on a signal with `keep`. Without it the signal would run on every request, and a keep signal waits for the model before the sampling decision.

## Keep what sampling would drop

Sampling keeps what a rule can name: errors, slow requests, a path pattern. A `keep` signal keeps what only a judgment can name. It receives the verdict and returns `true` to force the event through:

```typescript [signals/silent-failure.ts]
export const silentFailure = defineSignal({
  name: 'silent-failure',
  when: e => e.status === 200 && e.path === '/api/checkout',
  ask: 'The request returned 200, but the customer did not get what they came for',
  criteria: {
    true: 'No order or confirmation, a fallback path, an empty or partial result',
    false: 'Order created and confirmed',
  },
  keep: v => v.value && v.confidence > 0.8,
})
```

`keep` is typed on the verdict the shape produces: on a choice signal, `v.value === 'us'` autocompletes to the option names. It is promote only. Returning `false` never drops an event that head sampling or a [keep rule](/learn/sampling#keep-an-event-once-you-know-its-outcome) would have kept, so the baseline stays deterministic. A promoted event carries `kept: true` on the column, which is how rate-weighted counts stay honest.

The verdict is computed once. When the same signal is also due in `enrich`, the plugin reuses the keep-time verdict instead of asking again.

## Collapse an error storm with `cacheKey`

One upstream outage produces thousands of identical 502s. Asking the model about each one is the same question with the same answer. `cacheKey` returns a string for events that should share a verdict, and the plugin serves the cached one without a call:

```typescript
cacheKey: e => e.error ? `${e.method} ${e.path} ${e.status} ${(e.error as { name?: string }).name}` : undefined
```

Return `undefined` to skip caching for an event. The cache holds the last 1,000 verdicts per process. Cached hits count in `stats().cached`, so you can see how much of the budget the key saved.

## Options

| Option | Type | Notes |
| --- | --- | --- |
| `name` | `string` | Column name under `event.signals`. Letters, digits, dashes. Unique. |
| `ask` | `string` | The question. |
| `when` | `(event) => boolean` | Predicate. No model call when `false`. Required with `keep`. |
| `choice` | `Record<option, description>` | At least two. Makes a choice signal. |
| `score` | `[level, level, ...]` | Ordered, lowest first, at least two. Makes a score signal. |
| `criteria` | `{ true?, false? }` | Boolean signals only: what makes each answer true. |
| `keep` | `(verdict) => boolean` | Promote the event past sampling when `true`. Never drops. |
| `cacheKey` | `(event) => string \| undefined` | Reuse the verdict for events sharing a key. |

## Write a question the model can answer

The model reads the event and the question, nothing else. A question that needs a fact the event does not carry gets a confident wrong answer. Three checks before shipping a signal:

- The answer is in the event. "Would a retry succeed" works because the error name and status are there. "Is this user about to churn" does not.
- The answer is one value. A question with two parts ("was it slow, and was it our fault") is two signals.
- A rule could not do it. If `when` alone answers the question, you do not need the model. `status >= 500` is a rule. "Transient or permanent" is not.

See [Recipes](/use-cases/signals/recipes) for twelve questions that pass those checks, and the ones that do not.
