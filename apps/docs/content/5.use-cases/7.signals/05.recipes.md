Every signal here is a question a rule cannot answer from the fields alone. Change the `when` to your paths and they are yours.

## Start with these three

One file, three columns, and a week later you have numbers you did not have before.

```typescript [server/signals.ts]
import { defineSignal } from '@evlog/signals'

const errorName = (e: Record<string, unknown>) => (e.error as { name?: string } | undefined)?.name ?? 'none'

/** Every 4xx/5xx. Splits the error budget between the client, the code and the dependencies. */
export const fault = defineSignal({
  name: 'fault',
  when: e => (e.status ?? 0) >= 400,
  ask: 'Who is responsible for this failure?',
  choice: {
    client: 'Bad input, expired session, missing permission, client mistake',
    app: 'A bug, a misconfiguration or a validation error in our own code',
    upstream: 'A third-party dependency failed, timed out or rate-limited us',
  },
  cacheKey: e => e.error ? `${e.method} ${e.path} ${e.status} ${errorName(e)}` : undefined,
})

/** Every 5xx. Tells a retry policy which failures are worth a second attempt. */
export const retryable = defineSignal({
  name: 'retryable',
  when: e => (e.status ?? 0) >= 500,
  ask: 'Would the same request most likely succeed if retried in a few seconds?',
  criteria: { true: 'Timeout, connection reset, rate limit, transient upstream error', false: 'Bug, bad data, missing resource' },
  cacheKey: e => e.error ? `${e.path} ${errorName(e)}` : undefined,
})

/** Successful checkouts. The 200 that sampling deletes and nobody notices. */
export const silentFailure = defineSignal({
  name: 'silent-failure',
  when: e => e.status === 200 && e.path === '/api/checkout',
  ask: 'The request returned 200, but the customer did not get what they came for',
  criteria: { true: 'No order or confirmation, a fallback path, an empty or partial result', false: 'Order created and confirmed' },
  keep: 0.8,
})
```

What each one gives you:

- `GROUP BY signals.fault.value` over a week says whether the next sprint goes to validation messages, your own bugs, or a dependency's SLA. `cacheKey` on the error name makes an outage one call, not one per request.
- `signals.retryable.value = true` on a 502 is the difference between a retry policy and a guess.
- `silent-failure` promotes the checkouts that returned 200 with no order. Point `when` at your own money path.

## All twelve

| Signal | Hook | Question | Why a rule cannot |
| --- | --- | --- | --- |
| `fault` | enrich, cached | Who is responsible: user, us, upstream | A Stripe timeout and a null deref are both a 500 |
| `severity` | enrich | noise, watch or page | Urgency depends on what failed and for whom |
| `retryable` | enrich, cached | Would a retry succeed | Transient and permanent errors share status codes |
| `slow-cause` | enrich | database, upstream, compute | Reading the timings takes a human |
| `silent-failure` | keep | 200, but the customer left empty-handed | Sampling only keeps what a predicate can name |
| `webhook-ignored` | keep | Acknowledged but not acted on | The provider only sees the 200 |
| `validation-bug` | keep | The rejected input was valid | Looks identical to bad input |
| `turn-resolved` | enrich | The agent did what was asked | A sampled LLM-as-judge misses the rest |
| `turn-looping` | keep | Repeated a tool call without progress | Loops hide in successful turns |
| `turn-off-script` | keep | Did something nobody asked for | Same |
| `audit-review` | keep | This action deserves a reviewer | Risk is in the combination, not one field |
| `job-flaky` | enrich | Succeeded only because it retried | The retry hides the cause |

### Rank failures and explain slow requests

```typescript
export const severity = defineSignal({
  name: 'severity',
  when: e => (e.status ?? 0) >= 500,
  ask: 'How urgent is this failure for the on-call engineer?',
  score: ['noise', 'watch', 'page'],
})

export const slowCause = defineSignal({
  name: 'slow-cause',
  when: e => (e.durationMs ?? 0) > 2_000,
  ask: 'What dominated the duration of this request?',
  choice: {
    database: 'Query time, lock waits, many round trips',
    upstream: 'A third-party API or another service',
    compute: 'Serialization, rendering, large payloads, CPU work',
    unknown: 'Nothing in the event explains the time',
  },
})
```

The `unknown` option on `slow-cause` is deliberate: without it the model picks the least wrong of three, and you lose the signal that your events do not carry the timings they should.

### Rescue the other 200s that lied

```typescript
export const webhookIgnored = defineSignal({
  name: 'webhook-ignored',
  when: e => e.status === 200 && (e.path ?? '').startsWith('/api/webhooks/'),
  ask: 'The webhook was acknowledged but not acted on',
  criteria: { true: 'Unhandled event type, skipped, no side effect recorded', false: 'The event was processed' },
  keep: 0.85,
})

export const validationBug = defineSignal({
  name: 'validation-bug',
  when: e => e.status === 400,
  ask: 'The rejected input was actually valid and our validation is wrong',
  keep: 0.85,
})
```

A validator that rejects `hugo+test@example.com` returns the same 400 as one that rejects `notanemail`. `validation-bug` reads the rejected value and the reason, and keeps the ones where the reason is wrong.

### Judge agent turns

`evlog/eve` emits one wide event per agent turn with `method: 'EVE'`. A sampled LLM-as-judge reads a few percent; a signal reads every turn. See [eve](/use-cases/eve) for the event shape.

```typescript
const isTurn = (e: Record<string, unknown>) =>
  e.method === 'EVE' && typeof (e.eve as { turnId?: string } | undefined)?.turnId === 'string'

export const turnResolved = defineSignal({
  name: 'turn-resolved',
  when: isTurn,
  ask: 'The agent accomplished what the user asked for in this turn',
})

export const turnLooping = defineSignal({
  name: 'turn-looping',
  when: isTurn,
  ask: 'The agent repeated the same tool call without making progress',
  keep: 0.85,
})

export const turnOffScript = defineSignal({
  name: 'turn-off-script',
  when: isTurn,
  ask: 'The agent took an action the user did not ask for',
  keep: 0.85,
})
```

### Flag audit actions and flaky jobs

```typescript
export const auditReview = defineSignal({
  name: 'audit-review',
  when: e => typeof e.audit === 'object' && e.audit !== null,
  ask: 'This action deserves a human review',
  criteria: {
    true: 'Privilege change, bulk deletion, export of personal data, action outside business hours by a non-admin',
    false: 'Routine self-service action',
  },
  keep: 0.8,
})

export const jobFlaky = defineSignal({
  name: 'job-flaky',
  when: e => typeof e.operation === 'string' && ((e.retries as number | undefined) ?? 0) > 0,
  ask: 'The job only succeeded because it retried, and the underlying cause is still there',
})
```

[Audit events](/use-cases/audit/overview) carry the actor, the action and the target; the risk is in the combination, and `audit-review` is one reviewer queue instead of a rule per combination.

## Match raw errors to your catalog

An [error catalog](/learn/catalogs) names the failures you know about, but only the ones you throw through it carry its `code`. The Stripe exception you forgot to wrap, the JWT library's `jwt expired`, the stock check that throws a plain `Error`: they reach the event with a message and nothing to group them by. `knownError` ships with the package and puts each of them to the model, with one option per catalog entry plus `new`:

```typescript [evlog.config.ts]
import { createSignals, knownError } from '@evlog/signals'
import { authErrors, billingErrors, outOfStock } from './errors'

export default defineEvlog({
  plugins: [
    createSignals({ signals: [knownError([billingErrors, authErrors, outOfStock])] }),
  ],
})
```

It takes whole catalogs from `defineErrorCatalog` and single factories from `defineError`. Each entry's `message`, when it is a string, and its `why` are the description the model matches against, so an entry with neither is matched on its code alone. Errors that already carry a catalog `code` are skipped without a call, and errors sharing a name and message share one verdict.

Seven errors from a demo checkout, put to Jev through the plugin against a five-entry catalog:

| Error | `known-error` |
| --- | --- |
| `StripeCardError: Your card was declined.` | `billing.PAYMENT_DECLINED` 1.00 |
| `StripeCardError: Your card has insufficient funds.` | `billing.INSUFFICIENT_FUNDS` 0.91 |
| `JsonWebTokenError: jwt expired` | `auth.SESSION_EXPIRED` 0.99 |
| `Error: SKU tshirt-m-blue: requested 2, available 0` | `inventory.OUT_OF_STOCK` 1.00 |
| `TypeError: Cannot read properties of undefined (reading 'sku')` | `new` 1.00 |
| `PrismaClientKnownRequestError`, unique constraint failed on `email` | `new` 1.00 |
| `EvlogError: Card declined` with `code: 'billing.PAYMENT_DECLINED'` | skipped, no call |

Six calls, 3,187 input tokens. `signals.known-error.value = 'new'` is the query to watch: a failure your catalog does not describe yet, which is either a bug or the next entry to add. The others tell you which known failures arrive unwrapped, and where to call the factory instead.

## Triage browser errors

Errors your front end logs with `log.error` reach the server through the [ingest endpoint](/use-cases/client-logging) as events with `source: 'client'`. Most of them are not yours: the device went offline, an ad blocker stopped a script, an extension crashed in the page. `clientFault` ships with the package and sorts them into `app`, `network`, `third-party` and `browser`:

```typescript [evlog.config.ts]
import { clientFault, createSignals } from '@evlog/signals'

export default defineEvlog({
  plugins: [
    createSignals({ signals: [fault, retryable, silentFailure] }),
    createSignals({ name: 'client-signals', signals: [clientFault], budget: { perMinute: 60 } }),
  ],
})
```

The ingest endpoint is unauthenticated, so client signals get their own instance and their own budget. Your server signals still see every ingested event, and the payload can carry any field, `status: 500` included: a crafted error matches `fault` and `retryable` above and spends their budget. Add `e.source !== 'client'` to their `when` to keep client events off it. Errors sharing a name and message share one verdict, so a thousand `Failed to fetch` cost one call.

Six browser errors put to Jev, each answered with a confidence of 0.98 or more:

| Error | `client-fault` |
| --- | --- |
| `TypeError: Failed to fetch` while offline | `network` |
| `Cannot read properties of undefined (reading 'items')` in `CartSummary` | `app` |
| `Cannot read properties of null` in a `chrome-extension://` script | `third-party` |
| `stripe.js did not load … net::ERR_BLOCKED_BY_CLIENT` | `third-party` |
| `QuotaExceededError` on `localStorage.setItem` | `browser` |
| `Expected cart.total to be a number, got "9,99"` | `app` |

The events where `client-fault` is `app` are the list worth a ticket. The default `state` sends the whole client event, identity fields included; pick fields with `state` if your client logs carry anything you would not send to a model.

## More that fit the shape

`first-seen` (is this error new for this route), `user-impact` (none, degraded, blocked), `owner` (which team should look), `frustration` on support conversations, `did-succeed` on session events.

## Not a fit

- **Secret or PII detection.** Sending a value to a model to ask whether it is a secret is the leak. Use [redaction](/learn/redaction).
- **Paging.** Never page on a probability. `severity` ranks what to read first; an alert on `status` and `durationMs` decides who wakes up.
- **Anything adversarial as a single verdict.** A model that can be asked can be prompted.
- **Anything numeric.** A decision model returns a distribution over options, not a number. Compute it in the handler and log it.
