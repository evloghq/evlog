Your checkout handler returned 200, and the customer left without an order. Stripe asked for a second factor, the code took the fallback path, the page said "we will email you shortly", and sampling dropped the event because nothing in it looked wrong. A rule cannot name that case: `status === 200 && payment.fallback === true` describes this one bug, not the next one.

`@evlog/signals` lets you ask the question in English instead. A signal is one question about an event, answered by a decision model as a typed value with a probability. The answer lands on the event as a column you can `GROUP BY`, alert on, and use to keep events that sampling would have dropped:

```json [Wide Event]
{
  "path": "/api/checkout",
  "status": 200,
  "payment": { "provider": "stripe", "fallback": true },
  "signals": {
    "silent-failure": { "value": true, "confidence": 0.94, "kept": true }
  },
  "signalsModel": "jev-1.13.0"
}
```

The model is Jev from TypeSafe AI by default, a model that returns decisions and probabilities instead of text, called through the AI SDK `experimental_evaluate` contract. Inference runs in your process with your key. evlog holds no key and proxies nothing.

::callout{icon="i-lucide-flask-conical" color="warning"}
Experimental. The AI SDK API it wraps is `experimental_evaluate`, and `@evlog/signals` is `0.x`. The question shapes and the column format are the parts expected to hold.
::

Add @evlog/signals to my evlog app.

- Install: pnpm add @evlog/signals ai (ai 7.0.105 or later)
- Define signals with defineSignal({ name, when, ask }) plus choice: {...} for a pick-one answer or score: [...] for a rubric; keep: v => ... promotes the event past sampling
- Register with createSignals({ signals, budget: { perMinute: 600 } }): on Nuxt or Nitro hook plugin.keep on 'evlog:emit:keep' and plugin.enrich on 'evlog:enrich' in a server plugin; on Next.js or standalone pass it in initLogger({ plugins: [...] }); on Hono, Express, Fastify or Elysia pass it in the middleware's plugins option
- Set AI_GATEWAY_API_KEY (default model typesafe-ai/jev through AI Gateway), or pass model from @ai-sdk/typesafe-ai
- Verdicts land on event.signals.<name>.{ value, confidence } through drains, not in console output
- In tests, pass evaluate from scriptedEvaluate() in @evlog/signals/testing so no model is called

Docs: https://www.evlog.dev/use-cases/signals/overview

## Install

`ai` 7.0.105 or later. The default model is `typesafe-ai/jev` through Vercel AI Gateway, which reads `AI_GATEWAY_API_KEY` or OIDC on Vercel. For a direct TypeSafe key, pass a model from `@ai-sdk/typesafe-ai` as `model`.

::code-group
```bash [pnpm]
pnpm add @evlog/signals ai
```
```bash [bun]
bun add @evlog/signals ai
```
```bash [yarn]
yarn add @evlog/signals ai
```
```bash [npm]
npm install @evlog/signals ai
```
::

## Quick start

Two signals: one that labels every failure, one that rescues the silent checkout above. `when` is a plain predicate and runs first, so the model only sees events that pass it:

```typescript [server/signals.ts]
import { defineSignal } from '@evlog/signals'

export const fault = defineSignal({
  name: 'fault',
  when: e => (e.status ?? 0) >= 400,
  ask: 'Who is responsible for this failure?',
  choice: {
    user: 'Bad input, expired session, client mistake',
    us: 'A bug or misconfiguration in our own code',
    upstream: 'A third-party dependency failed',
  },
})

export const silentFailure = defineSignal({
  name: 'silent-failure',
  when: e => e.status === 200 && e.path === '/api/checkout',
  ask: 'Returned 200, but the customer did not get what they came for',
  keep: v => v.value && v.confidence > 0.8,
})
```

`createSignals` turns them into one evlog [plugin](/extend/plugins) with a `keep` hook and an `enrich` hook. Where you register it depends on the framework, because Nuxt and Nitro expose the hooks directly while the other integrations take a `plugins` array:

::code-group
```typescript [Nuxt / Nitro]
// server/plugins/evlog-signals.ts
import { createSignals } from '@evlog/signals'
import { fault, silentFailure } from '../signals'

export default defineNitroPlugin((nitroApp) => {
  const plugin = createSignals({ signals: [fault, silentFailure], budget: { perMinute: 600 } })
  nitroApp.hooks.hook('evlog:emit:keep', plugin.keep)
  nitroApp.hooks.hook('evlog:enrich', plugin.enrich)
})
```

```typescript [Next.js / standalone]
import { initLogger } from 'evlog'
import { createSignals } from '@evlog/signals'
import { fault, silentFailure } from './signals'

initLogger({
  sampling: { rates: { info: 5 } },
  plugins: [createSignals({ signals: [fault, silentFailure], budget: { perMinute: 600 } })],
})
```

```typescript [Hono]
import { Hono } from 'hono'
import { evlog } from 'evlog/hono'
import { createSignals } from '@evlog/signals'
import { fault, silentFailure } from './signals'

const app = new Hono()
app.use(evlog({
  plugins: [createSignals({ signals: [fault, silentFailure], budget: { perMinute: 600 } })],
}))
```
::

Every event that passes a signal's `when` gets judged. All due signals for one event go into a single model call, so the state is billed once and takes one slot of the rate limit whatever the number of questions.

## What you get back

Every column has the same two fields. `value` is the answer, `confidence` is the probability of that answer. Score signals add `score`, the probability-weighted position between levels. `kept: true` marks the signal that promoted the event past sampling, so rate-weighted counts stay valid.

| Signal shape | `value` | Extra |
| --- | --- | --- |
| `ask` | `boolean` | |
| `ask` + `choice` | one of the option names | |
| `ask` + `score` | one of the level names | `score: number` |

Columns arrive through [drains](/integrate/adapters/overview). Console output is written at emit, before enrichment, so they do not show in the dev terminal or in stdout JSON. Run the [playground](https://github.com/evloghq/evlog/tree/main/apps/playground) with an fs or memory drain to see them locally.

## What it costs

- A model call per judged event, in your process, on your key. Jev bills input tokens only, at $0.042 per million at the time of writing: a 1.5k-token event is about $0.00006, so 100k judged events are about $6. Prices move; check the model page before budgeting.
- Rate, not price, is the binding limit: 1,200 requests per minute per TypeSafe account. `budget.perMinute` is per process, so divide it across your instances. See [Configure](/use-cases/signals/configure).
- Latency on the keep path. A keep signal runs before the sampling decision and waits for the model, up to `timeoutMs` (2 s by default). It runs after the response is sent, so the client never waits, but the event's drain is delayed by that much. `durationMs` is measured before keep hooks run, so the number on the event is the request, not the judgment.
- Egress. The default `state` is the whole event, and a keep signal runs before redaction. Use `state` to pick fields when the request context holds anything you would not send to a model.

## Guarantees

- Promote only. A keep signal can force an event past sampling. It cannot drop one, and head sampling stays deterministic.
- Fails open. A timeout, a failed call, an exhausted budget or an oversized state leaves the event as it was, and counts in `plugin.stats()`.
- Typed output only. No prose on events. The model id is stamped on every judged event as `signalsModel`.
- No call for what a predicate can answer. `when` runs first, always.
