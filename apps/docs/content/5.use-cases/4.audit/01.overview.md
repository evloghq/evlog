Your customers ask who changed a setting, your auditor asks for every denied access last quarter, and your request logs are sampled. evlog records each audit as its own event: one per `log.audit()` call, with an `id` to dedupe on, the tenant it belongs to, and the request it came from. Sampling never drops it. Every existing primitive (drains, enrichers, redaction) applies as is, so audit logs take **one drain wrapper and one call**.

Add a tamper-evident audit log to my app on top of evlog.

- Identify my framework and follow its evlog integration pattern
- Register a separate auditOnly(signed(createFsDrain({ dir: '.audit' }), { strategy: 'hash-chain' })) drain alongside my main drain, or auditOnly() around a drain that writes to my database keyed on audit.id
- Call await log.audit({ action, actor, target, tenantId, outcome, reason }) for every security-sensitive action (login, role change, refund, data export, deletion), once per action and once per tenant
- Use log.audit.deny(reason, input) on every authorization failure
- For API tokens and agents acting for a user, set actor.onBehalfOf to that user
- If every audit of a request belongs to one tenant, register auditEnricher({ tenantId }) to fill it
- Combine with the Better Auth integration to read the actor from the session

Docs: https://www.evlog.dev/use-cases/audit/overview
Drains: https://www.evlog.dev/integrate/adapters/overview

## Why Audit Logs?

Compliance frameworks (SOC2, HIPAA, GDPR, PCI) require knowing **who did what, on which resource, when, from where, with which outcome**. evlog covers this without a second logging library.

::tip
**An audit event is a fact about an intent, not a measurement of an operation.** A regular wide event answers "how did this request behave?" (latency, status, tokens). An audit event answers "who tried to do what, and was it allowed?". Same pipeline, different question, which is why each audit is its own event with a reserved schema, and sampling never drops it.
::

## Quickstart

You already use evlog. Add a drain that stores audits, then record them from your handlers:

```typescript [server/plugins/evlog.ts]
import { auditOnly, signed } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createFsDrain } from 'evlog/fs'

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('evlog:drain', createAxiomDrain())
  nitro.hooks.hook('evlog:drain', auditOnly(
    signed(createFsDrain({ dir: '.audit' }), { strategy: 'hash-chain' }),
  ))
})
```

The audit event:

- Is its own event, one per call. The request's wide event is emitted separately and shares its `requestId`.
- Is never dropped by sampling, `log.discard()` or route filters.
- Reaches every drain. Axiom gets `a***@***.com` and `***.***.***.7`. The `auditOnly` store gets the email and IP, because recording who acted is what it is for.
- Carries `requestId`, `traceId`, `ip` and `userAgent` from the request, with no enricher to register.
- Is stored once `await log.audit()` resolves, which adds the drain's write time to the response. Without `await`, the response goes out first and evlog keeps the runtime alive with `waitUntil` until every drain has the event. [Recording](/use-cases/audit/recording#choose-when-the-record-is-stored) compares the two.

::tip
**Why two drains?** The main drain (Axiom, Datadog, ...) keeps audits next to the rest of your telemetry so dashboards and queries still work. The signed drain is your insurance: if the main drain has an outage, gets purged, or an admin quietly removes a row, the FS journal still holds the chain. Auditors want both: fast querying *and* a tamper-evident artefact.
::

## Composition

Each layer is **opt-in and replaceable**. Every node except `log.audit`, `auditEnricher`, `auditOnly` and `signed` is shared with regular wide events.
