Every `log.audit()` call emits one event whose `audit` field holds the record below. The event around it carries `timestamp`, `level`, `service`, `environment`, and the request's `requestId`, `method` and `path`, so a store can keep the record alone and still join it to the request log.

## `AuditFields` type

::code-collapse
```typescript
interface AuditFields {
  id: string                              // UUIDv7, the dedupe key
  timestamp: string                       // ISO 8601, when the record was made
  action: string                          // 'invoice.refund'
  actor: {
    type: 'user' | 'system' | 'api' | 'agent'
    id: string
    displayName?: string
    email?: string
    // For type === 'agent', mirrors evlog/ai fields:
    model?: string
    tools?: string[]
    reason?: string
    promptId?: string
    onBehalfOf?: { type, id, displayName?, email?, ... } // the user a token, agent or admin acted for
  }
  target?: { type: string, id: string, [k: string]: unknown }
  tenantId?: string                       // organization, team or workspace
  outcome: 'success' | 'failure' | 'denied'
  reason?: string
  changes?: { before?: unknown, after?: unknown, patch?: AuditPatchOp[] }
  metadata?: Record<string, unknown>      // free-form detail about the action
  causationId?: string                    // ID of the action that caused this one
  correlationId?: string                  // Shared by every action in one operation
  version: 2
  context?: {                             // Filled from the request
    requestId?: string
    traceId?: string
    ip?: string
    userAgent?: string
  }
  signature?: string                      // Set by signed({ strategy: 'hmac' })
  prevHash?: string                       // Set by signed({ strategy: 'hash-chain' })
  hash?: string
}
```
::

`log.audit()` sets `id`, `timestamp` and `version` itself, and reads `context` from the request. You pass the rest, and can [pass `context.ip`](/use-cases/audit/recording#pass-the-client-address-your-app-trusts) when your app resolves the client address itself. Use `buildAuditFields(input)` to make the same record without emitting it, for a write path that does not go through a drain.

## Action naming

::tip
**Naming convention for `action`.** Use `noun.verb` (`invoice.refund`, `user.invite`, `apiKey.revoke`). Past tense if the action already happened (`invoice.refunded`), present tense if `withAudit()` will resolve the outcome. Keep a small fixed dictionary in one file, because auditors and SIEM rules query on `action`, so a typo is a missing alert.
::

A single dictionary file makes alerting straightforward:

```typescript [src/audit/actions.ts]
export const AUDIT_ACTIONS = {
  USER_INVITE: 'user.invite',
  USER_REMOVE: 'user.remove',
  USER_ROLE_CHANGE: 'user.role-change',
  INVOICE_REFUND: 'invoice.refund',
  API_KEY_REVOKE: 'apiKey.revoke',
} as const
```

::tip
For more than a handful of actions, prefer [`defineAuditCatalog`](/use-cases/audit/recording#defineauditcatalog) over a plain object dictionary: same `noun.verb` convention, but you get autocomplete on the action union and per-entry `target` type inference for free.
::

## Say who acted

::warning
**Don't fake the actor.** Use `actor.type: 'system'` for cron jobs, queue workers, and background tasks; `actor.type: 'api'` for machine-to-machine calls authenticated by a token; `actor.type: 'agent'` for AI tool calls. Logging a synthetic `'user'` for system actions is the single fastest way to fail an audit review.
::

| `actor.type` | When to use |
|--------------|-------------|
| `'user'` | A human authenticated through your normal auth flow. |
| `'system'` | Cron jobs, queue workers, scheduled tasks, internal background processes. Give it a fixed `id`, such as `'billing-worker'`. |
| `'api'` | Calls authenticated by an API token or another service's credentials. |
| `'agent'` | AI tool calls (combine with `evlog/ai` fields like `model`, `tools`, `promptId`). |

### Record who a token or agent acted for

An API token, an AI agent and an admin impersonating a user all act for someone. The actor is the credential that made the call, and `onBehalfOf` is the person it acted for:

```typescript
await log.audit({
  action: 'variable.update',
  actor: {
    type: 'api',
    id: token.id,
    displayName: token.name,
    onBehalfOf: { type: 'user', id: token.userId, email: token.userEmail },
  },
  target: { type: 'variable', id: variable.id },
  tenantId: team.id,
})
```

For impersonation, the admin is the `actor` and the impersonated user is `onBehalfOf`. Finding everything done for one user then reads both fields: `actor.id = ? OR actor.onBehalfOf.id = ?`.

## Record how it ended

| `outcome` | Meaning |
|-----------|---------|
| `'success'` | The action completed as requested. |
| `'failure'` | The action was attempted but failed (downstream error, race condition, etc.). |
| `'denied'` | The action was rejected by an authorisation check. |

`'failure'` and `'denied'` are different things, and auditors care a lot about denied actions because they signal probing or misconfigured access controls. Always log denials (see [Recording Events](/use-cases/audit/recording#logauditdeny)).

## Scope each record to a tenant

In a multi-tenant app, every record belongs to one organization, team or workspace. Pass it as `tenantId`, and filter every read on it, so one customer never sees another's trail:

```typescript
for (const team of affectedTeams) {
  await log.audit({ action: 'token.create', actor, target, tenantId: team.id })
}
```

An action that touches several tenants is one record per tenant, each with its own `id`. When every audit of a request belongs to the same tenant, [`auditEnricher({ tenantId })`](/use-cases/audit/pipeline#auditenricher) fills it from the request instead.

## Make a retry safe

`id` is a UUIDv7: unique per record, and ordered by creation time within a process. A drain that retries a batch sends the same `id` again, so make it the primary key and insert with `ON CONFLICT DO NOTHING`:

```sql
CREATE TABLE audit_events (
  id         uuid PRIMARY KEY,
  tenant_id  text,
  timestamp  timestamptz NOT NULL,
  record     jsonb NOT NULL
);
```

Two real actions always get two ids, even when they have the same actor, target and second. Calling `log.audit()` twice for one action records it twice, so deduplicate in your code before the call, not in the store.

## Tie an action to what caused it

| Field | Use case |
|-------|----------|
| `correlationId` | Shared by every audit event that belongs to the **same operation** (e.g. one HTTP request that triggers a refund + an email + a webhook). |
| `causationId` | The `id` of the previous audit event that **caused** this one. Useful for reconstructing chains of cascading actions. |

Every record made in a request already carries `context.requestId`. Set `correlationId` when one operation spans several requests or jobs, and `causationId` when a single user action triggers many internal audit events.

## Put the rest in `metadata`

`metadata` holds what the action needs to be read later and does not fit a field above: the name of the created resource, the environment it ran in, the plan a customer moved to. Keep it small and free of secrets. Redaction still applies to it ([Compliance](/use-cases/audit/compliance#redact)). Before and after values belong in `changes`, built with [`auditDiff`](/use-cases/audit/recording#auditdiff).
