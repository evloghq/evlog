Four building blocks: `auditOnly` turns a drain into your audit store, `auditEnricher` fills the tenant, `signed` adds tamper-evident integrity, and `relayAudit` with `evlog/webhook` sends each tenant's records to an endpoint they own. Each is opt-in and replaceable.

## `auditOnly()`

::tip
**Why filter audits to a separate drain?** Three reasons: **cost** (audit volume is tiny next to product telemetry, so keep them separate and retention costs don't explode), **permissions** (the audit dataset should be read-only for engineers and write-only for the app), and **retention** (audits often live 7+ years; product logs rarely live more than 90 days).
::

`auditOnly(drain)` forwards only the events `log.audit()` and `audit()` emitted, one call per record. Compose it with **any** drain:

```typescript
import { auditOnly } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'

// Send audits to a dedicated Axiom dataset:
nitro.hooks.hook('evlog:drain', auditOnly(
  createAxiomDrain({ dataset: 'audit', apiKey: process.env.AXIOM_AUDIT_API_KEY }),
))
```

The record it receives keeps the identities an audit exists to record. Redaction still applies your `paths`, `secrets`, custom patterns, and the credential and card maskers, but not the `email`, `ipv4` and `phone` maskers. Every other drain, and stdout, gets the fully masked event:

| Field | `auditOnly` drain | Every other drain |
| --- | --- | --- |
| `actor.email` | `ada@example.com` | `a***@***.com` |
| `context.ip` | `203.0.113.7` | `***.***.***.7` |
| a `password` key in `changes` | `[REDACTED]` | `[REDACTED]` |

Wrap only stores you control with `auditOnly`. A third-party drain wrapped in it receives the real emails and IPs.

`auditOnly` skips events rebuilt from JSON, such as client events, replays, and an `audit` field set with `log.set()`. Only records made in this process reach it, so a client cannot forge an audit row.

Each `log.audit()` call waits for every drain, `auditOnly` ones included. [Recording](/use-cases/audit/recording#choose-when-the-record-is-stored) explains when that lands before the response. An audit store that batches through `createDrainPipeline` resolves when the batch is queued, not written, so write to the store directly when a record must exist before the response.

## `auditEnricher()`

`log.audit()` records `requestId`, `traceId`, IP and user agent from the request on its own. `auditEnricher()` covers the one field it cannot know: the tenant, for apps where every audit of a request belongs to the same one, such as a workspace per subdomain:

```typescript [server/plugins/evlog.ts]
import { auditEnricher } from 'evlog'

nitro.hooks.hook('evlog:enrich', auditEnricher({
  tenantId: ctx => ctx.headers?.host?.split('.')[0],
}))
```

The resolver reads the request (`ctx.request`, `ctx.headers`) and the audit event, not fields you set on the request's wide event. It fills `audit.tenantId` only when the call did not pass one, and leaves events without an audit alone. Never resolve the tenant from a header the client controls, such as an `x-org-id` your app does not set. Enrichers run before redaction, so what they add is masked for every drain but the `auditOnly` one.

## `signed()`

`signed(drain, opts)` adds tamper-evident integrity. Two strategies:

| Strategy | What it adds | Use case |
|----------|--------------|----------|
| `'hmac'` | `event.audit.signature` (HMAC of the canonical event) | Single-event integrity check (any later mutation fails verification). |
| `'hash-chain'` | `event.audit.prevHash` and `event.audit.hash` | A verifiable chain, where deletions and reordering also become detectable. |

::tip
**What `signed()` actually buys you.** Detection, not prevention. Anyone with write access to the underlying drain can still nuke the file or table, but the chain proves *which* events were dropped or modified after the fact. Skip `signed()` if you already write to an append-only / WORM store (S3 Object Lock, Postgres with row-level immutability, BigQuery append-only tables); doubling integrity layers just adds latency without raising the bar.
::

### HMAC

Each event gets a signature. Tampering with one row breaks that row's verification, but doesn't break later rows.

```typescript
import { signed } from 'evlog'

signed(drain, { strategy: 'hmac', secret: process.env.AUDIT_SECRET! })
```

### Hash-chain

Each event references the previous event's hash. Deleting any row breaks the chain forward of that point, so the verifier can pinpoint the exact row that was tampered with.

```typescript
signed(drain, {
  strategy: 'hash-chain',
  state: {
    load: () => fs.readFile('.audit/head', 'utf8').catch(() => null),
    save: (h) => fs.writeFile('.audit/head', h),
  },
})
```

The `state` config is required for cross-process or durable chains: load the previous head hash from your own store (Redis, Postgres, file) before each event, save the new head after. `load` and `save` are not a compare-and-set, so two instances writing at once both extend the same head and the chain forks. Keep a hash chain to one writer, such as a single server or a queue consumer, and use HMAC on serverless functions that scale out.

::hash-chain-tamper
::

::note
A CLI to walk and verify the chain (`evlog audit verify`) is on the roadmap. Until then, validate by recomputing the hashes of stored events and comparing each `prevHash` against the previous event's `hash`.
::

## Send each tenant's audits to their endpoint

Enterprise customers ask for their audit trail in their own SIEM. Store every record first, then forward each tenant's records to the endpoint they registered. Your store doubles as the outbox, so an endpoint that is down for a day loses nothing within your retention window.

[`createWebhookDrain`](/integrate/adapters/hybrid/webhook) sends each record as a signed [Standard Webhooks](https://www.standardwebhooks.com) message, and `relayAudit` moves a cursor through your store:

```typescript [server/tasks/audit-relay.ts]
import { relayAudit } from 'evlog'
import { sendAuditWebhook } from 'evlog/webhook'

for (const destination of await db.auditDestinations.active()) {
  const result = await relayAudit({
    cursor: destination.cursor,
    read: (after, limit) => db.audit.readTeam(destination.teamId, after, limit),
    send: records => sendAuditWebhook(records, { url: destination.url, secret: destination.secret }),
    save: next => db.auditDestinations.moveCursor(destination.id, destination.cursor, next),
    signal: AbortSignal.timeout(50_000),
  })
  if (result.error) await db.auditDestinations.markFailing(destination.id, result.error)
}
```

| `relayAudit` option | What you provide |
| --- | --- |
| `cursor` | The position of the last record the destination accepted, `undefined` to start from the oldest. |
| `read(after, limit)` | Up to `limit` records stored after `after`, oldest first, as `{ cursor, record }`. |
| `send(records)` | Deliver them in order, and throw when the destination did not accept them all. |
| `save(cursor)` | Store the new position. Throw when another run already moved it, to stop this one. |
| `limit` | Records per `read` and `send`. Default `100`. |
| `signal` | Stops the run between batches. |

It reads a batch, sends it, saves the cursor, and repeats until the store has nothing newer. It never throws: a failure comes back in `result.error` with the cursor still on the last delivered batch, so the next run resends from there. Delivery is at least once and in store order. The receiver drops a redelivered record by its `id`, which `verifyWebhook` returns.

Your app keeps the parts that depend on it: the schedule (a cron or a task after each insert), backoff between failing runs, notifying the customer, and checking that a registered URL is not an internal address.

::warning
**Read only final positions.** With a database sequence as the cursor, concurrent inserts commit out of order: row 12 can become visible after row 13 was read and the cursor moved past it. Leave out rows written in the last few seconds (`created_at < now() - interval '15 seconds'`).
::
