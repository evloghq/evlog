Server logs tell you what happened on the backend. Frontend logging completes the picture: user interactions, page views, browser errors, and performance signals that never reach the server unless you capture them.

Ship browser logs to my server with evlog client logging.

- Detect my framework (Nuxt, Next.js, SvelteKit, etc.) and pick the matching client entrypoint
- Call initLog({ service: 'web' }) once at app start. On Nuxt, the module client plugin already calls initLog from nuxt.config; do not call it again
- Use log.info / log.warn / log.error in components, composables, and event handlers
- Set user identity with setIdentity({ userId, email }) after login, clearIdentity() on logout
- To ship each event, enable transport. Nuxt: set evlog.transport.enabled in nuxt.config.ts so the module registers the ingest route. Each event POSTs as one JSON object to transport.endpoint (default /api/_evlog/ingest) with fetch keepalive. Failures are silent. There is no batch buffer and no flush on hide
- For batching (default size 25, every 2s), retries, and a flush on visibilitychange to hidden, use createHttpLogDrain from evlog/http against a batch endpoint. Hidden sends use sendBeacon; other sends use fetch keepalive. Do not point that drain at the built-in ingest
- On Nuxt ingest, the server redacts the event and drains it with source: 'client'

Docs: https://www.evlog.dev/use-cases/client-logging
HTTP transport: https://www.evlog.dev/extend/drain-pipeline

## Quick Start

evlog provides a client-side logging API that works in any browser environment:

::framework-tabs
```typescript [Nuxt] app/plugins/app-init.client.ts
export default defineNuxtPlugin((nuxtApp) => {
  nuxtApp.hook('app:created', () => {
    log.info({ action: 'app_init', path: window.location.pathname })
  })
})
```
```typescript [app/providers.tsx (React / Next.js)]
'use client'
import { useEffect } from 'react'
import { initLog, log } from 'evlog/client'

export function LogProvider({ children }: { children: React.ReactNode }) {
  useEffect(() => {
    initLog({ service: 'web' })
    log.info({ action: 'app_init', path: window.location.pathname })
  }, [])

  return <>{children}</>
}
```
```typescript [src/app.ts (Any frontend)]
import { initLog, log } from 'evlog/client'

initLog({ service: 'web' })
log.info({ action: 'app_init', path: window.location.pathname })
```
::

On Nuxt, the module's client plugin already calls `evlog/client`'s `initLog` with the `evlog` options from `nuxt.config.ts`. Calling `initLog()` again resets every option, including `service`, `pretty`, `minLevel`, and `transport`, to its default. The client service name is fixed to `'client'`.

The `log` object works anywhere in your client code: components, composables, event handlers.

## Minimum level (`minLevel`)

Use `initLog({ minLevel: 'warn' })` to keep the browser console quiet (warnings and errors only). Severity order: `trace` < `debug` < `info` < `warn` < `error` < `fatal`. Default is `'debug'` (all levels).

For a **debug toggle** without reloading, call `setMinLevel('debug')` or `setMinLevel('warn')` from `evlog/client` when the user opts in or out of verbose logs.

`minLevel` applies to both console output and [server transport](#sending-logs-to-the-server) payloads.

## Call it two ways

The `log` API accepts two forms depending on the context.

### Object Form (structured context)

Pass an object to capture structured data, just like server-side `log.set()`:

```typescript [pages/products.vue]
log.info({ action: 'page_view', path: '/products', referrer: document.referrer })
```

```bash [Browser console]
[web] info  { action: 'page_view', path: '/products', referrer: 'https://google.com' }
```

### Tag + Message Form (quick logs)

Pass a tag and a message for quick, readable logs:

```typescript [composables/useAuth.ts]
log.info('auth', 'User logged in')
```

```bash [Browser console]
[auth] User logged in
```

The message accepts printf-style interpolation, the same [formatting as server-side logs](/learn/simple-logging#interpolate-values-into-the-message). When it contains `%s`, `%d`, or `%j` and extra arguments follow, evlog formats it before writing to the console:

```typescript [composables/useCart.ts]
log.info('cart', 'Item %s added, cart total %d', 'SKU-42', 9999)
```

```bash [Browser console]
[cart] Item SKU-42 added, cart total 9999
```

### Levels you can use

Both forms support six levels: `log.fatal()`, `log.info()`, `log.warn()`, `log.error()`, `log.debug()`, and `log.trace()`.

In the browser, `log.debug()` is emitted with `console.log` (not `console.debug`) so lines stay visible with the default DevTools **Info** filter; the structured event still has `level: 'debug'`.

## Errors in browser events

Errors inside browser events are serialized the same way as on the server. `log.error(err)`, or an `Error` inside an object-form event such as `log.error({ action: 'checkout', error })`, is logged with its `name`, `message`, `stack` and fields, not as `{}`. The rules are in [How errors are logged](/learn/structured-errors#how-errors-are-logged).

With `pretty: true` (the default), the browser console receives the real `Error`, so DevTools shows a live error you can expand. The JSON console output and the transport receive the serialized form.

## Attach who the log belongs to

Track which user generated a log with `setIdentity()`:

```typescript [composables/useAuth.ts]
import { setIdentity, clearIdentity, log } from 'evlog/client'

// After login
setIdentity({ userId: 'usr_123', plan: 'pro' })

log.info({ action: 'dashboard_view' })
// → { userId: 'usr_123', plan: 'pro', action: 'dashboard_view', ... }

// After logout
clearIdentity()
```

Identity fields are automatically merged into every log event until cleared. This lets you correlate browser events to specific users in your observability tools.

## Configuration

`initLog()` accepts the following options:

| Option | Default | Description |
|--------|---------|-------------|
| `enabled` | `true` | Enable or disable all client logging |
| `console` | `true` | Output logs to the browser console |
| `pretty` | `true` (`import.meta.dev` on Nuxt) | Use colored, formatted console output |
| `minLevel` | `'debug'` | Minimum severity: `trace` < `debug` < `info` < `warn` < `error` < `fatal` |
| `service` | `'client'` | Service name included in every log event |
| `transport` | - | Send logs to a server endpoint (see below) |

```typescript [src/app.ts]
import { initLog } from 'evlog/client'

initLog({
  service: 'web',
  transport: {
    enabled: true,
    endpoint: '/api/_evlog/ingest', // default endpoint
  },
})
```

::callout{icon="i-lucide-info" color="info"}
`enabled` and `console` default to `true`. `pretty` defaults to `true` in `initLog()`, and to `import.meta.dev` when the Nuxt module plugin calls it.
::

## Sending Logs to the Server

By default, client logs only appear in the browser console. To persist them, you have two options:

### Ship logs with the built-in transport

The built-in transport is the simplest option, fine for low-volume apps. It POSTs one JSON event per log with `fetch` and `keepalive: true`. There is no batch buffer, so nothing flushes on hide, and a failed POST is ignored.

::framework-tabs
```typescript [Nuxt] nuxt.config.ts
export default defineNuxtConfig({
  modules: ['evlog/nuxt'],
  evlog: {
    transport: {
      enabled: true,
      endpoint: '/api/_evlog/ingest',
    },
  },
})
```
```tsx [Next.js] app/layout.tsx
import { EvlogProvider } from 'evlog/next/client'

export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <EvlogProvider service="web" transport={{ enabled: true, endpoint: '/api/_evlog/ingest' }}>
          {children}
        </EvlogProvider>
      </body>
    </html>
  )
}
```
```typescript [src/app.ts (Any frontend)]
import { initLog } from 'evlog/client'

initLog({
  service: 'web',
  transport: {
    enabled: true,
    endpoint: '/api/_evlog/ingest',
  },
})
```
::

The Nuxt module registers that ingest route and a client plugin that calls `initLog` from the same config. Enabling transport only in a client `initLog()` call does not register the route, and those POSTs fail silently. For other frameworks, create a POST endpoint that accepts one JSON event. The built-in transport sends a single object (`timestamp`, `level`, `service`, and the logged fields), not an array:

```typescript [Next.js] app/api/_evlog/ingest/route.ts
export async function POST(request: Request) {
  const body = await request.json()
  if (body === null || typeof body !== 'object' || Array.isArray(body)) {
    return Response.json({ error: 'expected one event object' }, { status: 400 })
  }
  return new Response(null, { status: 204 })
}
```

::callout{icon="i-lucide-info" color="info"}
The built-in ingest has no auth: the Nuxt one rejects requests from other origins, which stops other websites but not a script. Treat client events as untrusted input, and rate-limit the route where traffic enters (your platform firewall or a middleware), as the [telemetry ingest](/use-cases/telemetry/ingest) page does.
::

### HTTP drain pipeline

For higher volume, or when you need batching, retries, and a flush when the page hides, use `createHttpLogDrain` from `evlog/http` with `log` from `evlog`. That is a different logger than `evlog/client`: `initLog` events, `setIdentity`, and client `minLevel` do not go through this drain. It works with any frontend and has no framework dependency.

The HTTP drain:
- **Batches** events (default size 25, every 2s)
- **Retries** failed sends with exponential backoff
- **Flushes** buffered events via `sendBeacon` when the page becomes hidden (tab switch, navigation, close) on `visibilitychange`

::callout{icon="i-lucide-triangle-alert" color="warning"}
Object-form events reach the drain. Tagged `log.info('tag', 'msg')` calls print and skip it when `pretty` is on (`pretty` defaults to `isDev()`, which is true in a browser without a `process` global) and `silent` is off. Use object-form events, or set `pretty: false` on `initLogger`. `useBeacon` belongs on `drain` (`drain: { endpoint, useBeacon: false }` if the endpoint needs an `Authorization` header), because `sendBeacon` does not send `headers`. The body is a JSON array, so do not point this drain at the built-in ingest. Create a POST handler at the path you configure (`/api/logs` in the Nuxt tab is a route you add). See [Server endpoint](/extend/drain-pipeline#server-endpoint).
::

::framework-tabs
```typescript [Nuxt] app/plugins/logger.client.ts
import { initLogger, log } from 'evlog'
import { createHttpLogDrain } from 'evlog/http'

export default defineNuxtPlugin(() => {
  const drain = createHttpLogDrain({
    drain: { endpoint: '/api/logs' },
    pipeline: {
      batch: { size: 25, intervalMs: 2000 },
      retry: { maxAttempts: 2 },
    },
  })

  initLogger({ drain })
  log.info({ action: 'app_init' })
})
```
```typescript [src/app.ts (Any frontend)]
import { initLogger, log } from 'evlog'
import { createHttpLogDrain } from 'evlog/http'

const drain = createHttpLogDrain({
  drain: { endpoint: 'https://logs.example.com/v1/ingest' },
  pipeline: {
    batch: { size: 25, intervalMs: 2000 },
    retry: { maxAttempts: 2 },
  },
})

initLogger({ drain })
log.info({ action: 'app_init' })
```
::

## FAQ

::accordion{type="single"}
  ::accordion-item{label="What should I log in the browser?"}
  Log the action, the route, and the outcome: `log.info({ action: 'page_view', path })` for a view, `log.error(err)` for a caught error. Attach who it belongs to with `setIdentity({ userId })` after login, and call `clearIdentity()` on logout. Skip form values, tokens, and full request bodies.
  ::
  ::accordion-item{label="How do I send frontend logs to the server?"}
  Enable the built-in transport so each event POSTs as one JSON object to `/api/_evlog/ingest` (Nuxt registers that route when `evlog.transport.enabled` is set). For batching, retries, and a flush when the tab hides, use the HTTP drain; both contracts are in [Sending Logs to the Server](#sending-logs-to-the-server).
  ::
  ::accordion-item{label="How do I avoid PII and noisy frontend logs?"}
  Raise `minLevel` to `'warn'` (or toggle it with `setMinLevel`) so debug chatter never hits the console or the transport. Put IDs on `setIdentity`, not emails, unless you intend to store them. Leave secrets off the event: the browser still prints what you logged, and the POST body still contains it. Nuxt ingest then runs the server [redaction](/learn/redaction) config before the drain.
  ::
::
