[eve](https://eve.dev/docs/introduction) records every session for you in **Agent Runs** and can export **OpenTelemetry** spans. `@evlog/eve` adds the record you query, chart and alert on: one wide event per agent turn, sent through your drains, with the fields your tools add and the errors they throw.

::callout{icon="i-lucide-info" color="info"}
`@evlog/eve` is an [eve extension](https://eve.dev/docs/extensions) and requires **eve 1.0 or later** and Node 24, eve's own floor. It replaces the `evlog/eve` subpath of evlog 2.x; see [Migrate to v3](/reference/migrate-v3#eve-moves-to-evlogeve).
::

Add evlog wide events to my eve agent.

- Install evlog and @evlog/eve: pnpm add evlog@beta @evlog/eve@beta
- Create agent/extensions/evlog.ts that default-exports evlog({ service, drain }) from '@evlog/eve'. It takes every evlog.config.ts setting plus record and tools
- In tools, import useLogger from '@evlog/eve/logger' and call useLogger().set({...}) inside execute()
- Throw evlog errors (createError or a defineErrorCatalog entry) as usual: the turn event keeps their code, status, why and fix
- Records are redacted in every environment by default. Tool inputs, outputs and the reply are recorded only with record: 'debug' or a per-tool rule
::

## Quick Start

### 1. Install

::code-group
```bash [pnpm]
pnpm add evlog@beta @evlog/eve@beta
```
```bash [bun]
bun add evlog@beta @evlog/eve@beta
```
```bash [yarn]
yarn add evlog@beta @evlog/eve@beta
```
```bash [npm]
npm install evlog@beta @evlog/eve@beta
```
::

The `beta` tags are needed until evlog 3.0 is stable: plain `evlog` still resolves to 2.x on npm, which does not satisfy the `@evlog/eve` peer. Once 3.0 is stable, the plain names work.

### 2. Mount the extension

eve mounts an extension from a file under `agent/extensions/`. With no options, one line is the whole setup:

```typescript [agent/extensions/evlog.ts]
export { default } from '@evlog/eve'
```

Pass options to choose a drain and a service. The extension accepts every runtime setting of [`evlog.config.ts`](/cli/config), so an agent that already has one spreads it:

```typescript [agent/extensions/evlog.ts]
import evlog from '@evlog/eve'
import config from '../../evlog.config'

export default evlog({ ...config, record: 'standard' })
```

The service defaults to `eve-agent`. When nothing initialised evlog before the first turn, the extension starts the logger from these settings, so an event emitted outside a turn reaches the same drain.

### 3. Add context from tools

`useLogger()` returns the running turn's logger. Its fields are stored with the eve session, so they reach the turn's event even when the turn resumes in another process after an approval:

```typescript [agent/tools/lookup_order.ts]
import { useLogger } from '@evlog/eve/logger'
import { defineTool } from 'eve/tools'
import { z } from 'zod'

export default defineTool({
  description: 'Look up an order by id.',
  inputSchema: z.object({ orderId: z.string() }),
  async execute({ orderId }) {
    const order = await fetchOrder(orderId)
    useLogger().set({ order: { id: order.id, amount: order.amount, status: order.status } })
    return order
  },
})
```

The logger also has `info`, `warn`, `error` (record and keep going) and `audit`, with the same signatures as every other evlog integration. An `audit` call keeps the turn's event past sampling.

### 4. Throw catalog errors

eve keeps only the name and message of an error a tool throws. `@evlog/eve` records each evlog error when it is built and pairs it with the failed call when the turn settles, so a plain `throw` keeps the fields that make an error actionable:

```typescript [agent/tools/issue_refund.ts]
import { billing } from '../lib/errors' // defineErrorCatalog('billing', { ... })

throw billing.PAYMENT_DECLINED({ order })
```

```json [Wide Event: error field]
{
  "error": {
    "code": "billing.PAYMENT_DECLINED",
    "status": 402,
    "message": "Refund for order 9001 declined",
    "why": "The card issuer rejected the reversal",
    "fix": "Ask the customer for another payment method"
  }
}
```

The stack is the tool's, not the hook's. A tool that throws a plain `Error` gets an `error` block too, with the name and message eve kept and no stack. A turn that completes after a failed call is a `warn` event with `eve.failedCalls` and that block, so `evlog logs errors` lists it without counting it as a failed turn.

## Wide event shape

Each settled turn emits one event:

```json [Wide Event: one turn]
{
  "method": "EVE",
  "path": "/agents/support/turns",
  "requestId": "wrun_01M7NW…:turn_0",
  "idempotencyKey": "wrun_01M7NW…:turn_0",
  "status": 200,
  "level": "info",
  "duration": "1.32s",
  "eve": {
    "sessionId": "wrun_01M7NW…",
    "turnId": "turn_0",
    "outcome": "completed",
    "channel": "channel:eve",
    "caller": { "principalId": "github:1", "principalType": "user", "authenticator": "github" }
  },
  "order": { "id": "4821", "amount": 890 },
  "customer": { "email": "j***@***.com" },
  "gen_ai": {
    "operation": { "name": "invoke_agent" },
    "agent": { "name": "support" },
    "conversation": { "id": "wrun_01M7NW…" },
    "calls": 2,
    "request": { "model": "anthropic/claude-sonnet-4.6" },
    "response": { "finish_reasons": ["tool-calls", "stop"] },
    "usage": { "input_tokens": 11724, "output_tokens": 282, "total_tokens": 12006, "cost": 0.0394 },
    "tools": [{ "name": "lookup_order", "kind": "tool", "duration_ms": 13, "success": true, "outcome": "completed" }]
  }
}
```

The fields are read from the session record eve stores, not from process memory, so a turn that resumed in another process is complete. `status` is `200` for a completed turn, `499` for a cancelled one and `500` for a failed one, and `duration` is eve's own timing for the turn.

| Field | What it tells you |
| --- | --- |
| `requestId` / `idempotencyKey` | `sessionId:turnId`. eve may retry a step, so a drain can receive a turn twice: the id stays the same, and `evlog logs` counts it once |
| `eve.caller` | Who asked. `subject` and `attributes` are never recorded, because a channel may put a name or an email in them |
| `eve.parent` | The session that delegated this turn, for a subagent |
| `eve.approvals` | Approval requests in the turn, with their tool and outcome |
| `eve.failedCalls` | Tool, skill and subagent calls that failed |
| `gen_ai.response.finish_reasons` | One reason per model call |
| `gen_ai.tools` | Every tool, skill and subagent call: `call_id`, name, kind, duration, outcome and error message. A failed call also carries the `code`, `why` and `fix` of the evlog error its tool threw, found by its message: when two calls fail with one message and different errors, neither gets them. `call_id` is the `gen_ai.tool.call.id` of eve's `execute_tool` span |
| `traceId` / `spanId` | The turn's trace and its `invoke_agent` span, when the agent exports [`evlogTraces()`](#correlate-traces-with-wide-events) |

## What gets recorded

`record` picks how much of a turn the event carries:

| `record` | Records |
| --- | --- |
| `minimal` | Outcome, duration, usage and errors. For high-volume agents |
| `standard` (default) | Adds every call, approvals, the caller and the parent session |
| `debug` | Adds tool inputs and outputs and a 200-character reply preview. For development and incidents |

Per-tool rules refine the preset. Keys are tool names as the model sees them, and a key ending in `*` matches by prefix:

```typescript [agent/extensions/evlog.ts]
export default evlog({
  record: 'standard',
  tools: {
    issue_refund: { input: true },  // record this tool's input
    'crm__*': false,                 // leave a mounted extension's tools out
  },
})
```

Records are **redacted in every environment**, development included: an agent's own records get read back and pasted into issues. Set `redact: false` only when a drain must receive raw values. `keep`, `sampling` and `enrich` apply as on any evlog integration.

## Draining

The hook awaits every drain before the turn's step ends, so a serverless function can't freeze while the event is in flight. A batching drain built with `createDrainPipeline` is flushed at the end of each turn, because serverless has no later moment to send the batch. A failing drain is logged and never fails the turn.

## Correlate traces with wide events

eve builds each turn's trace from its own records, so no span is active while a tool or hook runs and `createOtelPlugin()` finds nothing to read. Export `evlogTraces()` from an instrumentation file instead. Extensions cannot declare instrumentation, so the agent adds it. `npx evlog setup eve` writes the file and never overwrites one that exists; `--check` reports whether it is there and writes nothing:

```typescript [agent/instrumentation/evlog.ts]
import { evlogTraces } from '@evlog/eve/instrumentation'

export default evlogTraces()
```

Each turn's event then carries `traceId` and `spanId`, the turn's `invoke_agent` span. The [OTLP drain](/integrate/adapters/hybrid/otlp) writes them as the log record's `trace_id` and `span_id`, so a backend that receives both opens the trace from the event, and `vercel traces inspect <traceId>` opens it from the command line. It reads span ids from the turn's steps and exports nothing; the ids are absent when the turn's last step ran in another instance, or when nothing records the trace.

The other direction uses eve's `runtimeContext`, which it stamps on every model-call span. Give it the turn's event id and a span joins back to its wide event:

```typescript [agent/instrumentation/runtime-context.ts]
import { otelIntegration } from 'eve/instrumentation/otel'

export default otelIntegration({
  runtimeContext: input => input.turn
    ? { 'evlog.request_id': `${input.session.id}:${input.turn.id}`, 'evlog.session_id': input.session.id }
    : {},
})
```

## The agent reads its own events

Mounting the extension adds a `logs` tool, `evlog__logs` for a mount named `evlog`. It runs the query behind [`evlog logs`](/cli/logs) on the agent's own turns, so the model can find what failed or was slow, and why, from the same events you read:

```json
{ "view": "errors", "since": "6h" }
```

It takes the filters of the CLI: `view` (`recent`, `errors`, `slow`, `sessions`, `stats`, or `trace` with an `id`), `session`, `where` clauses, `since` and `until` as durations, `level`, `path`, `status` (`500` or `5xx`), `over` for `slow`, and `limit` (10 by default, 50 at most).

A turn's full event runs to about a thousand tokens, most of it the list of tool calls, so the list views return one row per turn instead: its `requestId`, time, level, status, duration, session, `result`, the error's `code`, `message`, `why` and `fix`, the number of tool calls, the tools that failed, and the tokens used. `result` is `completed`, `recovered` (the turn finished after a tool call failed, with status 200), `failed` or `cancelled`. `detail: "diagnostic"` adds the models, model calls, cost, cache reads and trace ids. `fields` adds named fields to each row, such as `["user.id"]`.

`sessions` returns one summary per session instead of one row per turn: first and last activity, wall-clock `elapsedMs` next to the summed `processingMs`, turns by result, failed tool calls, model and tool calls, tokens with cache reads and writes, cost, the slowest turn and the latest failure. Each token count and the cost sum only the turns that reported them, and `turnsReporting` says how many did. A total the events do not carry is left out rather than written as 0. `latestFailure` and `traceIds` (up to five, newest first) follow the events' timestamps, whatever order they were read in. The caller's own session is marked `current`.

`trace` returns one request's full wide events, not its OpenTelemetry span tree. `traces` lists every matched event's trace and span ids, with the `eve traces show` command that opens a local trace. `stats` returns the counts per route.

Every result stays under 24,000 characters of JSON, or 200,000 with `full: true`. Nothing is cut mid-value: the newest items are kept whole first, then a row that does not fit drops its `fields`, then everything but its `requestId`, time, level, `result` and session, and names what it dropped in `omittedFields`. A session drops its latest failure's message the same way. A `trace` event that does not fit is left out whole, and its ids stay in `traces`. `omitted` counts what was left out, and the notes say whether `full: true` would help or the read has to be narrowed.

Every result says what it covers: `origin` (files or Vercel, with the directory or project, and the environment), `caller` (the session and turn the tool was called from), `window`, `filters`, `matched` against `returned`, and `coverage`. `coverage.complete` is `false` when the read was cut short, and `coverage.reasons` says why, so the model is told not to conclude that nothing failed from a partial read. It is about the read, not the size budget: a complete read can still leave events out of the result. On files, the read stops at `window.until`, so an event stamped ahead of the clock is not reported under a window that excludes it. Pass `expect` to refuse a read from the wrong place:

```json
{ "view": "errors", "expect": { "source": "vercel", "environment": "production" } }
```

From `eve dev` that call fails with a 409 naming the files it would have read, instead of returning an empty list.

Where it reads is `logs.source`. On `auto`, the default, it reads the project's runtime logs through Vercel Connect when the agent runs on Vercel, authenticated by the deployment's OIDC token, over the last day unless `since` says otherwise; run [`npx evlog setup vercel`](/cli/logs#a-vercel-deployment) once in the agent's project. Anywhere else it reads the files in `logs.dir`, which is where the [file system drain](/integrate/adapters/self-hosted/fs) writes in `eve dev`. `source: 'vercel'` reads the linked project's runtime logs from `eve dev` too, with the `VERCEL_OIDC_TOKEN` that `vercel env pull` writes to `.env.local`. The token pins the read to that project, whatever the model asks for.

What the tool reads depends on who runs the turn:

| Caller | Reads |
| --- | --- |
| The agent's own scheduled work (`isScheduleAuth`) | Every turn of the agent |
| A signed-in caller | The turns of the session it is in |
| An anonymous caller | Nothing: the tool is not offered |

The tool's result enters the model's context, and the caller can ask the model to repeat it. Grant every turn only to callers who may see every caller's turns, with `logs.access`, which runs before each model call:

```ts [agent/extensions/evlog.ts]
import evlog from '@evlog/eve'

export default evlog({
  logs: {
    access: ctx => isAdmin(ctx.session.auth.current) ? 'agent' : 'session',
  },
})
```

It returns `'agent'` for every turn, `'session'` for the caller's own session, or `false` to leave the tool out.

## Options

| Option | Description |
| --- | --- |
| `record` | `'minimal'`, `'standard'` (default) or `'debug'` |
| `tools` | Per-tool rules: `false`, or `{ input?, output? }` |
| `init` | Passed to `initLogger()` as is, in place of the logger settings. Use it to give events emitted outside a turn their own drain or service |
| `service` / `environment` / `sampling` / `silent` / `redact` | Logger settings. `redact` defaults to `true` |
| `drain` / `enrich` / `keep` / `plugins` | Same as HTTP integrations ([plugins](/extend/plugins)) |
| `logs` | The `logs` tool: `{ source?, dir?, vercel?: { connector? }, access?, diagnostics? }`. `source` is `'auto'` (default), `'files'` or `'vercel'`; `dir` defaults to `.evlog/logs`, `vercel.connector` to `vercel/evlog`, `access` to the table above. `diagnostics: true` records each call under `evlog.logs.<callId>`: source, view, the filters, counts, coverage and duration, redacted like any field, never the rows it returned. A call that fails, before or during the read, is recorded with `failed: true` |

## Run locally

```bash
git clone https://github.com/evloghq/evlog
cd evlog
pnpm install
pnpm example eve
```
