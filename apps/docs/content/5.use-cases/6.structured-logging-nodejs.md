Give every request **one structured JSON event**, a *wide event*, instead of a trail of log lines. This guide takes a Node.js server there in about two minutes.

## The 30-second version

::code-group
```typescript [Before: 5 log lines]
console.log('checkout started', { requestId })
console.log('user loaded', { userId: 'u_42' })
console.log('cart loaded', { items: 3, total: 2999 })
console.log('charging card', { provider: 'stripe' })
console.log('checkout done', { status: 200, ms: 182 })
```
```typescript [After: 1 wide event]
log.set({ user: { id: 'u_42' } })
log.set({ cart: { items: 3, total: 2999 } })
log.set({ payment: { provider: 'stripe' } })
```
::

Your handler calls `log.set()`. evlog adds the method, path, status, duration and a request ID, and writes one event when the response is sent:

```json [Output]
{
  "level": "info",
  "method": "POST",
  "path": "/checkout",
  "status": 200,
  "durationMs": 182,
  "requestId": "4f1c…",
  "user": { "id": "u_42" },
  "cart": { "items": 3, "total": 2999 },
  "payment": { "provider": "stripe" }
}
```

When a request fails, you read one record instead of searching for five, and every field can be queried: `payment.provider = 'stripe' AND status >= 500`.

## Why wide events

::wide-event-collapse
::

| | Line logs | One wide event |
| --- | --- | --- |
| Records per request | One per log call | One, emitted at the end |
| Context | Repeated on every line, or missing on some | Collected once, next to the outcome |
| Debugging a failure | Find every line for the request ID, then rebuild the story | Read one event: inputs, outcome, error, duration |
| Volume | Grows with the number of calls | Fixed per operation, then reduced by [sampling](/learn/sampling) |

You can still write individual records for things outside a request, such as startup messages, with the global `log` API ([Simple Logging](/learn/simple-logging)). [Wide Events](/learn/wide-events) covers when to use each.

```typescript [Astro] src/middleware.ts
  }
})
```

## Log your first wide event

Add context with `log.set()` as the handler learns things. Nested objects merge, so `payment` can be filled in two steps. With a framework integration, method, path, status, duration and a request ID are recorded for you, and the event is emitted when the response finishes.

::framework-tabs
```typescript [Standalone] src/server.ts
import { randomUUID } from 'node:crypto'
import { createServer } from 'node:http'
import { createRequestLogger, initLogger, toLoggerConfig } from 'evlog'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

createServer((req, res) => {
  const log = createRequestLogger({ method: req.method, path: new URL(req.url ?? '/', 'http://localhost').pathname, requestId: randomUUID() })

  // Without a framework, you emit the event yourself: once, after the response is sent
  let emitted = false
  const emit = () => {
    if (emitted) return
    emitted = true
    log.emit({ status: res.statusCode })
  }
  res.once('finish', emit)
  res.once('close', emit)

  log.set({ orderId: 'order-123', payment: { amount: 2999, currency: 'EUR' } })
  log.set({ payment: { chargeId: 'ch_123' }, outcome: 'paid' })
  res.statusCode = 200
  res.end(JSON.stringify({ orderId: 'order-123' }))
}).listen(3000)
```

```typescript [AWS Lambda] src/handler.ts
initLogger(toLoggerConfig(config))

export async function handler(event: APIGatewayProxyEventV2) {
  const { method, path } = event.requestContext.http
  const log = createRequestLogger({ method, path, requestId: event.requestContext.requestId })
  let statusCode = 500
  try {
    log.set({ orderId: 'order-123', payment: { amount: 2999, currency: 'EUR' } })
    log.set({ payment: { chargeId: 'ch_123' }, outcome: 'paid' })
    statusCode = 200
    return { statusCode, body: JSON.stringify({ orderId: 'order-123' }) }
  } finally {
    // Lambda has no response lifecycle to hook: emit before the handler returns
    log.emit({ status: statusCode })
  }
}
```

## Errors that explain themselves

::structured-error-context
::

`createError()` gives an error a `status`, a `why` and a `fix`. evlog records them on the request event, next to the context you set before the failure, and `parseError()` reads them back to build the HTTP response.

::framework-tabs
```typescript [Standalone] src/server.ts
import { createError, parseError } from 'evlog'

// inside the request handler from the previous section, after the listeners
try {
  throw createError({
    message: 'Payment declined',
    status: 402,
    why: 'The card issuer declined the charge',
    fix: 'Try another payment method',
  })
} catch (error) {
  log.error(error instanceof Error ? error : new Error(String(error)))
  const parsed = parseError(error)
  res.statusCode = parsed.status
  res.end(JSON.stringify({ message: parsed.message, why: parsed.why, fix: parsed.fix }))
}
// the 'finish' listener emits the event with status 402
```

## Send logs somewhere

::drain-fan-out
::

Locally, events print to the terminal. In production, a **drain** ships them to a backend, without changing any handler. Add it to the config file, and every integration on this page picks it up:

```typescript [evlog.config.ts] {6}
import { defineEvlog } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'

export default defineEvlog({
  service: 'checkout',
  drain: createAxiomDrain(), // reads AXIOM_API_KEY and AXIOM_DATASET
})
```

Axiom is one option. Datadog, Sentry, PostHog, Better Stack, Loki, ClickHouse, OTLP and the filesystem are in the [adapters overview](/integrate/adapters/overview). An `enrich` function in the same file adds fields to every event, such as the user agent or the deployed version ([Enrichers](/use-cases/enrichers)).

::collapsible{open-text="Go deeper:" close-text="Hide:" name="batching and flushing"}
A pipeline batches events and retries failed sends. Buffered events must be flushed before the process exits, which matters most for scripts, workers and serverless functions:

```typescript [evlog.config.ts] {6-7}
import type { DrainContext } from 'evlog'
import { defineEvlog } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createDrainPipeline } from 'evlog/pipeline'

const pipeline = createDrainPipeline<DrainContext>({ batch: { size: 50 } })
export const drain = pipeline(createAxiomDrain())

export default defineEvlog({ service: 'checkout', drain })
```

```typescript [src/shutdown.ts] {9}
import type { Server } from 'node:http'
import { drain } from '../evlog.config'

// Stop accepting connections, let in-flight requests finish, then flush.
// Node exits on its own once nothing is left to do.
export function flushOnShutdown(server: Server) {
  process.once('SIGTERM', () => {
    server.close(async () => {
      await drain.flush()
    })
  })
}
```

See [Drain Pipeline](/extend/drain-pipeline) for batch size, intervals and retries.
::

## Production checklist

- **Sample by outcome.** Keep a share of successful `info` events and use `keep` rules so errors and slow requests are always kept ([Sampling](/learn/sampling)).

  ```typescript [evlog.config.ts]
  import { defineEvlog } from 'evlog'

  export default defineEvlog({
    service: 'checkout',
    sampling: { rates: { info: 10 }, keep: [{ status: 400 }, { duration: 1000 }] },
  })
  ```
- **Redact before shipping.** Redaction is on by default in production. Add paths for fields specific to your domain ([Redaction](/learn/redaction)).
- **Flush on exit.** Scripts, workers and serverless functions must wait for pending delivery before the process stops ([Standalone TypeScript](/integrate/frameworks/standalone)).
- **Check the wiring.** Run `evlog doctor` when nothing shows up, and [`evlog map`](/cli/map) to find handlers that still emit no event.

  ::code-group{sync="package-manager"}
  ```bash [pnpm]
  pnpm evlog doctor
  ```

  ```bash [npm]
  npx evlog doctor
  ```
  ```bash [yarn]
  yarn evlog doctor
  ```
  ```bash [bun]
  bunx evlog doctor
  ```

## FAQ

::accordion{type="single"}
  ::accordion-item{label="How is this different from pino or winston?"}
  Pino and winston write a record per call. evlog's request logger collects fields through the request and writes one event at the end, with the outcome, error and duration on it. It also has structured errors, sampling, redaction and drains built in. The [Pino](/compare/pino), [Winston](/compare/winston) and [all loggers](/reference/vs-other-loggers) comparisons cover the differences in detail.
  ::
  ::accordion-item{label="Does it slow down my app?"}
  A request builds one in-memory object and serializes it once, instead of writing several records. Drains run after the event is emitted, and a [pipeline](/extend/drain-pipeline) batches network sends. The cost still depends on what you log and where it goes, so measure your own configuration: [Performance](/reference/performance) lists the benchmarks and how to run them, and [sampling](/learn/sampling) reduces volume.
  ::
  ::accordion-item{label="Can I keep console.log while I migrate?"}
  Yes. evlog doesn't replace or patch `console`, so existing calls keep working. Move one route at a time to the request logger, and replace one-off messages with the global `log` API when you're ready ([Simple Logging](/learn/simple-logging)).
  ::
  ::accordion-item{label="How do I avoid logging secrets or personal data?"}
  Don't put them in the context in the first place: log IDs rather than whole objects. Redaction is on by default in production and masks common sensitive values; add your own paths and patterns in `evlog.config.ts` ([Redaction](/learn/redaction)).
  ::
  ::accordion-item{label="Does it work in serverless functions and at the edge?"}
  Yes. Wait for delivery before the function returns: on Cloudflare Workers pass `waitUntil` to the logger, and in short-lived processes call `flush()` on a pipeline drain. See [AWS Lambda](/integrate/frameworks/aws-lambda), [Cloudflare Workers](/integrate/frameworks/cloudflare-workers) and [Standalone TypeScript](/integrate/frameworks/standalone).
  ::
  ::accordion-item{label="Does it work with OpenTelemetry?"}
  Yes. The [OTLP adapter](/integrate/adapters/hybrid/otlp) exports events to any OpenTelemetry Collector or backend, and you can add the active span's `traceId` and `spanId` to the event. [evlog and OpenTelemetry](/compare/opentelemetry) shows the setup.
  ::
  ::accordion-item{label="How do I correlate logs across services?"}
  Every request event has a `requestId`. The Hono, Express, Fastify and NestJS integrations reuse the incoming `x-request-id` header when there is one, so forwarding that header links events across services. For distributed traces, `createTraceContextEnricher()` adds the incoming `traceparent` to each event ([Enrichers](/use-cases/enrichers)).
  ::
::

To keep field names consistent across handlers, continue with [Typed Fields](/learn/typed-fields). For your framework's full options, see the [framework guides](/integrate/frameworks/overview).
