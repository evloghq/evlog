A checkout fails. You have the request ID from the client. Your logs should let you find the payment amount, the outcome, and the reason for the decline together.

Build a small Node.js HTTP server that records those details in one JSON [wide event](/learn/wide-events) per request. You will run a successful checkout and a declined payment, then match each response to its log. The example uses Node’s built-in HTTP server so you can see the full logging lifecycle.

## Why structured logging in Node.js

A line such as `payment failed for order 123` is easy to write and hard to query. You can't filter on the amount, group by the decline reason, or join it to the request that caused it without parsing text. Structured logging writes each record as JSON with named fields, so your log platform can filter, aggregate and alert on them directly.

evlog goes one step further. Instead of several lines per request, each one carrying a fragment of the context, a handler accumulates fields with `log.set()` and emits **one wide event** when the work finishes:

| | Line logs | One wide event |
| --- | --- | --- |
| Records per request | One per `log.info()` call | One, emitted at the end |
| Context | Repeated on every line, or missing on some | Collected once, together with the outcome |
| Debugging a failure | Find every line for the request ID, then rebuild the story | Read one event: inputs, outcome, error, duration |
| Volume | Grows with the number of calls | Fixed per operation, then [sampling](/learn/sampling) |

Individual logs are still available through the global `log` API for things that aren't part of a request, such as startup messages. [Wide Events](/learn/wide-events) covers when to use each.

## Run a complete HTTP handler

Install evlog, then save the server below. It uses the Node.js HTTP server and no framework. Node.js 24 can run this TypeScript file directly:

```bash [Terminal]
npm install evlog
node server.ts
```

The `/checkout` route simulates a successful payment. Add `?decline=1` to exercise the error path. The payment IDs are fixture data, so no payment provider or credentials are needed.

```typescript [server.ts]
import { randomUUID } from 'node:crypto'
import { createServer } from 'node:http'
import { createError, createLogger, initLogger } from 'evlog'

initLogger({ env: { service: 'checkout' }, pretty: false })

createServer((req, res) => {
  const url = new URL(req.url ?? '/', 'http://localhost')
  const requestId = randomUUID()
  const log = createLogger({ requestId, method: req.method, path: url.pathname })
  res.setHeader('x-request-id', requestId)
  res.setHeader('content-type', 'application/json')

  try {
    if (req.method !== 'POST' || url.pathname !== '/checkout') {
      res.statusCode = 404
      log.set({ outcome: 'not-found' })
      res.end(JSON.stringify({ error: 'Not found', requestId }))
      return
    }

    log.set({ orderId: 'order-123', payment: { amount: 2999, currency: 'EUR' } })
    if (url.searchParams.get('decline') === '1') {
      throw createError({
        message: 'Payment declined',
        status: 402,
        why: 'The simulated card has insufficient funds',
        fix: 'Try another payment method',
      })
    }

    log.set({ payment: { chargeId: 'ch_123' }, outcome: 'paid' })
    res.statusCode = 200
    res.end(JSON.stringify({ orderId: 'order-123', requestId }))
  } catch (error) {
    log.error(error instanceof Error ? error : new Error(String(error)))
    log.set({ outcome: 'declined' })
    res.statusCode = 402
    res.end(JSON.stringify({ error: 'Payment declined', requestId }))
  } finally {
    log.emit({ status: res.statusCode })
  }
}).listen(3000)
```

Send both requests from another terminal:

```bash [Terminal]
curl -i -X POST http://localhost:3000/checkout
curl -i -X POST 'http://localhost:3000/checkout?decline=1'
```

## Read the result

The response's `x-request-id` header matches the event's `requestId`. The successful event includes the following fields, plus environment metadata and timing fields:

```json [Successful event, selected fields]
{
  "level": "info",
  "service": "checkout",
  "method": "POST",
  "path": "/checkout",
  "orderId": "order-123",
  "payment": { "amount": 2999, "currency": "EUR", "chargeId": "ch_123" },
  "outcome": "paid",
  "status": 200
}
```

The declined request emits an error event with `status: 402`, `outcome: 'declined'`, and the error's message, reason, and suggested fix. Both paths include `durationMs`, measured from logger creation to emission. This example measures handler work, not confirmation that the client received the response.

## Configure once in `evlog.config.ts`

The example above passes options inline, which is fine for one file. In an application, keep every option in `evlog.config.ts` at the root of the app. `npx evlog init` detects your framework, writes this file and wires the integration, then runs `evlog doctor` to check the result ([evlog init](/cli/init)):

```bash [Terminal]
npx evlog init
```

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'

export default defineEvlog({
  service: 'checkout',
  // Keep 10% of successful info events in production; errors are always kept
  sampling: process.env.NODE_ENV === 'production'
    ? {
        rates: { info: 10 },
        keep: [{ status: 400 }, { duration: 1000 }],
      }
    : undefined,
})
```

A plain Node.js process loads it with `toLoggerConfig()`:

```typescript [server.ts]
import { initLogger, toLoggerConfig } from 'evlog'
import config from './evlog.config'

initLogger(toLoggerConfig(config))
```

Every option is listed in the [Configuration reference](/reference/configuration).

## Use a framework integration

With Express, Fastify or Hono, the integration creates the request logger, fills in method, path, status and duration, and emits the event when the response finishes. Handlers only add context. Pass the same config file to the middleware with `toMiddlewareOptions()`:

::code-group
```typescript [Express]
import express from 'express'
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { evlog } from 'evlog/express'
import config from './evlog.config'

initLogger(toLoggerConfig(config))

const app = express()
app.use(evlog(toMiddlewareOptions(config)))

app.post('/checkout', (req, res) => {
  req.log.set({ orderId: 'order-123', payment: { amount: 2999 } })
  res.json({ ok: true })
})

app.listen(3000)
```

```typescript [Fastify]
import Fastify from 'fastify'
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { evlog } from 'evlog/fastify'
import config from './evlog.config'

initLogger(toLoggerConfig(config))

const app = Fastify({ logger: false })
await app.register(evlog, toMiddlewareOptions(config))

app.post('/checkout', async (request) => {
  request.log.set({ orderId: 'order-123', payment: { amount: 2999 } })
  return { ok: true }
})

await app.listen({ port: 3000 })
```

```typescript [Hono]
import { serve } from '@hono/node-server'
import { Hono } from 'hono'
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { evlog, type EvlogVariables } from 'evlog/hono'
import config from './evlog.config'

initLogger(toLoggerConfig(config))

const app = new Hono<EvlogVariables>()
app.use(evlog(toMiddlewareOptions(config)))

app.post('/checkout', (c) => {
  c.get('log').set({ orderId: 'order-123', payment: { amount: 2999 } })
  return c.json({ ok: true })
})

serve({ fetch: app.fetch, port: 3000 })
```
::

In service code below the handler, `useLogger()` from the framework entry (for example `evlog/express`) returns the same request logger, so deeper layers add fields without passing a logger around. See the [Express](/integrate/frameworks/express), [Fastify](/integrate/frameworks/fastify) and [Hono](/integrate/frameworks/hono) guides, or the [overview](/integrate/frameworks/overview) for NestJS and others.

## Throw errors that explain themselves

`createError()` gives an error a `status`, a `why` and a `fix`, and evlog records them on the event alongside the request context. `parseError()` reads them back to build the HTTP response. With Express, that happens in the 4-argument error handler:

```typescript [server.ts]
import { createError, parseError } from 'evlog'

app.post('/checkout', () => {
  throw createError({
    message: 'Payment declined',
    status: 402,
    why: 'The card issuer declined the charge',
    fix: 'Try another payment method',
  })
})

app.use((err, req, res, next) => {
  req.log.error(err)
  const parsed = parseError(err)
  res.status(parsed.status).json({ message: parsed.message, why: parsed.why, fix: parsed.fix })
})
```

[Structured Errors](/learn/structured-errors) covers `link`, error codes and [catalogs](/learn/catalogs) for failures that recur.

## Send events to your log platform

Locally, events print to the terminal. In production, a drain ships them to a backend without changing any handler. Add it to the config file:

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'

export default defineEvlog({
  service: 'checkout',
  drain: createAxiomDrain(), // reads AXIOM_API_KEY and AXIOM_DATASET
})
```

Axiom is one option. Datadog, Sentry, PostHog, Better Stack, Loki, ClickHouse, OTLP and the filesystem are listed in the [adapters overview](/integrate/adapters/overview). An `enrich` function in the same file can add fields to every event, such as the region or the deployed version ([Enrichers](/use-cases/enrichers)).

## Move from the example to your application

Choose the fields that will help you debug this operation, such as order IDs, payment outcomes, and timings. Keep credentials and unnecessary personal data out of the context, and use [Redaction](/learn/redaction) for sensitive fields you retain.

The `finally` block emits on normal returns and exceptions through this handler. It cannot guarantee delivery if the process is terminated.

`pretty: false` forces JSON in this example. Without that override, evlog selects pretty output in development and JSON in production.

For Express, Fastify, NestJS, or Hono, use a [framework integration](/integrate/frameworks/overview) to manage request logging. For remote delivery, choose a [drain adapter](/integrate/adapters/overview) and its batching/retry configuration. Short-lived processes must await pending delivery as described in [Standalone TypeScript](/integrate/frameworks/standalone).

## Production checklist

- **Sample by outcome.** Head-sample `info` events and use `keep` rules so errors, slow requests and critical paths always survive ([Sampling](/learn/sampling)).
- **Redact before shipping.** Redaction is on by default in production. Add paths for fields specific to your domain ([Redaction](/learn/redaction)).
- **Flush on exit.** Scripts, workers and serverless functions must wait for pending delivery before the process stops ([Standalone TypeScript](/integrate/frameworks/standalone)).
- **Check the wiring.** Run `npx evlog doctor` when nothing shows up, and [`evlog map`](/cli/map) to find handlers that still emit no event.

## FAQ

::accordion{type="single"}
  ::accordion-item{label="Does evlog replace console.log in Node.js?"}
  For application logging, yes. Use `log.set()` on the request logger for request context and the global `log` API for one-off messages. `pretty` output is selected in development and JSON in production unless you override it.
  ::
  ::accordion-item{label="Do I need a framework?"}
  No. The first example on this page uses `node:http` only. Framework integrations save the lifecycle code: creating the logger, measuring duration and emitting when the response ends.
  ::
  ::accordion-item{label="Can I use it next to pino or winston?"}
  Yes. Adopt it on one route at a time and keep your existing logger elsewhere. The [Pino](/compare/pino) and [Winston](/compare/winston) comparisons list what to check before migrating.
  ::
  ::accordion-item{label="Which Node.js versions are supported?"}
  The runnable examples here use Node.js 24, which runs TypeScript files directly. On older versions, compile the files or run them with a TypeScript runner.
  ::
::

To keep field names and values consistent across handlers, continue with [Typed Fields](/learn/typed-fields). The [Logging Lifecycle](/learn/lifecycle) explains how framework integrations collect context and emit events for you.
