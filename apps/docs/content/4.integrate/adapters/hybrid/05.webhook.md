Your customer's security team wants your audit trail in their SIEM, or you want a copy in a second system you run. The webhook drain POSTs each audit record to an endpoint as a [Standard Webhooks](https://www.standardwebhooks.com) message: an HMAC-SHA256 signature over the id, the timestamp and the body, which the receiver checks with `verifyWebhook` or any Standard Webhooks library.

It sends audit records only, one message per record. Other events reaching the drain are skipped, so it never carries request logs to a third party.

Send my evlog audit records to an HTTPS endpoint as signed webhooks.

1. Identify which framework I'm using and follow its evlog integration pattern
2. Generate a secret once with generateWebhookSecret() from 'evlog/webhook' and store it as EVLOG_WEBHOOK_SECRET
3. Set EVLOG_WEBHOOK_URL to the receiving endpoint
4. Wire auditOnly(createWebhookDrain()) into my framework's drain configuration
5. On the receiving side, check each message with verifyWebhook(rawBody, headers, secret) and dedupe on the returned record's id
6. For one endpoint per tenant, store the records first and forward them with relayAudit and sendAuditWebhook

Drain docs: https://www.evlog.dev/integrate/adapters/hybrid/webhook
Audit docs: https://www.evlog.dev/use-cases/audit/pipeline

::

## Installation

The webhook drain comes bundled with evlog:

```typescript [src/index.ts]
import { createWebhookDrain, verifyWebhook } from 'evlog/webhook'
```

## Quick Start

Generate a secret once and share it with the receiver:

```typescript
import { generateWebhookSecret } from 'evlog/webhook'

generateWebhookSecret() // 'whsec_' followed by 32 random bytes in base64
```

Set `EVLOG_WEBHOOK_URL` and `EVLOG_WEBHOOK_SECRET`, then wire the drain into your framework. `auditOnly` gives it the record with the identities an audit store keeps, as the [audit drains](/use-cases/audit/pipeline#auditonly) page explains.

## Configuration

### Environment variables

| Variable | Required | Description |
|----------|----------|-------------|
| `EVLOG_WEBHOOK_URL` | Yes | Endpoint that receives one POST per audit record |
| `EVLOG_WEBHOOK_SECRET` | Yes | Signing secret, `whsec_` followed by base64 |

### Priority

Configuration is resolved highest to lowest:

1. Overrides passed to `createWebhookDrain()`
2. `runtimeConfig.evlog.webhook` (Nitro)
3. `runtimeConfig.webhook` (Nitro)
4. Environment variables

### Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `url` | `string` | | Endpoint that receives the messages |
| `secret` | `string \| string[]` | | One secret, or two during a rotation |
| `headers` | `Record<string, string>` | | Extra headers on every message, such as a static token the receiver also checks |
| `timeout` | `number` | `5000` | Request timeout in ms |
| `retries` | `number` | `2` | Retry attempts on transient failures |

## What the receiver gets

Each record is one POST. The headers carry the record's `id`, the time of sending in Unix seconds, and one `v1,` signature per secret:

```http [Request headers]
content-type: application/json
webhook-id: 01a204b4-5493-70a5-b080-38d013fb8216
webhook-timestamp: 1795375256
webhook-signature: v1,f9A2kb9/q009IGJAQcvPeG+oyZRWJ8QahmLM/WLV6LE=
```

The body is the Standard Webhooks payload shape, with the audit record as `data`:

```json [Request body]
{
  "type": "audit.event",
  "timestamp": "2026-11-22T19:20:56.723Z",
  "data": {
    "id": "01a204b4-5493-70a5-b080-38d013fb8216",
    "timestamp": "2026-11-22T19:20:56.723Z",
    "action": "token.create",
    "actor": { "type": "user", "id": "usr_42", "email": "ada@example.com" },
    "target": { "type": "token", "id": "tok_9c1e" },
    "tenantId": "team_acme",
    "outcome": "success",
    "metadata": { "name": "CI token" },
    "version": 2,
    "context": { "requestId": "req_51c2" }
  }
}
```

The record is the only thing sent: no request fields, no service name, nothing from the request's wide event.

## Verify on the receiving side

`verifyWebhook(body, headers, secret)` checks the signature and the timestamp, and returns the record. Pass the raw body exactly as received, since parsing and re-serializing it changes the bytes the signature covers:

```typescript [server/api/hooks/audit.post.ts]
import { verifyWebhook, WebhookVerificationError } from 'evlog/webhook'

export default defineEventHandler(async (event) => {
  try {
    const record = await verifyWebhook(await readRawBody(event) ?? '', getHeaders(event), process.env.AUDIT_WEBHOOK_SECRET!)
    await db.insert(auditCopy).values({ id: record.id, record }).onConflictDoNothing()
    return null
  } catch (error) {
    if (error instanceof WebhookVerificationError) throw createError({ status: 401 })
    throw error
  }
})
```

It throws `WebhookVerificationError` when a header is missing, the timestamp is more than 5 minutes from the receiver's clock (`{ tolerance }` in seconds changes it), no signature matches, or `webhook-id` differs from the record's `id`. Delivery is at least once, so insert on the `id` and ignore a conflict.

Receivers that do not run evlog use any [Standard Webhooks library](https://github.com/standard-webhooks/standard-webhooks/tree/main/libraries). The signatures match the reference test vector.

## Rotate the secret

Pass both secrets while the receiver moves to the new one. Every message carries one signature per secret, and the receiver accepts either:

```typescript
createWebhookDrain({ secret: [process.env.WEBHOOK_SECRET_NEXT!, process.env.WEBHOOK_SECRET!] })
```

Drop the old secret once the receiver only knows the new one. `verifyWebhook` takes an array too, for a receiver that rotates on its side.

## Send each tenant to its own endpoint

`createWebhookDrain` sends to one endpoint, from the request that made the record. For an endpoint per customer, store the records first and forward each tenant's with `relayAudit` and `sendAuditWebhook(records, { url, secret })`. Your store keeps the backlog while an endpoint is down, and a cursor per endpoint resumes where it stopped. [Send each tenant's audits to their endpoint](/use-cases/audit/pipeline#send-each-tenants-audits-to-their-endpoint) has the full loop.

## Delivery and failures

| Situation | What happens |
| --- | --- |
| Endpoint answers `2xx` | The record is delivered |
| Endpoint answers `408`, `429`, `502`, `503` or `504`, times out, or the connection fails | Retried `retries` times with backoff, then reported on the console |
| Endpoint answers another status, `500` included | Reported on the console, not retried |
| Several records in one batch, one refused | The records after it are not sent, so the endpoint never receives them out of order |

The drain never throws into your request. When records must survive an endpoint that is down for longer than the retries, use the relay above instead of the drain.

The drain does not check that the URL is a public address. When customers register their own URLs, refuse internal and link-local addresses before you store one.

## Direct API

Send records without a drain, for a relay or a backfill. `sendAuditWebhook` throws at the first message the endpoint refuses:

```typescript
import { sendAuditWebhook, signWebhook } from 'evlog/webhook'

await sendAuditWebhook(records, { url, secret })

// The three headers for a body you send yourself:
const headers = await signWebhook(record.id, body, secret)
```
