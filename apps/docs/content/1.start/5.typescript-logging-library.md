Your request context has a schema. Your logger should help you keep it consistent. evlog lets you declare that schema in TypeScript, add fields as work progresses, and emit the completed event with its outcome.

## Give your request context a type

Install evlog in a TypeScript project:

```bash [Terminal]
npm install evlog
```

This example constrains the context accepted by `log.set()` and `log.emit()`. Run it with Node.js 24, which supports the erasable TypeScript syntax used here:

```typescript [typed-context.ts]
import { createLogger, initLogger } from 'evlog'

initLogger({ env: { service: 'checkout' }, pretty: false })

type CheckoutContext = {
  orderId: string
  payment: { chargeId: string, amount: number }
  outcome: 'paid' | 'declined'
}

const log = createLogger<CheckoutContext>()
log.set({ orderId: 'order-123' })
log.set({ payment: { chargeId: 'ch_123', amount: 2999 } })
log.emit({ outcome: 'paid' })
```

Run `node typed-context.ts` to emit a JSON event. Check the file with your project's TypeScript compiler as well: Node strips types without checking them. These calls would fail type checking if inserted before `emit()`:

```typescript [Invalid context]
log.set({ payment: { amount: '2999' } })
log.set({ outcome: 'refunded' })
```

Types constrain your code, not incoming data. Validate request bodies at the boundary. The generic does not require every field to be present before emission, and the initial context passed to `createLogger()` is an open record. Use typed `set()` calls when you want these checks.

## Choose the logging API for the operation

For individual messages, the global `log.info()` and related methods send structured records through evlog's pipeline. For a request or job, `createLogger()` accumulates context with `set()` and emits when you call `emit()`. Framework integrations manage that lifecycle for their handlers. [Wide Events](/learn/wide-events) explains the accumulation model.

[Structured Errors](/learn/structured-errors) add `why`, `fix`, and `link` to errors. Redaction applies configured field paths and recognized patterns before output and drains, but does not identify every kind of personal data. It is enabled by default in production and can be disabled. [Sampling](/learn/sampling) can drop events or retain selected errors and slow requests.

## Account for the migration

Replacing Pino or Consola requires changes to call signatures and configuration. evlog is not API-compatible with either library. Existing queries may also need updating when several records become one event.

Severity is limited to `debug`, `info`, `warn`, and `error`. The global API uses `minLevel` for filtering, while wide events use sampling. evlog has a plugin API for lifecycle hooks and enrichment, but not Pino's per-key serializer API. Compare these tradeoffs in [evlog vs other loggers](/reference/vs-other-loggers).

The core package has no runtime dependencies. The [Performance reference](/reference/performance) explains which imports, output settings, and workloads determine bundle size and execution cost.

## Use the integration for your runtime

- **Nuxt and Nitro:** use the [Nuxt module](/integrate/frameworks/nuxt) or [Nitro plugin](/integrate/frameworks/nitro) and access the handler logger with `useLogger(event)`.
- **Cloudflare Workers:** use the [Workers integration](/integrate/frameworks/cloudflare-workers), pass its logger through the handler, and configure `waitUntil` for asynchronous delivery.
- **Scripts and jobs:** initialize logging explicitly and finish each operation yourself. See [Standalone TypeScript](/integrate/frameworks/standalone).

Follow [Structured Logging in Node.js](/start/structured-logging-nodejs) for a complete HTTP example, or the [Quick Start](/start/quick-start) to choose a framework. When events need a backend, choose a [drain adapter](/integrate/adapters/overview).
