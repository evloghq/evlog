Do you want to keep the logger you have, or replace it? LogLayer is an API layer: it gives your code one fluent API and forwards each record through a [transport](https://loglayer.dev/transports/) to pino, winston, LogTape, consola or a service such as Datadog, so the library underneath stays swappable. evlog is the logger itself. It builds the events and delivers them through drain adapters.

## At a glance

| | LogLayer | evlog |
| --- | --- | --- |
| Role | API in front of a logging library or service, one or several transports per instance | The logger, with its own output and drain adapters |
| Structured data | `withContext()` persists across records, `withMetadata()` and `withError()` apply to one record | `set()` accumulates on an operation logger until `emit()` |
| Wide events | `@loglayer/mixin-wide-events`: `withWideEvents()` then `emitWideEvent()`, with an `AsyncLocalStorage` you create | Built in: the request logger accumulates and the [framework integrations](/integrate/frameworks/overview) emit at the end of each request |
| Framework integrations | Express, Fastify, Hono, Koa and Elysia: a request-scoped child logger and pino-http style `incoming request` and `request completed` records | One event per request, with `useLogger()` and the framework's own accessor |
| Routing | Groups send records to chosen transports with per-group levels | No per-subsystem routing |
| Redaction | `@loglayer/plugin-redaction`: configured paths, through fast-redact | On by default in production once `initLogger()` has run: keys ending in `password`, `passwd`, `secret` or `token`, built-in patterns such as emails and card numbers, and configured paths |
| Sampling | A sampling plugin, and rate, per-level, `shouldEmit` and `forceKeep` options on the wide-events mixin | Per-level rates and tail sampling with `keep` conditions |
| Testing | `MockLogLayer`, a logger whose methods do nothing | A memory drain that captures emitted events |

Sources: the [LogLayer introduction](https://loglayer.dev/introduction), the [wide-events mixin](https://loglayer.dev/mixins/wide-events), the [redaction plugin](https://loglayer.dev/plugins/redaction), the [Express integration](https://loglayer.dev/integrations/express) and [unit testing](https://loglayer.dev/logging-api/unit-testing) pages, read for loglayer 9.4.0.

## Compare who emits the wide event

Both libraries accumulate fields and emit one record per operation. The difference is who wires that lifecycle. LogLayer's integrations write their two request records but do not emit a wide event. Its [Wide Events guide](https://loglayer.dev/guides/wide-events) has the application write Express middleware that runs the async context and calls `emitWideEvent()` when the response finishes. evlog's integrations open the request logger and emit it themselves.

Outside `asyncContext.run()`, LogLayer keeps nothing: with mixin 1.4.0, `emitWideEvent()` then writes a record that holds only its message, and no warning is printed. Run every request inside the context.

Each example below records one simulated checkout and its outcome. Install the corresponding packages and run the file with Node.js 24. Pass `decline` to exercise the error path.

LogLayer accumulates through the mixin inside an async context:

```typescript [checkout-loglayer.ts]
import { AsyncLocalStorage } from 'node:async_hooks'
import { LogLayer, StructuredTransport, useLogLayerMixin } from 'loglayer'
import { createWideEventMixin } from '@loglayer/mixin-wide-events'

const asyncContext = new AsyncLocalStorage()
useLogLayerMixin(createWideEventMixin({ asyncContext }))
const log = new LogLayer({ transport: new StructuredTransport({ logger: console }) })

await asyncContext.run({}, async () => {
  log.withWideEvents({ orderId: 'order-123', amount: 2999 })
  try {
    if (process.argv.includes('decline')) throw new Error('Payment declined')
    log.withWideEvents({ outcome: 'paid' })
    log.emitWideEvent({ message: 'checkout' })
  } catch (error) {
    log.withWideEventError(error)
    log.withWideEvents({ outcome: 'declined' })
    log.emitWideEvent({ message: 'checkout', level: 'error' })
    process.exitCode = 1
  }
})
```

evlog accumulates on the operation logger and emits in `finally`:

```typescript [checkout-evlog.ts]
import { createLogger, initLogger } from 'evlog'

initLogger({ env: { service: 'checkout' }, pretty: false })
const log = createLogger({ orderId: 'order-123', amount: 2999 })
try {
  if (process.argv.includes('decline')) throw new Error('Payment declined')
  log.set({ outcome: 'paid' })
} catch (error) {
  log.error(error instanceof Error ? error : new Error(String(error)))
  log.set({ outcome: 'declined' })
  process.exitCode = 1
} finally {
  log.emit()
}
```

LogLayer emits at `info` unless you pass a level, so the error path passes `level: 'error'`. evlog raises the event to `error` once `log.error()` has run, and adds `durationMs`. These examples compare how emission is owned, not output formats or speed.

## Keep LogLayer, or plan the migration

Keep LogLayer when its purpose is the one you need: keeping pino or winston swappable behind one API, routing subsystems to different transports with groups, or sending one record to several destinations. LogLayer can also sit in front of a logger you are not ready to replace.

If you migrate, plan these mappings before changing call sites:

| LogLayer | evlog |
| --- | --- |
| `withContext()` | Initial context of `createLogger()`, or `set()` on the request logger |
| `withMetadata().info()` for one record | `log.info({ ... })` from [Simple Logging](/learn/simple-logging) |
| Wide-events mixin and your middleware | A [framework integration](/integrate/frameworks/overview), which emits per request |
| Groups and per-group levels | No direct equivalent. Decide which records still need separate routing |
| Redaction plugin paths | `redact.paths`, on top of the default redaction in production |
| `MockLogLayer` | `enabled: false` to silence, or the memory drain to assert on events |

## Measure the stack you will run

A LogLayer call costs the LogLayer layer plus the logger behind its transport, so a measurement of LogLayer over pino is not a measurement of LogLayer alone. The [Performance reference](/reference/performance) explains evlog's benchmark boundaries. Compare both on the transport, payload and redaction you intend to deploy.

For the logger LogLayer most often sits in front of, see [evlog vs Pino](/compare/pino). The [logger overview](/reference/vs-other-loggers) covers the other choices.
