You run, or plan to run, an OpenTelemetry collector, and you wonder whether evlog competes with it. It does not. evlog creates application-level wide events; OpenTelemetry (OTel) is an instrumentation SDK, collector ecosystem, and wire protocol. The OTLP drain is the bridge: `evlog/otlp` exports each evlog wide event to any OTLP endpoint, so the conclusion is different layers, not a replacement.

## Different layers

- **OpenTelemetry** defines three signals: traces, metrics, and logs. SDKs instrument the runtime, the Collector receives, processes, and exports, and OTLP is the wire protocol over gRPC or HTTP ([opentelemetry.io/docs](https://opentelemetry.io/docs/)). Semantic conventions fix attribute names (`http.request.method`, `server.address`, `error.type`).
- **evlog** builds the application-level event itself: you accumulate fields with `log.set()` during a request and evlog emits one wide event when it ends, including when the handler throws.
- **The bridge**: the [OTLP adapter](/integrate/adapters/hybrid/otlp) maps each wide event to an OTLP log record, so an evlog event lands next to spans the rest of your stack already emits.

A wide event and a span with rich attributes are close relatives. The difference is where the field is written and what it costs, not what it is. If your team already runs a collector, keep it; evlog feeds it.

## Benchmark methodology

evlog does not benchmark against OpenTelemetry, because the two do not do the same job: OTel SDKs produce spans and metrics through instrumentation, evlog produces wide events through its logging API. The numbers worth quoting here are evlog's own cost, from the open-source suite in [`packages/evlog/bench/`](https://github.com/evloghq/evlog/tree/main/packages/evlog/bench), measured with Vitest bench (tinybench), 500ms warmup after JIT stabilization, JSON output to a no-op destination, all in one process:

- Wide event lifecycle (create + 3 `set()` + `emit()`): 1.58M ops/s, full lifecycle ~500ns per event.
- All enrichers combined on a fully featured request: 2.14µs, for a total of ~2.7µs per request against database calls of 1-50ms.
- OTLP export cost is network I/O and runs off the hot path through the drain pipeline; the benchmarks measure the event construction, not the shipment.

Run it yourself: `pnpm exec vitest bench bench/comparison/` in `packages/evlog`. Full conditions on [Performance](/reference/performance).

## API differences

| Aspect | evlog | OpenTelemetry |
|--------|-------|---------------|
| What it produces | One wide event per operation, accumulated with `log.set()` | Spans (name, duration, status, attributes), metrics, and log records via SDK instrumentation |
| Field naming | Your application's own typed fields | [Semantic conventions](https://opentelemetry.io/docs/specs/semconv/) fix attribute names; nonconforming fields are yours alone |
| Sampling | Built-in head and tail sampling on events | Head-based at the SDK, tail-based in the Collector |
| Context propagation | `TraceContext` enricher reads the incoming `traceparent` | Native `traceparent` / `tracestate` propagation across services |
| Transport | Drain pipeline with batching and retry | OTLP over gRPC or HTTP to a Collector or gateway |
| Runtime coverage | Node.js, Bun, Deno, Workers, browsers | SDKs per language and runtime, Collector as a separate process |

## Migration snippet

There is nothing to migrate away from. The usual adoption is "keep OTel, add evlog as the event builder, ship through OTLP":

```typescript [server/plugins/evlog-drain.ts]
import { createOTLPDrain } from 'evlog/otlp'

export default defineNitroPlugin((nitroApp) => {
  nitroApp.hooks.hook('evlog:drain', createOTLPDrain())
})
```

With the endpoint configured, every wide event becomes an OTLP log record:

```bash [.env]
OTLP_ENDPOINT=http://localhost:4318
```

The adapter maps `level` to `severityNumber`/`severityText`, `timestamp` to `timeUnixNano`, `service`/`environment`/`version`/`region` to resource attributes, and `traceId`/`spanId` to their OTLP fields; every other wide-event field travels as a log attribute. Full mapping in the [OTLP adapter docs](/integrate/adapters/hybrid/otlp).

## Limitations

- evlog does not produce spans or metrics. For distributed tracing you still need OTel SDK instrumentation or a framework that emits spans.
- The OTLP adapter speaks OTLP HTTP (`/v1/logs`), not gRPC; point it at a collector or an HTTP-capable gateway.
- The `TraceContext` enricher makes an evlog event joinable to a trace someone else started, but evlog does not create the trace itself.
- OTel semantic conventions are a contract. If your backend expects conforming attribute names, map your evlog fields explicitly rather than inventing lookalike names.

## When to choose OpenTelemetry

Choose OTel, with or without evlog, when you need:

- Cross-service traces, metrics, and alerting from a vendor-neutral SDK and Collector.
- Instrumentation of libraries and infrastructure you do not control, via auto-instrumentation.
- Tail-based sampling policies executed in the Collector rather than in your application.

Choose evlog alongside it when your application logs need one queryable event per request with structured errors. The two compose: evlog builds the event, the OTLP drain ships it. See [OTLP Adapter](/integrate/adapters/hybrid/otlp) for configuration, or [evlog vs other loggers](/reference/vs-other-loggers) for logger-to-logger comparisons.
