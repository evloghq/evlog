Your Pino setup already ships JSON logs. The next decision is how your application assembles request context. evlog provides an accumulator and a lifecycle for that context. Pino provides JSON logging, bindings, serializers, and transports that you can keep if they already fit your application.

## Compare the work you maintain

| Concern | evlog | Pino |
| --- | --- | --- |
| Request context | `createLogger()` and typed `set()` calls accumulate fields until `emit()` | `child()` attaches bindings to records. The application can accumulate an object and log it once. |
| Adding bindings | `set()` merges fields into the pending event | `setBindings()` adds bindings after creation. It does not overwrite existing keys and can introduce duplicate keys. |
| Error fields | `createError()` carries `why`, `fix`, and `link` | Error serializers, including `pino.stdSerializers.err`, shape error records. |
| Extensibility | Plugins and enrichers hook into the event lifecycle | Per-key serializers, formatters, and transports |
| Levels | Six severities (`trace` to `fatal`), global `minLevel`, sampling for wide events | Built-in and custom levels, mutable logger level |
| Delivery | Drain adapters and configurable batching/retry | Destinations and transports, including worker-thread transports |

Pino documents these contracts in its [API reference](https://github.com/pinojs/pino/blob/main/docs/api.md). A worker transport moves transport processing and delivery to a worker. The logger still performs the initial JSON serialization on the calling thread. See [Pino transports](https://github.com/pinojs/pino/blob/main/docs/transports.md).

## Compare one completed operation

Both libraries can emit one structured record for an operation. Install `pino` or `evlog` and run the corresponding TypeScript file with Node.js 24. The `decline` argument exercises the failure path. These examples simulate the same checkout decision without calling a payment provider.

With Pino, the application owns the accumulated context and emits it in `finally`:

```typescript [checkout-pino.ts]
import pino from 'pino'

const logger = pino()
const context = { orderId: 'order-123', amount: 2999, outcome: 'pending' }
let failure: Error | undefined

try {
  if (process.argv.includes('decline')) throw new Error('Payment declined')
  context.outcome = 'paid'
} catch (error) {
  failure = error instanceof Error ? error : new Error(String(error))
  context.outcome = 'declined'
  process.exitCode = 1
} finally {
  if (failure) logger.error({ ...context, err: failure }, 'checkout completed')
  else logger.info(context, 'checkout completed')
}
```

With evlog, the logger owns the accumulator and selects error severity after `error()`:

```typescript [checkout-evlog.ts]
import { createLogger, initLogger } from 'evlog'

initLogger({ env: { service: 'checkout' }, pretty: false })
const log = createLogger({ orderId: 'order-123', amount: 2999, outcome: 'pending' })

try {
  if (process.argv.includes('decline')) throw new Error('Payment declined')
  log.set({ outcome: 'paid' })
} catch (error) {
  log.error(error instanceof Error ? error : new Error(String(error)))
  log.set({ outcome: 'declined' })
  process.exitCode = 1
} finally {
  log.emit()
}
```

Each version emits one record on either path. Their envelopes differ: Pino uses a numeric level and its error serializer, while evlog adds its event metadata and duration. evlog's [wide-event model](/learn/wide-events) becomes useful when several layers contribute fields and framework integrations own the request lifecycle. Pino's `pino-http` also provides automatic HTTP request logging.

## Using Pino with TypeScript

Pino 10 ships first-party types in the `pino` package (`pino.d.ts`). `import pino from 'pino'` is typed, and custom level names become methods on `Logger`. Pino checks some printf argument types, but it does not require a value for every placeholder. You do not need `@types/pino`. See Pino's [TypeScript section](https://github.com/pinojs/pino/blob/main/docs/api.md#typescript).

Those types cover each log call, not the request-shaped object you build yourself. `child()` and `setBindings()` take `Bindings`, which is `Record<string, any>` in [pino.d.ts](https://github.com/pinojs/pino/blob/main/pino.d.ts). A child logger does not know that this request has `orderId` and `amount`. The `checkout-pino.ts` example above is valid TypeScript. Type the `context` object yourself if you want excess-property checks on that accumulator.

To constrain fields on every `logger.info({ ... })` call, augment Pino's `LogFnFields` interface, as documented under [module augmentation](https://github.com/pinojs/pino/blob/main/docs/api.md#logfnfields-interface). That types the merging object on each line. It does not type `child()` bindings. Required fields on `LogFnFields` also apply when you pass an `Error`, which is the caveat Pino documents.

```typescript [pino-log-fn-fields.ts]
import 'pino'

declare module 'pino' {
  interface LogFnFields {
    orderId?: string
    amount?: number
  }
}
```

TypeScript applies that augmentation only if this file is part of the same program as the `pino` log calls it should constrain. It is an alternative to typing the `context` object in `checkout-pino.ts`, not a file that example already loads.

evlog types later `set()` calls against a fields interface you pass as a generic:

```typescript
interface CheckoutFields {
  orderId: string
  amount: number
  outcome: string
}
```

`createLogger<CheckoutFields>()` does not type-check the object you pass into `createLogger`. Subsequent `set()` calls reject unknown keys. The `checkout-evlog.ts` example above is untyped until you add that generic. Framework request loggers take the same generic: `useLogger<CheckoutFields>(event)` on Nuxt and Nitro, with an explicit `import { useLogger } from 'evlog'` (the Nuxt auto-import drops excess-property checks), and `useLogger<CheckoutFields>()` where AsyncLocalStorage holds the logger, such as Next.js. See [Typed Fields](/learn/typed-fields).

Reach for evlog when you want that accumulator typed and a framework integration to emit it.

This section matches Pino 10.4.0 first-party types (`pino.d.ts`).

## FAQ

::accordion{type="single"}
  ::accordion-item{label="Does Pino support TypeScript?"}
  Yes. Pino 10 ships first-party types. You do not need `@types/pino`. See [Using Pino with TypeScript](#using-pino-with-typescript).
  ::
  ::accordion-item{label="Can I type Pino child loggers and bindings?"}
  Not through `child()` bindings, which stay `Record<string, any>`. Type the object you accumulate, or augment `LogFnFields`. Both are in the section above.
  ::
  ::accordion-item{label="How does evlog type context compared to Pino?"}
  Pino types each log call. evlog types later `set()` calls: `createLogger<CheckoutFields>()` on the standalone logger, `useLogger<CheckoutFields>(event)` on Nuxt and Nitro with an explicit `import { useLogger } from 'evlog'`, `useLogger<CheckoutFields>()` where AsyncLocalStorage holds the logger ([Typed Fields](/learn/typed-fields)). `set()` rejects unknown keys. The object passed into `createLogger` stays untyped. You can keep Pino and still accumulate an object yourself. Reach for evlog when you want that accumulator typed and a framework integration to emit it.

## Migrate one handler before changing the whole application

Inventory the fields your dashboards query, custom levels, serializers, and transport configuration. Map them explicitly before switching output. Pino serializers do not transfer unchanged into evlog plugins, and a custom transport may need a new drain.

Keep the existing Pino path for unrelated handlers while you [validate one evlog integration](/integrate/frameworks/overview). Avoid emitting duplicate records for the same request through both paths unless you deliberately account for that in queries and ingestion costs. Test successful requests, thrown errors, shutdown, and redaction using the same assertions about required fields.

## Read benchmark conditions before choosing on speed

The repository's historical comparison uses silent evlog event construction, Pino JSON writes to `/dev/null`, and different output counts in the request-lifecycle scenario. It does not establish an equivalent-output throughput ranking. The [Performance reference](/reference/performance) records the workloads and how to measure your own configuration.

Keep Pino when its serializers, ecosystem integrations, or worker transports already solve your problem. Choose evlog when its context accumulator, structured errors, and framework lifecycle remove application code you would otherwise maintain. If you chose evlog, start with the [framework integrations](/integrate/frameworks/overview). For other choices, use [evlog vs other loggers](/reference/vs-other-loggers).
