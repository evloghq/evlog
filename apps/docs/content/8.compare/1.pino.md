You are choosing a TypeScript logger and pino is the default candidate: it is the fast JSON logger for Node, its low overhead is a stated design goal, and its benchmarks are published in its repository. This page compares evlog and pino on methodology, API shape, migration effort, and known gaps, then states plainly when you should stay on pino.

## Benchmark methodology

All evlog vs pino numbers on this page come from the open-source benchmark suite in [`packages/evlog/bench/`](https://github.com/evloghq/evlog/tree/main/packages/evlog/bench). The conditions, from [Performance](/reference/performance):

- Same output mode: JSON to a no-op destination, no disk or network I/O measured. pino writes to `/dev/null` (sync), evlog uses silent mode.
- Same warmup: each benchmark runs 500ms after JIT stabilization.
- Same tooling: [Vitest bench](https://vitest.dev/guide/features#benchmarking) powered by [tinybench](https://github.com/tinylibs/tinybench).
- Same machine: both libraries run in the same process on the same hardware.

Snapshot results from a single MacBook run (numbers shift ±5-10% between runs):

| Scenario | evlog | pino |
|----------|------:|-----:|
| Simple string log | 1.83M ops/s | 1.09M ops/s |
| Structured (5 fields) | 1.64M ops/s | 716.1K ops/s |
| Deep nested log | 1.55M ops/s | 464.9K ops/s |
| Child / scoped logger | 1.70M ops/s | 845.0K ops/s |
| Wide event lifecycle | 1.58M ops/s | 205.8K ops/s |
| Burst (100 logs) | 17.8K ops/s | 10.3K ops/s |

The wide-event lifecycle row compares different work by design: evlog accumulates fields and emits one event, pino emits four separate lines for the same request. Run the suite yourself with `pnpm exec vitest bench bench/comparison/` before trusting any number on your hardware.

## API differences

| Aspect | evlog | pino |
|--------|-------|------|
| Output | One wide event per operation, fields accumulated with `log.set()` | One JSON line per call ([getpino.io](https://getpino.io)) |
| Levels | `debug` / `info` / `warn` / `error`, fixed | Numeric `trace` 10 to `fatal` 60, custom levels supported |
| Child loggers | `log.fork()` branches accumulated context and can be discarded | `logger.child(bindings)`, bindings fixed at creation |
| Redaction | Built-in, auto in prod | Built-in: `redact: ['req.headers.authorization']` with path syntax |
| Serializers | Handled via `createError` + `parseError` and custom drains | Per-key serializers: `serializers: { err: pino.stdSerializers.err }` |
| Request logging | Framework integrations emit one wide event per request | `pino-http` emits on response |
| Transport / drain | Built-in drain pipeline with batching, retry, fan-out | Transports (`pino.transport`, `pino/file`, `pino-pretty`) run in a worker thread over `thread-stream` |
| Custom levels | Not supported | Supported |
| Runtime level mutation | Global `minLevel` set once at startup | `logger.level = 'debug'` at runtime |

pino has redaction, serializers, and request logging. Do not read the table as "pino lacks features"; the real difference is the accumulation model: pino writes a line per call ([getpino.io](https://getpino.io)), evlog accumulates fields over the request and emits one event at the end, including when the handler throws.

## Migration snippet

The same checkout flow, first in pino's API, then in evlog's:

```typescript [Before (pino)]
import pino from 'pino'

const log = pino({ name: 'checkout' })
const child = log.child({ flow: 'checkout' })

child.info({ event: 'checkout_started' })

try {
  const cart = await getCart(userId)
  child.info({ cart: { items: cart.items.length, total: cart.total } }, 'cart loaded')

  const charge = await stripe.charge(cart.total)
  child.info({ stripe: { chargeId: charge.id } }, 'charge ok')

  if (!charge.success) {
    throw new Error(`Payment failed: ${charge.decline_reason}`)
  }
} catch (err) {
  child.error({ err }, 'checkout failed')
  throw err
}
```

```typescript [After (evlog)]
import { initLogger, createLogger, createError } from 'evlog'

initLogger({ env: { service: 'checkout' } })

const log = createLogger({ flow: 'checkout' })

try {
  const cart = await getCart(userId)
  log.set({ cart: { items: cart.items.length, total: cart.total } })

  const charge = await stripe.charge(cart.total)
  log.set({ stripe: { chargeId: charge.id } })

  if (!charge.success) {
    throw createError({
      message: 'Payment failed',
      status: 402,
      why: charge.decline_reason,
      fix: 'Try a different payment method',
    })
  }
} catch (err) {
  log.error(err as Error)
  throw err
} finally {
  log.emit()
}
```

Three things move in the migration:

- N log lines become `log.set` accumulations plus one `log.emit`.
- `new Error` becomes `createError`, so the error carries `why` and `fix`.
- Formatter and transport assembly become one `initLogger` call plus a drain if you ship logs anywhere.

## Limitations of evlog

- No custom levels. If your pipeline depends on `fatal` or `trace`, map them to the closest of the four evlog levels.
- Global `log.*` `minLevel` is fixed at startup; pino mutates level at runtime. Request-scoped loggers expose `log.setLevel()`.
- No `log.child(bindings)` shorthand on the simple API; use `createLogger({ ... })` or a framework integration's request middleware.
- No serializer plugin system; custom transforms live in a custom drain or before `log.set`.
- pino's worker-thread transports keep serialization and I/O off the main thread; evlog drains run on the hot path's async boundary instead.

## When to choose pino

- You emit hundreds of thousands of fire-and-forget lines per second with no context accumulation, and you run a [worker-thread transport](https://getpino.io/#/docs/transports). That is the one shape where pino is faster; see [Performance](/reference/performance).
- Your codebase is deep in the pino ecosystem: `pino-http`, `pino-pretty`, custom transports you do not want to port.
- You need custom levels (`trace`, `fatal`) as first-class severities in an existing pipeline.

For everything else, wide events, structured errors, redaction, and the drain pipeline come built in with evlog. See [evlog vs other loggers](/reference/vs-other-loggers) for winston and consola, or [Simple Logging](/learn/simple-logging) to start.
