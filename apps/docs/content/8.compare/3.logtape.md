You are comparing TypeScript loggers and you have come across LogTape, a zero-dependency logging library built "library-first": your code records freely, and the application decides if, where, and how those logs play back ([logtape.org](https://logtape.org/)). This page compares evlog and LogTape on methodology, API shape, migration effort, and known gaps, then states plainly when LogTape is the better pick.

## Benchmark methodology

evlog's open-source benchmark suite in [`packages/evlog/bench/`](https://github.com/evloghq/evlog/tree/main/packages/evlog/bench) compares evlog against pino, winston, and consola; LogTape is not part of that head-to-head table yet, so no direct evlog-vs-LogTape number is claimed here.

What you can fairly compare comes from each project's own published measurements, with an important caveat: they measure different things.

- **LogTape publishes** console-overhead numbers on Node.js: LogTape at 451 ns per record and pino at 339 ns, several times ahead of winston, bunyan, and log4js ([logtape.org](https://logtape.org/)). It also publishes bundle size: 5.3 KB min+gzip with zero dependencies.
- **evlog publishes** request-lifecycle numbers from its Vitest bench (tinybench) suite: wide event lifecycle (create + 3 `set()` + `emit()`) at 1.58M ops/s, roughly 500 ns per full event, and ~2.7 µs per fully enriched request ([Performance](/reference/performance)). All runs use JSON output to a no-op destination, 500 ms warmup after JIT stabilization, in one process.

A per-record console write and a full wide-event lifecycle are not the same workload, so treat these as sizing each library's own bill, not a head-to-head result. Reproduce evlog's numbers yourself with `pnpm exec vitest bench bench/comparison/` in `packages/evlog`.

## API differences

| Aspect | evlog | LogTape |
|--------|-------|---------|
| Output | One wide event per operation, fields accumulated with `log.set()` | One record per call, values kept as first-class data |
| Library vs app | Application-first: the app configures logging for its own events | Library-first: libraries stay silent until the application calls `configure()` |
| Logger identity | Request-scoped logger per unit of work | `getLogger(["app", "module"])` hierarchical categories, config inherited parent to child |
| Levels | `debug` / `info` / `warn` / `error`, fixed | Six levels: `trace`, `debug`, `info`, `warning`, `error`, `fatal` |
| Message style | Typed fields attached to the event | Message templates (`"user {userId} signed in"`, { userId }) or tagged templates |
| Context | `log.fork()` branches accumulated context | `withContext({ requestId })` implicit contexts follow every log in scope |
| Redaction | Built-in redaction of sensitive fields | Separate `@logtape/redaction` package: by field, by pattern, or HMAC pseudonyms |
| Sinks / drains | Built-in drain pipeline with batching, retry, fan-out | Sinks are plain functions; console, file, rotating file, OTel, Sentry, syslog, CloudWatch, Windows Event Log |
| Testing | Not built in | `@logtape/testing` capture and assertion utilities, plus lint rules |
| Package | npm | npm and JSR, dual ESM/CommonJS, bundled types |

The core difference is the unit of output: LogTape records a stream of categorized, structured lines; evlog accumulates fields over the request and emits one correlated event at the end, including when the handler throws.

## Migration snippet

The same checkout flow, first in LogTape's API, then in evlog's:

```typescript [Before (LogTape)]
import { configure, getConsoleSink, getLogger } from "@logtape/logtape";

await configure({
  sinks: { console: getConsoleSink() },
  loggers: [
    { category: "checkout", lowestLevel: "debug", sinks: ["console"] },
  ],
});

const logger = getLogger(["checkout"]);

export async function checkout(userId: string) {
  logger.info("checkout started for {userId}", { userId });
  try {
    const cart = await getCart(userId);
    logger.info("cart loaded: {cart}", { cart: { items: cart.items.length, total: cart.total } });

    const charge = await stripe.charge(cart.total);
    logger.info("charge {chargeId} succeeded", { chargeId: charge.id });

    if (!charge.success) {
      logger.error("payment failed: {reason}", { reason: charge.decline_reason });
      throw new Error(`Payment failed: ${charge.decline_reason}`);
    }
  } catch (err) {
    logger.error("checkout failed: {err}", { err });
    throw err;
  }
}
```

```typescript [After (evlog)]
import { initLogger, createLogger, createError } from 'evlog'

initLogger({ env: { service: 'checkout' } })

export async function checkout(userId: string) {
  const log = createLogger({ flow: 'checkout', userId })
  try {
    const cart = await getCart(userId)
    log.set({ cart: { items: cart.items.length, total: cart.total } })

    const charge = await stripe.charge(cart.total)
    log.set({ stripe: { chargeId: charge.id } })

    if (!charge.success) {
      throw createError({
        message: 'Payment failed',
        status: 402,
        why: charge.decline_reason,
        fix: 'Try a different payment method',
      })
    }
  } catch (err) {
    log.error(err as Error)
    throw err
  } finally {
    log.emit()
  }
}
```

Three things move in the migration:

- N categorized lines become `log.set` accumulations plus one `log.emit`.
- `getLogger` categories with inherited levels become one request-scoped logger per unit of work.
- LogTape's `configure()`-based output setup becomes `initLogger` plus a drain if you ship logs anywhere.

## Limitations of evlog

- **Severity levels are fixed to four.** There is no `trace` or `fatal`, so map them to the closest of `debug` through `error`.
- **A hierarchical category tree is absent.** LogTape raises verbosity per subtree; evlog instead branches request-scoped context with `log.fork()`, which is a different model.
- **Message-template logging is not the style.** Where LogTape writes "user {id} signed in", evlog attaches fields to the event rather than interpolating them into text.
- **Log-capture testing utilities are not built in.** With evlog you test your drains rather than assert on captured records.
- **Bundle-sensitive front-end work favors LogTape.** Its 5.3 KB zero-dependency core is lighter than evlog's pipeline, which is built for server-side application observability.

## When to choose LogTape

- **Writing a library, not an application.** LogTape is designed for exactly this: library code logs freely and stays completely silent until the consuming application opts in with `configure()` ([Using in libraries](https://logtape.org/manual/library)), so your dependency never forces a logger on anyone.
- **Zero dependencies and a tiny footprint** (5.3 KB min+gzip, tree-shakable) across Node.js, Deno, Bun, browsers, and edge runtimes.
- **Per-category verbosity control**: turn one subtree like `["app", "db"]` up to `debug` while siblings stay at `info`.
- **Testing your logging itself**: use LogTape's recorder and lint rules.

If you are building an application and want one queryable wide event per request with structured errors, redaction, and a drain pipeline built in, evlog is the better fit.
