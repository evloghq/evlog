Do you publish a library or operate an application? Start with who should own the logging configuration. LogTape lets a library record through categories while the application that consumes it selects the output, a contract its [library guide](https://logtape.org/manual/library) describes. evlog supplies event accumulation and integrations for an application's request lifecycle.

LogTape also works in applications. What you decide is whether you need its category and configuration model, evlog's accumulated events, or one of each for library code and application code.

| Concern | evlog | LogTape |
| --- | --- | --- |
| Event construction | `set()` accumulates fields until `emit()` | Structured records with message templates and properties |
| Organization | A logger per operation. `fork()` exists only on request loggers from integrations that attach it | Hierarchical categories. Sinks inherit from parent categories, and `lowestLevel` does not |
| Explicit context | Fields on the operation logger | `logger.with()` attaches reusable properties |
| Implicit access | `useLogger()` in integrations backed by `AsyncLocalStorage`. On Nitro and Nuxt, `useLogger(event)` reads `event.context.log`. On Cloudflare Workers it needs the `nodejs_compat` or `nodejs_als` flag | `withContext()` when context-local storage is configured |
| Levels | `trace`, `debug`, `info`, `warn`, `error`, `fatal` | `trace`, `debug`, `info`, `warning`, `error`, `fatal` |
| Testing | A memory drain that captures events for you to inspect | Dedicated capture and assertion packages |

LogTape's [context documentation](https://logtape.org/manual/contexts) separates explicit and implicit contexts. Implicit context needs a compatible runtime and a configured `contextLocalStorage`, such as Node's `AsyncLocalStorage`, so check runtime support before you assume it works in a browser. It is not the same feature as `log.fork()`, which exists only on request loggers from integrations that attach it, and not on the `createLogger()` logger used below.

## One completed checkout

Each file emits one business record with an explicit outcome. The checkout is simulated, so neither needs a payment provider. Run either with Node.js 24, and pass `decline` to exercise the error path.

LogTape records the final outcome through a category the application configures:

```typescript [checkout-logtape.ts]
import { configure, getConsoleSink, getLogger } from '@logtape/logtape'

await configure({
  sinks: { console: getConsoleSink() },
  loggers: [
    { category: 'checkout', lowestLevel: 'info', sinks: ['console'] },
    { category: ['logtape', 'meta'], lowestLevel: 'warning', sinks: ['console'] },
  ],
})

const logger = getLogger('checkout').with({ orderId: 'order-123', amount: 2999 })
try {
  if (process.argv.includes('decline')) throw new Error('Payment declined')
  logger.info('Checkout {outcome}', { outcome: 'paid' })
} catch (error) {
  logger.error('Checkout {outcome}: {error}', { outcome: 'declined', error })
  process.exitCode = 1
}
```

evlog accumulates the result and emits in `finally`:

```typescript [checkout-evlog.ts]
import { createLogger, initLogger } from 'evlog'

initLogger({ env: { service: 'checkout' }, pretty: false })
const log = createLogger({ orderId: 'order-123', amount: 2999 })
try {
  if (process.argv.includes('decline')) throw new Error('Payment declined')
  log.set({ outcome: 'paid' })
} catch (error) {
  log.error(error instanceof Error ? error : new Error(String(error)))
  log.set({ outcome: 'declined' })
  process.exitCode = 1
} finally {
  log.emit()
}
```

The two files compare who owns context and emission. They do not compare output formats or speed: the LogTape file configures `getConsoleSink()`, and the evlog file sets `pretty: false`.

## Plan the migration around the features you use

Keep LogTape when consumer-owned configuration, categories or its testing tools are central to your design. Consider evlog when its [wide events](/events), structured errors and framework integrations reduce code in your application. What to plan for:

| LogTape feature | In evlog |
| --- | --- |
| Verbosity per category | No direct equivalent in the operation model. Decide how to preserve that control before you map categories to context fields |
| `trace` and `fatal` | Both exist. `trace` is dropped unless you set `sampling.rates.trace` |
| Redaction, a separate package | Configured [redaction](/events/redaction) applied before output |
| Testing packages | The [memory drain](/drains/memory): `createMemoryDrain()`, `readMemoryLogs()` and `clearMemoryLogs()` from `evlog/memory`. It supplies events for your assertions and has no assertion DSL. Compare with the [LogTape testing guide](https://logtape.org/manual/testing) |
| A custom sink | A drain behind the [drain pipeline](/drains/pipeline), with options you set for your destination and do not carry over from the sink |

The pipeline sends events in batches, flushes a partial batch on a timer, and retries each failed batch up to `retry.maxAttempts` total attempts, the first one included. When the buffer is full, it drops the oldest event.

For a Node.js logger with serializers and worker transports, see [evlog vs Pino](/compare/pino). [Compare](/compare) covers the other loggers, and [simple logging](/events/simple-logging) introduces evlog's per-message API.

## Check the bundle you will ship

Published measurements from different projects use different workloads, versions and imports. LogTape's [comparison table](https://logtape.org/comparison) names historical versions for its figures, so it does not establish the size or throughput of your current bundle next to evlog. [Performance](/reference/performance) explains what evlog's benchmarks cover. Measure the entry points and output settings you intend to deploy before choosing on size or speed.
