You already export traces to an OpenTelemetry Collector and want application logs beside them. evlog builds those log events and sends them through OTLP. Keep the tracing instrumentation: evlog does not create spans or metrics.

```text [Data flow]
Application fields -> evlog event -> OTLP HTTP /v1/logs -> Collector -> backend
Active OTel span  -> traceId + spanId on the event
OTel SDK         -> spans and metrics                -> Collector -> backend
```

Two paths reach the Collector. The evlog event carries your application fields and the active span's IDs. The OTel SDK exports spans and metrics on its own. [OpenTelemetry's documentation](https://opentelemetry.io/docs/) describes the SDK and Collector roles: the SDK instruments operations, the Collector receives and processes telemetry, and a backend stores it. Semantic conventions standardize shared attributes, and custom application attributes remain valid. evlog can also keep the same events in your own files or database through its [file system](/drains/fs) and [NuxtHub](/drains/nuxthub) drains.

## Attach the active span to every request event

`createOtelPlugin()` from `evlog/otel` reads the span OpenTelemetry has active when a request starts, and sets `traceId` and `spanId` on that request's wide event. The [OTLP drain](/drains/otlp) sends them as the log record's `trace_id` and `span_id`. A request without an active span still logs, without the two fields, and a `traceId` or `spanId` you set yourself is kept. Because the plugin reads the span when the request starts and not when the event is emitted, a streamed response that finishes after the span ended keeps its IDs.

The plugin needs `@opentelemetry/api` 1.9 or later, which your OpenTelemetry SDK already installed: SDK 3 uses 1.10, SDK 2 uses 1.9. evlog adds no other dependency, and an app that does not import `evlog/otel` never loads `@opentelemetry/api`.

Start the SDK before the app loads. With SDK 3, which needs Node.js 22.15 or later:

```bash [Terminal]
npm install evlog @opentelemetry/api @opentelemetry/sdk-node @opentelemetry/instrumentation-http
```

```javascript [instrumentation.mjs]
import { HttpInstrumentation } from '@opentelemetry/instrumentation-http'
import { startNodeSdk } from '@opentelemetry/sdk-node'

startNodeSdk({ instrumentations: [new HttpInstrumentation()] })
```

`startNodeSdk()` replaces the deprecated `startNodeSDK()`, and `@opentelemetry/sdk-node` still marks it experimental. On SDK 2, start `new NodeSDK({ instrumentations })` the same way.

Load that file before the app. An ES module app also needs OpenTelemetry's [loader hook](https://github.com/open-telemetry/opentelemetry-js/blob/main/doc/esm-support.md): without it `node:http` is never instrumented, no span is active, and the event has no IDs.

```bash [Terminal]
node --experimental-loader=@opentelemetry/instrumentation/hook.mjs --import ./instrumentation.mjs app.mjs
```

Then add the plugin to the integration:

```javascript [app.mjs]
import { Hono } from 'hono'
import { evlog } from 'evlog/hono'
import { createOtelPlugin } from 'evlog/otel'
import { createOTLPDrain } from 'evlog/otlp'

const app = new Hono()
app.use(evlog({ drain: createOTLPDrain(), plugins: [createOtelPlugin()] }))
```

Every integration built on evlog's middleware takes the same `plugins` option: Hono, Express, Fastify, Elysia, NestJS, Next.js, SvelteKit, React Router, oRPC and Cloudflare Workers. `initLogger({ plugins: [createOtelPlugin()] })` registers it once for all of them. On Nuxt, Nitro and TanStack Start, list it in `evlog.config.ts`, then start the built server with the same flags: `node --import ./instrumentation.mjs .output/server/index.mjs`, with the loader hook in front.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createOtelPlugin } from 'evlog/otel'

export default defineEvlog({ plugins: [createOtelPlugin()] })
```

## Attach the span outside a request

In a job or a script, read the span yourself. This example assumes a Node.js application whose OpenTelemetry SDK and context manager are already initialized, and the function must run inside an active span. Follow the [JavaScript instrumentation guide](https://opentelemetry.io/docs/languages/js/instrumentation/) if tracing is not configured yet.

```bash [Terminal]
npm install evlog @opentelemetry/api
```

```typescript [checkout-log.ts]
import { isSpanContextValid, trace } from '@opentelemetry/api'
import { createLogger, initLogger } from 'evlog'
import { createOTLPDrain } from 'evlog/otlp'

initLogger({ env: { service: 'checkout' }, pretty: false })
const drain = createOTLPDrain()

export async function recordCheckout(orderId: string, outcome: 'paid' | 'declined') {
  const log = createLogger({ orderId, outcome })
  const spanContext = trace.getActiveSpan()?.spanContext()
  if (spanContext && isSpanContextValid(spanContext)) {
    log.set({ traceId: spanContext.traceId, spanId: spanContext.spanId })
  }
  if (outcome === 'declined') log.error(new Error('Payment declined'))
  const event = log.emit()
  if (event) await drain({ event })
}
```

The function writes the completed event as local JSON and awaits its export. How a failure reaches you depends on the call:

| Call | On a failed export |
| --- | --- |
| `drain({ event })` | Retries transient failures twice, then logs the failure with the drain name. It does not throw, so the request path never breaks |
| `drain.raw({ event })` | Makes one attempt and rejects, so the caller observes the failure. Set `retries` on `createOTLPDrain()` to keep retries |

Do not also register this drain globally, which would export the event twice.

Set the OTLP HTTP base endpoint in the application's environment. If it is unset, the drain logs a missing-endpoint error and skips delivery. A file named `.env` does not configure a Node.js process on its own: load it through your application or Node's `--env-file` option.

```bash [.env]
OTLP_ENDPOINT=http://localhost:4318
```

For a local Collector, enable a logs pipeline. This configuration prints received records through the debug exporter:

```yaml [otel-collector.yaml]
receivers:
  otlp:
    protocols:
      http:
        endpoint: 127.0.0.1:4318
exporters:
  debug:
    verbosity: detailed
service:
  pipelines:
    logs:
      receivers: [otlp]
      exporters: [debug]
```

Run the Collector with this configuration and call `recordCheckout('order-123', 'paid')` inside an instrumented operation. The loopback address works for processes on the same host. A Collector in a separate container needs a reachable receiver address and a port mapping.

## Verify correlation before shipping

Find the record by `orderId`. Its resource should contain `service.name: checkout`, and its `traceId` and `spanId` should match the active span of the same operation. Without a valid active span the event still exports, without those identifiers.

The drain maps level and timestamp to the OTLP severity and time fields. Nested application fields become dotted attributes, and the body is a one-line summary. The drain also adds OpenTelemetry attribute names such as `http.request.method` and `gen_ai.usage.input_tokens` next to the evlog ones.

The TraceContext [enricher](/events/enrichers) reads an incoming `traceparent` and records its span identifier as `parentSpanId`, because that span belongs to the caller. It never sets `spanId`. Use the active SDK context, as above, to link the event to the server span.

## Sampling and delivery

Event sampling in evlog and [trace sampling in OpenTelemetry](https://opentelemetry.io/docs/concepts/sampling/) work on different signals. evlog keeps a percentage of each log level with `sampling.rates`, and force-keeps requests by status, duration or path with `sampling.keep`, both covered in [sampling](/events/sampling). A log you kept can reference a trace your tracing policy discarded. Coordinate the two policies before you rely on navigating from every error log to a stored trace.

The example above waits for the network request. In a production handler, configure the [drain pipeline](/drains/pipeline) and your framework's background delivery, starting from your [integration](/integrations). On Nitro, register `createOTLPDrain()` on the `evlog:drain` hook. The drain sends OTLP logs over HTTP and does not reach a gRPC-only endpoint. Serialization, batching, retries and export add costs that the event-construction microbenchmarks on [Performance](/reference/performance) do not measure.

For a choice between logging libraries, see [Compare](/compare).
