You already run a logger, and it works. Choose around the code and the delivery pipeline you want to maintain: evlog combines individual structured logs with accumulated request events, structured errors, plugins and drains, and the other libraries have configuration and extension models that may already fit your application.

| Compared with | Its model | What evlog does differently | Check before you migrate |
| --- | --- | --- | --- |
| [Pino](/compare/pino) | A JSON line per call, with child bindings, per-key serializers, path redaction and transports that can run in a worker thread | Accumulates fields over the request and emits one event at the end, including when the handler throws | Child bindings, serializers, custom levels, worker transports, existing HTTP logging |
| [Winston](/compare/winston) | A message with metadata per call, shaped by composable formats and sent to one or more transports, each with its own level | Makes the operation the unit: fields accumulate on one logger and the message is one of them | Format composition, per-transport levels, custom transports, exception handling |
| [Consola](/compare/consola) | Console output through reporters for Node.js, browsers and CLIs, with prompts and console wrapping | Builds request events and delivers them to a backend through drains | Reporters, terminal interaction, output formatting, request context |
| [LogTape](/compare/logtape) | Hierarchical categories: a library logs, and the application that consumes it configures the output | Gives the application a logger per operation and integrations for its request lifecycle | Consumer-owned configuration, categories, explicit and implicit context, testing |
| [LogLayer](/compare/loglayer) | One fluent API in front of a logging library or service, with wide events through a mixin | Is the logger itself, and its integrations emit the wide event when the request ends | Transports to the logger you keep, groups, the wide-events mixin and the middleware it needs |
| [OpenTelemetry](/compare/opentelemetry) | Traces, metrics and logs, with an SDK, a Collector and the OTLP protocol | Works with it: evlog builds log events and sends them over OTLP HTTP. It creates no spans and no metrics | OTLP logs, active span correlation, separate sampling policies |

Each of these libraries can also receive one completed object and log it once. The difference is which accumulation and lifecycle code the library supplies. [Events](/events) explains evlog's: application code calls `set()` as work progresses, and the event is emitted when the work ends.

## Pino vs Winston

Both write a record per call, and both produce JSON. They differ in how the record is shaped and where it goes.

| | [Pino](https://github.com/pinojs/pino/blob/main/docs/api.md) | [Winston](https://github.com/winstonjs/winston) |
| --- | --- | --- |
| Levels | Numeric, `trace` 10 to `fatal` 60, written as a number unless a formatter changes it | npm levels by default, custom level sets supported |
| Shaping output | Serializers per key, such as `pino.stdSerializers.err` | Formats composed through `logform`: `combine`, `timestamp`, `json`, `printf` |
| Context | `logger.child(bindings)`, plus `setBindings()` later | `logger.child()` |
| Destinations | [Transports](https://github.com/pinojs/pino/blob/main/docs/transports.md) run in a worker thread, so the write leaves the main thread | Several transports on one logger, each with its own level |
| Built in | Redaction paths. Request logs come from the separate [`pino-http`](https://github.com/pinojs/pino-http) package | Profiling, exception and rejection handlers |

Low overhead is pino's stated design goal, and its [benchmarks](https://github.com/pinojs/pino/blob/main/docs/benchmarks.md) include Winston and name their setup. Rerun them on your own versions and payload before you rely on the gap. Pino suits a service that wants lean JSON lines and offloaded writes. Winston suits a codebase that already composes formats and fans out to several transports with different levels. evlog takes a third route: it accumulates fields over a request and emits one event at the end.

## What evlog commits to

Check these against what your current logger does for you.

| Concern | evlog contract |
| --- | --- |
| Severity | Six levels: `trace`, `debug`, `info`, `warn`, `error`, `fatal`. `trace` is dropped unless `sampling.rates.trace` is set |
| Filtering | Global `minLevel` for individual logs, [sampling](/events/sampling) for wide events |
| Extensibility | Plugins, enrichers and drains. Pino serializers and Winston formats need an explicit port |
| Redaction | Configured paths and recognized patterns, on by default in production once `initLogger()` has run. It does not guarantee that all personal data is found |
| Delivery | You choose a [drain](/drains) and its pipeline configuration, then handle pending delivery in the runtime you deploy |
| Testing | You capture emitted events with the [memory drain](/drains/memory) and assert on the fields you require |

evlog's global `log` API handles individual messages, described in [simple logging](/events/simple-logging). Its signatures do not make evlog a drop-in replacement for Pino, Winston or Consola, so review call sites and output envelopes.

## Before you migrate

Keeping your logger is reasonable when its integrations already meet your requirements. If you migrate, first preserve the fields your dashboards and alerts use, then verify success, failure and shutdown behavior on one handler before you change the rest.

[Performance](/reference/performance) compares evlog, Pino, LogLayer, LogTape and Winston writing the same JSON line, with the reason behind each row where evlog is slower. Those are per-call measurements without delivery to a backend, so measure your own payload and destination too.
