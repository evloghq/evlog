Your Pino setup already ships JSON logs. What is left to decide is how your application assembles request context. evlog supplies an accumulator and a lifecycle for it. Pino supplies JSON logging, bindings, serializers and transports, which you can keep if they already fit.

| Concern | evlog | Pino |
| --- | --- | --- |
| Request context | `createLogger()` and typed `set()` calls accumulate fields until `emit()` | `child()` attaches bindings to records. The application can accumulate an object and log it once |
| Adding bindings | `set()` merges fields into the pending event | `setBindings()` adds bindings after creation. It does not overwrite existing keys and can introduce duplicate keys |
| Error fields | `createError()` carries `why`, `fix` and `link` | Error serializers, including `pino.stdSerializers.err`, shape error records |
| Extensibility | Plugins and enrichers hook into the event lifecycle | Per-key serializers, formatters and transports |
| Levels | Six severities (`trace` to `fatal`), global `minLevel`, sampling for wide events | Built-in and custom levels, mutable logger level |
| Redaction | Configured paths and built-in value patterns, on by default in production | Configured paths, censored or removed |
| Request logging | Framework integrations emit one event per request | The separate [`pino-http`](https://github.com/pinojs/pino-http) package logs each request |
| Delivery | Drains, with configurable batching and retry | Destinations and transports, including worker-thread transports |

Pino documents these contracts in its [API reference](https://github.com/pinojs/pino/blob/main/docs/api.md). A worker transport moves transport processing and delivery to a worker, and the logger still serializes the record to JSON on the calling thread ([Pino transports](https://github.com/pinojs/pino/blob/main/docs/transports.md)).

## Compare one completed operation

Both libraries can emit one structured record for an operation. These two files simulate the same checkout decision without calling a payment provider. Run either with Node.js 24, and pass `decline` to exercise the failure path.

With Pino, the application owns the accumulated context and emits it in `finally`:

```typescript [checkout-pino.ts]
import pino from 'pino'

const logger = pino()
const context = { orderId: 'order-123', amount: 2999, outcome: 'pending' }
let failure: Error | undefined

try {
  if (process.argv.includes('decline')) throw new Error('Payment declined')
  context.outcome = 'paid'
} catch (error) {
  failure = error instanceof Error ? error : new Error(String(error))
  context.outcome = 'declined'
  process.exitCode = 1
} finally {
  if (failure) logger.error({ ...context, err: failure }, 'checkout completed')
  else logger.info(context, 'checkout completed')
}
```

With evlog, the logger owns the accumulator and selects error severity after `error()`:

```typescript [checkout-evlog.ts]
import { createLogger, initLogger } from 'evlog'

initLogger({ env: { service: 'checkout' }, pretty: false })
const log = createLogger({ orderId: 'order-123', amount: 2999, outcome: 'pending' })

try {
  if (process.argv.includes('decline')) throw new Error('Payment declined')
  log.set({ outcome: 'paid' })
} catch (error) {
  log.error(error instanceof Error ? error : new Error(String(error)))
  log.set({ outcome: 'declined' })
  process.exitCode = 1
} finally {
  log.emit()
}
```

Each version emits one record on either path. The envelopes differ: Pino writes a numeric level and uses its error serializer, and evlog adds its event metadata and the duration. evlog's [wide events](/events) pay off when several layers contribute fields and a framework integration owns the request lifecycle.

## Type the request context

Pino 10 ships first-party types in the `pino` package, so you do not need `@types/pino`. `import pino from 'pino'` is typed, and custom level names become methods on `Logger`. Pino checks some printf argument types and does not require a value for every placeholder. See Pino's [TypeScript section](https://github.com/pinojs/pino/blob/main/docs/api.md#typescript).

Those types cover each log call, not the request-shaped object you build yourself. `child()` and `setBindings()` take `Bindings`, which is `Record<string, any>` in [pino.d.ts](https://github.com/pinojs/pino/blob/main/pino.d.ts), so a child logger does not know that this request has `orderId` and `amount`. To check the accumulator in `checkout-pino.ts`, type the `context` object yourself.

To constrain the fields of every `logger.info({ ... })` call, augment Pino's `LogFnFields` interface, as documented under [module augmentation](https://github.com/pinojs/pino/blob/main/docs/api.md#logfnfields-interface):

```typescript [pino-log-fn-fields.ts]
import 'pino'

declare module 'pino' {
  interface LogFnFields {
    orderId?: string
    amount?: number
  }
}
```

The augmentation types the merging object on each line and leaves `child()` bindings untyped. Required fields on `LogFnFields` also apply when you pass an `Error`, a caveat Pino documents. TypeScript applies it only when this file is part of the same program as the log calls.

evlog types later `set()` calls against a fields interface you pass as a generic:

```typescript [checkout-fields.ts]
interface CheckoutFields {
  orderId: string
  amount: number
  outcome: string
}
```

`createLogger<CheckoutFields>()` does not type-check the object you pass into `createLogger`. The `set()` calls that follow reject unknown keys. Framework request loggers take the same generic: `useLogger<CheckoutFields>(event)` on Nuxt and Nitro, and `useLogger<CheckoutFields>()` where `AsyncLocalStorage` holds the logger, such as Next.js. On Nuxt, import it explicitly with `import { useLogger } from 'evlog'`, because the auto-import drops excess-property checks. [Typed fields](/events/typed-fields) has the details.

This section matches the first-party types of Pino 10.4.0.

## Migrate one handler first

List the fields your dashboards query, your custom levels, your serializers and your transport configuration, and map each one before you switch output. Pino serializers do not transfer unchanged into evlog plugins, and a custom transport may need a new drain.

Keep the Pino path for unrelated handlers while you validate one evlog [integration](/integrations). Do not emit the same request through both paths unless your queries and your ingestion cost account for the duplicate. Test successful requests, thrown errors, shutdown and redaction with the same assertions on the required fields.

## Compare speed on the same JSON line

[Performance](/reference/performance) measures evlog and Pino writing the same fields as one JSON line to the same stream. On Node.js 24, a request record costs 1.22 µs with evlog and 1.02 µs with Pino, and redacting two paths costs 3.15 µs and 1.40 µs. That page lists every row, the Node.js 26 numbers, and what evlog does on each row that Pino does not. Measure your own payload and destination before choosing on speed.

Keep Pino when its serializers, ecosystem integrations or worker transports already solve your problem. Choose evlog when its context accumulator, structured errors and framework lifecycle remove application code you would otherwise maintain. [Compare](/compare) covers the other loggers.
