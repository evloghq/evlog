Your Winston configuration may encode years of operational decisions: which fields reach a backend, which errors trigger alerts, and which transports receive each severity. Start a migration by preserving those decisions.

| | Winston | evlog |
| --- | --- | --- |
| Core model | Each call writes an `info` object through a format chain to one or more transports | Individual structured logs, plus an operation logger that accumulates fields and emits one event |
| Output shaping | Composable formats from `logform` (`combine`, `json`, `printf`, custom formats) | Event fields set by the application, plugins and enrichers, then drain serialization |
| Destinations | Core Console, File and Http transports, plus community transports | Drains such as Axiom, OTLP, Sentry, PostHog, Datadog and Better Stack |
| Levels | npm levels by default (`error` to `silly`), or custom levels | Six fixed severities, with sampling for wide events |
| Process failures | `exceptionHandlers` and `rejectionHandlers` | Request errors become structured error events. Process handlers stay your choice |
| Extras | Child loggers, profiling, querying and streaming logs from some transports | Structured errors with `why`, `fix` and `link` |

Sources: the [Winston README](https://github.com/winstonjs/winston#readme) sections on formats, logging levels, transports, exceptions, rejections and profiling. JSON output is `format.json()`. All of these are reasons to keep Winston when the pipeline already works.

## Map what the configuration already does

| Existing requirement | What to check in evlog |
| --- | --- |
| Custom levels | Map them to the six severities, and update the queries and alerts that depend on the original values |
| Format chain | Decide which transformations become context fields, plugin hooks or drain serialization |
| Custom transport | Find a matching [drain](/drains), or port the protocol and the delivery behavior |
| Per-transport level | Preserve destination-specific filtering explicitly in the delivery configuration |
| Exception and rejection handlers | Keep process-level failure handling separate from one request's error event |

## Decide who assembles the final event

Winston can log a completed object once, and the application decides how to collect it. evlog's `createLogger()` is that accumulator: `set()` adds context, `emit()` produces the final event, and a framework integration manages the lifecycle of the operation.

[Events](/events) helps you decide whether this model removes code from your handlers. It does not preserve a Winston output schema for you, and turning several records into one may require new dashboard queries.

## Migrate with observable checkpoints

evlog is not a drop-in replacement: call signatures, levels and the output envelope differ. Choose one operation and write down the output fields its consumers require. Configure a drain, then exercise success and failure against a test destination. Confirm that redaction, severity mapping, retries and process shutdown meet the same requirements as the existing path.

You can keep Winston and add evlog. One split is to keep Winston for the transports you have and adopt evlog request events on new routes, as long as the two do not forward the same records to the same backend.

Keep Winston when format composition or custom transports already solve the problem. Consider evlog when accumulated context, structured errors and its integration lifecycle reduce application code. A library's age does not establish which is better for your workload, and neither does a benchmark where the two write different output. [Performance](/reference/performance) measures both writing the same JSON line. Compare them on your own workload with equivalent output.
