A Nuxt application can need both readable terminal messages and request events that reach a logging backend. Consola and evlog answer those two needs with different APIs, and the two can run side by side. Start with where the output goes and who maintains the delivery code.

| | Consola | evlog |
| --- | --- | --- |
| Primary job | Readable console output for Node.js, browsers and CLIs, and the logger behind Nuxt Kit's `useLogger` | Structured logs and request events delivered to a logging backend |
| Output | Fancy reporter by default, basic reporter in CI and tests, browser reporter. The `consola/basic` and `consola/browser` builds are smaller | Pretty output in development, JSON events in production |
| Extension point | Reporters implementing `log(logObject)` | Plugins, enrichers and drains |
| Context | `withTag()` and `withDefaults()` scope records | `set()` accumulates fields on an operation logger until `emit()` |
| CLI helpers | `prompt()` (powered by clack), `wrapConsole()` and `wrapStd()`, pause and resume, throttling of repeated logs | None. Keep Consola for terminal interaction |
| Levels | Numeric levels (default `3`), set with the `level` option or `CONSOLA_LEVEL` | Six fixed severities, with sampling for wide events |

Sources: the [Consola README](https://github.com/unjs/consola#readme) and the [Nuxt Kit logging docs](https://nuxt.com/docs/api/kit/logging).

## Keep the reporter behavior you rely on

A Consola reporter receives log objects and controls rendering or delivery. Consola ships no JSON reporter, and its [custom reporters section](https://github.com/unjs/consola#custom-reporters) shows how to write one that serializes JSON and forwards records. Delivery, batching and retries then stay in your code. Paused logs are queued, and repeated messages can be throttled.

Those behaviors suit a CLI and a production application alike. Replacing them takes more than changing an import.

## Compare the application work

| Need | evlog approach | Migration question |
| --- | --- | --- |
| Context across a request | `set()` accumulates fields on an operation logger | Which layers add fields, and who finishes the event? |
| Output to a backend | Drains and pipeline configuration | Does a [drain](/drains) preserve the protocol your reporter implements today? |
| Individual messages | The global structured logging API | Which call signatures and fields need changing? |
| Terminal interaction | Logging output only | Should prompts and other CLI interaction remain with Consola? |

Consola tags scope records, and an evlog operation logger accumulates context until emission. The two contracts differ, so map a tag to an application field only if that preserves how you query or display it.

## Adopt request events where they help

Nuxt Kit's `useLogger` is a Consola instance meant for module and build output. Add the [evlog Nuxt module](/integrations/nuxt) when you want one structured event per server request delivered to a backend.

In an application, keep terminal interaction separate from request instrumentation. Choose the evlog [integration](/integrations) for your handlers and call `useLogger()` in the layers that contribute fields. Do not also capture those emitted records through a custom reporter that forwards to the same destination, unless you intend the duplicate ingestion.

For a CLI, [Standalone](/integrations/standalone) covers explicit initialization and pending delivery. For handlers, [Events](/events) explains when to accumulate and when to emit.

Keep Consola when its reporters and terminal workflow meet your needs. Add or adopt evlog when its request context, structured errors and drain pipeline remove code you would otherwise maintain. [Compare](/compare) covers the other loggers.
