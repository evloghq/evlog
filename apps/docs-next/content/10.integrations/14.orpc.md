Two pieces: a middleware that puts the logger on the procedure context, and a wrapper around the handler that opens and emits one event per request.

```typescript [server/orpc.ts]
import { os } from '@orpc/server'
import { RPCHandler } from '@orpc/server/fetch'
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { evlog, withEvlog, type EvlogOrpcContext } from 'evlog/orpc'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

export const base = os.$context<EvlogOrpcContext>().use(evlog())

export const handler = withEvlog(new RPCHandler(router), toMiddlewareOptions(config))
```

You call the wrapped handler as you call the original:

```typescript [server/orpc.ts]
export default async function fetch(request: Request) {
  const { matched, response } = await handler.handle(request, { prefix: '/rpc' })
  return matched ? response : new Response('Not Found', { status: 404 })
}
```

| Piece | What it does | Without it |
| --- | --- | --- |
| `withEvlog(handler, options)` | Creates the request logger, puts it on the context as `log`, and emits when the response is ready | No logger and no event: `context.log` is `undefined` |
| `evlog()` | Sets `operation` to the procedure path, records what a procedure throws, and turns an evlog error into an `ORPCError` | The event has no `operation`, and a thrown `createError()` reaches the client as oRPC's `INTERNAL_SERVER_ERROR` |

`withEvlog()` wraps a handler of oRPC's fetch adapter, `RPCHandler` or `OpenAPIHandler` from `@orpc/server/fetch`, or any object with the same `handle(request, options)`. It returns a proxy that only intercepts `handle`, so the handler's other members are untouched. `evlog()` takes no argument: every option goes to `withEvlog()`.

[`evlog init`](/cli/init) writes `evlog.config.ts` and these lines for you.

## In a procedure

```typescript [server/procedures/users.ts]
export const getUser = base
  .input(z.object({ id: z.string() }))
  .handler(async ({ input, context }) => {
    const user = await db.findUser(input.id)
    context.log.set({ user: { id: input.id, plan: user.plan } })

    return user
  })
```

In a service the procedure calls, `useLogger()` from `evlog/orpc` returns the same logger.

```typescript [server/services/user.ts]
import { useLogger } from 'evlog/orpc'

export async function findUser(id: string) {
  const log = useLogger()
  log.set({ user: { id } })

  const user = await db.findUser(id)
  log.set({ user: { name: user.name, plan: user.plan } })

  return user
}
```

`EvlogOrpcContext` types `context.log` in every procedure built from `base`, with `set`, `fork` and `audit`. `useLogger()` reads the logger from `AsyncLocalStorage`. It throws outside a handler wrapped with `withEvlog()` and on a route the wrapper does not log. `useLogger<MyFields>()` types the fields you set. See [Typed fields](/events/typed-fields).

The event names the procedure in `operation`: `getUser` here, and `users.profile.get` for a procedure in a nested router.

## Background work

The request's event is sealed once it is emitted, so work that outlives the response needs its own. `log.fork(label, fn)` runs `fn` under a forked logger, and `useLogger()` returns that logger inside it:

```typescript [server/services/user.ts]
import { useLogger } from 'evlog/orpc'

export async function findUser(id: string) {
  const log = useLogger()

  log.fork!('background', async () => {
    const child = useLogger()
    child.set({ step: 'complete' })
  })

  const user = await db.findUser(id)
  log.set({ user: { name: user.name, plan: user.plan } })

  return user
}
```

The logger `useLogger()` returns types `fork` as optional, hence the `!`. On `context.log` it is required, so `context.log.fork('background', fn)` needs none.

The fork emits a second event when `fn` settles, with `operation: 'background'` and `_parentRequestId` set to the request's `requestId`. A `set()` on the request logger after its event is emitted is dropped with an `[evlog]` warning. [After the event is emitted](/events#after-the-event-is-emitted) covers both, and when to await the fork.

## Errors

Throw [`createError()`](/errors) or a [catalog](/errors/catalogs) error from a procedure. The `evlog()` middleware records it on the event and rethrows it as an `ORPCError` with the same `code`, `status` and `message`:

```typescript [server/orpc.ts]
import { createError } from 'evlog'

const checkout = base
  .handler(({ context }) => {
    context.log.set({ cart: { items: 3, total: 9999 } })

    throw createError({
      message: 'Payment failed',
      code: 'PAYMENT_DECLINED',
      status: 402,
      why: 'Card declined by issuer',
      fix: 'Try a different payment method',
      link: 'https://docs.example.com/payments/declined',
    })
  })
```

The client receives oRPC's error envelope, with `why`, `fix` and `link` under `data` and not at the root of the body:

```json [HTTP 402]
{
  "defined": false,
  "code": "PAYMENT_DECLINED",
  "status": 402,
  "message": "Payment failed",
  "data": {
    "why": "Card declined by issuer",
    "fix": "Try a different payment method",
    "link": "https://docs.example.com/payments/declined"
  }
}
```

Three details:

- An error created without a `code` is sent with the code `EVLOG_ERROR`.
- An error that is not an evlog error is recorded on the event and rethrown as it is. oRPC answers it its own way.
- The event's `status` is the status of the response oRPC built, `402` here. A request that matches no procedure is recorded as `404`.

Clients read the envelope as a typed union with `safe()` from `@orpc/client`.

## Streaming responses

When a procedure streams, the wrapper returns the response and emits when the body closes, fails or is cancelled, so fields set while streaming land on the event. A response counts as streamed when its `content-type` is `text/event-stream` or `application/x-ndjson`, when it has the `x-vercel-ai-ui-message-stream` header, or when `transfer-encoding` is `chunked`.

## Options

`withEvlog()` takes the request options of `evlog.config.ts` as its second argument, which `toMiddlewareOptions(config)` passes. [Configuration](/reference/configuration) lists the logger options that go to `initLogger()`.

| Option | Default | What it does |
| --- | --- | --- |
| `include` | Every route | Globs of the routes to log. `*` stops at a `/`, `**` crosses it |
| `exclude` | None | Globs of the routes to skip. Wins over `include` |
| `routes` | None | A `service` name per route glob. The first glob that matches wins, so list the specific ones first |
| `drain` | The drain given to `initLogger()` | Receives every emitted event. See [Drains](/drains) |
| `enrich` | None | Adds fields after redaction, before the console output and the drain. See [Enrichers](/events/enrichers) |
| `keep` | None | Tail sampling: set `ctx.shouldKeep = true` to keep an event the rates would drop. See [Sampling](/events/sampling) |
| `redact` | The `initLogger()` setting | Redacts the event when `initLogger()` did not: `true` for the built-in patterns, or a config. See [Redaction](/events/redaction) |
| `plugins` | None | Merged with the plugins given to `initLogger()`. A plugin here replaces a global one of the same `name` |
| `waitUntil` | The Vercel Functions runtime, when there is one | Registers the drain with the runtime instead of awaiting it |

The globs match the HTTP path of the request, not the procedure name:

```typescript [server/orpc.ts]
const handler = withEvlog(new RPCHandler(router), {
  ...toMiddlewareOptions(config),
  include: ['/rpc/**'],
  exclude: ['/rpc/_internal/**', '/health'],
  routes: {
    '/rpc/auth/**': { service: 'auth-service' },
    '/rpc/payment/**': { service: 'payment-service' },
  },
})
```

A field you pass next to the config replaces that field. It is not merged with the file's. The event's `requestId` is the `x-request-id` header when the caller sends one, and a random UUID otherwise.

On a route the globs filter out, `context.log` is still there: it accepts every call and emits nothing, and no drain or enricher runs. `useLogger()` throws there.

## Shutdown and serverless

Without `waitUntil`, the wrapper awaits the drain before it returns the response, which is why a [pipeline](/drains/pipeline) matters: its `drain(ctx)` only buffers. A pipeline that holds events is flushed on `SIGTERM`, `SIGINT` and `beforeExit`. `process.exit()` skips that, so call `await drain.flush()` before it.

On Vercel Functions the wrapper finds the request's `waitUntil` in the runtime and keeps the instance alive until the drain is done. Everywhere else it has none unless you pass `waitUntil` in the options. [Serverless](/drains/pipeline#serverless) has the limits of a request-end flush.
