SvelteKit runs every request through `hooks.server.ts`. evlog provides both hooks, so the whole setup is that file and one type:

```typescript [src/hooks.server.ts]
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { createEvlogHooks } from 'evlog/sveltekit'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

export const { handle, handleError } = createEvlogHooks(toMiddlewareOptions(config))
```

```typescript [src/app.d.ts]
import type { ForkableLogger } from 'evlog'

declare global {
  namespace App {
    interface Locals {
      log: ForkableLogger
    }
  }
}

export {}
```

If you already export a `handle`, compose them with `sequence()` from `@sveltejs/kit/hooks`.

`toLoggerConfig` passes the file's logger options and `toMiddlewareOptions` its request options, so the sampling, drain, `enrich` and route filters of `evlog.config.ts` all apply. The hooks support SvelteKit 2 and 3. Export both: `handle` creates and emits the event, and `handleError` is what puts an error SvelteKit caught on it.

## In an endpoint

```typescript [src/routes/api/users/[id]/+server.ts]
import { json } from '@sveltejs/kit'

export async function GET({ locals, params }) {
  const user = await db.findUser(params.id)
  locals.log.set({ user: { id: params.id, plan: user.plan } })

  return json(user)
}
```

Load functions receive the same `locals`. In a module under `$lib/server`, `useLogger()` from `evlog/sveltekit` returns the logger of the current request.

## Under the endpoint

`useLogger()` reads the request from `AsyncLocalStorage`, so a service does not need `locals` passed down. It returns the same logger as `event.locals.log`:

```typescript [src/lib/services/user.ts]
import { useLogger } from 'evlog/sveltekit'

export async function findUser(id: string) {
  const log = useLogger()
  log.set({ user: { id } })

  const user = await db.findUser(id)
  log.set({ user: { name: user.name, plan: user.plan } })

  return user
}
```

Outside a request, `useLogger()` throws. It also throws on a route that `include` or `exclude` filters out, where `locals.log` is still there: it accepts every call and emits nothing. Code that can run on a filtered route reads `locals.log`.

## Background work

`locals.log.fork(label, fn)` gives work that outlives the response its own event. Inside `fn`, `useLogger()` returns the forked logger:

```typescript [src/routes/api/orders/+server.ts]
import { useLogger } from 'evlog/sveltekit'
import type { RequestHandler } from './$types'

export const POST: RequestHandler = async ({ locals }) => {
  locals.log.fork('process', async () => {
    const log = useLogger()
    log.set({ step: 'done' })
  })
  return new Response(JSON.stringify({ ok: true }))
}
```

The child event carries `operation: 'process'` and `_parentRequestId`. Where the request has a `waitUntil`, the fork is registered with it. [After the event is emitted](/events#after-the-event-is-emitted) explains why the request's own logger is sealed by then.

## Errors

Throw `createError()` with a `why` and a `fix`. The integration records it on the event and answers with the status you set:

```typescript [src/routes/api/checkout/+server.ts]
import { createError } from 'evlog'

throw createError({
  status: 402,
  message: 'Payment failed',
  why: 'Card declined by issuer',
  fix: 'Try a different payment method',
})
```

What the caller receives:

| Thrown | Response | Event `status` |
| --- | --- | --- |
| An `EvlogError` with a `status` | JSON with that status: `url`, `status`, `message`, `error: true`, and `why`, `fix` and `link` under `data`. A load function gets the same JSON | The error's status |
| An `EvlogError` without a `status` | SvelteKit's own `500` response | `500` |
| Another error | SvelteKit's own response | The response's status |

In all three the event has level `error` and the error under `error`. `handleError` also returns `message`, `status`, `why`, `fix` and `link` to SvelteKit as the page's `App.Error`.

## Streaming responses

When an endpoint returns a streamed `Response` (a `text/event-stream` or `application/x-ndjson` content type, chunked transfer encoding, or the AI SDK's stream header), the event is emitted when the body finishes or the client disconnects. [AI SDK](/integrations/ai-sdk) fields set during the stream land on it.

## Options

Put options in `evlog.config.ts`: [Configuration](/reference/configuration) lists them. `createEvlogHooks()` takes the request options:

| Option | What it does |
| --- | --- |
| `include`, `exclude` | Route globs to log or skip. `exclude` wins |
| `routes` | A service name per route glob, such as `'/api/auth/**': { service: 'auth-service' }` |
| `drain` | Where request events go. Without it, the drain given to `initLogger()` is used |
| `enrich` | Adds fields after the event is emitted, before the drain |
| `keep` | Custom tail sampling: set `ctx.shouldKeep = true` |
| `redact` | See [Redaction](/events/redaction) |
| `plugins` | See [Plugins](/reference/plugins), merged by name with the global ones |
| `waitUntil` | Keeps the runtime alive for the drain. Read from the platform when you leave it out |

An option you pass inline replaces the same option from the file. It is not merged:

```typescript [src/hooks.server.ts]
export const { handle, handleError } = createEvlogHooks({
  ...toMiddlewareOptions(config),
  include: ['/api/**'],
  exclude: ['/_internal/**', '/health'],
  keep: (ctx) => {
    if (ctx.duration && ctx.duration > 2000) ctx.shouldKeep = true
  },
})
```

The [`evlog/vite` plugin](/integrations/vite) is optional. It strips `log.debug()` from production builds and adds source locations, and it reads `evlog.config.ts` too. Keep the `initLogger()` call: it runs after the plugin's own start and replaces it.

## Deploy

A drain must outlive the response on a serverless runtime. `handle` finds the request's `waitUntil` itself:

| Adapter | Where `waitUntil` comes from |
| --- | --- |
| Cloudflare, Netlify | `event.platform.context` |
| Vercel | The Vercel Functions runtime |
| Node | None needed. A [pipeline](/drains/pipeline) is flushed on `SIGTERM` and `SIGINT` |

With a `waitUntil`, each request sends what a pipeline holds when it ends. [Serverless](/drains/pipeline#serverless) has the limits of that flush.
