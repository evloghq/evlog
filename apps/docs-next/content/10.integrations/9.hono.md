Hono does not load `evlog.config.ts` on its own, so the entry file passes it in two calls: one to start the logger, one for the middleware.

```typescript [src/index.ts]
import { serve } from '@hono/node-server'
import { Hono } from 'hono'
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { evlog, type EvlogVariables } from 'evlog/hono'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

const app = new Hono<EvlogVariables>()
app.use(evlog(toMiddlewareOptions(config)))

serve({ fetch: app.fetch, port: 3000 })
```

`EvlogVariables` types `c.get('log')` in every handler.

[`evlog init`](/cli/init) writes `evlog.config.ts` and these lines for you. If you build with Vite, the [`evlog/vite` plugin](/extend/vite) reads the same file but cannot carry the drain, so keep the `initLogger()` call.

## In a handler

::emits{step="handler"}
```typescript [src/routes/users.ts]
app.get('/users/:id', async (c) => {
  const log = c.get('log')
  const userId = c.req.param('id')

  const user = await db.findUser(userId)
  log.set({ user: { id: userId, plan: user.plan } })

  return c.json(user)
})
```
::

In a service the route calls, `useLogger()` from `evlog/hono` returns the same logger without passing `c` down.

```typescript [src/services/payment.ts]
import { useLogger } from 'evlog/hono'

export async function chargeCard(amount: number) {
  const log = useLogger()
  log.set({ payment: { amount } })
}
```

`useLogger()` reads the logger from `AsyncLocalStorage`, which has two consequences:

- On Cloudflare Workers it needs the `nodejs_compat` or `nodejs_als` compatibility flag. `c.get('log')` works without it.
- Outside a request, and on a route the middleware does not log, it throws. `c.get('log')` is always there: on a skipped route it accepts every call and emits nothing.

`useLogger<MyFields>()` types the fields you set. See [Typed fields](/events/typed-fields).

## Background work

The request's event is sealed once it is emitted, so work that outlives the response needs its own. `log.fork(label, fn)` runs `fn` under a forked logger, and `useLogger()` returns that logger inside it:

```typescript [src/index.ts]
app.post('/api/orders', (c) => {
  c.get('log').fork('send-receipt', async () => {
    await sendReceipt()
    useLogger().set({ email: { sent: true } })
  })
  return c.json({ ok: true })
})
```

The fork emits a second event when `fn` settles, with `operation: 'send-receipt'` and `_parentRequestId` set to the request's `requestId`. A `set()` on the request logger after its event is emitted is dropped with an `[evlog]` warning. [After the event is emitted](/events#after-the-event-is-emitted) covers both, and when to await the fork.

## When a handler throws

Hono hands a thrown error to `app.onError`. The middleware has already put it on the event, so the handler only turns it into a response with `parseError()`:

::emits{step="error"}
```typescript [src/index.ts]
import type { ContentfulStatusCode } from 'hono/utils/http-status'
import { createError, parseError } from 'evlog'

app.onError((error, c) => {
  const parsed = parseError(error)

  return c.json(
    {
      message: parsed.message,
      why: parsed.why,
      fix: parsed.fix,
      link: parsed.link,
    },
    parsed.status as ContentfulStatusCode,
  )
})

app.get('/users/:id', async (c) => {
  const log = c.get('log')
  const userId = c.req.param('id')

  const user = await db.findUser(userId)
  if (!user) {
    throw createError({
      status: 404,
      message: 'User not found',
      why: `No user has the id ${userId}`,
      fix: 'Check the id in the URL',
    })
  }
  log.set({ user: { id: userId, plan: user.plan } })

  return c.json(user)
})
```
::

`parseError()` types `status` as a `number` and `c.json()` wants a `ContentfulStatusCode`, hence the cast. Without `app.onError`, Hono answers every thrown error with a plain `500`, and the event's `status` is that `500`, not the one the error carried.

On Hono 5, `app.onError` is a middleware: it receives `(c, next)` and the error is on `c.error`. The handler becomes:

```typescript [src/index.ts]
app.onError((c) => {
  const parsed = parseError(c.error)

  return c.json(
    { message: parsed.message, why: parsed.why, fix: parsed.fix, link: parsed.link },
    parsed.status as ContentfulStatusCode,
  )
})
```

## Streaming responses

For a streamed body, the middleware returns the response and emits when the body closes, fails or is cancelled, so fields set while streaming land on the event and a stream failure becomes its `error`. A response counts as streamed when its `content-type` is `text/event-stream` or `application/x-ndjson`, when it has the `x-vercel-ai-ui-message-stream` header, or when `transfer-encoding` is `chunked`. Every other response emits before the middleware returns.

## Options

`evlog()` takes the request options of `evlog.config.ts`, which `toMiddlewareOptions(config)` passes. [Configuration](/reference/configuration) lists the logger options that go to `initLogger()`.

| Option | Default | What it does |
| --- | --- | --- |
| `include` | Every route | Globs of the routes to log. `*` stops at a `/`, `**` crosses it |
| `exclude` | None | Globs of the routes to skip. Wins over `include` |
| `routes` | None | A `service` name per route glob. The first glob that matches wins, so list the specific ones first |
| `drain` | The drain given to `initLogger()` | Receives every emitted event. See [Drains](/drains) |
| `enrich` | None | Adds fields after redaction, before the console output and the drain. See [Enrichers](/events/enrichers) |
| `keep` | None | Tail sampling: set `ctx.shouldKeep = true` to keep an event the rates would drop. See [Sampling](/events/sampling) |
| `redact` | The `initLogger()` setting | Redacts the event when `initLogger()` did not: `true` for the built-in patterns, or a config. See [Redaction](/events/redaction) |
| `plugins` | None | Merged with the plugins given to `initLogger()`. A plugin here replaces a global one of the same `name` |
| `waitUntil` | `c.executionCtx`, then the Vercel Functions runtime | Registers the drain with the runtime instead of awaiting it |

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'

export default defineEvlog({
  service: 'my-api',
  include: ['/api/**'],
  exclude: ['/_internal/**', '/health'],
  routes: {
    '/api/auth/**': { service: 'auth-service' },
    '/api/payment/**': { service: 'payment-service' },
  },
  keep: (ctx) => {
    if (ctx.duration && ctx.duration > 2000) ctx.shouldKeep = true
  },
})
```

The event's `requestId` is the `x-request-id` header when the caller sends one, and a random UUID otherwise.

## Override an option

A field you pass next to the config replaces that field: `evlog({ ...toMiddlewareOptions(config), exclude: ['/health'] })` uses your `exclude`, not the file's.

## On Workers and serverless

On Cloudflare Workers and Vercel Edge, the middleware takes `waitUntil` from `c.executionCtx` and registers the drain and every `log.fork()` with it, so they finish after the response. On Vercel Functions it finds the request's `waitUntil` in the runtime. On Node, Bun and Deno there is none: the middleware awaits the drain before the response leaves, which is why a [pipeline](/drains/pipeline) matters there. Its `drain(ctx)` only buffers.

A pipeline that holds events is flushed on `SIGTERM`, `SIGINT` and `beforeExit`. `process.exit()` skips that, so call `await drain.flush()` before it. On a serverless runtime the middleware also sends what the pipeline holds when the request ends: [Serverless](/drains/pipeline#serverless) has the conditions and the limits.

## Receive browser logs

[`evlog/http`](/drains/http) posts batches of browser events to a route you write. It receives a JSON array of `DrainContext`:

```typescript [src/index.ts]
import type { DrainContext } from 'evlog'

app.post('/v1/ingest', async (c) => {
  const batch = await c.req.json<DrainContext[]>()
  for (const ctx of batch) {
    console.log('[BROWSER]', JSON.stringify(ctx.event))
  }
  return c.body(null, 204)
})
```

The [Hono example](https://github.com/evloghq/evlog/tree/main/examples/hono) is a complete app.
