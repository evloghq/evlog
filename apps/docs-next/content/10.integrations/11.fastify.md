evlog registers as a Fastify plugin and puts the request logger on `request.evlog`:

```typescript [src/index.ts]
import Fastify from 'fastify'
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { evlog } from 'evlog/fastify'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

const app = Fastify({ logger: false })
await app.register(evlog, toMiddlewareOptions(config))

await app.listen({ port: 3000 })
```

`logger: false` turns off Fastify's own request lines, which the wide event replaces. The plugin is not encapsulated: registered once on the root instance, before your routes, its hooks cover every route of the app.

[`evlog init`](/cli/init) writes `evlog.config.ts` and these lines for you. If you build with Vite, the [`evlog/vite` plugin](/extend/vite) reads the same file but cannot carry the drain, so keep the `initLogger()` call.

## In a route

```typescript [src/routes/users.ts]
app.get('/users/:id', async (request) => {
  const { id } = request.params as { id: string }

  const user = await db.findUser(id)
  request.evlog.set({ user: { id, plan: user.plan } })

  return user
})
```

`request.evlog` is typed by the package, with `set`, `fork` and `audit`. Fastify already types `request.log` as its own logger, and a module augmentation cannot change the type of an existing property, so evlog uses its own name. At runtime `request.log` holds the same evlog logger, for code written before `request.evlog`, but TypeScript keeps Fastify's type there. Fastify's own logger stays on `app.log`.

In a service the route calls, `useLogger()` from `evlog/fastify` returns the same logger.

```typescript [src/services/user.ts]
import { useLogger } from 'evlog/fastify'

export async function findUser(id: string) {
  const log = useLogger()
  log.set({ user: { id } })

  const user = await db.findUser(id)
  log.set({ user: { name: user.name, plan: user.plan } })

  return user
}
```

`useLogger()` reads the logger from `AsyncLocalStorage`. It throws outside a request and on a route the plugin does not log. `useLogger<MyFields>()` types the fields you set. See [Typed fields](/events/typed-fields).

## Background work

The request's event is sealed once it is emitted, so work that outlives the response needs its own. `request.evlog.fork(label, fn)` runs `fn` under a forked logger, and `useLogger()` returns that logger inside it:

```typescript [src/index.ts]
import { evlog, useLogger } from 'evlog/fastify'

app.post('/orders', async (request, reply) => {
  request.evlog.fork('fulfill', async () => {
    const log = useLogger()
    log.set({ step: 'ok' })
  })
  return { ok: true }
})
```

The fork emits a second event when `fn` settles, with `operation: 'fulfill'` and `_parentRequestId` set to the request's `requestId`. A `set()` on the request logger after its event is emitted is dropped with an `[evlog]` warning. [After the event is emitted](/events#after-the-event-is-emitted) covers both, and when to await the fork.

## Errors

A thrown error is recorded on the event. Answer with its fields from `setErrorHandler`:

```typescript [src/index.ts]
import { parseError } from 'evlog'

app.setErrorHandler((error, _request, reply) => {
  const { status, message, why, fix, link } = parseError(error)
  reply.status(status).send({ message, why, fix, link })
})
```

The plugin records the error in Fastify's `onError` hook and emits there. The event's `status` is the one the error carries (`status` or `statusCode`), and `500` when it carries none, whatever status the handler sends. Throw it with [`createError()`](/errors) to set the status, `why`, `fix` and `link`:

```typescript [src/index.ts]
import { createError } from 'evlog'

app.get('/checkout', async () => {
  throw createError({
    message: 'Payment failed',
    status: 402,
    why: 'Card declined by issuer',
    fix: 'Try a different payment method',
    link: 'https://docs.example.com/payments/declined',
  })
})
```

## When the event is emitted

Without an error, the plugin emits in Fastify's `onResponse` hook, which runs once the reply has been sent in full. A streamed reply emits when the stream ends, with the fields set while streaming.

## Options

The second argument of `app.register(evlog, options)` takes the request options of `evlog.config.ts`, which `toMiddlewareOptions(config)` passes. [Configuration](/reference/configuration) lists the logger options that go to `initLogger()`.

| Option | Default | What it does |
| --- | --- | --- |
| `include` | Every route | Globs of the routes to log. `*` stops at a `/`, `**` crosses it |
| `exclude` | None | Globs of the routes to skip. Wins over `include` |
| `routes` | None | A `service` name per route glob. The first glob that matches wins, so list the specific ones first |
| `drain` | The drain given to `initLogger()` | Receives every emitted event. See [Drains](/drains) |
| `enrich` | None | Adds fields after redaction, before the console output and the drain. See [Enrichers](/events/enrichers) |
| `keep` | None | Tail sampling: set `ctx.shouldKeep = true` to keep an event the rates would drop. See [Sampling](/events/sampling) |
| `redact` | The `initLogger()` setting | Redacts the event when `initLogger()` did not: `true` for the built-in patterns, or a config. See [Redaction](/events/redaction) |
| `plugins` | None | Merged with the plugins given to `initLogger()`. A plugin here replaces a global one of the same `name` |
| `waitUntil` | The Vercel Functions runtime, when there is one | Registers the drain with the runtime instead of awaiting it |

```typescript [src/index.ts]
await app.register(evlog, {
  ...toMiddlewareOptions(config),
  include: ['/api/**'],
  exclude: ['/_internal/**', '/health'],
  routes: {
    '/api/auth/**': { service: 'auth-service' },
    '/api/payment/**': { service: 'payment-service' },
  },
})
```

A field you pass next to the config replaces that field. It is not merged with the file's. The globs match the pathname, without the query string. The event's `requestId` is the `x-request-id` header when the caller sends one, and a random UUID otherwise.

On a route that `include` or `exclude` filters out, `request.evlog` accepts every call and emits nothing, `request.log` keeps Fastify's logger, and `useLogger()` throws.

## Shutdown and serverless

A [pipeline](/drains/pipeline) that holds events is flushed when the app closes, in Fastify's `onClose` hook, and on `SIGTERM`, `SIGINT` and `beforeExit`. `process.exit()` skips that, so call `await app.close()` or `await drain.flush()` before it.

On Vercel Functions the plugin finds the request's `waitUntil` in the runtime and keeps the instance alive until the drain is done. Anywhere else, pass the platform's `waitUntil` as an option. Without one, the plugin awaits the drain inside the hook that emits. [Serverless](/drains/pipeline#serverless) has the limits of a request-end flush.

The [Fastify example](https://github.com/evloghq/evlog/tree/main/examples/fastify) is a complete app.
