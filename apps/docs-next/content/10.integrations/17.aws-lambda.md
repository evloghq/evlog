A Lambda function has no request middleware, so the handler creates and emits its loggers. Start evlog outside the handler, where it runs once per cold start:

::emits{step="record"}
```typescript [src/handler.ts]
import type { SQSEvent } from 'aws-lambda'
import { createLogger, initLogger, toLoggerConfig } from 'evlog'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

export async function handler(event: SQSEvent) {
  for (const record of event.Records) {
    const log = createLogger({ messageId: record.messageId })

    try {
      log.set({ queue: { name: record.eventSourceARN } })
      await processMessage(JSON.parse(record.body))
    } catch (error) {
      log.error(error instanceof Error ? error : new Error(String(error)))
      throw error
    } finally {
      log.emit()
    }
  }
}
```
::

Your bundler includes `evlog.config.ts` with the handler, so the drain and the `process.env` reads in it run at cold start. [`evlog init`](/cli/init) writes the file for you.

This page uses the core API, the same as [Standalone](/integrations/standalone). There is no `evlog()` middleware, no `useLogger()` and no `log.fork()`: pass `log` to the functions that add to the event.

## One logger per unit of work

Create the logger inside the loop, not at the top of the file. A logger shared by every record would merge their fields into one event, and a warm container would carry them into the next invocation.

For an API Gateway handler, `createRequestLogger({ method, path })` adds the HTTP fields, and one logger covers the invocation.

Set `silent` in the config when a drain is the only destination, so CloudWatch does not receive a second copy on stdout.

When the whole batch is one unit of work, create a single logger per invocation and put the batch on it, such as the number of records, in place of one logger per record.

`log.emit()` seals the logger and adds the duration since `createLogger()`. A logger you never emit produces no event, which is why the handler above emits in `finally`.

## Deliver before the function freezes

Lambda freezes the runtime as soon as the handler returns. `log.emit()` hands the event to the drain and returns without waiting for it, so a send still in flight is suspended with the runtime, and is lost if the container is never thawed.

The request integrations deliver before they answer, but a handler that calls `createLogger()` itself has none. Wrap the drain in a [pipeline](/drains/pipeline), which exposes `flush()`, and await it before the handler returns:

```typescript [evlog.config.ts]
import { defineEvlog, type DrainContext } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createDrainPipeline } from 'evlog/pipeline'

const pipeline = createDrainPipeline<DrainContext>({ batch: { size: 50 } })

export const drain = pipeline(createAxiomDrain())

export default defineEvlog({
  service: 'sqs-consumer',
  silent: process.env.NODE_ENV === 'production',
  drain,
})
```

```typescript [src/handler.ts]
import { drain } from '../evlog.config'

export async function handler(event: SQSEvent) {
  try {
    // one logger per record, as above
  } finally {
    await drain.flush()
  }
}
```

`flush()` sends everything buffered and resolves once it is delivered or dropped, retries included, so the invocation lasts that long. When a pipeline on Lambda still holds events after `batch.intervalMs`, evlog prints a warning once: the timer that would send them is frozen with the runtime. [Serverless](/drains/pipeline#serverless) has the details.

## Stdout and silent

Without a drain, the event goes to stdout, which CloudWatch ingests. With a drain, `silent: true` stops that second copy. With `silent` and no drain, events are built and written nowhere, and `initLogger()` prints a warning that says so.

evlog reads `NODE_ENV` to pick the output and the [redaction](/events/redaction) default: one JSON line per event and redaction on when it is `production`, the development tree and no redaction otherwise. Set `NODE_ENV` in the function's environment, or set `pretty` and `redact` in the config.

## What the config file covers

`toLoggerConfig(config)` keeps every option `initLogger()` takes: the service and environment, `enabled`, `pretty`, `stringify`, `silent`, `minLevel`, `sampling`, `redact`, the drain and the plugins. [Configuration](/reference/configuration) lists them.

`include`, `exclude`, `routes`, `enrich` and `keep` belong to the request integrations and do nothing in a handler. Tail sampling still works through [`sampling.keep`](/events/sampling). The event's `region` comes from `AWS_REGION`.

## Errors

`log.error(error)` puts the error on the event and raises its level. Rethrow afterwards, as the handler above does: evlog does not change what Lambda sees, so SQS retries and dead-letter queues behave as before. Throw [`createError()`](/errors) where the failure should carry a `why` and a `fix`:

```typescript [src/handler.ts]
import { createError } from 'evlog'

throw createError({
  message: 'Invalid payload',
  status: 400,
  why: 'Required field missing',
  fix: 'Include orderId in the message body',
})
```
