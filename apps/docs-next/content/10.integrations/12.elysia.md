The plugin adds `log` to the context of every handler after it:

```typescript [src/index.ts]
import { Elysia } from 'elysia'
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { evlog } from 'evlog/elysia'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

const app = new Elysia()
  .use(evlog(toMiddlewareOptions(config)))
  .listen(3000)
```

[`evlog init`](/cli/init) writes `evlog.config.ts` and these lines for you. If you build with Vite, the [`evlog/vite` plugin](/integrations/vite) reads the same file but cannot carry the drain, so keep the `initLogger()` call.

## In a handler

```typescript [src/index.ts]
app.get('/users/:id', async ({ log, params }) => {
  const user = await db.findUser(params.id)
  log.set({ user: { id: params.id, plan: user.plan } })

  return user
})
```

The plugin derives `log` globally, so it is typed in every route registered after `.use(evlog())`, with `set`, `fork` and `audit`.

In a service the handler calls, `useLogger()` from `evlog/elysia` returns the same logger.

```typescript [src/services/user.ts]
import { useLogger } from 'evlog/elysia'

export async function findUser(id: string) {
  const log = useLogger()
  log.set({ user: { id } })

  const user = await db.findUser(id)
  log.set({ user: { name: user.name, plan: user.plan } })

  return user
}
```

`useLogger()` reads the logger from `AsyncLocalStorage`. It throws outside a request and on a route the plugin does not log. `useLogger<MyFields>()` types the fields you set. See [Typed fields](/events/typed-fields).

::callout{icon="i-lucide-triangle-alert" color="neutral"}
Elysia's lifecycle hooks run apart from the handler, so the plugin binds the logger with `enterWith()` and not with `run()`. Cloudflare Workers has no working `enterWith()`: evlog falls back to one logger per isolate there, which is wrong as soon as two requests interleave. On Workers, read `log` from the context and do not call `useLogger()`. `evlog/elysia` imports `node:async_hooks`, so it needs the `nodejs_compat` or `nodejs_als` flag there.
::

## Background work

The request's event is sealed once it is emitted, so work that outlives the response needs its own. `log.fork(label, fn)` runs `fn` under a forked logger, and `useLogger()` returns that logger inside it:

```typescript [src/index.ts]
import { evlog, useLogger } from 'evlog/elysia'

app
  .use(evlog())
  .post('/orders', ({ log }) => {
    log.fork('ship', async () => {
      const l = useLogger()
      l.set({ shipped: true })
    })
    return { ok: true }
  })
```

The fork emits a second event when `fn` settles, with `operation: 'ship'` and `_parentRequestId` set to the request's `requestId`. A `set()` on the request logger after its event is emitted is dropped with an `[evlog]` warning. [After the event is emitted](/events#after-the-event-is-emitted) covers both, and when to await the fork.

On Elysia the forked event goes to the drain given to `initLogger()`. The `drain`, `enrich` and `redact` you pass to `evlog()` itself do not apply to it, so keep them in `evlog.config.ts`, where `toLoggerConfig(config)` passes the drain and the redaction to `initLogger()` too.

## Errors

The plugin records a thrown error on the event in Elysia's `onError` hook. Your own `onError` turns it into a response with `parseError()`:

```typescript [src/index.ts]
import { createError, parseError } from 'evlog'

app
  .use(evlog())
  .get('/checkout', ({ log }) => {
    log.set({ cart: { items: 3, total: 9999 } })
    throw createError({
      message: 'Payment failed',
      status: 402,
      why: 'Card declined by issuer',
      fix: 'Try a different payment method',
      link: 'https://docs.example.com/payments/declined',
    })
  })
  .onError(({ error, set }) => {
    const parsed = parseError(error)
    set.status = parsed.status
    return {
      message: parsed.message,
      why: parsed.why,
      fix: parsed.fix,
      link: parsed.link,
    }
  })
```

The event's `status` is the one the error carries (`status` or `statusCode`), and `500` when it carries none.

## Streaming responses

When a handler returns a `Response` with a streamed body, the plugin emits when the body closes, fails or is cancelled, so fields set while streaming land on the event. A `Response` counts as streamed when its `content-type` is `text/event-stream` or `application/x-ndjson`, when it has the `x-vercel-ai-ui-message-stream` header, or when `transfer-encoding` is `chunked`. Everything else emits in `onAfterResponse`, with the status from `set.status` and `200` when it is unset.

## Options

`evlog()` takes the request options of `evlog.config.ts`, which `toMiddlewareOptions(config)` passes. [Configuration](/reference/configuration) lists the logger options that go to `initLogger()`.

| Option | Default | What it does |
| --- | --- | --- |
| `include` | Every route | Globs of the routes to log. `*` stops at a `/`, `**` crosses it |
| `exclude` | None | Globs of the routes to skip. Wins over `include` |
| `routes` | None | A `service` name per route glob. The first glob that matches wins, so list the specific ones first |
| `drain` | The drain given to `initLogger()` | Receives every emitted event. See [Drains](/drains) |
| `enrich` | None | Adds fields after redaction, before the console output and the drain. See [Enrichers](/events/enrichers) |
| `keep` | None | Tail sampling: set `ctx.shouldKeep = true` to keep an event the rates would drop. See [Sampling](/events/sampling) |
| `redact` | The `initLogger()` setting | Redacts the event when `initLogger()` did not: `true` for the built-in patterns, or a config. See [Redaction](/events/redaction) |
| `plugins` | None | Merged with the plugins given to `initLogger()`. A plugin here replaces a global one of the same `name` |
| `waitUntil` | The Vercel Functions runtime, when there is one | Registers the drain with the runtime instead of awaiting it |

```typescript [src/index.ts]
app.use(evlog({
  ...toMiddlewareOptions(config),
  include: ['/api/**'],
  exclude: ['/_internal/**', '/health'],
  routes: {
    '/api/auth/**': { service: 'auth-service' },
    '/api/payment/**': { service: 'payment-service' },
  },
}))
```

A field you pass next to the config replaces that field. It is not merged with the file's. The event's `requestId` is the `x-request-id` header when the caller sends one, and a random UUID otherwise.

On a route that `include` or `exclude` filters out, `log` is still in the context: it accepts every call and emits nothing, and `fn` passed to `log.fork()` still runs. `useLogger()` throws there.

## Shutdown and serverless

A [pipeline](/drains/pipeline) that holds events is flushed on `SIGTERM`, `SIGINT` and `beforeExit`. Elysia does not await its `onStop` handlers, so on Bun that signal flush is what delivers the last batch. `process.exit()` skips it, so call `await drain.flush()` before it.

On Vercel Functions the plugin finds the request's `waitUntil` in the runtime and keeps the instance alive until the drain is done. Anywhere else, pass the platform's `waitUntil` as an option. [Serverless](/drains/pipeline#serverless) has the limits of a request-end flush.

## Receive browser logs

[`evlog/http`](/drains/http) posts batches of browser events to a route you write. It receives a JSON array of `DrainContext`:

```typescript [src/index.ts]
import type { DrainContext } from 'evlog'

app.post('/v1/ingest', async ({ body }) => {
  const batch = body as DrainContext[]
  for (const ctx of batch) {
    console.log('[BROWSER]', JSON.stringify(ctx.event))
  }
  return new Response(null, { status: 204 })
})
```

The [Elysia example](https://github.com/evloghq/evlog/tree/main/examples/elysia) is a complete app.
