The module registers the middleware for every route; `main.ts` starts the logger before Nest boots:

```typescript [src/app.module.ts]
import { Module } from '@nestjs/common'
import { toMiddlewareOptions } from 'evlog'
import { EvlogModule } from 'evlog/nestjs'
import config from '../evlog.config'

@Module({
  imports: [EvlogModule.forRoot(toMiddlewareOptions(config))],
})
export class AppModule {}
```

```typescript [src/main.ts]
import 'reflect-metadata'
import { NestFactory } from '@nestjs/core'
import { initLogger, toLoggerConfig } from 'evlog'
import { AppModule } from './app.module'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

const app = await NestFactory.create(AppModule)
await app.listen(3000)
```

The same module works on the Fastify platform: pass a `FastifyAdapter` to `NestFactory.create()`.

`EvlogModule` is a global module, so you import it once, in the root module. [`evlog init`](/cli/init) writes `evlog.config.ts` and these lines for you.

## In a controller

```typescript [src/users.controller.ts]
import { Controller, Get, Param } from '@nestjs/common'
import { useLogger } from 'evlog/nestjs'

@Controller('users')
export class UsersController {
  @Get(':id')
  async findOne(@Param('id') id: string) {
    const user = await db.findUser(id)
    useLogger().set({ user: { id, plan: user.plan } })

    return user
  }
}
```

`useLogger()` works the same way in any provider the controller calls; there is nothing to inject.

```typescript [src/users.service.ts]
import { useLogger } from 'evlog/nestjs'

export class UsersService {
  async findUser(id: string) {
    const log = useLogger()
    log.set({ user: { id } })

    const user = await db.findUser(id)
    log.set({ user: { name: user.name, plan: user.plan } })

    return user
  }
}
```

`useLogger()` reads the logger from `AsyncLocalStorage`. It throws outside a request and on a route the middleware does not log. `useLogger<MyFields>()` types the fields you set. See [Typed fields](/events/typed-fields).

The same logger is on the request object, for code that already has it:

| Platform | Accessor | Type | On a route the middleware skips |
| --- | --- | --- | --- |
| Express | `req.log` | `ForkableLogger \| undefined` | `undefined` |
| Fastify | `request.evlog` | `ForkableLogger` | Accepts every call and emits nothing |

## On the Fastify platform

Install `@nestjs/platform-fastify` in place of `@nestjs/platform-express`. Nest runs middleware on the raw Node request, so on Fastify the module also registers a `preHandler` hook that copies the logger to `request.evlog` before guards, interceptors, pipes and controllers run. Three limits follow:

- The hook also puts the logger on `request.log`, for code written before `request.evlog`, but TypeScript keeps Fastify's own logger type there.
- A Fastify `onRequest` hook runs before `preHandler` and sees neither `request.evlog` nor the evlog logger on `request.log`.
- Do not register the `evlog/fastify` plugin on the same app. Each one emits its own event, so every request would be logged twice.

## Background work

The request's event is sealed once it is emitted, so work that outlives the response needs its own. `log.fork(label, fn)` runs `fn` under a forked logger, and `useLogger()` returns that logger inside it:

```typescript [src/orders.controller.ts]
import { Controller, Post, Req } from '@nestjs/common'
import type { Request } from 'express'
import { useLogger } from 'evlog/nestjs'

@Controller('orders')
export class OrdersController {
  @Post()
  create(@Req() req: Request) {
    req.log?.fork('enqueue', async () => {
      const log = useLogger()
      log.set({ queued: true })
    })
    return { ok: true }
  }
}
```

The fork emits a second event when `fn` settles, with `operation: 'enqueue'` and `_parentRequestId` set to the request's `requestId`. A `set()` on the request logger after its event is emitted is dropped with an `[evlog]` warning. [After the event is emitted](/events#after-the-event-is-emitted) covers both, and when to await the fork.

On a route the middleware skips, `req.log` is `undefined`, so `req.log?.fork()` does not run `fn`.

## Errors

Nest's exception layer answers a thrown error before the evlog middleware can see it. The event gets the status of the response, but no `error` field and no `error` level. An exception filter records the error and builds the response from its fields:

```typescript [src/evlog-exception.filter.ts]
import { Catch } from '@nestjs/common'
import type { ExceptionFilter, ArgumentsHost } from '@nestjs/common'
import { parseError } from 'evlog'
import { useLogger } from 'evlog/nestjs'

@Catch()
export class EvlogExceptionFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const response = host.switchToHttp().getResponse()
    const error = exception instanceof Error ? exception : new Error(String(exception))

    try {
      useLogger().error(error)
    } catch {
      // Outside an evlog request scope: no logger to record on
    }

    const parsed = parseError(error)
    response.status(parsed.status).json({
      message: parsed.message,
      why: parsed.why,
      fix: parsed.fix,
      link: parsed.link,
    })
  }
}
```

Apply it to a controller with `@UseFilters(new EvlogExceptionFilter())`, then throw [`createError()`](/errors) from a handler:

```typescript [src/checkout.controller.ts]
import { Controller, Get, UseFilters } from '@nestjs/common'
import { createError } from 'evlog'
import { EvlogExceptionFilter } from './evlog-exception.filter'

@Controller()
@UseFilters(new EvlogExceptionFilter())
export class CheckoutController {
  @Get('checkout')
  checkout() {
    throw createError({
      message: 'Payment failed',
      status: 402,
      why: 'Card declined by issuer',
      fix: 'Try a different payment method',
      link: 'https://docs.example.com/payments/declined',
    })
  }
}
```

## When the event is emitted

The middleware emits when the response has been written in full, so a streamed response emits when it ends. When the client disconnects first, it emits at that moment with `connectionClosed: true`. The event's `status` is the one the response was sent with.

## Options

`EvlogModule.forRoot()` takes the request options of `evlog.config.ts`, which `toMiddlewareOptions(config)` passes. [Configuration](/reference/configuration) lists the logger options that go to `initLogger()`.

| Option | Default | What it does |
| --- | --- | --- |
| `include` | Every route | Globs of the routes to log. `*` stops at a `/`, `**` crosses it |
| `exclude` | None | Globs of the routes to skip. Wins over `include` |
| `routes` | None | A `service` name per route glob. The first glob that matches wins, so list the specific ones first |
| `drain` | The drain given to `initLogger()` | Receives every emitted event. See [Drains](/drains) |
| `enrich` | None | Adds fields after redaction, before the console output and the drain. See [Enrichers](/events/enrichers) |
| `keep` | None | Tail sampling: set `ctx.shouldKeep = true` to keep an event the rates would drop. See [Sampling](/events/sampling) |
| `redact` | The `initLogger()` setting | Redacts the event when `initLogger()` did not: `true` for the built-in patterns, or a config. See [Redaction](/events/redaction) |
| `plugins` | None | Merged with the plugins given to `initLogger()`. A plugin here replaces a global one of the same `name` |
| `waitUntil` | The Vercel Functions runtime, when there is one | Registers the drain with the runtime instead of awaiting it |

```typescript [src/app.module.ts]
EvlogModule.forRoot({
  include: ['/api/**'],
  exclude: ['/_internal/**', '/health'],
  routes: {
    '/api/auth/**': { service: 'auth-service' },
    '/api/payment/**': { service: 'payment-service' },
  },
})
```

A field you pass next to the config, as in `forRoot({ ...toMiddlewareOptions(config), exclude: ['/health'] })`, replaces that field. It is not merged with the file's. The globs match the pathname, without the query string. The event's `requestId` is the `x-request-id` header when the caller sends one, and a random UUID otherwise.

### Options from another provider

`forRootAsync()` builds the options from providers Nest injects, such as `ConfigService`:

```typescript [src/app.module.ts]
import { Module } from '@nestjs/common'
import { ConfigModule, ConfigService } from '@nestjs/config'
import { EvlogModule } from 'evlog/nestjs'
import { createAxiomDrain } from 'evlog/axiom'

@Module({
  imports: [
    ConfigModule.forRoot(),
    EvlogModule.forRootAsync({
      imports: [ConfigModule],
      inject: [ConfigService],
      useFactory: (config: ConfigService) => ({
        drain: createAxiomDrain({ apiKey: config.get('AXIOM_API_KEY') }),
      }),
    }),
  ],
})
export class AppModule {}
```

| Field | What it does |
| --- | --- |
| `useFactory` | Returns the options, or a promise of them. Required |
| `inject` | Tokens Nest resolves and passes to `useFactory`, in order |
| `imports` | Modules that provide those tokens |

## Shutdown and serverless

A [pipeline](/drains/pipeline) that holds events is flushed when the app closes, in the module's `onApplicationShutdown`, and on `SIGTERM`, `SIGINT` and `beforeExit`. `process.exit()` skips that, so call `await app.close()` or `await drain.flush()` before it.

On Vercel Functions the middleware finds the request's `waitUntil` in the runtime and keeps the instance alive until the drain is done. Anywhere else, pass the platform's `waitUntil` as an option. [Serverless](/drains/pipeline#serverless) has the limits of a request-end flush.

The [NestJS example](https://github.com/evloghq/evlog/tree/main/examples/nestjs) is a complete app.
