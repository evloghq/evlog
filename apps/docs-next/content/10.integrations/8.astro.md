Astro has no evlog-specific entry point: the middleware creates a request logger from the core and emits it itself.

```typescript [src/middleware.ts]
import { defineMiddleware } from 'astro:middleware'
import { createRequestLogger, initLogger, toLoggerConfig } from 'evlog'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

export const onRequest = defineMiddleware(async ({ request, locals }, next) => {
  const log = createRequestLogger({ method: request.method, path: new URL(request.url).pathname })
  locals.log = log

  try {
    return await next()
  }
  catch (error) {
    log.error(error instanceof Error ? error : new Error(String(error)))
    throw error
  }
  finally {
    log.emit()
  }
})
```

```typescript [src/env.d.ts]
/// <reference types="astro/client" />

declare namespace App {
  interface Locals {
    log: import('evlog').RequestLogger
  }
}
```

This is a guide on the core API, not an integration. You own the middleware above, so what it does not do, evlog does not do: [What the middleware leaves out](#what-the-middleware-leaves-out) lists it.

## In an endpoint

```typescript [src/pages/api/users/[id].ts]
import type { APIRoute } from 'astro'

export const GET: APIRoute = async ({ params, locals }) => {
  const user = await db.findUser(params.id)
  locals.log.set({ user: { id: params.id, plan: user.plan } })

  return Response.json(user)
}
```

Pages rendered on the server receive `Astro.locals.log` too.

There is no `useLogger()` on Astro. A function the endpoint calls takes `locals.log` as an argument.

## Errors

An error that escapes a page or an endpoint reaches the `catch` in the middleware: it lands on the event with level `error`, then Astro answers it. To answer a structured error yourself, record it on the logger and build the response with `parseError()`:

```typescript [src/pages/api/checkout.ts]
import type { APIRoute } from 'astro'
import { createError, parseError } from 'evlog'

export const POST: APIRoute = async ({ request, locals }) => {
  const body = await request.json()
  locals.log.set({ cart: { items: body.items } })

  if (!body.paymentMethod) {
    const error = createError({
      status: 400,
      message: 'Missing payment method',
      why: 'No payment method was provided',
      fix: 'Include a paymentMethod field in the request body',
    })
    locals.log.error(error)
    const parsed = parseError(error)
    return new Response(JSON.stringify(parsed), { status: parsed.status })
  }

  return new Response(JSON.stringify({ success: true }))
}
```

`parseError()` returns `message`, `status`, `why`, `fix` and `link`. [Errors](/errors) describes the fields.

## What the middleware leaves out

`createRequestLogger()` is the logger scripts and jobs use. It knows nothing about the response, and the request options of `evlog.config.ts` do not reach it:

| What | On Astro |
| --- | --- |
| `sampling`, `redact`, `drain`, `pretty`, `silent` | Apply. `toLoggerConfig(config)` passes them to `initLogger()` |
| `include`, `exclude`, `routes` | Do not apply. Every request the middleware sees is logged, under one service. Skip a path with your own `if` |
| `enrich`, `keep` | Do not apply. Rule-based `sampling.keep` still does |
| `status` | Not set. Call `log.set({ status: response.status })` before the emit, or a `sampling.keep` rule on status never matches |
| `requestId` | Not set. Pass `requestId` to `createRequestLogger()` |
| `log.fork()` | Not available on this logger. For work that outlives the response, create a second logger with `createRequestLogger({ operation: 'send_receipt' })` and emit it when the work ends |
| Streaming | The event is emitted when `next()` returns the response, not when a streamed body finishes. A `log.set()` after that is dropped with a warning |

[Standalone](/integrations/standalone) covers the same logger outside a framework, and [Configuration](/reference/configuration) lists every option of the file.

## Drain

Set the drain in `evlog.config.ts`, wrapped in a [pipeline](/drains/pipeline) to batch and retry:

```typescript [evlog.config.ts]
import { defineEvlog, type DrainContext } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createDrainPipeline } from 'evlog/pipeline'

const pipeline = createDrainPipeline<DrainContext>({
  batch: { size: 50, intervalMs: 5000 },
})

export default defineEvlog({
  service: 'my-astro-app',
  drain: pipeline(createAxiomDrain()),
})
```

::callout{icon="i-lucide-cloud" color="neutral"}
On Cloudflare, with `@astrojs/cloudflare`, the runtime stops once the response is returned, and a drain still running is lost. Pass the platform's `waitUntil`, bound to its context, as the `waitUntil` option of `createRequestLogger()`. Where the middleware reads that context depends on the adapter version: see the [Cloudflare adapter docs](https://docs.astro.build/en/guides/integrations-guide/cloudflare/).
::
