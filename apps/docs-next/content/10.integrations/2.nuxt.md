The module reads `evlog.config.ts`, creates a logger for each server request, and emits it when the response ends.

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['evlog/nuxt'],
})
```

`useLogger` and `parseError` are auto-imported. Import `createError` from `evlog`: the auto-imported one is Nuxt's, and it drops `why`, `fix` and `link`.

What the module auto-imports, and where:

| Name | Server | App | What it is |
| --- | --- | --- | --- |
| `useLogger` | Yes | No | The logger of the current request |
| `log` | Yes | Yes | On the server, the [`log` API](/events/simple-logging) for lines outside a request. In the app, the [browser logger](/events/client) |
| `createEvlogError` | Yes | Yes | evlog's `createError` under a name Nuxt does not use |
| `parseError` | No | Yes | Reads `why`, `fix` and `link` from a failed `$fetch` |
| `setIdentity`, `clearIdentity`, `setMinLevel` | No | Yes | Browser logger controls |

## In a route

```typescript [server/api/checkout.post.ts]
import { createError } from 'evlog'

export default defineEventHandler(async (event) => {
  const log = useLogger(event)
  const body = await readBody(event)

  const cart = await db.findCart(body.cartId)
  log.set({ cart: { items: cart.items.length, total: cart.total } })

  if (body.amount <= 0) {
    throw createError({
      status: 400,
      message: 'Invalid payment amount',
      why: 'The amount must be a positive number',
      fix: 'Pass a positive integer in cents, such as 4999 for $49.99',
    })
  }

  return { ok: true }
})
```

The module's error handler returns an `EvlogError` as JSON with `why`, `fix` and `link` under `data`. Errors thrown with h3's `createError` keep their own `data`.

A second argument sets the service name of this request's event: `useLogger(event, 'payment-service')`.

## Under the route

To reach the logger from a service without passing the event, turn on Nitro's request context and call `useLogger()` with no argument:

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['evlog/nuxt'],
  nitro: { experimental: { asyncContext: true } },
})
```

This uses `AsyncLocalStorage`, so it runs on Node and on runtimes that provide it, such as Cloudflare with `nodejs_compat`. Without the flag, `useLogger()` throws and names the flag. `useLogger(event)` works everywhere.

## Background work

`log.fork(label, fn)` runs work that outlives the response under its own event, such as a receipt sent after the handler returned. `fn` receives the forked logger:

```typescript [server/api/checkout.post.ts]
export default defineEventHandler(async (event) => {
  const log = useLogger(event)
  log.fork('send_receipt', async (child) => {
    child.set({ receipt: { sent: true } })
    await sendReceipt()
  })
  return { ok: true }
})
```

The child event carries `operation: 'send_receipt'` and `_parentRequestId`, goes through the same `evlog:enrich` and `evlog:drain` hooks, and is registered with `waitUntil` where the runtime provides one. Inside `fn`, `useLogger()` still returns the parent logger, so use the `child` argument. [After the event is emitted](/events#after-the-event-is-emitted) explains why the parent logger is sealed by then.

## When a handler throws

The error lands on the request's event with its `why`, `fix` and `link`. The event's `status` is the error's `status` or `statusCode`, and `500` when it has neither. The event is emitted once.

The module's error handler then answers:

| Thrown | Response |
| --- | --- |
| An `EvlogError` | JSON on every route: `url`, `status`, `message`, `error: true` and `data` |
| Another error, on `/api/**` or on a request that does not ask for an HTML page | The same JSON shape. Outside development, an error with no status answers `Internal Server Error`, without its message or `data` |
| Another error, on a request for an HTML page | Nothing from evlog: Nuxt renders its error page |

Set `errorHandler: false` when your app answers errors itself. The error still reaches the event. In the app, `parseError()` turns a failed `$fetch` back into the same fields: see [Errors](/errors#read-it-on-the-client).

## Streaming responses

A streamed response emits when its body has been sent, not when the handler returns. Fields set while the stream runs, [AI SDK](/extend/ai-sdk) token counts included, land on the request's event.

## Configuration

Options go in `evlog.config.ts`. The `evlog` key in `nuxt.config.ts` takes the same options and overrides the file key by key, with one exception: the file's `drain`, `enrich` and `keep` always run, alongside any `evlog:*` hook.

`nuxt.config.ts` is serialized to JSON, so the `evlog` key takes no function: `drain`, `enrich`, `keep` and `plugins` belong in the file. It also writes the service under `env`, as `env: { service: 'my-app' }`. When both set a list, the key's list replaces the file's, except `redact.paths`, `redact.patterns` and `sampling.keep`, which are joined.

[Configuration](/reference/configuration) lists the shared options. The `evlog` key takes `enabled`, `env`, `pretty`, `silent`, `minLevel`, `sampling`, `redact`, `dev`, `include`, `exclude` and `routes` from that list.

These options exist only in `nuxt.config.ts`:

| Option | Default | What it does |
| --- | --- | --- |
| `console` | `true` | Browser console output |
| `transport.enabled` | `false` | Sends browser logs to `/api/_evlog/ingest`, then through your drain. See [Client logging](/events/client#send-events-to-your-server) |
| `transport.endpoint` | `'/api/_evlog/ingest'` | The route the module registers for browser logs |
| `transport.credentials` | `'same-origin'` | The `credentials` mode of the browser's `fetch` call |
| `client` | `true` | `false` skips the browser plugin, the `log`, `setIdentity`, `clearIdentity` and `setMinLevel` auto-imports, and `runtimeConfig.public.evlog`. The server side stays. Use it for a server-only app |
| `errorHandler` | `true` | `false` leaves error responses to your own Nitro `errorHandler`, or to Nuxt |
| `stream` | Off | `true` or an options object starts the local [stream](/drains/stream) server and registers `GET /api/_evlog/stream-info` |
| `strip` | `['debug']` | Log levels removed from production builds. `[]` turns stripping off. See [Vite](/extend/vite) |
| `sourceLocation` | `'dev'` | Adds the source file and line to log calls: `true` always, `'dev'` in development only, `false` never |
| `retention` | `'7d'` | How long [`@evlog/nuxthub`](/drains/nuxthub) keeps events: `'30d'`, `'24h'` or `'60m'` |
| `axiom`, `otlp`, `posthog`, `sentry` | None | Credentials the matching drain reads when you pass it none. Environment variables do the same job |

The browser logger takes `enabled`, `pretty` and `minLevel` from `evlog.config.ts`, unless the `evlog` key or a `NUXT_PUBLIC_EVLOG_*` variable sets them.

In development, `dev: 'evlog'` prints one error block with evlog's own stack and hides Nitro's overlay. `'nitro'` keeps Nitro's stack and prints only `why` and `fix` from evlog. `'both'` prints the two. With `pretty: false`, set `dev: { frameworkOverlay: false }` to keep Nitro quiet while you log JSON.

## Route filters

`include` limits logging to the globs you list, `exclude` wins over `include`, and `routes` gives a group of routes its own service name:

```typescript [evlog.config.ts]
export default defineEvlog({
  service: 'default-service',
  include: ['/api/**', '/auth/**'],
  exclude: ['/api/_nuxt_icon/**', '/api/_content/**', '/api/health'],
  routes: {
    '/api/auth/**': { service: 'auth-service' },
    '/api/payment/**': { service: 'payment-service' },
  },
})
```

On a filtered-out route, `useLogger(event)` still returns a logger. It accepts every call and emits nothing, and `log.fork()` still runs its function.

## Hooks

Nitro hooks run next to the config file, for what needs the Nitro app:

| Hook | Runs |
| --- | --- |
| `evlog:enrich` | Before the event is printed and drained |
| `evlog:drain` | After the event is emitted |
| `evlog:emit:keep` | Before sampling, to force-keep an event |

A drain registered from a plugin, batched by the [pipeline](/drains/pipeline):

```typescript [server/plugins/evlog-drain.ts]
import type { DrainContext } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createDrainPipeline } from 'evlog/pipeline'

const pipeline = createDrainPipeline<DrainContext>({
  batch: { size: 50, intervalMs: 5000 },
  retry: { maxAttempts: 3 },
})
const drain = pipeline(createAxiomDrain())

export default defineNitroPlugin((nitroApp) => {
  nitroApp.hooks.hook('evlog:drain', drain)
})
```

A keep rule that reads what the handler logged:

```typescript [server/plugins/evlog-sampling.ts]
export default defineNitroPlugin((nitroApp) => {
  nitroApp.hooks.hook('evlog:emit:keep', (ctx) => {
    const user = ctx.context.user as { premium?: boolean } | undefined
    if (user?.premium) {
      ctx.shouldKeep = true
    }
  })
})
```

`evlog:enrich` receives the event with the request, its safe headers and the response status. Call the [built-in enrichers](/events/enrichers) from it, or set fields on `ctx.event`. A hook that throws is caught and reported as `[evlog] enrich failed` or `[evlog] drain failed`, and the request is not affected.

## Browser logs

In the app, `log` is the browser logger. It prints to the console, and posts each event to your server once the transport is on:

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['evlog/nuxt'],
  evlog: {
    transport: {
      enabled: true,
      endpoint: '/api/_evlog/ingest',
    },
  },
})
```

The module registers the ingest route. Each browser event gets the server's service and environment, `source: 'client'`, your redaction and head sampling, then runs through `evlog:enrich` and `evlog:drain` like a server event. A successful request to the ingest route emits no request event of its own.

`setIdentity()` attaches the signed-in user to every browser event. A route middleware keeps it in sync with your auth state:

```typescript [middleware/identity.global.ts]
export default defineNuxtRouteMiddleware(() => {
  const { user } = useAuth()

  if (user.value) {
    setIdentity({ userId: user.value.id, email: user.value.email })
  } else {
    clearIdentity()
  }
})
```

[Browser events](/events/client) covers the calls, the ingest route's checks and its limits.

## Deploy

Where the request has a `waitUntil`, as on Cloudflare Workers and Vercel Edge, the drain is registered with it and finishes after the response. Elsewhere evlog awaits it, so a function that freezes after the response does not lose the event. An error event is the exception: its drain never holds the error response back.

A buffered drain from `evlog.config.ts`, such as one built with `createDrainPipeline`, is flushed when the server closes. [Serverless](/drains/pipeline#serverless) covers what a pipeline does at the end of a request.

To sample or silence the console in production only, put those options under Nuxt's `$production` key: see [Sample in production only](/events/sampling#sample-in-production-only).
