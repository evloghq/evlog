The module loads `evlog.config.ts`, creates a logger per request, and emits it when the response ends. `evlog/nitro` targets Nitro 3:

```typescript [nitro.config.ts]
import { defineConfig } from 'nitro'
import evlog from 'evlog/nitro'

export default defineConfig({
  modules: [evlog()],
})
```

On Nitro 2 (`nitropack`), import the module and `useLogger` from `evlog/nitro/v2` instead.

The samples on this page are Nitro 3. On Nitro 2, these imports change:

| | Nitro 3 | Nitro 2 |
| --- | --- | --- |
| Module and `useLogger` | `evlog/nitro` | `evlog/nitro/v2` |
| Config | `defineConfig` from `nitro` | `defineNitroConfig` from `nitropack/config` |
| Handler | `defineHandler` from `nitro/h3` | `defineEventHandler` from `h3` |
| Plugin | `definePlugin` from `nitro` | `defineNitroPlugin`, auto-imported |
| `createError`, `parseError` | `evlog/nitro` or `evlog` | `evlog` |

## In a route

```typescript [routes/api/checkout.post.ts]
import { defineHandler, readBody } from 'nitro/h3'
import { useLogger } from 'evlog/nitro'

export default defineHandler(async (event) => {
  const log = useLogger(event)
  const body = await readBody(event)

  log.set({ user: { id: body.userId }, cart: { items: body.items.length } })

  return { ok: true }
})
```

Drains, enrichers and keep rules go in `evlog.config.ts`, or in a Nitro plugin through the `evlog:drain`, `evlog:enrich` and `evlog:emit:keep` hooks.

A second argument sets the service name of this request's event: `useLogger(event, 'payment-service')`.

## Under the route

To reach the logger from a service without passing the event, turn on Nitro's request context and call `useLogger()` with no argument:

```typescript [nitro.config.ts]
import { defineConfig } from 'nitro'
import evlog from 'evlog/nitro'

export default defineConfig({
  modules: [evlog()],
  experimental: { asyncContext: true },
})
```

This uses `AsyncLocalStorage`, so it runs on Node and on runtimes that provide it, such as Cloudflare with `nodejs_compat`. Without the flag, `useLogger()` throws and names the flag. `useLogger(event)` works everywhere.

## Background work

`log.fork(label, fn)` runs work that outlives the response under its own event, such as a receipt sent after the handler returned. `fn` receives the forked logger:

```typescript [routes/api/checkout.post.ts]
import { defineHandler } from 'nitro/h3'
import { useLogger } from 'evlog/nitro'

export default defineHandler(async (event) => {
  const log = useLogger(event)
  log.fork('send_receipt', async (child) => {
    child.set({ receipt: { sent: true } })
    await sendReceipt()
  })
  return { ok: true }
})
```

The child event carries `operation: 'send_receipt'` and `_parentRequestId`, goes through the same `evlog:enrich` and `evlog:drain` hooks, and is registered with `waitUntil` where the runtime provides one. Inside `fn`, `useLogger()` still returns the parent logger, so use the `child` argument. [After the event is emitted](/events#after-the-event-is-emitted) explains why the parent logger is sealed by then.

## Errors

Throw `createError()` with a `why` and a `fix`. The integration records it on the event and answers with the status you set:

```typescript [routes/api/payment.post.ts]
import { createError } from 'evlog/nitro'

throw createError({
  status: 402,
  message: 'Payment failed',
  why: 'Card declined by issuer',
  fix: 'Try a different payment method',
})
```

`createError` from `evlog/nitro` is the one from `evlog`, exported again so a Nitro 3 route needs one import. The event's `status` is the error's `status` or `statusCode`, and `500` when it has neither. The event is emitted once.

The module registers a Nitro error handler, ahead of any other, that answers:

| Thrown | Response |
| --- | --- |
| An `EvlogError` | JSON on every route: `url`, `status`, `message`, `error: true`, and `why`, `fix` and `link` under `data` |
| Another error, on `/api/**` or on a request that does not ask for an HTML page | The same JSON shape, with the error's own `data`. Outside development, an error with no status answers `Internal Server Error`, without its message or `data` |
| Another error, on a request for an HTML page | Nothing from evlog: the next error handler answers |

When your app owns its error responses, for example to keep `why` and `fix` internal, turn the handler off:

```typescript [nitro.config.ts]
import { defineConfig } from 'nitro'
import evlog from 'evlog/nitro'

export default defineConfig({
  modules: [
    evlog({ errorHandler: false }),
  ],
})
```

The next error handler then answers: the one you set with `errorHandler` in the Nitro config, or Nitro's default, which also prints its own error log. The error still reaches the event, with `why` and `fix`.

## Streaming responses

A response with a `text/event-stream` or `application/x-ndjson` content type, chunked transfer encoding, or the AI SDK's stream header emits when its body ends or the client leaves, not when the handler returns. Fields set while the stream runs, [AI SDK](/extend/ai-sdk) token counts included, land on the request's event, and an error thrown mid-stream is recorded on it.

On Nitro 3 this needs h3 2.0.1 or later. With an older h3, the event is emitted when the headers are sent, and a later `log.set()` prints the warning described in [After the event is emitted](/events#after-the-event-is-emitted).

## Module options

Every option goes in `evlog.config.ts`: [Configuration](/reference/configuration) has the full list. Options passed to `evlog()` override the file, merged key by key. The file's `drain`, `enrich` and `keep` are never overridden: they run alongside the `evlog:*` hooks, so an event reaches both.

`nitro.config.ts` is serialized to JSON, so `evlog()` takes no function. It takes:

| Option | Default | What it does |
| --- | --- | --- |
| `enabled` | `true` | `false` turns every call into a no-op. `useLogger(event)` still returns a logger |
| `env` | Detected | Environment context, such as `env: { service: 'my-app' }` |
| `pretty` | `true` in development | Tree output instead of JSON |
| `dev` | `'evlog'` | Development terminal output: `'evlog'`, `'nitro'`, `'both'`, or `{ frameworkOverlay, prettyError }` |
| `silent` | `false` | No console output. Events still reach the drain |
| `minLevel` | `'debug'` | Lowest level for the `log` API |
| `sampling` | None | Head rates and tail `keep` rules. See [Sampling](/events/sampling) |
| `redact` | `true` in production | See [Redaction](/events/redaction) |
| `include`, `exclude` | None | Route globs to log or skip. `exclude` wins |
| `routes` | None | A service name per route glob |
| `errorHandler` | `true` | `false` skips evlog's error handler |

`dev: 'evlog'` prints one error block with evlog's own stack and hides Nitro's error overlay. `'nitro'` keeps Nitro's stack and prints only `why` and `fix` from evlog. `'both'` prints the two.

## Route filters

```typescript [evlog.config.ts]
export default defineEvlog({
  include: ['/api/**'],
  exclude: ['/api/health'],
  routes: {
    '/api/auth/**': { service: 'auth-service' },
    '/api/payment/**': { service: 'payment-service' },
  },
})
```

A path that matches both `include` and `exclude` is excluded. On a filtered-out route, `useLogger(event)` still returns a logger. It accepts every call and emits nothing, and `log.fork()` still runs its function.

## Hooks

Three Nitro hooks run next to the config file, for what needs the Nitro app:

| Hook | Runs | Receives |
| --- | --- | --- |
| `evlog:emit:keep` | After the request ends, before sampling | `status`, `duration`, `path`, `method`, the logger's `context`, and `shouldKeep` to set |
| `evlog:enrich` | After redaction, before the console output and the drain | The event, the request, its safe headers and the response status |
| `evlog:drain` | After enrichment | The event, the request and its safe headers |

```typescript [server/plugins/evlog-drain.ts]
import { definePlugin } from 'nitro'
import type { DrainContext } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createDrainPipeline } from 'evlog/pipeline'

export default definePlugin((nitroApp) => {
  const pipeline = createDrainPipeline<DrainContext>({
    batch: { size: 50, intervalMs: 5000 },
    retry: { maxAttempts: 3 },
  })
  const drain = pipeline(createAxiomDrain())

  nitroApp.hooks.hook('evlog:drain', drain)
})
```

```typescript [server/plugins/evlog-keep.ts]
import { definePlugin } from 'nitro'

export default definePlugin((nitroApp) => {
  nitroApp.hooks.hook('evlog:emit:keep', (ctx) => {
    if (ctx.duration && ctx.duration > 2000) ctx.shouldKeep = true
    if (ctx.status && ctx.status >= 500) ctx.shouldKeep = true
  })
})
```

An `evlog:enrich` hook calls the [built-in enrichers](/events/enrichers) or sets fields on `ctx.event`. An enrich or drain hook that throws is caught and reported as `[evlog] enrich failed` or `[evlog] drain failed`, and the request is not affected.

## Deploy

Where the request has a `waitUntil`, as on Cloudflare Workers and Vercel Edge, the drain is registered with it and finishes after the response. Elsewhere evlog awaits it, so a function that freezes after the response does not lose the event. An error event is the exception: its drain never holds the error response back.

Every [pipeline](/drains/pipeline) that still holds events is flushed when the server closes, whether it came from `evlog.config.ts` or from an `evlog:drain` hook. [Serverless](/drains/pipeline#serverless) covers what a pipeline does at the end of a request.
