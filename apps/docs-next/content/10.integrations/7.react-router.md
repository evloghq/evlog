evlog runs as React Router middleware, which is behind a future flag:

```typescript [react-router.config.ts]
import type { Config } from '@react-router/dev/config'

export default {
  future: { v8_middleware: true },
} satisfies Config
```

```tsx [app/root.tsx]
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { evlog } from 'evlog/react-router'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

export const middleware: Route.MiddlewareFunction[] = [
  evlog(toMiddlewareOptions(config)),
]
```

React Router has three [modes](https://reactrouter.com/start/modes). The middleware API exists in Framework and Data modes only. In Declarative mode there is no server middleware: log from the browser with [browser events](/events/client), and batch to your server with the [HTTP drain](/drains/http).

## In a loader

```typescript [app/routes/users.$id.tsx]
import { loggerContext } from 'evlog/react-router'

export async function loader({ params, context }: Route.LoaderArgs) {
  const log = context.get(loggerContext)

  const user = await db.findUser(params.id)
  log.set({ user: { id: params.id, plan: user.plan } })

  return { user }
}
```

Actions read it the same way. Underneath, `useLogger()` from `evlog/react-router` returns the logger of the current request.

## Under the loader

`useLogger()` reads the request from `AsyncLocalStorage`, so a service does not need `context` passed down:

```typescript [app/services/user.server.ts]
import { useLogger } from 'evlog/react-router'

export async function findUser(userId: string) {
  const log = useLogger()
  log.set({ db: { query: 'findUser', userId } })
  return await db.users.find(userId)
}
```

Outside a request, `useLogger()` throws. It also throws on a route that `include` or `exclude` filters out, where `context.get(loggerContext)` is still there: it accepts every call and emits nothing. Code that can run on a filtered route reads the context.

## Background work

`log.fork(label, fn)` gives work that outlives the response its own event. Inside `fn`, `useLogger()` returns the forked logger:

```typescript [app/routes/orders.tsx]
import { loggerContext, useLogger } from 'evlog/react-router'
import type { Route } from './+types/orders'

export async function action({ context }: Route.ActionArgs) {
  const log = context.get(loggerContext)
  log.fork('background', async () => {
    const child = useLogger()
    child.set({ step: 'complete' })
  })
  return { ok: true }
}
```

The child event carries `operation: 'background'` and `_parentRequestId`. [After the event is emitted](/events#after-the-event-is-emitted) explains why the request's own logger is sealed by then.

## When a loader throws

What lands on the event depends on whether React Router lets the error reach the middleware:

| Route | What React Router does | The event |
| --- | --- | --- |
| A resource route, with no component | Lets the error through | Level `error`, the error under `error`, and `status` from the error's `status` or `statusCode`, `500` when it has neither |
| A route with a component | Catches the error and renders the nearest `ErrorBoundary` | The response's status, `500` for a thrown error, and no `error` field |

The middleware never changes the response: it records the error and rethrows it. To get the error on the event of a page route too, record it before you throw:

```typescript [app/routes/checkout.tsx]
import { loggerContext } from 'evlog/react-router'
import { createError } from 'evlog'

export async function loader({ context }: Route.LoaderArgs) {
  const log = context.get(loggerContext)
  log.set({ cart: { items: 3, total: 9999 } })

  const error = createError({
    message: 'Payment failed',
    status: 402,
    why: 'Card declined by issuer',
    fix: 'Try a different payment method',
    link: 'https://docs.example.com/payments/declined',
  })
  log.error(error)
  throw error
}
```

The event then has level `error` with `why`, `fix` and `link`. Its `status` is still the one React Router answered with.

## Streaming responses

A response with a `text/event-stream` or `application/x-ndjson` content type, chunked transfer encoding, or the AI SDK's stream header emits when its body finishes or the client disconnects. [AI SDK](/extend/ai-sdk) fields set during the stream land on the request's event. Any other response emits when the middleware gets it back.

## Options

Put options in `evlog.config.ts`: [Configuration](/reference/configuration) lists them. `evlog()` takes the request options:

| Option | What it does |
| --- | --- |
| `include`, `exclude` | Route globs to log or skip. `exclude` wins |
| `routes` | A service name per route glob, such as `'/api/auth/**': { service: 'auth-service' }` |
| `drain` | Where request events go. Without it, the drain given to `initLogger()` is used |
| `enrich` | Adds fields after the event is emitted, before the drain |
| `keep` | Custom tail sampling: set `ctx.shouldKeep = true` |
| `redact` | See [Redaction](/events/redaction) |
| `plugins` | See [Plugins](/extend/plugins), merged by name with the global ones |
| `waitUntil` | Keeps the runtime alive for the drain on a serverless platform |

An option you pass inline replaces the same option from the file. It is not merged:

```tsx [app/root.tsx]
export const middleware: Route.MiddlewareFunction[] = [
  evlog({
    ...toMiddlewareOptions(config),
    include: ['/api/**'],
    exclude: ['/_internal/**', '/health'],
    keep: (ctx) => {
      if (ctx.duration && ctx.duration > 2000) ctx.shouldKeep = true
    },
  }),
]
```

The [`evlog/vite` plugin](/extend/vite) is optional. It strips `log.debug()` from production builds and adds source locations, and it reads `evlog.config.ts` too. Keep the `initLogger()` call: it runs after the plugin's own start and replaces it.

## Deploy

On Vercel, the middleware finds the request's `waitUntil` in the Vercel Functions runtime, with no option. On another serverless platform, pass the platform's `waitUntil`. Without one, evlog awaits the drain before the response is returned.

On a Node server, a [pipeline](/drains/pipeline) that still holds events is flushed on `SIGTERM` and `SIGINT`, so you do not call `drain.flush()` yourself. [Serverless](/drains/pipeline#serverless) has the limits of a request-end flush.
