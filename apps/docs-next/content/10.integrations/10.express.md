Express does not load `evlog.config.ts` on its own, so the entry file passes it in two calls: one to start the logger, one for the middleware.

```typescript [src/index.ts]
import express from 'express'
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { evlog } from 'evlog/express'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

const app = express()
app.use(evlog(toMiddlewareOptions(config)))

app.listen(3000)
```

Routes registered before `app.use(evlog())` are not logged. [`evlog init`](/cli/init) writes `evlog.config.ts` and these lines for you. If you build with Vite, the [`evlog/vite` plugin](/extend/vite) reads the same file but cannot carry the drain, so keep the `initLogger()` call.

## In a route

```typescript [src/routes/users.ts]
app.get('/users/:id', async (req, res) => {
  const user = await db.findUser(req.params.id)
  req.log?.set({ user: { id: req.params.id, plan: user.plan } })

  res.json(user)
})
```

The package augments Express's `Request`, so `req.log` is typed without an annotation. Its type is `ForkableLogger | undefined`, hence the `?.`: the middleware leaves `req.log` unset on a route it does not log.

In a service the route calls, `useLogger()` from `evlog/express` returns the same logger without passing `req` down.

```typescript [src/services/user.ts]
import { useLogger } from 'evlog/express'

export async function findUser(id: string) {
  const log = useLogger()
  log.set({ user: { id } })

  const user = await db.findUser(id)
  log.set({ user: { name: user.name, plan: user.plan } })

  return user
}
```

`useLogger()` reads the logger from `AsyncLocalStorage`. It throws outside a request and on a route the middleware does not log. `useLogger<MyFields>()` types the fields you set. See [Typed fields](/events/typed-fields).

## Background work

The request's event is sealed once it is emitted, so work that outlives the response needs its own. `req.log.fork(label, fn)` runs `fn` under a forked logger, and `useLogger()` returns that logger inside it:

```typescript [src/index.ts]
import { evlog, useLogger } from 'evlog/express'

app.post('/orders', (req, res) => {
  req.log?.set({ orderId: 'ord_1' })
  req.log?.fork('fulfill_order', async () => {
    const log = useLogger()
    log.set({ step: 'inventory_ok' })
  })
  res.json({ ok: true })
})
```

The fork emits a second event when `fn` settles, with `operation: 'fulfill_order'` and `_parentRequestId` set to the request's `requestId`. A `set()` on the request logger after its event is emitted is dropped with an `[evlog]` warning. [After the event is emitted](/events#after-the-event-is-emitted) covers both, and when to await the fork.

## Errors

Express hands errors to a four-argument middleware. Record the error there and answer with its fields:

```typescript [src/index.ts]
import { createError, parseError } from 'evlog'

app.post('/checkout', () => {
  throw createError({ status: 402, message: 'Payment failed', why: 'Card declined by issuer', fix: 'Try a different payment method' })
})

app.use((err, req, res, next) => {
  req.log?.error(err)
  const { status, message, why, fix, link } = parseError(err)
  res.status(status).json({ message, why, fix, link })
})
```

The evlog middleware does not see what a route throws: Express passes it straight to the error middleware. Without the `req.log?.error(err)` call, the event carries the response status and no `error` field. The event's `status` is always the one the response was sent with.

## When the event is emitted

The middleware emits when the response has been written in full, so a streamed response emits when it ends, with the fields set while streaming. When the client disconnects first, it emits at that moment with `connectionClosed: true`.

## Options

`evlog()` takes the request options of `evlog.config.ts`, which `toMiddlewareOptions(config)` passes. [Configuration](/reference/configuration) lists the logger options that go to `initLogger()`.

| Option | Default | What it does |
| --- | --- | --- |
| `include` | Every route | Globs of the routes to log. `*` stops at a `/`, `**` crosses it |
| `exclude` | None | Globs of the routes to skip. Wins over `include` |
| `routes` | None | A `service` name per route glob. The first glob that matches wins, so list the specific ones first |
| `drain` | The drain given to `initLogger()` | Receives every emitted event. See [Drains](/drains) |
| `enrich` | None | Adds fields after redaction, before the console output and the drain. See [Enrichers](/events/enrichers) |
| `keep` | None | Tail sampling: set `ctx.shouldKeep = true` to keep an event the rates would drop. See [Sampling](/events/sampling) |
| `redact` | The `initLogger()` setting | Redacts the event when `initLogger()` did not: `true` for the built-in patterns, or a config. See [Redaction](/events/redaction) |
| `plugins` | None | Merged with the plugins given to `initLogger()`. A plugin here replaces a global one of the same `name` |
| `waitUntil` | The Vercel Functions runtime, when there is one | Registers the drain with the runtime instead of awaiting it |

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'

export default defineEvlog({
  service: 'my-api',
  include: ['/api/**'],
  exclude: ['/_internal/**', '/health'],
  routes: {
    '/api/auth/**': { service: 'auth-service' },
    '/api/payment/**': { service: 'payment-service' },
  },
  keep: (ctx) => {
    if (ctx.duration && ctx.duration > 2000) ctx.shouldKeep = true
  },
})
```

A field you pass next to the config replaces that field: `evlog({ ...toMiddlewareOptions(config), exclude: ['/health'] })` uses your `exclude`, not the file's. The path the globs match is the pathname of `req.originalUrl`, without the query string. The event's `requestId` is the `x-request-id` header when the caller sends one, and a random UUID otherwise.

::callout{icon="i-lucide-triangle-alert" color="neutral"}
On a route that `include` or `exclude` filters out, `req.log` is `undefined` and `useLogger()` throws. Code shared between logged and skipped routes reads `req.log?.` and does not call `useLogger()`. `req.log?.fork()` does not run `fn` there, so do not put work that must happen inside a fork on a route you exclude.
::

## Shutdown and serverless

The middleware emits after the response is sent, so the drain never delays it. A [pipeline](/drains/pipeline) that holds events is flushed on `SIGTERM`, `SIGINT` and `beforeExit`. `process.exit()` skips that, so call `await drain.flush()` before it.

On Vercel Functions the middleware finds the request's `waitUntil` in the runtime and keeps the instance alive until the drain is done. Anywhere else, pass the platform's `waitUntil` as an option. On AWS Lambda through `serverless-http`, the response is already written when the event is emitted, so evlog cannot hold the function open: see [Serverless](/drains/pipeline#serverless).

## Receive browser logs

[`evlog/http`](/drains/http) posts batches of browser events to a route you write. It receives a JSON array of `DrainContext`:

```typescript [src/index.ts]
import type { DrainContext } from 'evlog'

app.post('/v1/ingest', express.json(), (req, res) => {
  const batch = req.body as DrainContext[]
  for (const ctx of batch) {
    console.log('[BROWSER]', JSON.stringify(ctx.event))
  }
  res.sendStatus(204)
})
```

The [Express example](https://github.com/evloghq/evlog/tree/main/examples/express) is a complete app.
