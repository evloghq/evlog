Every framework integration does the same three things: it creates a logger when the request starts, gives your handler a way to reach it, and emits the event when the response ends, with the status, the duration and any error.

Two things differ from one framework to the next: how you start evlog, and how a handler reaches the logger. The rest is the same everywhere: `log.set()`, `createError()` and `parseError()` are the core API, and every integration reads its options from one [`evlog.config.ts`](/reference/configuration). Nuxt, Nitro and TanStack Start load that file for you. The other frameworks import it.

| Framework | Import | Start | In a handler |
| --- | --- | --- | --- |
| [Nuxt](/integrations/nuxt) | `evlog/nuxt` | Module | `useLogger(event)` |
| [Next.js](/integrations/next) | `evlog/next` | `createEvlog()` | `useLogger()` |
| [Hono](/integrations/hono) | `evlog/hono` | Middleware | `c.get('log')` |
| [Nitro](/integrations/nitro) | `evlog/nitro` | Module | `useLogger(event)` |
| [SvelteKit](/integrations/sveltekit) | `evlog/sveltekit` | Hooks | `event.locals.log` |
| [TanStack Start](/integrations/tanstack-start) | `evlog/nitro` | Module | `useRequest().context.log` |
| [React Router](/integrations/react-router) | `evlog/react-router` | Middleware | `context.get(loggerContext)` |
| [NestJS](/integrations/nestjs) | `evlog/nestjs` | `EvlogModule.forRoot()` | `useLogger()` |
| [Express](/integrations/express) | `evlog/express` | Middleware | `req.log` |
| [Fastify](/integrations/fastify) | `evlog/fastify` | Plugin | `request.evlog` |
| [Elysia](/integrations/elysia) | `evlog/elysia` | Plugin | `log` in the context |
| [oRPC](/integrations/orpc) | `evlog/orpc` | Handler wrapper | `context.log` |
| [Effect](/integrations/effect) | `evlog/effect` | Layer | `yield* EvlogLogger` |
| [Cloudflare Workers](/integrations/cloudflare-workers) | `evlog/workers` | `withEvlog()` | The handler's fourth argument |
| [Standalone](/integrations/standalone), [AWS Lambda](/integrations/aws-lambda), [Astro](/integrations/astro) | `evlog` | `initLogger()` | `createLogger()`, `createRequestLogger()` |

The framework accessor (`c.get('log')`, `req.log`) is the idiomatic path inside a handler. `useLogger()` reaches the same logger from the layers underneath, a service or a repository, through `AsyncLocalStorage`. Workers and Effect have no `useLogger()`: Workers avoids `node:async_hooks`, and Effect carries the logger in its context.

Three notes on the table:

- On Nuxt, Nitro and TanStack Start, `useLogger()` with no argument needs Nitro's `experimental.asyncContext`. `useLogger(event)` works without it.
- `log.fork(label, fn)` gives background work its own event on every integration except Effect, which nests `withLogger` instead, and the three in the last row. [After the event is emitted](/events#after-the-event-is-emitted) says how `fn` reaches the forked logger on each.
- Standalone, AWS Lambda and Astro are guides on the core API. You create the logger and emit it yourself, and there is no `useLogger()` and no `log.fork()`.

TanStack Router on its own is a client-side router with nothing to log on a server. The TanStack Start page covers the full-stack setup.

## Beyond frameworks

| Integration | What it adds | Page |
| --- | --- | --- |
| AI SDK | Tokens, tool calls, streaming timings and cost on the event | [AI SDK](/extend/ai-sdk) |
| Better Auth | The signed-in user, the session and the session lookup time on every event | [Better Auth](/extend/better-auth) |
| eve | One event per agent turn: tokens, tool calls and the errors tools throw | [eve](/extend/eve) |
| Vite | Starts the logger at build time, strips `log.debug()` from production builds and injects source locations | [Vite](/extend/vite) |

On Nuxt you do not add the Vite plugin: the `evlog/nuxt` module takes the same options and runs the same transforms.

A framework that is not listed can build the same contract with `defineFrameworkIntegration` from `evlog/toolkit`, which is in beta: see [Custom integration](/extend/custom-integration).
