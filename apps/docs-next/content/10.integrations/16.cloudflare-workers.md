Workers get the logger as an argument rather than from `useLogger()`, so `evlog/workers` needs no `nodejs_compat` flag:

```typescript [src/worker.ts]
import { toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { initWorkersLogger, withEvlog } from 'evlog/workers'
import config from '../evlog.config'

initWorkersLogger(toLoggerConfig(config))

export default withEvlog(async (request, env, ctx, log) => {
  const user = await env.DB.prepare('SELECT * FROM users WHERE id = ?').bind(1).first()
  log.set({ user: { id: user.id, plan: user.plan } })

  return Response.json(user)
}, toMiddlewareOptions(config))
```

`initWorkersLogger()` is `initLogger()` with `pretty` and `stringify` forced to `false`, whatever the file says, so the Workers runtime receives each event as an object. Call it once at module scope. [`evlog init`](/cli/init) writes `evlog.config.ts` and these lines for you.

## What the wrapper does

`withEvlog` emits one event per request when the handler returns, and defers it until a streaming body completes. It registers each drain call with `ctx.waitUntil`, so a send to Axiom or PostHog finishes after the response has gone.

The event carries the method, the path, `cf-ray`, `traceparent` and the safe fields of `request.cf`. `requestId` is the `x-request-id` header when the caller sends one, `cf-ray` otherwise.

| Field | From |
| --- | --- |
| `method`, `path` | The request |
| `requestId` | `x-request-id`, then `cf-ray`, then a random UUID |
| `cfRay` | The `cf-ray` header |
| `traceparent` | The `traceparent` header |
| `colo`, `country`, `asn` | `request.cf`, when it has them |

A response counts as streaming when its `content-type` is `text/event-stream` or `application/x-ndjson`, when it has the `x-vercel-ai-ui-message-stream` header, or when `transfer-encoding` is `chunked`. The stream's lifetime is registered with `ctx.waitUntil` too.

To own the emit yourself, use `defineWorkerFetch` and call `log.emit()` before returning.

## Background work

Workers has no `useLogger()`, so `log.fork(label, fn)` hands the forked logger to `fn` as its argument:

```typescript [src/worker.ts]
export default withEvlog(async (request, _env, _ctx, log) => {
  const order = await request.json()

  log.fork('send_receipt', async (child) => {
    child.set({ receipt: { orderId: order.id } })
    await sendReceipt(order)
  })

  return Response.json({ ok: true })
})
```

The child emits its own event when `fn` settles, with `operation: 'send_receipt'` and `_parentRequestId` set to the request's `requestId`. The fork is registered with `ctx.waitUntil`, so the Worker stays alive until the child drains. It returns a promise that never rejects: await it when the child must drain before the response. [After the event is emitted](/events#after-the-event-is-emitted) covers what happens to a `set()` that comes too late.

## When the handler throws

`withEvlog` records the error on the event, sets `status` from the error's `status` or `statusCode`, `500` when it has neither, emits, and rethrows, so the runtime answers the uncaught exception itself. To answer with the error's fields, catch it in the handler, call `log.error()`, and return a response built with `parseError()`. The event then carries the status of that response. [Errors](/errors) has the fields.

## Options

`withEvlog(handler, options)` takes the request options of `evlog.config.ts`, which `toMiddlewareOptions(config)` passes. [Configuration](/reference/configuration) lists the logger options that go to `initWorkersLogger()`.

| Option | Default | What it does |
| --- | --- | --- |
| `include` | Every route | Globs of the routes to log. `*` stops at a `/`, `**` crosses it |
| `exclude` | None | Globs of the routes to skip. Wins over `include` |
| `routes` | None | A `service` name per route glob. The first glob that matches wins, so list the specific ones first |
| `drain` | The drain given to `initWorkersLogger()` | Receives every emitted event. See [Drains](/drains) |
| `enrich` | None | Adds fields after redaction, before the console output and the drain. See [Enrichers](/events/enrichers) |
| `keep` | None | Tail sampling: set `ctx.shouldKeep = true` to keep an event the rates would drop. See [Sampling](/events/sampling) |
| `redact` | The `initWorkersLogger()` setting | Redacts the event when the logger config did not: `true` for the built-in patterns, or a config. See [Redaction](/events/redaction) |
| `plugins` | None | Merged with the plugins given to `initWorkersLogger()`. A plugin here replaces a global one of the same `name` |
| `waitUntil` | `ctx.waitUntil` | Registers the drain with the runtime instead of awaiting it |

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'

export default defineEvlog({
  service: 'my-worker',
  drain: createAxiomDrain(),
  exclude: ['/health'],
  routes: { '/api/**': { service: 'api' } },
  redact: true,
  enrich: (ctx) => {
    ctx.event.colo = ctx.event.colo ?? 'unknown'
  },
  keep: (ctx) => {
    if (ctx.duration && ctx.duration > 1000) ctx.shouldKeep = true
  },
})
```

On a route that `include` or `exclude` filters out, the handler still runs and still receives a logger. Nothing is emitted, and `fn` passed to `log.fork()` still runs.

::callout{icon="i-lucide-triangle-alert" color="neutral"}
The config file is bundled into the Worker and evaluated there. A `process.env` read in it, and the keys a drain such as `createAxiomDrain()` reads from the environment, only see your Worker's variables when Cloudflare exposes them on `process.env`, which takes the `nodejs_compat` flag.
::

## Typing

`withEvlog` and `defineWorkerFetch` take two type arguments, the `env` and the `ctx` of the handler. Unannotated, `ctx` only has `waitUntil`. Annotate it, for example as `ExecutionContext` from `@cloudflare/workers-types`, to reach the rest of Cloudflare's context such as `ctx.exports` or `ctx.props`. The package does not depend on `@cloudflare/workers-types`.

The fourth argument of a `withEvlog` handler is a `WorkersRequestLogger`. `createWorkersLogger<MyFields>(request)` types the fields you set: see [Typed fields](/events/typed-fields).

## Own the emit

`defineWorkerFetch` passes `ctx` to the logger for you and leaves `log.emit()` to you, on every path that returns:

```typescript [src/worker.ts]
import { createError, parseError, toLoggerConfig } from 'evlog'
import { defineWorkerFetch, initWorkersLogger } from 'evlog/workers'
import config from '../evlog.config'

initWorkersLogger(toLoggerConfig(config))

export default defineWorkerFetch(async (request, env, _ctx, log) => {
  try {
    const body = await request.json()
    log.set({ payment: { amount: body.amount } })

    if (body.amount <= 0) {
      throw createError({
        status: 400,
        message: 'Invalid payment amount',
        why: 'The amount must be a positive number',
        fix: 'Pass a positive integer in cents',
      })
    }

    log.emit()
    return Response.json({ success: true })
  } catch (error) {
    log.error(error instanceof Error ? error : new Error(String(error)))
    log.emit()
    const parsed = parseError(error)
    return Response.json({
      message: parsed.message,
      why: parsed.why,
      fix: parsed.fix,
    }, { status: parsed.status })
  }
})
```

`createWorkersLogger(request, options)` is the logger on its own, for a `fetch` that neither helper wraps:

| Option | Default | What it does |
| --- | --- | --- |
| `requestId` | The `cf-ray` header | The event's `requestId`. `x-request-id` is not read here |
| `headers` | None | Names of the request headers to copy to the event, under `requestHeaders` |
| `executionCtx` | None | The `ctx` of the `fetch` handler. Drains are registered with its `waitUntil` |
| `waitUntil` | None | The same, as a bound function: `ctx.waitUntil.bind(ctx)` |

On this path you run the lifecycle yourself, which has three consequences:

- `include`, `exclude`, `routes`, `enrich` and `keep` do not apply, and neither does anything else you would pass to `withEvlog`. What you gave `initWorkersLogger()` does: sampling, redaction and the drain.
- The logger has no `fork()`.
- Without `executionCtx` or `waitUntil`, nothing keeps the Worker alive for the drain, and the send can be cut off when the response returns.

## Deploy

Cloudflare writes its own invocation log for each request. Turn it off to avoid a duplicate of every event:

```toml [wrangler.toml]
[observability]
enabled = false
```

A [pipeline](/drains/pipeline) drain works on Workers: `withEvlog` sends what it holds when the request ends and keeps the Worker alive until those events are delivered or dropped. That flush stops 25 seconds after the request ends, and Workers Free allows 50 subrequests per request. [Serverless](/drains/pipeline#serverless) has every limit.

Hono and Effect have their own integrations that run on Workers: see [Hono](/integrations/hono#on-workers-and-serverless) and [Effect](/integrations/effect#on-workers-and-durable-objects).
