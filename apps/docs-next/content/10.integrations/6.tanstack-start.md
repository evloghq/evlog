TanStack Start serves through Nitro, so evlog plugs in as a Nitro module. Nitro's async context must be on, so a route can reach the request it is serving:

```typescript [nitro.config.ts]
import { defineConfig } from 'nitro'
import evlog from 'evlog/nitro'

export default defineConfig({
  experimental: { asyncContext: true },
  modules: [evlog()],
})
```

Register the error handler as server middleware on the root route, so a thrown error lands on the event:

```tsx [src/routes/__root.tsx]
import { createRootRoute } from '@tanstack/react-router'
import { createMiddleware } from '@tanstack/react-start'
import { evlogErrorHandler } from 'evlog/nitro'

export const Route = createRootRoute({
  server: {
    middleware: [createMiddleware().server(evlogErrorHandler)],
  },
})
```

Create `nitro.config.ts` at the project root. The `nitro()` plugin that `npm create @tanstack/start` puts in `vite.config.ts` picks it up, and the module finds `evlog.config.ts` on its own.

This page is for TanStack Start. TanStack Router on its own is a client-side router with no server to log from: use [browser events](/events/client) there.

## In a server route

```typescript [src/routes/api/hello.ts]
import { createFileRoute } from '@tanstack/react-router'
import { useRequest } from 'nitro/context'
import type { RequestLogger } from 'evlog'

export const Route = createFileRoute('/api/hello')({
  server: {
    handlers: {
      GET: async () => {
        const log = useRequest().context.log as RequestLogger
        log.set({ user: { id: 'user_123', plan: 'pro' } })

        return Response.json({ ok: true })
      },
    },
  },
})
```

Server functions run in the same request, so `useRequest()` reaches the same logger there.

`useRequest()` is an experimental Nitro 3 feature built on `AsyncLocalStorage`. It works on Node.js and Bun. Without `experimental.asyncContext` it has no request to return, and the route cannot reach its logger.

## Under the route

With the async context on, `useLogger()` from `evlog/nitro` takes no argument and returns the same logger, already typed. Use it in the functions a route calls:

```typescript [src/server/users.ts]
import { useLogger } from 'evlog/nitro'

export async function findUser(id: string) {
  const log = useLogger()
  log.set({ user: { id } })

  return await db.findUser(id)
}
```

## Background work

`log.fork(label, fn)` runs work that outlives the response under its own event. `fn` receives the forked logger:

```typescript [src/server/receipts.ts]
import { useLogger } from 'evlog/nitro'

export function queueReceipt() {
  const log = useLogger()
  log.fork('send_receipt', async (child) => {
    child.set({ receipt: { sent: true } })
    await sendReceipt()
  })
}
```

The child event carries `operation: 'send_receipt'` and `_parentRequestId`, and is registered with `waitUntil` where the runtime provides one. Inside `fn`, `useLogger()` and `useRequest()` still return the parent logger, so use the `child` argument. The `RequestLogger` type declares `fork` without that argument: take the logger from `useLogger()`, or cast to `NitroRequestLogger` from `evlog/nitro`.

## When a handler throws

TanStack Start catches a thrown error before Nitro's error handler runs, and drops `why`, `fix` and `link` on the way. `evlogErrorHandler` runs first: it records an `EvlogError` on the request's event and answers with JSON, at the status the error carries.

```typescript [src/routes/api/checkout.ts]
import { createError } from 'evlog'

throw createError({
  message: 'Payment failed',
  status: 402,
  why: 'Card declined by issuer',
  fix: 'Try a different payment method',
  link: 'https://docs.example.com/payments/declined',
})
```

The body has `name`, `message`, `status`, and `why`, `fix` and `link` under `data`. Any other error is rethrown untouched, and TanStack Start answers it. On the client, `parseError()` reads the body back:

```tsx [src/routes/checkout.tsx]
import { parseError } from 'evlog'

try {
  const res = await fetch('/api/checkout', {
    method: 'POST',
    body: JSON.stringify({ userId: 'user_123' }),
  })
  if (!res.ok) throw { data: await res.json(), status: res.status }
} catch (error) {
  const { message, status, why, fix, link } = parseError(error)
}
```

### Errors from server functions

A server function serializes what it throws, and TanStack Start only knows how to send an `Error`. An `EvlogError` reaches the client as a plain `Error` with its `message`, and `status`, `why`, `fix` and `link` are dropped. Register a serialization adapter in `src/start.ts` so it crosses the wire as an `EvlogError`:

```typescript [src/start.ts]
import { createSerializationAdapter } from '@tanstack/react-router'
import { createStart } from '@tanstack/react-start'
import { createError, EvlogError, parseError } from 'evlog'

const evlogErrorAdapter = createSerializationAdapter({
  key: 'evlog-error',
  test: EvlogError.isEvlogError,
  toSerializable: (error) => {
    const { message, status, code, why, fix, link } = parseError(error)
    return { message, status, code, why, fix, link }
  },
  fromSerializable: fields => createError(fields),
})

export const startInstance = createStart(() => ({
  serializationAdapters: [evlogErrorAdapter],
}))
```

Three limits of the adapter:

- It sends the guidance fields, not `data`. TanStack's types reject `Record<string, unknown>` as possibly not serializable, so list each `data` field you want on the client.
- `EvlogError.isEvlogError` checks a brand, not the class, so it matches an error from another copy of `evlog`. An error created by a copy older than 2.23.0 carries no brand and is not matched.
- `createSerializationAdapter` is not in TanStack's docs yet ([TanStack/router#6466](https://github.com/TanStack/router/discussions/6466)).

A server function answers its RPC request with HTTP `200` and the error in the body. `evlogErrorHandler` never sees it, and the event would record a success. Call `log.error(error)` before the `throw`:

```typescript [src/utils/checkout.ts]
import { createServerFn } from '@tanstack/react-start'
import { useRequest } from 'nitro/context'
import { createError } from 'evlog'
import type { RequestLogger } from 'evlog'

export const checkout = createServerFn({ method: 'POST' })
  .handler(async () => {
    const log = useRequest().context?.log as RequestLogger
    log.set({ cart: { items: 3, total: 9999 } })

    const error = createError({
      message: 'Payment failed',
      status: 402,
      why: 'Card declined by issuer',
      fix: 'Try a different payment method',
      link: 'https://docs.example.com/payments/declined',
    })
    log.error(error)
    throw error
  })
```

The event is then an error, and its status stays `200`:

```bash [Terminal output]
17:29:28.530 ERROR [my-app] POST /_serverFn/eyJmaWxlIjoi... 200 in 51ms
  ├─ error: Payment failed
  │ Why: Card declined by issuer
  │ Fix: Try a different payment method
  │ More: https://docs.example.com/payments/declined
  ├─ requestId: 4fc0f3f6-a61a-4c66-9be9-5d0e647ad37c
  └─ cart: items=3 total=9999
```

On the client, the caught value passes `EvlogError.isEvlogError(error)`, and `error.status`, `error.why`, `error.fix` and `error.link` are set again.

## Options, filters and hooks

The module is the Nitro one, so everything on the [Nitro page](/integrations/nitro) applies: the [module options](/integrations/nitro#module-options), streaming responses, the three hooks and the deployment notes. Options go in `evlog.config.ts`, and what you pass to `evlog()` in `nitro.config.ts` overrides the file key by key. The file's `drain`, `enrich` and `keep` always run, alongside any `evlog:*` hook.

```typescript [evlog.config.ts]
export default defineEvlog({
  service: 'my-app',
  include: ['/api/**'],
  exclude: ['/_internal/**', '/health'],
  routes: {
    '/api/auth/**': { service: 'auth-service' },
    '/api/payment/**': { service: 'payment-service' },
  },
})
```

A Nitro plugin reaches the `evlog:drain`, `evlog:enrich` and `evlog:emit:keep` hooks:

```typescript [server/plugins/evlog-enrich.ts]
import { definePlugin } from 'nitro'
import { createUserAgentEnricher, createRequestSizeEnricher } from 'evlog/enrichers'

export default definePlugin((nitroApp) => {
  const enrichers = [createUserAgentEnricher(), createRequestSizeEnricher()]

  nitroApp.hooks.hook('evlog:enrich', (ctx) => {
    for (const enricher of enrichers) enricher(ctx)
  })
})
```

A [pipeline](/drains/pipeline) that still holds events is flushed when the server closes, so you do not call `drain.flush()` yourself.

TanStack Start builds with Vite, so the [`evlog/vite` plugin](/extend/vite) can sit next to the TanStack Start plugin in `vite.config.ts` to strip `log.debug()` from production builds and add source locations.
