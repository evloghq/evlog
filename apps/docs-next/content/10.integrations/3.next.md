Next.js has no request middleware evlog can hook into for every route, so you create one instance and wrap the handlers you want logged.

```typescript [lib/evlog.ts]
import { createEvlog } from 'evlog/next'
import config from '../evlog.config'

export const { withEvlog, useLogger, log, createError } = createEvlog(config)
```

`createEvlog(config)` starts the logger the first time `lib/evlog.ts` is imported. Routes wrapped with `withEvlog` use the file's route filters, drain, `enrich` and `keep`.

## In a route

```typescript [app/api/checkout/route.ts]
import { withEvlog, useLogger, createError } from '@/lib/evlog'

export const POST = withEvlog(async (req) => {
  const log = useLogger()
  const { cartId } = await req.json()

  const cart = await db.findCart(cartId)
  log.set({ cart: { items: cart.items.length, total: cart.total } })

  if (!cart.items.length) {
    throw createError({ status: 400, message: 'Empty cart', fix: 'Add an item before checking out' })
  }

  return Response.json({ ok: true })
})
```

`useLogger()` takes no argument: inside `withEvlog`, it reads the request from `AsyncLocalStorage`, so a service called from the route reaches the same logger.

Outside `withEvlog`, `useLogger()` throws. That includes a wrapped route that `include` or `exclude` filters out, and every route when `enabled` is `false`: the handler runs, with no logger to read.

## Server actions

`withEvlog` wraps a server action the same way:

```typescript [app/actions/checkout.ts]
'use server'
import { withEvlog, useLogger } from '@/lib/evlog'

export const checkout = withEvlog(async (formData: FormData) => {
  const log = useLogger()
  log.set({ action: 'checkout', cartId: formData.get('cartId') })
  // ...
})
```

An action receives no `Request`, so its event has the method `UNKNOWN` and the path `/`, and route filters match against `/`. Set a field such as `action` to tell actions apart.

## Background work

`log.fork(label, fn)` gives work that outlives the response its own event. Inside `fn`, `useLogger()` returns the forked logger:

```typescript [app/api/orders/route.ts]
import { withEvlog, useLogger } from '@/lib/evlog'

export const POST = withEvlog(async () => {
  const log = useLogger()
  log.fork!('enqueue', async () => {
    const child = useLogger()
    child.set({ job: 'queued' })
  })
  return Response.json({ ok: true })
})
```

`useLogger()` types `fork` as optional, hence the `!`. The child event carries `operation: 'enqueue'` and `_parentRequestId`, and the fork is registered with Next's `after()`, so the function stays alive until the child has drained. [After the event is emitted](/events#after-the-event-is-emitted) has the rest.

## When a handler throws

`withEvlog` records the error on the event, with the status from the error's `status` or `statusCode`, and `500` when it has neither. What the caller receives depends on what was thrown:

| Thrown | In a route handler | In a server action |
| --- | --- | --- |
| An `EvlogError` | A JSON response with the error's status: `name`, `message`, `status`, and `why`, `fix` and `link` under `data` | Rethrown |
| Another error | Rethrown, and Next.js answers | Rethrown |
| `redirect()`, `notFound()`, `forbidden()`, `unauthorized()` | Rethrown untouched, and no event is emitted | The same |

The last row is deliberate: Next.js throws those as control flow and turns them into a real response, so evlog does not log them as errors. A route that redirects leaves no event.

On the client, `parseError()` from `evlog` reads the JSON back into `message`, `status`, `why`, `fix` and `link`: see [Errors](/errors#read-it-on-the-client).

## Streaming responses

When a handler returns a streamed `Response` (a `text/event-stream` or `application/x-ndjson` content type, chunked transfer encoding, or the AI SDK's stream header), the event is emitted when the body finishes or the client disconnects. [AI SDK](/integrations/ai-sdk) fields set during the stream land on it, and an error that breaks the stream is recorded on it.

## Options

`createEvlog()` takes the options of `evlog.config.ts`, which [Configuration](/reference/configuration) describes:

| Option | Default | What it does |
| --- | --- | --- |
| `service` | `SERVICE_NAME` or `'app'` | Service name on every event |
| `env` | Detected | Full environment context, such as `env: { environment: 'staging' }` |
| `enabled` | `true` | `false` runs every handler without logging |
| `pretty` | `true` in development | Tree output instead of JSON |
| `silent` | `false` | No console output. Events still reach the drain |
| `stringify` | `true` | Print JSON strings when `pretty` is off |
| `minLevel` | `'debug'` | Lowest level for the `log` API |
| `sampling` | None | Head rates and tail `keep` rules. See [Sampling](/events/sampling) |
| `redact` | `true` in production | See [Redaction](/events/redaction) |
| `include`, `exclude` | None | Route globs to log or skip. `exclude` wins |
| `routes` | None | A service name per route glob |
| `drain` | None | Where request events go |
| `enrich` | None | Adds fields before the drain |
| `keep` | None | Custom tail sampling: set `ctx.shouldKeep = true` |
| `plugins` | None | See [Plugins](/reference/plugins) |
| `waitUntil` | None | Keeps the runtime alive for the drain. Next's `after()` replaces it wherever `after()` exists |

Two things `createEvlog()` does not do on its own. It does not read the file's top-level `environment`, and its `drain` receives request events only: a `log.info()` call is printed, not drained. [Starting the logger from `instrumentation.ts`](#start-the-logger-from-evlogconfigts) covers both.

## Errors outside a wrapped route

`instrumentation.ts` reports what `withEvlog` never sees, such as a render error in a server component. `defineNodeInstrumentation` loads evlog in the Node.js runtime only:

```typescript [instrumentation.ts]
import { defineNodeInstrumentation } from 'evlog/next/instrumentation'

export const { register, onRequestError } = defineNodeInstrumentation({
  service: 'my-app',
  captureOutput: true,
})
```

To run your own startup code next to evlog, pass a loader function instead of the options, and call `createInstrumentation()` from `evlog/next/instrumentation/create` inside it.

Next.js calls the two exports itself:

- `register()` runs once when the server starts. It starts the logger with these options and locks it, so a later `createEvlog()` keeps this configuration instead of replacing it.
- `onRequestError()` runs on every unhandled request error, server components included. It logs an error with the `message`, `digest`, `stack`, `path`, `method`, `routerKind`, `routePath`, `routeType` and `renderSource`.

Next.js evaluates `instrumentation.ts` in the Edge runtime too. There both exports do nothing, and the Node-only code stays out of the Edge bundle.

Both functions take `enabled`, `service`, `env`, `pretty`, `silent`, `sampling`, `minLevel`, `stringify`, `redact` and `drain`, plus:

| Option | Default | What it does |
| --- | --- | --- |
| `captureOutput` | `false` | `true` turns `stdout` and `stderr` writes into `log.info` and `log.error` events with a `source` field. Node.js runtime only |
| `captureOutput.stdout` | `true` | Capture `stdout` writes |
| `captureOutput.stderr` | `true` | Capture `stderr` writes |
| `captureOutput.ignore` | Next.js Edge bundler warnings | Strings or regexes. A matching write is not turned into an event |

A captured write is printed once, as the structured line. With `silent: true`, the raw write goes through and the event still reaches the drain. evlog's own output is never captured, so a drain receives each wide event once.

### Start the logger from evlog.config.ts

To give the instrumentation the same file as your routes, create both in `lib/evlog.ts` and load that module from `instrumentation.ts`:

```typescript [lib/evlog.ts]
import { toLoggerConfig } from 'evlog'
import { createEvlog } from 'evlog/next'
import { createInstrumentation } from 'evlog/next/instrumentation/create'
import config from '../evlog.config'

export const { register, onRequestError } = createInstrumentation({
  ...toLoggerConfig(config),
  captureOutput: true,
})

export const { withEvlog, useLogger, log, createError } = createEvlog(config)
```

```typescript [instrumentation.ts]
import { defineNodeInstrumentation } from 'evlog/next/instrumentation'

export const { register, onRequestError } = defineNodeInstrumentation(() => import('./lib/evlog'))
```

`register()` starts the logger from the file before any route runs, `environment` and the drain for `log.*` calls included, and `createEvlog()` takes the route filters, `enrich` and `keep` from it. [`evlog init`](/cli/init#what-each-framework-gets) writes both files for you.

To also serve the local [stream](/drains/stream), replace `createInstrumentation` with `defineStreamedInstrumentation` from `evlog/next/stream` and pass `stream: true`.

## Middleware

`evlogMiddleware()` sets an `x-request-id` header, reusing the incoming one when there is one, and an `x-evlog-start` header. `withEvlog` then uses that request ID for the event and records the start time as `middlewareStart`:

```typescript [proxy.ts]
import { evlogMiddleware } from 'evlog/next'

export const proxy = evlogMiddleware()

export const config = {
  matcher: ['/api/:path*'],
}
```

Older versions of Next.js name the file `middleware.ts` and the export `middleware`. `evlogMiddleware()` takes `include` and `exclude` globs of its own, and passes a filtered-out request through without the headers.

## Browser logs

`EvlogProvider` starts the [browser logger](/events/client) for every client component under it:

```tsx [app/layout.tsx]
import { EvlogProvider } from 'evlog/next/client'

export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <EvlogProvider service="my-app" transport={{ enabled: true }}>
          {children}
        </EvlogProvider>
      </body>
    </html>
  )
}
```

| Prop | Default | What it does |
| --- | --- | --- |
| `service` | `'client'` | Service name on browser events |
| `enabled` | `true` | `false` turns every client `log` call into a no-op |
| `console` | `true` | `false` stops the console output. Events still go to the transport |
| `pretty` | `true` | Formatted console output |
| `minLevel` | `'debug'` | Lowest level that is printed and sent |
| `transport` | Off | `enabled`, `endpoint` (`'/api/_evlog/ingest'`) and `credentials` (`'same-origin'`) |

Client components import `log`, `setIdentity`, `clearIdentity` and `setMinLevel` from `evlog/next/client`:

```tsx [app/components/Dashboard.tsx]
'use client'
import { useEffect } from 'react'
import { log, setIdentity, clearIdentity } from 'evlog/next/client'

export function Dashboard({ user }: { user: { id: string } }) {
  // Set identity once - all subsequent logs include it
  useEffect(() => {
    setIdentity({ userId: user.id })
    return () => clearIdentity()
  }, [user.id])

  return (
    <button onClick={() => log.info({ action: 'export_clicked', format: 'csv' })}>
      Export
    </button>
  )
}
```

::callout{icon="i-lucide-triangle-alert" color="neutral"}
`evlog/next` registers no ingest route. With `transport.enabled`, the browser posts each event to `transport.endpoint`, and the request fails silently until you create a POST route there. [Browser events](/events/client#on-other-frameworks) shows that route.
::

For batches, retries and a flush when the page hides, use the [HTTP drain](/drains/http) instead.

## Deploy

`withEvlog` registers drain work with Next's `after()`, so the response is not held back and the function stays alive until the events are delivered. On Vercel, a [pipeline](/drains/pipeline#serverless) sends what it holds when the request ends, without waiting for `batch.intervalMs`.

If your ingest endpoint is slow enough to hit a drain's default 5 s timeout, raise it, as in `createAxiomDrain({ timeout: 15000 })`. A request that timed out but landed is retried, and an ingest API that is not idempotent counts it twice.

Keep Node-only drains such as `evlog/fs` in `lib/evlog.ts`, not in the root `instrumentation.ts`, which Next.js also bundles for Edge.
