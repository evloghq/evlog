The drain posts each wide event to the [Datadog Logs](https://docs.datadoghq.com/logs/) HTTP intake. Every field becomes a log attribute you can facet on, such as `@evlog.user.plan` or `@evlog.path`.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createDatadogDrain } from 'evlog/datadog'

export default defineEvlog({
  service: 'my-app',
  drain: createDatadogDrain(),
})
```

The [drains overview](/drains#wire-it-into-your-framework) shows where the drain goes in each framework, for an `evlog:drain` hook or one integration's `drain` option.

To send through OpenTelemetry instead, use the [OTLP drain](/drains/otlp).

## Credentials

Create an API key with Logs intake permission. The drain reads the variables the Datadog agent already uses:

```bash [.env]
DD_API_KEY=your-api-key
DD_SITE=datadoghq.eu
```

`DD_SITE` is `datadoghq.com` when unset. Set it to the site in your Datadog URL: `datadoghq.eu`, `us3.datadoghq.com`, `us5.datadoghq.com`, `ap1.datadoghq.com` or `ddog-gov.com`. `DATADOG_API_KEY` and `DATADOG_SITE` work too.

API keys are under [Organization Settings, API Keys](https://app.datadoghq.com/organization-settings/api-keys). When both spellings of a variable are set, the `DATADOG_` one wins. Without a key, the drain logs an error that names `DATADOG_API_KEY` and `DD_API_KEY`, and sends nothing.

## Options

| Option | Env | What it is |
| --- | --- | --- |
| `apiKey` | `DD_API_KEY` | An API key with Logs intake permission |
| `site` | `DD_SITE` | The Datadog site, `datadoghq.com` by default |
| `intakeUrl` | `DATADOG_LOGS_URL` | A full intake URL. Overrides `site` |
| `timeout` | | Request timeout in ms, `5000` by default |
| `retries` | | Retries on a transient failure, `2` by default |

On Nuxt, each variable also reads with a `NUXT_` prefix, such as `NUXT_DATADOG_API_KEY`.

The drain posts to `https://http-intake.logs.{site}/api/v2/logs` and sends the key in the `DD-API-KEY` header. Each option is read from the argument first, then on Nuxt and Nitro from runtime config under the `datadog` namespace, then from its environment variable. [Custom drain](/extend/custom-drain#which-config-wins) has the full order.

## What a log carries

Each wide event becomes one Datadog log:

| Datadog field | Value |
| --- | --- |
| `message` | A one-line summary for the list view, such as `ERROR GET /api/checkout (400)`: the level, then the method, path and status. An event with none of them gets the level and the service |
| `evlog` | The whole wide event, as a JSON object. A numeric `status` at any depth is renamed `httpStatusCode`, because Datadog reserves `status` for the severity |
| `status` | The severity, from the table below |
| `service` | The event's `service` |
| `ddsource` | `evlog` |
| `ddtags` | `env:` with the event's `environment`, and `version:` when the event has a `version` |
| `dd` | `{ trace_id, span_id }`, when the event carries trace context |
| `timestamp` | The event's `timestamp`, in Unix milliseconds |

The severity comes from the event's `level` first, then from its HTTP status:

| Event | Datadog `status` |
| --- | --- |
| `level` is `error` or `fatal` | `error` |
| `level` is `warn` | `warn` |
| `level` is `debug` or `trace` | `debug` |
| `level` is `info` and `status` is 500 or more | `error` |
| `level` is `info` and `status` is 400 to 499 | `warn` |
| Anything else | `info` |

A business failure answered with a `200` stays `info` unless the handler calls `log.error()`.

## Trace correlation

Datadog links a log to a trace through `dd.trace_id` and `dd.span_id` at the root of the payload. The copies under `@evlog.traceId` are searchable but do not correlate without a [Trace Id Remapper](https://docs.datadoghq.com/logs/log_configuration/processors/trace_remapper/) in a Datadog log pipeline. The drain lifts `traceId` and `spanId` into a root `dd` block, so correlation needs no pipeline:

```json
{
  "message": "ERROR GET /api/checkout (400)",
  "evlog": { "traceId": "4bf92f35…", "spanId": "00f067aa…", "…": "full wide event" },
  "dd": { "trace_id": "4bf92f35…", "span_id": "00f067aa…" },
  "service": "my-app",
  "status": "error",
  "ddsource": "evlog"
}
```

Only a non-empty string is lifted, and the `dd` key is absent when neither id is one. The copy under `evlog` stays, so `@evlog.*` facets keep working.

The [trace context enricher](/events/enrichers#trace-context) sets `traceId` from an incoming `traceparent` header. The span id in that header belongs to the caller, so it goes to `parentSpanId`, and `dd.span_id` is set only when something else provides `spanId`. To take the ids from a tracer, set them yourself:

```typescript
const span = tracer.scope().active()?.context()
log.set({ traceId: span?.toTraceId(), spanId: span?.toSpanId() })
```

## Requests

Each batch is sent as gzip-compressed JSON with `Content-Encoding: gzip`. The Logs intake accepts at most 1000 entries and 5 MB uncompressed per request, so a larger batch goes out as several requests that each fit, one after another. If one of them fails, the requests already accepted stay accepted, and a retry of the whole batch can send those entries twice.

A single event above 5 MB uncompressed still goes out in a request of its own, and the intake rejects it with a `413`.

## When a request fails

A request is aborted after `timeout` milliseconds. A network error, a timeout, or a `408`, `429`, `500`, `502`, `503` or `504` response is retried up to `retries` times, with a wait that starts at 200 ms and doubles. The `500` is specific to this drain: Datadog documents it as an intake error to retry. Any other status fails on the first response.

The drain never throws into your request. It logs `[evlog/datadog] Failed to send events:` with the error, which starts with `Datadog API error:` and the status, and those events are lost. Wrap the drain in the [pipeline](/drains/pipeline#what-gets-retried) to batch events and retry a failed batch.

## Find the logs

Open **Logs** > **Explorer** and search `source:evlog`, with `service:your-app` or `status:error` to narrow it.

- Facet on `@evlog.path`, `@evlog.requestId`, `@evlog.level` and the like. The fields are under `evlog`, and `message` holds only the summary line.
- The HTTP status of a request is `@evlog.httpStatusCode`.
- Build log-based metrics on `@evlog.*` attributes.

A tagged log such as `log.info('auth', 'User logged in')` is not part of a request's wide event. With `pretty` on, the default in development, it is printed to the console and not drained. With `pretty` off, it is sent as an event of its own, with the text under `@evlog.message`.

## Troubleshooting

| What you see | Cause and fix |
| --- | --- |
| `[evlog/datadog] Missing API key. Set DATADOG_API_KEY, DD_API_KEY, or pass apiKey to createDatadogDrain()` | The variable is unset, or the process was not restarted after you added it |
| `403 Forbidden` | The key lacks log ingestion permission or belongs to another organization |
| No error and no logs | `DD_SITE` does not match your account, such as `datadoghq.eu` for the EU. For a custom intake, set `DATADOG_LOGS_URL` |
| Facets built on a JSON string in `message` are empty | Move them to `@evlog.*`. `message` is a summary line |

## Send without the drain

`sendToDatadog()` and `sendBatchToDatadog()` post from your own code. They take the options above as their second argument, read nothing from the environment, and throw when the request fails:

```typescript [server/utils/datadog.ts]
import { sendToDatadog, sendBatchToDatadog } from 'evlog/datadog'

await sendToDatadog(event, {
  apiKey: process.env.DD_API_KEY!,
  site: process.env.DD_SITE,
})

await sendBatchToDatadog(events, {
  apiKey: process.env.DD_API_KEY!,
})
```

The mapping is exported too, for a drain of your own:

| Function | Returns |
| --- | --- |
| `toDatadogLog(event)` | The whole log object |
| `formatDatadogMessageLine(event)` | The `message` line |
| `resolveDatadogLogStatus(event)` | The severity |
| `resolveDatadogTraceContext(event)` | The `dd` block, or `undefined` |
| `sanitizeWideEventForDatadog(event)` | The object stored under `evlog` |
| `resolveDatadogIntakeUrl({ site, intakeUrl })` | The intake URL |
