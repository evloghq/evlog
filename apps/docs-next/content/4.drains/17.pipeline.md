One HTTP request per event does not scale. The pipeline wraps a drain: it buffers events, sends them in batches, retries a failed batch with backoff, and drops the oldest events when the buffer is full, so memory stays flat while a backend is down.

::drain-pipeline-batching
::

```typescript [evlog.config.ts]
import { defineEvlog, type DrainContext } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createDrainPipeline } from 'evlog/pipeline'

const pipeline = createDrainPipeline<DrainContext>()

export default defineEvlog({
  service: 'my-app',
  drain: pipeline(createAxiomDrain()),
})
```

The wrapped drain goes wherever a drain goes: the config file, an integration's `drain` option, or the `evlog:drain` hook on Nuxt and Nitro.

A batch is sent when `batch.size` events are buffered or `batch.intervalMs` has passed, whichever comes first. A failed batch is sent again after a backoff. Once `retry.maxAttempts` is spent, the events go to `onDropped`.

## Options

```typescript [evlog.config.ts]
import type { DrainContext } from 'evlog'
import { createDrainPipeline } from 'evlog/pipeline'
import { DrainDeliveryError } from 'evlog/toolkit'

const pipeline = createDrainPipeline<DrainContext>({
  batch: { size: 50, intervalMs: 5000 },
  retry: {
    maxAttempts: 3,
    backoff: 'exponential',
    initialDelayMs: 1000,
    maxDelayMs: 30000,
  },
  maxBufferSize: 1000,
  onDropped: (events, error, reason) => {
    // A partial rejection passes the whole batch; error.rejected is how many were lost.
    const lost = (error instanceof DrainDeliveryError ? error.rejected : undefined) ?? events.length
    console.error(`[evlog] Dropped ${lost} events (${reason}):`, error?.message)
  },
})
```

| Option | Default | What it does |
| --- | --- | --- |
| `batch.size` | `50` | Most events in one batch |
| `batch.intervalMs` | `5000` | Longest time in ms an event waits before a partial batch is sent |
| `retry.maxAttempts` | `3` | Attempts per batch, the first one included |
| `retry.backoff` | `'exponential'` | `'exponential'`, `'linear'` or `'fixed'` |
| `retry.initialDelayMs` | `1000` | Delay before the first retry |
| `retry.maxDelayMs` | `30000` | Upper bound for one retry delay. A longer `Retry-After` pauses the pipeline |
| `maxBufferSize` | `1000` | Events held before the oldest is dropped |
| `requestBudget` | `10` | Drain calls, retries included, that one request-end flush may make on a serverless platform |
| `onDropped` | | Called with the dropped events, the error when there is one, and the reason |

`createDrainPipeline` throws when `batch.size`, `batch.intervalMs`, `maxBufferSize`, `requestBudget` or `retry.maxAttempts` is not a positive finite number, or when a retry delay is negative or not finite.

| Backoff | Delays | Good for |
| --- | --- | --- |
| `exponential` | 1 s, 2 s, 4 s, 8 s | The default: a backend that needs time to recover |
| `linear` | 1 s, 2 s, 3 s, 4 s | Delays that grow at a steady rate |
| `fixed` | 1 s, 1 s, 1 s, 1 s | A rate-limited API |

Those are the upper values. Each delay is capped at `retry.maxDelayMs`, then a random amount between half of it and all of it is used, so instances that failed together do not retry together.

## What the wrapped drain exposes

| Member | Type | What it does |
| --- | --- | --- |
| `drain(ctx)` | `(ctx: T) => void` | Buffers one event and returns |
| `drain.flush()` | `() => Promise<void>` | Sends everything buffered now |
| `drain.settled()` | `() => Promise<void>` | Resolves once everything buffered so far is delivered or dropped, without forcing a flush |
| `drain.pending` | `number` | Events in the buffer |
| `drain.stats()` | `() => DrainPipelineStats` | Events delivered, and dropped per reason, since the pipeline was created |

## Dropped events

`onDropped(events, error, reason)` receives every event the pipeline gives up on while the process runs. Events still in flight when a [shutdown](#shutdown) signal's deadline passes are the one exception.

| Reason | When |
| --- | --- |
| `buffer-full` | `maxBufferSize` was reached and the oldest events made room |
| `rejected` | The provider answered with a status that fails the same way on every attempt, such as a `400`, or accepted the batch and rejected some of its events, such as an OTLP `partialSuccess` |
| `retries-exhausted` | Every one of `retry.maxAttempts` failed |
| `rate-limited` | `flush()` ran while the provider's `Retry-After` was still in force |
| `deferred` | A request-end flush on a serverless platform spent `requestBudget` before the events were sent |
| `deadline` | A request-end flush reached the runtime's deadline, or a retry would have started after it |

A partial rejection never says which events the provider refused. `onDropped` gets the whole batch and `error.rejected` holds the count. `stats()` counts the rejected events as dropped and the rest as delivered.

Without `onDropped`, drops are logged with `console.error` at most once a minute, with the count per reason, and once more on `flush()` for what is left. `drain.stats()` returns the totals: `{ delivered, dropped: { 'buffer-full', 'rejected', 'retries-exhausted', 'rate-limited', 'deferred', 'deadline' } }`.

## What gets retried

Built-in HTTP drains retry network errors, timeouts, and `408`, `429`, `502`, `503` and `504` responses, plus the statuses a provider documents as retryable, such as Datadog's `500`. Any other response, a `400` for a malformed payload or a `401` for a bad key, fails the same way every time, so the batch goes to `onDropped` after one request.

When the provider answers with `Retry-After`, the pipeline waits that long instead of its own backoff. A `Retry-After` longer than `retry.maxDelayMs` pauses the pipeline: the batch stays in the buffer, new events keep buffering up to `maxBufferSize`, and delivery resumes once the delay has passed. `flush()` does not wait out a pause. It hands what is still buffered to `onDropped`.

Called directly, a built-in drain swallows a delivery failure so it cannot break a request. Inside the pipeline that would leave `retry` and `onDropped` with nothing to see, so the pipeline calls the drain's throwing `raw` variant. That variant makes one HTTP attempt per call, so a batch is not retried twice. Set `retries` on the drain's own config only when you want extra HTTP attempts inside each pipeline attempt.

A function you wrote is retried whenever it throws. To stop retries for a request the backend will never accept, throw a `DrainDeliveryError` from `evlog/toolkit` with `retryable: false`. When the backend accepted part of the batch, add `rejected` with the number of events it refused.

## Shutdown

On Node and Bun, a pipeline that holds events is flushed when the process is about to stop:

| Trigger | What happens |
| --- | --- |
| `SIGTERM`, `SIGINT` | Every pending pipeline flushes for up to 400 ms, inside Vercel's 500 ms window. Then the signal's default exit runs, as if evlog were not listening. When your app has its own listener for that signal, evlog flushes and leaves the exit to it. A second signal during the flush exits at once |
| `beforeExit` | The event loop ran out of work, as at the end of a script: pending pipelines flush to completion |
| Nitro `close`, Fastify `onClose`, NestJS `onApplicationShutdown` | The integration flushes every pending pipeline before the app finishes closing |

An idle pipeline is not tracked, so a process with nothing buffered handles signals exactly as it would without evlog. Elysia runs its `onStop` handlers without awaiting them, so on Bun the signal flush is what delivers. When delivery takes longer than the 400 ms signal deadline, the process exits with those events unsent, and neither `onDropped` nor `stats()` counts them.

::callout{icon="i-lucide-triangle-alert" color="neutral"}
`process.exit()` and `SIGKILL` stop the process before any flush runs. Call `await drain.flush()` before `process.exit()`.
::

## Serverless

`drain(ctx)` returns after buffering, so on a serverless runtime something has to keep the instance alive until the batch is sent. evlog handles Cloudflare Workers, Vercel, Netlify and AWS Lambda.

An integration that has the request's `waitUntil` sends what the pipeline holds when the request ends, without waiting for `batch.intervalMs`, and keeps the instance alive until those events are delivered or dropped. That covers Next's `after()`, Workers' `ctx.waitUntil`, Nitro's request context, including drains on the `evlog:drain` hook, and SvelteKit's `event.platform.context` on the Cloudflare and Netlify adapters. On Vercel, Express, Fastify, Elysia, NestJS, React Router, oRPC and SvelteKit find the request's `waitUntil` in the Vercel Functions runtime with no option. It is the one `waitUntil()` from `@vercel/functions` calls, and that package does not need to be installed. Anywhere else, pass the platform's `waitUntil` to the integration.

What a request-end flush does and does not do:

- Events of concurrent requests on the same instance go in the same batch.
- The pipeline tracks each event by object, so pass a given context to `drain(ctx)` once. A request-end flush may finish before a second push of the same object is sent.
- It makes at most `requestBudget` drain calls, retries included, and drops what is left as `deferred`. Workers Free allows 50 subrequests per request.
- It skips any retry that would start after the runtime stops the request, and drops those events as `deadline`. The deadline is the invocation deadline on Vercel, the one `getDeadline()` from `@vercel/functions` returns, and 25 s after the request ends on Workers.
- A batch that an explicit `flush()` is already sending keeps all its retries. Only the deadline cuts it short.
- Retries follow `retry`, but a provider pause longer than `retry.maxDelayMs` drops the request's events as `rate-limited` instead of holding the instance.
- A drain call still running when the runtime stops the request is cut off without a drop report.

On a long-lived server that also exposes `waitUntil`, such as Nitro 3 on Node through srvx or `next start`, batches keep filling until `batch.intervalMs`.

On AWS Lambda without `waitUntil`, the runtime freezes as soon as the handler returns, so the integration delivers what the pipeline holds before it returns the response. The response waits for that whole flush: one provider round trip per batch, plus any retries and their backoff, up to `requestBudget` calls. An integration that calls `finish()` after the response is written, such as Express through `serverless-http`, cannot hold the response back, and neither can Nitro error drains, which run after the error response.

Two warnings, each logged once, catch a missing `waitUntil`:

- A pipeline holds events past `batch.intervalMs` on one of these platforms, and no request-end flush has run in the process. The warning says the timer that would send them dies with the request.
- Request-end flushes do run, but a request finds events older than `batch.intervalMs`: a route without `waitUntil` left them, and the runtime froze before their timer fired. This warning starts with `stale-buffer`. Those events go out with the next request-end flush, or are lost if the instance stops first.

## Fan out to several destinations

To reach more than one destination, wrap one function that calls every drain. The pipeline batches once, and `Promise.allSettled` keeps a slow or failing destination from blocking the others.

```typescript [evlog.config.ts]
import { createDrainPipeline } from 'evlog/pipeline'
import { createAxiomDrain } from 'evlog/axiom'
import { createDatadogDrain } from 'evlog/datadog'
import { createFsDrain } from 'evlog/fs'
import type { DrainContext } from 'evlog'

const pipeline = createDrainPipeline<DrainContext>({
  batch: { size: 50, intervalMs: 5000 },
  retry: { maxAttempts: 3 },
  maxBufferSize: 1000,
})

const axiom = createAxiomDrain()
const datadog = createDatadogDrain()
const fs = createFsDrain({ dir: '.evlog/logs', maxFiles: 14 })

export const drain = pipeline(async (batch) => {
  await Promise.allSettled([
    axiom(batch),
    datadog(batch),
    fs(batch),
  ])
})
```

The destinations share one buffer: when the wrapping function falls behind, the oldest events are dropped for all of them. The pipeline retries a batch only when the wrapping function rejects. Here it never does, because each drain called directly swallows its failure and retries its own HTTP request, so `retry` and `onDropped` do not see a failing destination. Run one pipeline per drain when a destination needs its own retries and drop reports.

To send a destination only some events, filter the batch before calling it:

```typescript [evlog.config.ts]
import type { DrainContext } from 'evlog'

const sentry = createSentryDrain({ dsn: process.env.SENTRY_DSN! })

async function sentryErrorsOnly(batch: DrainContext[]): Promise<void> {
  const errors = batch.filter(c => c.event?.level === 'error')
  if (errors.length > 0) await sentry(errors)
}

export const drain = pipeline(async (batch) => {
  await Promise.allSettled([
    axiom(batch),
    sentryErrorsOnly(batch),
  ])
})
```

## Wrap your own function

The pipeline takes any function that accepts a batch:

```typescript [evlog.config.ts]
import type { DrainContext } from 'evlog'
import { createDrainPipeline } from 'evlog/pipeline'

const pipeline = createDrainPipeline<DrainContext>({ batch: { size: 100 } })

export const drain = pipeline(async (batch) => {
  await fetch('https://your-service.com/logs', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(batch.map(ctx => ctx.event)),
  })
})
```

`fetch` does not reject on a `500`, so this function must throw on a failed response for the pipeline to retry it. For config resolution, timeouts and identity headers, write a [custom drain](/extend/custom-drain) with `defineHttpDrain` instead. The [HTTP drain](/drains/http) runs browser logs through this same pipeline, with a batch of 25 every 2 seconds.

Match `batch.size` to the payload your provider recommends: a small batch spends a request on few events, and a large one can be rejected for its size.
