The drain inserts each batch of wide events into a [ClickHouse](https://clickhouse.com) table over HTTP. It uses asynchronous inserts by default, so ClickHouse groups the small writes itself instead of creating one part per request.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createClickHouseDrain } from 'evlog/clickhouse'

export default defineEvlog({
  service: 'my-app',
  drain: createClickHouseDrain(),
})
```

## Credentials

```bash [.env]
CLICKHOUSE_ENDPOINT=https://abc123.eu-west-1.aws.clickhouse.cloud:8443
CLICKHOUSE_USER=default
CLICKHOUSE_PASSWORD=your-password
```

The database is `default` and the table `evlog_events` unless you set `CLICKHOUSE_DATABASE` or `CLICKHOUSE_TABLE`. A local instance without a password needs only the endpoint.

The endpoint is the URL of the HTTP interface. It works with a local instance, a self-managed cluster and ClickHouse Cloud:

| Deployment | Endpoint | Credentials |
| --- | --- | --- |
| Local or self-managed | `http://localhost:8123` | A fresh container runs as `default` with no password. Set the user and password only when your instance requires them |
| ClickHouse Cloud | The HTTPS URL from Connect in the Cloud console, with its `:8443` port | Always required |

The drain sends the user as an `X-ClickHouse-User` header, and the password as `X-ClickHouse-Key` when there is one. Neither goes in the query string, so they never reach `system.query_log` or a proxy's access log.

A ClickHouse Cloud service suspends when idle, so the first insert after a pause can take a few seconds. Raise `timeout` if you see aborted requests.

## The table

The drain does not create the table. This schema matches the rows it writes, with the common fields as columns and the whole event in `data`:

```sql [schema.sql]
CREATE TABLE IF NOT EXISTS evlog_events
(
  timestamp     DateTime64(3, 'UTC'),
  level         LowCardinality(String),
  service       LowCardinality(String),
  environment   LowCardinality(String),
  request_id    String,
  trace_id      String,
  span_id       String,
  method        LowCardinality(String),
  path          String,
  status        Nullable(UInt16),
  duration      String,
  duration_ms   Nullable(UInt32),
  error_name    String,
  error_message String,
  data          String
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(timestamp)
ORDER BY (service, environment, timestamp)
TTL toDateTime(timestamp) + INTERVAL 30 DAY;
```

Run it once before the first event. The sort key matches the usual filter: a service, an environment, a time range. The `TTL` deletes events after 30 days. Change the interval to your retention, or remove the clause to keep events forever.

Each wide event becomes one row:

| Column | Filled from | When the field is missing |
| --- | --- | --- |
| `timestamp` | `timestamp`, written as `YYYY-MM-DD HH:MM:SS.mmm` in UTC | The time of the insert, when it does not parse |
| `level`, `service`, `environment` | The fields of the same name | |
| `request_id`, `trace_id`, `span_id` | `requestId`, `traceId`, `spanId` | Empty string |
| `method`, `path` | `method`, `path` | Empty string |
| `status` | `status`, when it is a number | `NULL`, as on an event that is not an HTTP request |
| `duration` | `duration`, the formatted string | Empty string |
| `duration_ms` | `durationMs`, when it is an integer from 0 to 4,294,967,295 | `NULL` |
| `error_name`, `error_message` | `error.name`, `error.message` | Empty string |
| `data` | The whole event as JSON, the fields above included | |

Because `data` holds every field, adding a field to your events needs no migration. `duration_ms` falls back to `NULL` on a value the column cannot hold, because ClickHouse rejects the whole insert on one out-of-range value.

Any field not in a column is still in `data`, and `JSONExtract` reads it:

```sql
SELECT path, quantile(0.95)(duration_ms) AS p95_ms
FROM evlog_events
WHERE timestamp > now() - INTERVAL 1 DAY
  AND JSONExtractString(data, 'user', 'plan') = 'pro'
GROUP BY path
ORDER BY p95_ms DESC
LIMIT 20;
```

For another schema, pass `transform`: it receives a wide event and returns the row.

```typescript [evlog.config.ts]
createClickHouseDrain({
  table: 'app_logs',
  transform: event => ({
    ts: event.timestamp,
    lvl: event.level,
    svc: event.service,
    payload: JSON.stringify(event),
  }),
})
```

The keys must be your column names: ClickHouse rejects a `JSONEachRow` insert that contains an unknown column.

## How the insert is sent

Each call is one `POST` to the HTTP interface. The URL carries the database and the query `INSERT INTO <table> FORMAT JSONEachRow`, and the body is one JSON object per line. By default the URL also carries:

```text
async_insert=1&wait_for_async_insert=0
```

Many small inserts would create one MergeTree part each and degrade the table. With [asynchronous inserts](https://clickhouse.com/docs/en/optimize/asynchronous-inserts), ClickHouse buffers the rows and writes them in batches, and the drain does not wait for that write.

| Setting | Effect |
| --- | --- |
| `waitForAsyncInsert: true` | ClickHouse acknowledges the insert as durable before the drain resolves, at the cost of latency |
| `asyncInsert: false` | A synchronous insert, with neither parameter in the URL. Use it only when the [pipeline](/drains/pipeline) already batches |

Without the pipeline, the drain inserts once per event. With it, one insert carries a batch, for example up to 500 rows every 5 seconds with `batch: { size: 500, intervalMs: 5000 }`.

## Query the events

The columns cover the common filters:

```sql
-- Error rate per service over the last hour
SELECT service, countIf(level = 'error') / count() AS error_rate
FROM evlog_events
WHERE timestamp > now() - INTERVAL 1 HOUR
GROUP BY service;
```

```sql
-- Slowest routes
SELECT path, count() AS hits, avg(duration_ms) AS avg_ms, quantile(0.95)(duration_ms) AS p95_ms
FROM evlog_events
WHERE timestamp > now() - INTERVAL 1 DAY AND method = 'GET' AND duration_ms IS NOT NULL
GROUP BY path
ORDER BY avg_ms DESC
LIMIT 20;
```

```sql
-- One request end to end
SELECT timestamp, level, path, status, data
FROM evlog_events
WHERE request_id = '4a8ff3a8-...'
ORDER BY timestamp;
```

```sql
-- Reach into a custom field kept only in data
SELECT JSONExtractString(data, 'user', 'plan') AS plan, count()
FROM evlog_events
WHERE timestamp > now() - INTERVAL 7 DAY
GROUP BY plan;
```

## Options

| Option | Env | What it is |
| --- | --- | --- |
| `endpoint` | `CLICKHOUSE_ENDPOINT`, `CLICKHOUSE_URL` | The HTTP interface URL. Required |
| `database` | `CLICKHOUSE_DATABASE` | `default` by default |
| `table` | `CLICKHOUSE_TABLE` | `evlog_events` by default |
| `username` | `CLICKHOUSE_USER` | `default` by default |
| `password` | `CLICKHOUSE_PASSWORD` | Omit for a local instance without auth |
| `asyncInsert` | | `true` by default |
| `waitForAsyncInsert` | | Wait for the insert to be flushed, `false` by default. Only read when `asyncInsert` is on |
| `transform` | | Maps an event to a row, `toClickHouseRow` by default |
| `timeout` | | Request timeout in ms, `5000` by default |
| `retries` | | Retries on a transient failure, `2` by default |

An option passed to `createClickHouseDrain()` wins. On Nuxt and Nitro, `runtimeConfig.evlog.clickhouse` is read next, then `runtimeConfig.clickhouse`. The environment comes last, where the five `CLICKHOUSE_` names of the first column are also read with a `NUXT_` prefix, such as `NUXT_CLICKHOUSE_ENDPOINT`, before the unprefixed names.

## When a request fails

Without an endpoint, the drain sends nothing and logs `[evlog/clickhouse] Missing endpoint` with the variables to set, each time it is called.

An insert that gets no answer within `timeout` is aborted. The drain retries a network error, a timeout and a `408`, `429`, `502`, `503` or `504` response, up to `retries` times, with exponential backoff and jitter. It waits for the response's `Retry-After` when that is 10 seconds or less, and stops retrying when it is longer. Any other status fails at once.

After the last attempt the drain logs `[evlog/clickhouse] Failed to send events:` with the error and drops the events. The request that produced them is not affected. Wrapped in the pipeline, the drain makes one attempt per batch and the pipeline's `retry` takes over, unless you set `retries` yourself.

| Error | Cause and fix |
| --- | --- |
| `ClickHouse API error: 401` | Check `CLICKHOUSE_USER` and `CLICKHOUSE_PASSWORD` |
| `ClickHouse API error: 400` naming an unknown column | The table does not match the rows. Create it from the schema above, or pass a `transform` that returns your columns |
| `Cannot parse input` | The table exists but a column type differs from the schema above. `status` is `Nullable(UInt16)` because an event that is not an HTTP request has none |

## Send without the drain

A script or a backfill can insert events directly:

```typescript [scripts/backfill.ts]
import { sendBatchToClickHouse, sendToClickHouse } from 'evlog/clickhouse'

await sendToClickHouse(event, { endpoint: 'http://localhost:8123' })
await sendBatchToClickHouse(events, { endpoint: 'http://localhost:8123' })
```

Both take a complete config, read nothing from the environment, and reject when the insert fails. `toClickHouseRow()`, `toClickHouseDateTime()`, `toJSONEachRow()` and `resolveClickHouseUrl()` are exported too, for code that builds the insert itself.
