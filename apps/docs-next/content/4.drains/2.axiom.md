[Axiom](https://axiom.co) indexes every field of an event, so `user.plan` or `cart.total` is queryable the moment the first event arrives, with no schema to declare.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'

export default defineEvlog({
  service: 'my-app',
  drain: createAxiomDrain(),
})
```

## Credentials

Create a dataset and an API token with ingest permission, then set:

```bash [.env]
AXIOM_API_KEY=xaat-your-token
AXIOM_DATASET=your-dataset
```

Axiom calls this credential an API token (`xaat-...`). evlog names the option `apiKey`, like every other drain. Use an API token, not a personal access token: Axiom's [edge ingest endpoint](https://axiom.co/docs/restapi/endpoints/ingestToDataset) rejects personal tokens, and its [ingest guide](https://axiom.co/docs/restapi/ingest) lists API tokens only.

Without both values, the drain logs an error that names the two variables and sends nothing.

::callout{icon="i-lucide-arrow-up-circle" color="neutral"}
evlog 3 removed the `token` option and the `AXIOM_TOKEN` variable. See [Upgrade to v3](/start/upgrade#credential-aliases-removed).
::

## Options

Pass options to override the environment:

| Option | Env | Default | What it is |
| --- | --- | --- | --- |
| `apiKey` | `AXIOM_API_KEY` | required | The API token, sent as `Authorization: Bearer` |
| `dataset` | `AXIOM_DATASET` | required | The dataset events land in |
| `orgId` | `AXIOM_ORG_ID` | | Organization ID, sent as `X-Axiom-Org-Id`. Not needed with an API token |
| `baseUrl` | `AXIOM_URL` | `https://api.axiom.co` | The API base URL. The drain posts to `/v1/datasets/{dataset}/ingest` |
| `edgeUrl` | `AXIOM_EDGE_URL` | | An edge ingest URL. With no path, the drain posts to `/v1/ingest/{dataset}`. A path you give is used as is, without its trailing slash |
| `timeout` | | `5000` | Milliseconds before a request is aborted |
| `retries` | | `2` | Retries after a transient failure |

The types accept `edgeUrl` or `baseUrl`, not both. When both arrive through the environment, the drain warns and uses `edgeUrl`.

On Nuxt, each variable also reads with a `NUXT_` prefix, such as `NUXT_AXIOM_API_KEY`, and the prefixed name wins.

Each option is read from the argument first, then on Nuxt and Nitro from runtime config under the `axiom` namespace, then from its environment variable. [Custom drain](/drains/custom#which-config-wins) has the full order. On Nuxt, the `evlog.axiom` key of `nuxt.config.ts` is typed for `dataset`, `apiKey`, `orgId`, `baseUrl` or `edgeUrl`, and `timeout`.

## What is sent

The drain posts the batch as a JSON array of wide events, with no renaming: every field of the event is a field in Axiom.

Axiom's own timestamp field is `_time`. The drain adds `timestamp-field=timestamp` to the ingest URL, so Axiom takes `_time` from the event's `timestamp`. Events keep their original time when they are batched or retried. Bin time-based queries and monitors on `_time`.

Axiom ingests at most 10,000 events per request, so a larger batch goes out as several requests of up to 10,000, one after another. If one of them fails, the requests already accepted stay accepted, and a retry of the whole batch can send those events twice.

## When a request fails

A request is aborted after `timeout` milliseconds. A network error, a timeout, or a `408`, `429`, `502`, `503` or `504` response is retried up to `retries` times. The wait starts at 200 ms, doubles, carries jitter, and is never shorter than a `Retry-After` header of up to 10 seconds. Any other status, such as a `401`, fails on the first response.

The drain never throws into your request. Once the attempts are spent, it logs `[evlog/axiom] Failed to send events:` with the error, which starts with `Axiom API error:` and the status, and those events are lost. Wrap the drain in the [pipeline](/drains/pipeline#what-gets-retried) to batch events and retry a failed batch. The pipeline then owns the retries, and the drain makes one attempt per call unless you set `retries` yourself.

Axiom can accept a request and still refuse part of it. The drain reads the `2xx` response and logs a `[evlog/axiom]` warning with the number of events that failed to ingest and Axiom's reason for each, then one warning per schema message, such as a field dropped by a locked schema.

## Query the events

Every field of the wide event is a column in APL:

```apl [Axiom APL queries]
// Find slow requests
['your-dataset']
| where durationMs > 1000
| project _time, path, durationMs, status

// Error rate by endpoint
['your-dataset']
| where level == "error"
| summarize count() by path
| order by count_ desc

// Request volume over time
['your-dataset']
| summarize count() by bin(_time, 1h)
| render timechart
```

## Troubleshooting

| What you see | Cause and fix |
| --- | --- |
| `[evlog/axiom] Missing dataset or apiKey. Set AXIOM_API_KEY/AXIOM_DATASET env vars or pass to createAxiomDrain()` | A variable is unset, or the server was not restarted after you added it |
| `401 Unauthorized` | The token is invalid or expired. Create a new one with ingest permission |
| `403 Forbidden` | The token cannot ingest into the dataset, the dataset is shared from another organization, or the organization is suspended. A personal access token fails here too, and `AXIOM_ORG_ID` does not fix it. Create an API token whose dataset access includes `AXIOM_DATASET` |

A dataset shared from another organization does not accept ingest from yours, whatever the token. Send to a dataset in the organization that owns it, with an API token from that organization.

## Send without the drain

`sendToAxiom()` and `sendBatchToAxiom()` post from your own code. They take the options above as their second argument, read nothing from the environment, and throw when the request fails:

```typescript [server/utils/axiom.ts]
import { sendToAxiom, sendBatchToAxiom } from 'evlog/axiom'

await sendToAxiom(event, {
  apiKey: 'xaat-xxx',
  dataset: 'logs',
})

await sendBatchToAxiom(events, {
  apiKey: 'xaat-xxx',
  dataset: 'logs',
})
```
