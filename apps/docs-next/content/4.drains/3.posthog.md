The drain sends each wide event to [PostHog Logs](https://posthog.com/docs/logs) over OTLP. When the event carries a user id and a session id, PostHog shows the log on that person's profile and next to their session replay.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createPostHogDrain } from 'evlog/posthog'

export default defineEvlog({
  service: 'my-app',
  drain: createPostHogDrain(),
})
```

The [drains overview](/drains#wire-it-into-your-framework) shows where the drain goes in each framework, for an `evlog:drain` hook or one integration's `drain` option.

## Credentials

Use the project API key, the one your frontend already sends with:

```bash [.env]
POSTHOG_API_KEY=phc_your_project_key
POSTHOG_HOST=https://eu.i.posthog.com
```

`POSTHOG_HOST` is `https://us.i.posthog.com` when unset. Set it for the EU cloud or a self-hosted instance.

The key starts with `phc_` and is under **Settings** > **Project** > **Project API Key**. Without it, the drain logs an error that names `POSTHOG_API_KEY` and sends nothing.

| Region | Host |
| --- | --- |
| US, the default | `https://us.i.posthog.com` |
| EU | `https://eu.i.posthog.com` |
| Self-hosted | Your instance URL |

## Link logs to people and replays

Record the ids on the event, and the drain sends them as the attributes PostHog matches on:

```typescript [server/api/checkout.post.ts]
log.set({
  userId: user.id,
  sessionId: getHeader(event, 'x-posthog-session-id'),
})
```

Read the session id in the browser with `posthog.get_session_id()` and pass it in a header. The fields are `userId` and `sessionId` by default; `distinctIdField` and `sessionIdField` take another dot path, such as `user.id`.

The drain copies the person id to a `posthogDistinctId` attribute and the session id to a `sessionId` attribute. A log with `posthogDistinctId` appears under the **Logs** tab of that person's profile, and one with `sessionId` links to the session replay. The drain reads a string or a number from each path and skips an empty string or any other type.

```typescript [evlog.config.ts]
createPostHogDrain({
  distinctIdField: 'user.id',
  sessionIdField: 'session.id',
})
```

For an [eve agent](/extend/eve), the caller principal is the identity eve itself routes on:

```typescript [agent/hooks/evlog.ts]
const drain = createPostHogDrain({ distinctIdField: 'eve.caller.principalId' })
```

A static `distinctId` replaces the field lookup. Use it for a backend that acts as one identity instead of on behalf of users.

PostHog matches the attribute value against every `distinct_id` it knows for a person, so any one of their identifiers works. The attribute key PostHog reads is a project setting under **Settings** > **Logs**. The drain always writes `posthogDistinctId`, so leave that setting at its default.

## Logs or events

| `mode` | Where events land | When to pick it |
| --- | --- | --- |
| `'logs'` | PostHog Logs, over OTLP | The default, and the cheapest |
| `'events'` | Custom events through `/batch/`, named `evlog_wide_event` | You want to chart events in Insights next to product events |

In `'events'` mode, nested fields are flattened to dotted properties such as `gen_ai.usage.cost`, because PostHog filters and breaks down by top-level properties.

`mode` is read from the argument of `createPostHogDrain()` only. Custom events count towards your PostHog event quota.

| | `'logs'` | `'events'` |
| --- | --- | --- |
| Endpoint | `{host}/i/v1/logs` | `{host}/batch/` |
| Authentication | `Authorization: Bearer {apiKey}` | `api_key` in the request body |
| PostHog UI | Logs | Events explorer |
| Good for | Debugging, log search | Product analytics, cohorts, funnels |

To get both, write one drain that calls the two:

```typescript [evlog.config.ts]
import { defineEvlog, type DrainContext } from 'evlog'
import { createPostHogDrain } from 'evlog/posthog'

const logs = createPostHogDrain()
const events = createPostHogDrain({ mode: 'events' })

export default defineEvlog({
  service: 'my-app',
  drain: async (ctx: DrainContext) => {
    await Promise.allSettled([logs(ctx), events(ctx)])
  },
})
```

### What an event carries

| PostHog field | Value |
| --- | --- |
| `event` | `eventName`, `evlog_wide_event` by default |
| `distinct_id` | The `distinctId` option, else the value at `distinctIdField`, else `service` |
| `timestamp` | The event's `timestamp` |
| `properties.level`, `properties.service` | The event's `level` and `service` |
| `properties.*` | Every other field, flattened to dotted keys such as `gen_ai.usage.cost`. With `recordShape: 'json'`, a nested object stays one property |

An event that resolves to a person id is an identified event: PostHog creates or updates a person profile for it. When no id resolves, the drain sends `service` as the `distinct_id` and sets `$process_person_profile: false`. The event is then anonymous: it stays out of person profiles, and PostHog bills it at a lower rate.

PostHog's `/batch/` endpoint accepts request bodies under 20 MB, so a larger batch goes out as several requests that each fit, one after another. If one of them fails, the requests already accepted stay accepted, and a retry of the whole batch can send those events twice.

## The record shape

In logs mode the drain uses the [OTLP drain](/drains/otlp#the-record-shape)'s encoder with its defaults: the body is a one-line summary, nested fields become dotted attributes such as `gen_ai.usage.cost`, and the record also carries the OpenTelemetry attribute names. PostHog filters, breaks down and alerts on attributes, so each leaf has to be its own attribute.

With `recordShape: 'json'`, a nested field arrives as one attribute that PostHog can display but not chart. Set it only to keep saved views and alerts built on the 2.x output, together with `semanticConventions: false`:

```typescript
createPostHogDrain({ recordShape: 'json', semanticConventions: false })
```

In events mode, `recordShape` is the only one of the two that applies. Severity, trace context and attribute types follow the [OTLP mapping](/drains/otlp#how-fields-are-mapped).

## Options

| Option | Env | What it is |
| --- | --- | --- |
| `apiKey` | `POSTHOG_API_KEY` | The project API key |
| `host` | `POSTHOG_HOST` | The PostHog host, `https://us.i.posthog.com` by default |
| `mode` | | `'logs'` or `'events'` |
| `eventName` | | The event name in `'events'` mode, `evlog_wide_event` by default |
| `distinctId` | | One person id for every event |
| `distinctIdField` | | The field holding the person id, `userId` by default |
| `sessionIdField` | | The field holding the session id, `sessionId` by default |
| `recordShape` | | `'compact'` by default, or `'json'` |
| `semanticConventions` | | Logs mode only. `true` by default: also emits `http.request.method`, `url.path`, `exception.*` and the like |
| `timeout` | | Request timeout in ms, `5000` by default |
| `retries` | | Retries on a transient failure, `2` by default |

On Nuxt, each variable also reads with a `NUXT_` prefix, such as `NUXT_POSTHOG_API_KEY`.

`sessionIdField` applies in logs mode only. Each option except `mode` is read from the argument first, then on Nuxt and Nitro from runtime config under the `posthog` namespace, then from its environment variable. [Custom drain](/extend/custom-drain#which-config-wins) has the full order. On Nuxt, the `evlog.posthog` key of `nuxt.config.ts` is typed for `apiKey`, `host` and `timeout`.

## When a request fails

A request is aborted after `timeout` milliseconds. A network error, a timeout, or a `408`, `429`, `502`, `503` or `504` response is retried up to `retries` times, with a wait that starts at 200 ms and doubles. Any other status fails on the first response.

The drain never throws into your request. It logs `[evlog/posthog] Failed to send events:` with the error, or `[evlog/posthog-events]` in events mode, and those events are lost. In logs mode the error starts with `OTLP API error:`, because the request goes through the OTLP sender. Wrap the drain in the [pipeline](/drains/pipeline#what-gets-retried) to batch events and retry a failed batch.

A logs endpoint can answer `2xx` and still refuse some records. The drain treats that as a failure it does not retry, as the [OTLP drain](/drains/otlp#when-a-request-fails) does.

## Find the logs

Open **Logs** in PostHog. Filter by service, by severity or by any attribute, search the body, and open an entry to see every attribute.

## Troubleshooting

| What you see | Cause and fix |
| --- | --- |
| `[evlog/posthog] Missing apiKey. Set POSTHOG_API_KEY env var or pass to createPostHogDrain()` | The variable is unset, or the server was not restarted after you added it |
| Nothing in PostHog, errors in the server console | The host does not match your region. On the EU cloud, set `POSTHOG_HOST=https://eu.i.posthog.com` |
| Nothing in PostHog, no error | PostHog processes events asynchronously, often in under a minute. Check that the key starts with `phc_` |

## Send without the drain

These functions post from your own code. They take the options above as their second argument, read nothing from the environment, and throw when the request fails:

```typescript [server/utils/posthog.ts]
import {
  sendToPostHog,
  sendBatchToPostHog,
  sendToPostHogEvents,
  sendBatchToPostHogEvents,
  toPostHogEvent,
} from 'evlog/posthog'

// PostHog Logs, over OTLP
await sendToPostHog(event, { apiKey: 'phc_xxx' })
await sendBatchToPostHog(events, { apiKey: 'phc_xxx' })

// Custom events
await sendToPostHogEvents(event, { apiKey: 'phc_xxx' })
await sendBatchToPostHogEvents(events, { apiKey: 'phc_xxx' })

// Convert an event to the PostHog format, to inspect it
const posthogEvent = toPostHogEvent(event, { apiKey: 'phc_xxx' })
```
