The drain appends each wide event as one JSON line to a file under `.evlog/logs/`, one file per day. Nothing leaves the machine, and your editor, `jq` or an agent can read the logs where they are.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createFsDrain } from 'evlog/fs'

export default defineEvlog({
  service: 'my-app',
  drain: createFsDrain({ maxFiles: 7 }),
})
```

The [drains overview](/drains#wire-it-into-your-framework) shows where the drain goes in each framework, for an `evlog:drain` hook or one integration's `drain` option.

## Where the files land

Each file is named by the UTC date of the write:

```text [.evlog/logs]
.evlog/
  .gitignore
  logs/
    2026-03-14.jsonl
    2026-03-13.jsonl
    2026-03-12.jsonl
```

On its first write the drain creates a `.gitignore` containing `*`, so the logs stay out of version control. It goes in the `.evlog/` directory when `dir` is inside one, and in `dir` itself otherwise. An existing `.gitignore` is left alone.

With `maxSizePerFile`, a day's file that has reached the limit is followed by a suffixed one. The check runs before each write, so a file can end a little past the limit:

```text [.evlog/logs]
2026-03-14.jsonl
2026-03-14.1.jsonl
2026-03-14.2.jsonl
```

With `maxFiles`, the drain counts the `.jsonl` files in `dir` after each write and deletes the oldest until that many remain. The count covers rotated files too, so `maxFiles: 7` keeps seven files, not seven days, once `maxSizePerFile` is set.

```typescript [evlog.config.ts]
// The last 7 days
createFsDrain({ maxFiles: 7 })

// Rotate at 10 MB, keep 30 files
createFsDrain({ maxSizePerFile: 10 * 1024 * 1024, maxFiles: 30 })

// Indented JSON, for reading by eye
createFsDrain({ pretty: true })

// Another directory
createFsDrain({ dir: '/var/log/my-app' })
```

## Who can read the files

On macOS and Linux, the drain creates its directories with mode `0700` and each file with mode `0600`, so only the account that runs your app can list or read them. An agent or `evlog logs` started from your terminal runs as that account and reads them as usual.

The modes apply when the drain creates a path. A directory or file that already exists keeps its mode, including a `dir` you created yourself. To restrict files written before evlog 3:

```bash [Terminal]
chmod -R go= .evlog
```

On Windows, Node applies only the write bit, so the files get the permissions of their folder.

A process running as another account cannot open the files. Two setups hit this:

- A log shipper that runs as its own user. Run it as the app's account, or send it the events through an HTTP drain instead of having it tail the files.
- A container running as root that writes into a bind-mounted project on a Linux host. The files belong to root on the host, so your account, your agent and `evlog logs` get "permission denied". Run the container as your user, with `docker run --user "$(id -u):$(id -g)"` or `user:` in Compose, or read the logs from inside the container.

## Where it does not run

The drain needs `node:fs` and a writable directory. Where either is missing, it warns once and drops events, and never fails a request:

| Runtime | What happens |
| --- | --- |
| Next.js Edge runtime | `[evlog/fs] File system drain is not available on the Edge runtime`, then nothing is written |
| A read-only or forbidden `dir` (`EROFS`, `EACCES`, `EPERM`) | `[evlog/fs] "<dir>" is not writable`, then the drain is off for that directory until the process restarts |
| Serverless functions | The app directory is read-only, so the row above applies. Only the temp directory is writable, and it does not outlive the instance |

Use the [memory drain](/drains/memory) on Workers and edge runtimes, and a hosted drain in production. Any other write error, such as a full disk, is logged as `[evlog/fs] Failed to send events:` like the other drains.

## Read it back

The files are plain NDJSON, so the usual tools work:

```bash [Terminal]
# Follow every file as it grows
tail -f .evlog/logs/*.jsonl | jq 'select(.status >= 500)'

# Errors of one day
jq 'select(.level == "error")' .evlog/logs/2026-03-14.jsonl

# Requests over one second
jq 'select(.durationMs > 1000)' .evlog/logs/*.jsonl

# One request end to end
grep 'req_abc123' .evlog/logs/*.jsonl
```

`jq` reads files written with `pretty: true` too. `grep` and `tail` on those files see one field per line.

[`evlog logs`](/cli/logs) reads and filters the files from the terminal, and the [analyze-logs skill](/skills) teaches an agent to do the same while it debugs.

## Read events from code

`evlog/fs` also exports two readers. They work from any Node script, with no hook into the running app, so a sidecar process, a CI report or a local dashboard can use them.

::ndjson-tail
::

`readFsLogs()` replays history. It walks the files in date order, a day's rotated files (`2026-05-08.1.jsonl`) after its first one, and skips whole files outside the date window, so a replay stays fast with weeks of logs on disk:

```typescript [scripts/errors.ts]
import { readFsLogs } from 'evlog/fs'

for await (const event of readFsLogs({ since: '2026-03-01', level: 'error' })) {
  console.log(event.timestamp, event.action ?? event.message)
}
```

| Option | Type | What it does |
| --- | --- | --- |
| `dir` | `string` | The directory to read, `.evlog/logs` by default |
| `since` | `Date \| string` | Yields events with `timestamp >= since` |
| `until` | `Date \| string` | Yields events with `timestamp <= until` |
| `level` | `LogLevel \| LogLevel[]` | Yields events at these levels |
| `filter` | `(event) => boolean` | Your own predicate. `false` skips the event |

A line that does not parse, from a partial write or a manual edit, is skipped without an error. Files written with `pretty: true` are read too.

`tailFsLogs()` follows the files. It yields the existing events first, then each new one as it is appended, including events in a daily file created after it started:

```typescript [scripts/tail.ts]
import { tailFsLogs } from 'evlog/fs'

const ac = new AbortController()
process.on('SIGINT', () => ac.abort())

for await (const event of tailFsLogs({ signal: ac.signal })) {
  if (event.level === 'error') notifyOps(event)
}
```

It takes every `readFsLogs()` option, and three of its own:

| Option | Default | What it does |
| --- | --- | --- |
| `pollIntervalMs` | `500` | How often it checks for new bytes and new files, 50 ms at least |
| `fromEnd` | `false` | Skips the existing events and yields only new ones |
| `signal` | | An `AbortSignal` that stops the tail |

A write split across two polls is put back together before it is parsed.

To show history and then follow live traffic, replay from disk and switch to the [stream](/drains/stream) server:

```typescript [scripts/bootstrap.ts]
import { readFsLogs } from 'evlog/fs'
import { readFile } from 'node:fs/promises'
import type { WideEvent } from 'evlog'

async function bootstrap(handle: (e: WideEvent) => void) {
  // 1. Replay the last hour from `.evlog/logs/`
  const since = new Date(Date.now() - 60 * 60 * 1000)
  for await (const event of readFsLogs({ since })) {
    handle(event)
  }

  // 2. Switch to the live SSE stream
  const url = (await readFile('.evlog/stream.url', 'utf-8')).trim()
  const es = new EventSource(url)
  es.onmessage = (e) => {
    const env = JSON.parse(e.data)
    if (env.evlog !== '1') return
    if (env.type === 'event' || env.type === 'replay') {
      handle(env.data)
    }
  }
  return () => es.close()
}
```

Without the files, connect to the stream server with `?since=<iso>` and it replays its in-memory buffer instead.

## Options

| Option | Env | What it is |
| --- | --- | --- |
| `dir` | `EVLOG_FS_DIR` | The directory, `.evlog/logs` by default |
| `maxFiles` | | How many files to keep. The oldest are deleted. No limit by default |
| `maxSizePerFile` | | Bytes per file before it rotates to a suffixed file. No limit by default |
| `pretty` | | Indented JSON instead of one line per event, `false` by default |

On Nuxt, `NUXT_EVLOG_FS_DIR` is read too. On Nuxt and Nitro, the options are also read from `runtimeConfig.evlog.fs`, then `runtimeConfig.fs`.

## Keep a local copy next to a hosted drain

The files are a copy on the machine you can replay with `readFsLogs()` when the hosted backend was down. Write one drain that calls both:

```typescript [evlog.config.ts]
import { defineEvlog, type DrainContext } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createFsDrain } from 'evlog/fs'

const fs = createFsDrain({ maxFiles: 7 })
const axiom = createAxiomDrain()

export default defineEvlog({
  service: 'my-app',
  drain: async (ctx: DrainContext) => {
    await Promise.allSettled([fs(ctx), axiom(ctx)])
  },
})
```

Wrap it in the [pipeline](/drains/pipeline#fan-out-to-several-destinations) to batch both.

## Write without the drain

`writeToFs()` and `writeBatchToFs()` append events from your own code. They take a complete config, read nothing from the environment, and reject when the write fails:

```typescript [scripts/import.ts]
import { writeBatchToFs, writeToFs } from 'evlog/fs'

await writeToFs(event, { dir: '.evlog/logs', pretty: false })
await writeBatchToFs(events, { dir: '.evlog/logs', pretty: false, maxFiles: 7 })
```
