`@evlog/nuxthub` writes wide events to an `evlog_events` table in your [NuxtHub](https://hub.nuxt.com) database. There is no external service and no per-event pricing; your logs live where your data does.

```bash [Terminal]
pnpm add @nuxthub/core @evlog/nuxthub
```

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@evlog/nuxthub'],
})
```

Your NuxtHub project needs a database. The module registers `evlog/nuxt` if you have not, adds an `evlog_events` table to NuxtHub's schema, and stores every event through the `evlog:drain` hook. Columns hold the level, path, status and duration, and the rest of the event is in a JSON column.

`pnpm dlx nuxi module add @nuxthub/core @evlog/nuxthub` installs both and edits `modules` for you. The module also registers `@nuxthub/core` when it is missing from `modules`. List it yourself anyway, so the setup does not depend on that. `drizzle-orm` 0.45.4 or later is a peer dependency: the module reads and writes the table through Drizzle.

The drain takes no credentials. The module has one option, `retention`, and reads one environment variable, `CRON_SECRET`. [Retention](#retention) covers both.

## The table

The module adds the table for the dialect of your NuxtHub database: SQLite, which Cloudflare D1 uses, MySQL or PostgreSQL.

| Column | Type | Filled from |
| --- | --- | --- |
| `id` | `text`, primary key | A random UUID |
| `timestamp` | `text` | `timestamp` |
| `level` | `text` | `level` |
| `service` | `text` | `service` |
| `environment` | `text` | `environment` |
| `method` | `text` | The request's method, else `method` on the event |
| `path` | `text` | The request's path, else `path` on the event |
| `status` | `integer` | `status`, when it is a number |
| `duration_ms` | `integer` | `durationMs`, else `duration` when it is a number or a string such as `45ms` or `1.2s` |
| `request_id` | `text` | The request's ID, else `requestId` on the event |
| `source` | `text` | `source`, such as `server` or `client` |
| `error` | `text` on SQLite, `json` on MySQL, `jsonb` on PostgreSQL | `error`, as JSON. A string is stored as is |
| `data` | `text` on SQLite, `json` on MySQL, `jsonb` on PostgreSQL | Every other field of the event, as JSON |
| `created_at` | `text` | The time of the insert |

`timestamp`, `level`, `service`, `environment` and `created_at` are never null. Every other column is null when the event has no value for it. `timestamp`, `level`, `service`, `status`, `request_id` and `created_at` each have an index.

The table is part of NuxtHub's schema, so you read it with the same Drizzle client as the rest of your data. A route that returns the latest events, filtered by level:

```typescript [server/api/logs.get.ts]
import { db, schema } from '@nuxthub/db'
import { desc, eq } from 'drizzle-orm'

export default defineEventHandler(async (event) => {
  const query = getQuery(event)
  const level = typeof query.level === 'string' ? query.level : undefined
  const limit = Math.min(Number(query.limit) || 50, 200)

  return db.select()
    .from(schema.evlogEvents)
    .where(level ? eq(schema.evlogEvents.level, level) : undefined)
    .orderBy(desc(schema.evlogEvents.createdAt))
    .limit(limit)
})
```

Add that route to `exclude` in the `evlog` options, or every read of the logs adds an event to them.

## Retention

Events older than the retention window are deleted by a scheduled task. The window is seven days unless you set it:

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  evlog: { retention: '30d' },
})
```

The value is a whole number followed by one unit:

| Unit | Meaning | Example |
| --- | --- | --- |
| `d` | Days | `7d` |
| `h` | Hours | `24h` |
| `m` | Minutes | `60m` |

On any other value, such as `1w` or `1.5d`, the module throws `[evlog/nuxthub] Invalid retention format` when Nuxt starts or builds.

The module registers a Nitro task, `evlog:cleanup`, and enables `experimental.tasks` for it. The task deletes every row whose `created_at` is older than the window. It runs at about half the window, and at most once a day:

| Retention | Cron schedule | Runs |
| --- | --- | --- |
| `60m` | `*/30 * * * *` | Every 30 minutes |
| `24h` | `0 */12 * * *` | Every 12 hours |
| `7d` | `0 3 * * *` | Daily at 3:00 AM |
| `30d` | `0 3 * * *` | Daily at 3:00 AM |

An expired event stays in the table until the next run. A cleanup that fails logs `[evlog/nuxthub] Cleanup task failed:` with the error, and the next run tries again.

### Run the cleanup yourself

The module also adds a route that runs the task:

```bash [Terminal]
curl https://your-app.com/api/_cron/evlog-cleanup
```

When the `CRON_SECRET` environment variable is set, the route answers `401` unless the request carries it as a Bearer token:

```bash [Terminal]
curl -H "Authorization: Bearer your-secret" \
  https://your-app.com/api/_cron/evlog-cleanup
```

Without `CRON_SECRET`, anyone can call the route. Set it in production.

### On Vercel

On Vercel, a cron job calls that route. When you install the module with `nuxi module add`, it asks whether to create a `vercel.json` with the schedule, and adds or updates the entry when the file already exists:

```json [vercel.json]
{
  "crons": [
    {
      "path": "/api/_cron/evlog-cleanup",
      "schedule": "0 3 * * *"
    }
  ]
}
```

The schedule written there is the one derived from your retention at that moment. Update it by hand when you change `retention` later. When the project has a `CRON_SECRET` variable, Vercel sends it as the Bearer token on each cron call.

On Cloudflare Workers and the other platforms that run Nitro scheduled tasks, the task runs on its schedule with no cron to declare.

## When an insert fails

The drain inserts one row per event, in a single statement when the hook receives several events at once. An insert that fails on a connection error (`CONNECT_TIMEOUT`, `ETIMEDOUT`, `ECONNREFUSED`, `ECONNRESET` or `CONNECTION_ENDED`) is tried three times in all, after 500 ms and then 1 second. Any other error fails at once.

After the last attempt the drain logs `[evlog/nuxthub] Failed to insert events:` with the error and drops the events. The request that produced them is not affected. The drain sets no timeout of its own: your database driver decides how long an insert can take.

## When to add another drain

The table is a good fit for development, staging and small apps. For high traffic, or retention past a few weeks, add a hosted drain such as [Axiom](/drains/axiom) next to it.

The module registers its own `evlog:drain` hook, so a second drain runs alongside it, from `evlog.config.ts` or from a server plugin:

```typescript [server/plugins/evlog-drain.ts]
import { createAxiomDrain } from 'evlog/axiom'

export default defineNitroPlugin((nitroApp) => {
  // This runs alongside @evlog/nuxthub's built-in drain
  nitroApp.hooks.hook('evlog:drain', createAxiomDrain())
})
```
