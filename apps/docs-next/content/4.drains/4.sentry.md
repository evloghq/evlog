The drain sends every wide event to [Sentry Logs](https://docs.sentry.io/product/explore/logs/), with the event's fields as attributes. Turn on `issues` and the events that ended in a server error also open Sentry issues.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createSentryDrain } from 'evlog/sentry'

export default defineEvlog({
  service: 'my-app',
  drain: createSentryDrain({ issues: true }),
})
```

## Credentials

The drain needs the project DSN, from the project's Client Keys settings:

```bash [.env]
SENTRY_DSN=https://key@o0.ingest.sentry.io/0
```

`environment` and `release` come from the event's own `environment` and `version` unless you set `SENTRY_ENVIRONMENT` or `SENTRY_RELEASE`.

The DSN has the form `https://<public-key>@<host>/<project-id>`. The drain posts to `/api/<project-id>/envelope/` on that host and sends the public key in the `X-Sentry-Auth` header, with the secret key when the DSN carries one. Without a DSN, the drain logs an error that names `SENTRY_DSN` and sends nothing.

## Issues

With `issues: true`, an `error` or `fatal` event is sent twice: once as a log, once as an error event that opens an issue and triggers your alert rules. The issue carries the event's `trace_id`, so it links back to the log of the same request.

An event with a 4xx status stays a log. A declined card or an expired session is the client's doing, and should not page anyone.

The status is read from `error.status`, then from the event's `status`. `issues` is `false` by default, so upgrading evlog never starts opening issues on its own.

::callout{icon="i-lucide-triangle-alert" color="neutral"}
If the app also runs `@sentry/node` or another Sentry SDK with error capture on, leave `issues` off. Both would report the same failure, and every issue would open twice.
::

The error event is built from the wide event:

| Sentry field | Value |
| --- | --- |
| Exception type | `error.name`, else `Error` |
| Exception value | `error.message`, else the log body |
| Stack frames | Parsed from `error.stack`. Sentry groups on them |
| `fingerprint` | Set only when there is no stack: the type and the transaction, so a message that carries an id, such as `User 8231 not found`, stays one issue |
| `transaction` | `METHOD /path`, else `action`, else `path` |
| `level` | `error` or `fatal` |
| `environment`, `release` | As on the log |
| `tags` | `service`, plus your `tags` |
| `user.id` | `userId`, else `user.id` |
| `contexts.trace` | `traceId`, `spanId` and `parentSpanId` |

Other fields stay on the log. `contexts.trace.trace_id` is the event's `traceId`, the same value as the `trace_id` of its log, so the issue opens on that log. When the `traceId` came from an incoming `traceparent`, the same id links the issue to the other services in the trace. An event with no `traceId` gets one generated inside the drain, shared by its log and its issue only: other drains do not see it.

Browser errors sent through the [client transport](/events/client#send-events-to-your-server) open issues too, and anyone can post to that endpoint. Keep Sentry's spike protection or a project rate limit on.

## What a log carries

| Sentry log field | Value |
| --- | --- |
| `timestamp` | The event's `timestamp`, in seconds |
| `level` | The event's `level`, unchanged: `trace`, `debug`, `info`, `warn`, `error` or `fatal` |
| `severity_number` | The OpenTelemetry number: `1`, `5`, `9`, `13`, `17` or `21` |
| `body` | The first of `message`, `action` and `path` that is a non-empty string, else `evlog wide event` |
| `trace_id` | `traceId`, or a generated id |
| `span_id` | `spanId`, when the event has one |
| `attributes` | See below |

The attributes are, in this order:

- `sentry.environment` and `sentry.release`.
- `service`.
- Each entry of `tags`.
- Every other top-level field of the event. A string, a boolean, an integer and a double keep their type. An object or an array is sent as a JSON string, and `null` and `undefined` are left out.
- `user.id`, from `userId` or `user.id`, the attribute the Sentry SDK sets from its user scope.
- `sentry.sdk.name`, which is `evlog`, and `sentry.sdk.version`.

A field of the event replaces a tag of the same name.

## Requests and rate limits

Logs go first, in envelopes of at most 100 logs and 1 MiB of log payload. Issues follow, one request each.

- A failed log envelope fails the batch. When a batch takes several envelopes, a retry can resend the ones already accepted.
- An issue failure never fails the batch, so a retry does not resend logs because of it. An issue Sentry rejects, such as a `400`, is logged and skipped. A transient failure, a `5xx` or a timeout, stops the remaining issues of that batch.
- A retried issue keeps its `event_id`, so Sentry drops the duplicate.

The drain honours `X-Sentry-Rate-Limits` and `Retry-After` per data category, as the Sentry SDKs do:

| Sentry limits | What the drain does |
| --- | --- |
| The `error` category | Stops sending issues until the limit expires, logs one warning, and keeps sending logs. A burst costs one rejected request, not one per error |
| The `log_item` category | Fails the batch without sending it, with the remaining delay attached, so the [pipeline](/drains/pipeline#what-gets-retried) holds the batch until then |
| Every category: a `Retry-After` with no `X-Sentry-Rate-Limits`, or a limit with no category | Stops logs and issues |
| A `429` with neither header | Stops logs and issues for 60 seconds |

`drain.flush()` does not wait out a limit. It hands the held batch to `onDropped` with the reason `rate-limited`.

## Options

| Option | Env | What it is |
| --- | --- | --- |
| `dsn` | `SENTRY_DSN` | The project DSN |
| `environment` | `SENTRY_ENVIRONMENT` | Overrides the event's `environment` |
| `release` | `SENTRY_RELEASE` | Overrides the event's `version` |
| `tags` | | Extra attributes on every log |
| `issues` | | Also open issues for server errors, `false` by default |
| `timeout` | | Request timeout in ms, `5000` by default |
| `retries` | | Retries on a transient failure, `2` by default |

On Nuxt, each variable also reads with a `NUXT_` prefix, such as `NUXT_SENTRY_DSN`.

Each option is read from the argument first, then on Nuxt and Nitro from runtime config under the `sentry` namespace, then from its environment variable. [Custom drain](/drains/custom#which-config-wins) has the full order. On Nuxt, the `evlog.sentry` key of `nuxt.config.ts` is typed for `dsn`, `environment`, `release`, `tags` and `timeout`.

## When a request fails

A request is aborted after `timeout` milliseconds. A network error, a timeout, or a `408`, `429`, `502`, `503` or `504` response is retried up to `retries` times, with a wait that starts at 200 ms and doubles, and never into a rate limit Sentry announced. Any other status fails on the first response.

The drain never throws into your request. It logs `[evlog/sentry] Failed to send events:` with the error, and those events are lost unless the drain is wrapped in the [pipeline](/drains/pipeline).

## Find the logs

Open **Explore** > **Logs** in Sentry. Filter on any attribute, such as `service:my-app` or `level:error`, and follow `trace_id` from a log to its trace. Issues opened by the drain are under **Issues**.

## Troubleshooting

| What you see | Cause and fix |
| --- | --- |
| `[evlog/sentry] Missing DSN. Set SENTRY_DSN env var or pass to createSentryDrain()` | The variable is unset, or the server was not restarted after you added it |
| `Invalid Sentry DSN: missing public key` or `missing project ID` | The DSN is malformed. The drain logs it as a failed send. Copy the DSN again from **Settings** > **Projects** > **Client Keys (DSN)** |
| `401 Unauthorized` | The DSN is revoked or invalid. Generate a new one |
| An error is in Logs and not in Issues | `issues` is off, the event has a 4xx status, or Sentry is rate-limiting error events |

## Send without the drain

`sendToSentry()` and `sendBatchToSentry()` post from your own code. They take the options above as their second argument, read nothing from the environment, and throw when a log request fails:

```typescript [server/utils/sentry.ts]
import { sendToSentry, sendBatchToSentry } from 'evlog/sentry'

await sendToSentry(event, {
  dsn: process.env.SENTRY_DSN!,
})

await sendBatchToSentry(events, {
  dsn: process.env.SENTRY_DSN!,
})
```

`toSentryLog()` and `toSentryErrorEvent()` return the log and the error event the drain would send.
