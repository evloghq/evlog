The drain sends each wide event to [Better Stack](https://betterstack.com/telemetry) as one log line with the event's fields attached.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createBetterStackDrain } from 'evlog/better-stack'

export default defineEvlog({
  service: 'my-app',
  drain: createBetterStackDrain(),
})
```

## Credentials

Create an HTTP source in Better Stack and copy its source token and ingesting host:

```bash [.env]
BETTER_STACK_API_KEY=your-source-token
BETTER_STACK_ENDPOINT=https://s1234567.eu-nbg-2.betterstackdata.com
```

Without `BETTER_STACK_ENDPOINT`, the drain posts to `https://in.logs.betterstack.com`.

Sources are under **Telemetry** > **Sources**. Better Stack calls the credential a source token. evlog names the option `apiKey`, like every other drain, and sends it as `Authorization: Bearer`. Without it, the drain logs an error that names `BETTER_STACK_API_KEY` and sends nothing.

::callout{icon="i-lucide-arrow-up-circle" color="neutral"}
evlog 3 renamed the `sourceToken` option to `apiKey`, and `BETTER_STACK_SOURCE_TOKEN` to `BETTER_STACK_API_KEY`. `evlog upgrade` rewrites both. See [Upgrade to v3](/start/upgrade).
::

## Options

| Option | Env | What it is |
| --- | --- | --- |
| `apiKey` | `BETTER_STACK_API_KEY` | The source token |
| `endpoint` | `BETTER_STACK_ENDPOINT` | The ingesting host, `https://in.logs.betterstack.com` by default |
| `timeout` | | Request timeout in ms, `5000` by default |
| `retries` | | Retries on a transient failure, `2` by default |

On Nuxt, each variable also reads with a `NUXT_` prefix, such as `NUXT_BETTER_STACK_API_KEY`.

Each option is read from the argument first, then on Nuxt and Nitro from runtime config under the `betterStack` namespace, then from its environment variable. [Custom drain](/extend/custom-drain#which-config-wins) has the full order.

## What is sent

The drain posts the batch as a JSON array to `endpoint`. Each entry is the wide event with two changes:

| Field | Value |
| --- | --- |
| `dt` | The event's `timestamp`, under the name Better Stack reads the time from. `timestamp` itself is not sent |
| `message` | Added when the event has none. See below |
| Every other field | Unchanged, at the same depth |

Better Stack accepts arbitrary JSON fields, so `level`, `service`, `user.plan` and the rest are searchable as they are.

### The message field

A request's wide event has no top-level `message`: lines from `log.info()` sit under `requestLogs[].message` and a thrown error under `error.message`. Live tail headlines a line with `message`, and Better Stack builds its [`_pattern`](https://betterstack.com/docs/logs/using-logtail/using-pattern-field/) from it. So the drain sends the headline the pretty console prints for the event, followed by the error message:

| Event | `message` sent |
| --- | --- |
| `POST /api/checkout` answered `402` in 104 ms, `error.message` is `Payment failed` | `POST /api/checkout 402 in 104ms Payment failed` |
| `GET /api/hello` answered `200` in 12 ms | `GET /api/hello 200 in 12ms` |
| No `method`, `path`, `status`, `duration` or `error` | no `message` field |

Better Stack strips numbers, hex values and UUIDs when it builds `_pattern`, so a different duration or status code does not split a route into separate patterns.

A `message` already on the event is sent unchanged: one you set with `log.set({ message: 'Checkout completed' })`, or a tagged log such as `log.info('auth', 'User logged in')`. A tagged log reaches the drain only with `pretty: false`. With `pretty` on, the default in development, and `silent` off, it is printed to the console and not drained.

## Requests

Better Stack accepts at most 10 MiB per request, so a larger batch goes out as several requests that each fit, one after another. If one of them fails, the requests already accepted stay accepted, and a retry of the whole batch can send those events twice. A single event above 10 MiB still goes out in a request of its own.

## When a request fails

A request is aborted after `timeout` milliseconds. A network error, a timeout, or a `408`, `429`, `502`, `503` or `504` response is retried up to `retries` times, with a wait that starts at 200 ms and doubles. Any other status fails on the first response.

The drain never throws into your request. It logs `[evlog/better-stack] Failed to send events:` with the error, which starts with `Better Stack API error:` and the status, and those events are lost. Wrap the drain in the [pipeline](/drains/pipeline#what-gets-retried) to batch events and retry a failed batch.

## Find the logs

Open the source in Better Stack. Live tail streams events as they arrive, full-text search covers every field, and a structured query such as `level:error` or `service:my-app` filters on one. Dashboards and alerts take the same fields.

## Troubleshooting

| What you see | Cause and fix |
| --- | --- |
| `[evlog/better-stack] Missing apiKey. Set BETTER_STACK_API_KEY env var or pass to createBetterStackDrain()` | The variable is unset, or the server was not restarted after you added it |
| `401 Unauthorized` | The source token is invalid or revoked. Copy it again from **Telemetry** > **Sources** |
| `403 Forbidden` | The source is archived or deleted. Create a new one |

## Send without the drain

`sendToBetterStack()` and `sendBatchToBetterStack()` post from your own code. They take the options above as their second argument, read nothing from the environment, and throw when the request fails:

```typescript [server/utils/better-stack.ts]
import { sendToBetterStack, sendBatchToBetterStack } from 'evlog/better-stack'

await sendToBetterStack(event, {
  apiKey: process.env.BETTER_STACK_API_KEY!,
})

await sendBatchToBetterStack(events, {
  apiKey: process.env.BETTER_STACK_API_KEY!,
})
```

`toBetterStackEvent(event)` returns the entry the drain would send.
