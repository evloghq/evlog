[Sazabi](https://sazabi.com) reads your logs and answers questions about them. The drain sends each wide event to a log stream as one OTLP record, with nested fields flattened to attributes such as `user.plan` that Sazabi can filter on.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createSazabiDrain } from 'evlog/sazabi'

export default defineEvlog({
  service: 'my-app',
  drain: createSazabiDrain(),
})
```

## Credentials

In Sazabi, open **Log streams**, create or open an **OpenTelemetry** log stream, and copy its **Intake URL**. The stream's public key is part of the URL, so there is no header to set:

```bash [.env]
SAZABI_INTAKE_URL=https://your-key.us-west-2.intake.sazabi.com
```

evlog appends `/v1/logs`. A URL that already ends with it is used as is.

Trigger a request and the wide event appears in the log stream within a few seconds. Without an intake URL, the drain sends nothing and logs this each time it is called:

```text [Output]
[evlog/sazabi] Missing endpoint. Set SAZABI_INTAKE_URL, or pass to createSazabiDrain()
```

## What Sazabi receives

The drain reuses the [OTLP](/drains/otlp) encoder and posts JSON over HTTP with no auth header. Each wide event becomes one log record:

| Part of the event | Where it goes |
| --- | --- |
| `service`, `environment`, `version`, `region`, `commitHash` | Resource attributes: `service.name`, `deployment.environment`, `service.version`, `cloud.region`, `vcs.commit.id` |
| `level` | The OTLP severity number and text |
| `timestamp` | The record's time, in nanoseconds |
| `traceId`, `spanId` | The record's trace context, when they are 32 and 16 hex characters. Otherwise they stay attributes |
| Every other field | A log attribute. Nested fields flatten to dotted keys such as `user.plan` or `cart.total` |

The body is a one-line summary such as `POST /api/checkout (500)`. With `semanticConventions` on, the record also carries the OpenTelemetry names (`http.request.method`, `url.path`, `http.response.status_code`, `exception.*`, `gen_ai.*`) next to the evlog ones, and the resource gets `deployment.environment.name`.

Both are the evlog 3 defaults. To keep the 2.x output, set both options:

```typescript [evlog.config.ts]
createSazabiDrain({
  recordShape: 'json',
  semanticConventions: false,
})
```

In Sazabi, open the log stream and ask a question in plain language, such as "how many checkout requests failed in the last hour?", or filter on any field the wide event carries.

## Options

| Option | Env | What it is |
| --- | --- | --- |
| `endpoint` | `SAZABI_INTAKE_URL` | The stream's intake URL. Required |
| `serviceName` | `SAZABI_SERVICE_NAME`, `OTEL_SERVICE_NAME` | `service.name` on the resource. The event's `service` by default |
| `resourceAttributes` | | Extra resource attributes, such as `{ 'deployment.region': 'us-west-2' }`. They replace the derived ones that share a key |
| `recordShape` | | `'compact'` by default: a one-line body and dotted attributes. `'json'` sends the whole event as the body |
| `semanticConventions` | | `true` by default: also emits `http.request.method`, `url.path`, `exception.*` and the like |
| `timeout` | | Request timeout in ms, `5000` by default |
| `retries` | | Retries on a transient failure, `2` by default |

An option passed to `createSazabiDrain()` wins. On Nuxt and Nitro, `runtimeConfig.evlog.sazabi` is read next, then `runtimeConfig.sazabi`. The environment comes last, where `NUXT_SAZABI_INTAKE_URL` and `NUXT_SAZABI_SERVICE_NAME` are read before the unprefixed names.

## When a request fails

A request that gets no answer within `timeout` is aborted. The drain retries a network error, a timeout and a `408`, `429`, `502`, `503` or `504` response, up to `retries` times, with exponential backoff and jitter. It waits for the response's `Retry-After` when that is 10 seconds or less, and stops retrying when it is longer. Any other status fails at once.

After the last attempt the drain logs `[evlog/sazabi] Failed to send events:` with the error and drops the events. The request that produced them is not affected. Two cases to recognise in that log line:

| Error | What to do |
| --- | --- |
| `OTLP API error: 4xx` | Copy the intake URL again from the log stream. A truncated host or an old stream's URL is rejected. The message says OTLP because the request goes through the OTLP encoder |
| `OTLP collector rejected N log record(s)` | Sazabi accepted the request and refused some records in it. The drain does not resend them |

Wrapped in the [pipeline](/drains/pipeline), the drain makes one attempt per batch and the pipeline's `retry` takes over, unless you set `retries` yourself.

## Send without the drain

A script or a job can post events directly:

```typescript [scripts/send.ts]
import { sendBatchToSazabi, sendToSazabi } from 'evlog/sazabi'

await sendToSazabi(event, { endpoint: process.env.SAZABI_INTAKE_URL! })
await sendBatchToSazabi(events, { endpoint: process.env.SAZABI_INTAKE_URL! })
```

Both take a complete config, read nothing from the environment, and reject when the request fails. `toSazabiOTLPConfig()` and `toSazabiOTLPEndpoint()` are exported too, for code that builds the OTLP request itself.
