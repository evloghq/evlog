OTLP is the protocol every OpenTelemetry backend accepts: Grafana, Honeycomb, New Relic, a collector you run. The drain turns each wide event into one log record.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createOTLPDrain } from 'evlog/otlp'

export default defineEvlog({
  service: 'my-app',
  drain: createOTLPDrain(),
})
```

```bash [.env]
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
```

The drain reads the standard OpenTelemetry variables: `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` is used as the full logs URL, `OTEL_EXPORTER_OTLP_ENDPOINT` (or `OTLP_ENDPOINT`) gets `/v1/logs` appended, and `OTEL_SERVICE_NAME` names the service.

The drain speaks OTLP over HTTP, as JSON or protobuf. It does not speak gRPC. Without an endpoint, it logs an error that names the three endpoint variables and sends nothing.

## Environment variables

The names follow the [OpenTelemetry exporter specification](https://opentelemetry.io/docs/specs/otel/protocol/exporter/), so a deployment that already configures an OpenTelemetry SDK through the environment needs no variable of its own for evlog.

| Variable | What it sets |
| --- | --- |
| `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` | The full logs URL, used as is. Wins over the two below |
| `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTLP_ENDPOINT` | The base URL. The drain appends `/v1/logs` |
| `OTEL_EXPORTER_OTLP_HEADERS`, `OTLP_HEADERS` | Headers as `key=value` pairs, comma-separated. Values are percent-decoded |
| `OTEL_EXPORTER_OTLP_LOGS_HEADERS` | Headers for logs only. Merged over the generic ones, and wins on a shared key |
| `OTEL_EXPORTER_OTLP_LOGS_COMPRESSION`, `OTEL_EXPORTER_OTLP_COMPRESSION` | `gzip` or `none`. The logs variable wins |
| `OTEL_EXPORTER_OTLP_LOGS_PROTOCOL`, `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/json` or `http/protobuf`. The logs variable wins. `grpc` is not supported |
| `OTEL_SERVICE_NAME` | `service.name` on the resource |
| `OTEL_RESOURCE_ATTRIBUTES` | Resource attributes as `key=value` pairs, comma-separated |

Nuxt adds four names of its own: `NUXT_OTLP_ENDPOINT`, a base URL that wins over every endpoint variable above, `NUXT_OTLP_SERVICE_NAME`, `NUXT_OTLP_HEADERS`, and `NUXT_OTLP_AUTH`, which becomes the `Authorization` header when no headers variable is set.

## Options

| Option | Default | What it is |
| --- | --- | --- |
| `endpoint` | required | The OTLP HTTP base URL, such as `http://localhost:4318`. The drain appends `/v1/logs` |
| `headers` | from the environment | HTTP headers, for authentication. When set, the header variables are not read |
| `serviceName` | the event's `service` | `service.name` on the resource |
| `resourceAttributes` | | Extra resource attributes. They win over `OTEL_RESOURCE_ATTRIBUTES` and over the attributes taken from the event |
| `recordShape` | `'compact'` | `'compact'` or `'json'`. See [The record shape](#the-record-shape) |
| `semanticConventions` | `true` | Also emit the OpenTelemetry attribute names. See [Semantic conventions](#semantic-conventions) |
| `protocol` | `'http/json'` | `'http/json'` or `'http/protobuf'` |
| `compression` | `'none'` | `'gzip'` compresses the body and sends `Content-Encoding: gzip` |
| `timeout` | `5000` | Milliseconds before a request is aborted |
| `retries` | `2` | Retries after a transient failure |

```typescript [evlog.config.ts]
createOTLPDrain({
  endpoint: 'http://localhost:4318',
  serviceName: 'my-api',
  headers: {
    'Authorization': 'Bearer xxx',
  },
  resourceAttributes: {
    'deployment.environment': 'staging',
  },
})
```

Each option is read from the argument first, then on Nuxt and Nitro from runtime config under the `otlp` namespace, then from the environment. [Custom drain](/drains/custom#which-config-wins) has the full order. On Nuxt, the `evlog.otlp` key of `nuxt.config.ts` is typed for `endpoint`, `serviceName`, `resourceAttributes`, `headers` and `timeout`.

## Where to send

The same drain talks to a collector you run and to a managed gateway. Only the endpoint and the headers change.

A collector needs an OTLP HTTP receiver:

```yaml [otel-collector.yaml]
receivers:
  otlp:
    protocols:
      http:
        endpoint: 0.0.0.0:4318

exporters:
  debug:
    verbosity: detailed

service:
  pipelines:
    logs:
      receivers: [otlp]
      exporters: [debug]
```

```bash [Terminal]
docker run --rm -p 4318:4318 \
  -v $(pwd)/otel-collector.yaml:/etc/otelcol/config.yaml \
  otel/opentelemetry-collector:latest
```

From there the collector forwards to Loki, ClickHouse, Elasticsearch, a managed backend, or several at once.

A managed gateway takes a credential in a header:

::code-group
```bash [Grafana Cloud]
OTLP_ENDPOINT=https://otlp-gateway-prod-us-central-0.grafana.net/otlp
OTEL_EXPORTER_OTLP_HEADERS=Authorization=Basic%20base64-encoded-credentials
```

```bash [Honeycomb]
OTLP_ENDPOINT=https://api.honeycomb.io
OTLP_HEADERS=x-honeycomb-team=your-api-key
```
::

Grafana Cloud documents its header URL-encoded, so the `%20` is a space. The drain decodes it.

## The record shape

In evlog 3, records are compact by default:

- The body is a one-line summary, such as `POST /api/checkout (500)`.
- Nested fields become dotted attributes, such as `user.id`.
- Records also carry the OpenTelemetry semantic conventions: `http.request.method`, `url.path`, `http.response.status_code`, `exception.*` and `gen_ai.*`. The evlog field names stay next to them.

For the same 100 events, that takes the request from 151,235 to 140,250 bytes as JSON. To keep the 2.x output:

```typescript [evlog.config.ts]
createOTLPDrain({ recordShape: 'json', semanticConventions: false })
```

HyperDX and Sazabi are built on this encoder, so they share the same defaults.

The two shapes, for the same event:

::code-group
```json [compact (default)]
{
  "body": { "stringValue": "POST /api/checkout (500)" },
  "attributes": [
    { "key": "method", "value": { "stringValue": "POST" } },
    { "key": "user.id", "value": { "stringValue": "usr_123" } },
    { "key": "user.plan", "value": { "stringValue": "premium" } }
  ]
}
```
```json [json]
{
  "body": { "stringValue": "{\"timestamp\":\"…\",\"method\":\"POST\",\"user\":{\"id\":\"usr_123\"}}" },
  "attributes": [
    { "key": "method", "value": { "stringValue": "POST" } },
    { "key": "user", "value": { "kvlistValue": { "values": [
      { "key": "id", "value": { "stringValue": "usr_123" } },
      { "key": "plan", "value": { "stringValue": "premium" } }
    ] } } }
  ]
}
```
::

In the compact shape, the summary is the method, the path and the status, and the service name when the event has none of them. A backend that clusters messages into templates needs that stable body. In the `json` shape, the body is the whole event serialized, next to the same fields as attributes.

Only plain objects are flattened. An array is one attribute, because indexing it as `gen_ai.tools.0.name` would turn a list into an unbounded set of attribute keys. Anything else that is not a plain object, such as a `Date`, is one attribute too, and an empty object stays a single `{}` attribute.

## How fields are mapped

| evlog field | OTLP field |
| --- | --- |
| `timestamp` | `timeUnixNano` |
| `level` | `severityNumber` and `severityText` |
| `traceId`, `spanId` | The record's `traceId` and `spanId` |
| `service` | Resource attribute `service.name` |
| `environment` | Resource attribute `deployment.environment`, plus `deployment.environment.name` with `semanticConventions` |
| `version` | Resource attribute `service.version` |
| `region` | Resource attribute `cloud.region` |
| `commitHash` | Resource attribute `vcs.commit.id` |
| Every other field | A log attribute |

`null` and `undefined` are left out at every depth, in both shapes. Events are grouped into one resource per distinct `service`, `environment`, `version`, `region` and `commitHash`, under a scope named `evlog`. For a resource attribute, `OTEL_RESOURCE_ATTRIBUTES` is the lowest source, the event's fields replace it, and `resourceAttributes` replaces both.

Attribute values keep their type:

| Value | Sent as |
| --- | --- |
| A string | `stringValue` |
| A boolean | `boolValue` |
| A safe integer | `intValue` |
| Another finite number | `doubleValue` |
| A non-empty array whose elements share one primitive type | `arrayValue` |
| A nested plain object, in the `json` shape | `kvlistValue` |
| Anything else | A JSON string in `stringValue` |

### Severity

| evlog level | `severityNumber` | `severityText` |
| --- | --- | --- |
| `trace` | 1 | TRACE |
| `debug` | 5 | DEBUG |
| `info` | 9 | INFO |
| `warn` | 13 | WARN |
| `error` | 17 | ERROR |
| `fatal` | 21 | FATAL |

### Trace context

`traceId` must be 32 hex characters and `spanId` 16, and neither all zeros. A valid id goes to the record's trace fields in lowercase. An invalid one stays an ordinary attribute, because a collector would reject it in a trace field.

`spanId` is the span of the request that produced the event. The [trace context enricher](/events/enrichers#trace-context) records the caller's span from an incoming `traceparent` as `parentSpanId`, which is sent as an attribute. To link the record to your server span, add [`createOtelPlugin()`](/compare/opentelemetry#attach-the-active-span-to-every-request-event) from `evlog/otel`, which sets `traceId` and `spanId` from the active OpenTelemetry span.

### Semantic conventions

With `semanticConventions` on, each record also carries the [OpenTelemetry semantic convention](https://opentelemetry.io/docs/specs/semconv/) names for the fields evlog knows, so a backend with built-in HTTP, error and GenAI views picks them up.

| evlog field | Attribute |
| --- | --- |
| `method` | `http.request.method` |
| `path` | `url.path`, without the query string and the fragment |
| `status` | `http.response.status_code` |
| `userAgent.raw` | `user_agent.original` |
| `error.name`, `error.message`, `error.stack` | `exception.type`, `exception.message`, `exception.stacktrace` |
| `gen_ai.*` | The same name. The `gen_ai` block already uses the OpenTelemetry names for `request.model`, `provider.name`, `response.id`, `response.finish_reasons`, `usage.input_tokens`, `usage.output_tokens`, `usage.cache_read.input_tokens`, `usage.cache_write.input_tokens`, `conversation.id` and `agent.name` |

A field is mapped only when it has the type the convention requires, and an attribute the event already sets under that name is not overwritten. Set `semanticConventions: false` to send the evlog names only.

## Protobuf and compression

With `protocol: 'http/protobuf'`, the drain sends the same request as binary protobuf with `Content-Type: application/x-protobuf`. Use it for a collector or a gateway that accepts protobuf only, or to shrink the payload:

```typescript [evlog.config.ts]
createOTLPDrain({
  endpoint: 'http://localhost:4318',
  protocol: 'http/protobuf',
  compression: 'gzip',
})
```

The encoder ships with evlog, has no dependencies, and is loaded only when this protocol is selected. To encode a request yourself, `evlog/otlp/protobuf` exports `encodeOTLPLogsRequest()`.

A `protocol` or `compression` value outside the two the drain accepts, such as `grpc`, logs an error and the drain sends nothing.

## When a request fails

A request is aborted after `timeout` milliseconds. A network error, a timeout, or a `408`, `429`, `502`, `503` or `504` response is retried up to `retries` times. The wait starts at 200 ms, doubles, carries jitter, and is never shorter than a `Retry-After` header of up to 10 seconds. Any other status fails on the first response.

The drain never throws into your request. It logs `[evlog/otlp] Failed to send events:` with the error, which starts with `OTLP API error:` and the status, and those events are lost. Wrap the drain in the [pipeline](/drains/pipeline#what-gets-retried) to batch events and retry a failed batch.

A collector can accept a request and still refuse some of its records, answering `2xx` with a `partialSuccess`. The drain reads it from JSON and protobuf responses alike and does not retry, since the same records would be refused again:

```text [Console]
OTLP collector rejected 2 log record(s): invalid trace id
```

Inside the pipeline, the batch goes to `onDropped` with the reason `rejected`, and `drain.stats()` counts the 2 records as dropped and the rest as delivered. A `partialSuccess` with an `errorMessage` and no rejected record is logged as a warning. The HyperDX, Sazabi and PostHog logs drains send through this code and behave the same way.

## Troubleshooting

| What you see | Cause and fix |
| --- | --- |
| `[evlog/otlp] Missing endpoint. Set OTEL_EXPORTER_OTLP_LOGS_ENDPOINT, OTEL_EXPORTER_OTLP_ENDPOINT, OTLP_ENDPOINT env var, or pass to createOTLPDrain()` | No endpoint is set, or the server was not restarted after you added it |
| `401 Unauthorized` | The headers are missing or wrong. Check the `key=value` format of the headers variable, the credential, and the endpoint |
| `404 Not Found` | The endpoint is not an OTLP HTTP base URL. Give the base URL without `/v1/logs`, and not a gRPC port. For a receiver that accepts protobuf only, set `protocol: 'http/protobuf'` |
| No error and no logs | Send to a local collector first to check the format. Some backends take a minute or two to show a record |

## Send without the drain

`sendToOTLP()` and `sendBatchToOTLP()` post from your own code. They take the options above as their second argument, read nothing from the environment, and throw when the request fails. On a partial success they throw a `DrainDeliveryError` whose `rejected` holds the count.

```typescript [server/utils/otlp.ts]
import { sendToOTLP, sendBatchToOTLP, toOTLPLogRecord } from 'evlog/otlp'

await sendToOTLP(event, {
  endpoint: 'http://localhost:4318',
})

await sendBatchToOTLP(events, {
  endpoint: 'http://localhost:4318',
})

// Convert an event to an OTLP record, to inspect it
const otlpRecord = toOTLPLogRecord(event)
```
