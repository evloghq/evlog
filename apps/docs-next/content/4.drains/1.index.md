A drain is where events leave the process. You name it once in `evlog.config.ts`, and every route, job and script sends its events there. Your handlers never import it.

::drain-timeline
::

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'

export default defineEvlog({
  service: 'my-app',
  drain: createAxiomDrain(),
})
```

The drain runs fire-and-forget: the response does not wait for it, and a drain that throws cannot fail the request. On Cloudflare Workers and Vercel, evlog registers the drain with `waitUntil()`, so the send finishes after the response has gone. [Lifecycle](/events/lifecycle) has the order of the stages before it.

## Wire it into your framework

Every integration loads `evlog.config.ts`, as [Installation](/start/installation#3-wire-your-framework) shows, so the drain above reaches every framework. Set it somewhere else when it needs the app's runtime to be built, or when it belongs to one integration only:

- On Nuxt, Nitro and TanStack Start, a server plugin registers it on the `evlog:drain` hook. The hook runs next to the drain of the config file, and an event reaches both.
- Every other integration takes a `drain` option. It replaces the drain given to `initLogger()` for the request events that integration emits. A `log.info()` outside a request still goes to the one in `initLogger()`.

export default defineNitroPlugin((nitroApp) => {

})

On Next.js, the `drain` of `createEvlog()` receives request events only. To drain `log.*` calls too, start the logger from `instrumentation.ts`, as [Next.js](/integrations/next#start-the-logger-from-evlogconfigts) shows. Every example on the drain pages uses the config file. Swap `createAxiomDrain()` in the tab of your framework for the factory of the page you are on.

## Destinations

Every drain ships with the `evlog` package, under its own entry point, and reads its credentials from the environment when you pass none.

::drain-picker
::

Each drain has its own page:

| Drain | Import | Required variables | What you get |
| --- | --- | --- | --- |
| [Axiom](/drains/axiom) | `evlog/axiom` | `AXIOM_API_KEY`, `AXIOM_DATASET` | Every field queryable on arrival, no schema |
| [PostHog](/drains/posthog) | `evlog/posthog` | `POSTHOG_API_KEY` | Logs on the person and next to their session replay |
| [Sentry](/drains/sentry) | `evlog/sentry` | `SENTRY_DSN` | Logs, and an issue for each server error |
| [Datadog](/drains/datadog) | `evlog/datadog` | `DD_API_KEY` | Fields become log attributes you can facet on |
| [Better Stack](/drains/better-stack) | `evlog/better-stack` | `BETTER_STACK_API_KEY` | Each field a column to filter and chart |
| [OTLP](/drains/otlp) | `evlog/otlp` | `OTEL_EXPORTER_OTLP_ENDPOINT` | Any collector: Grafana, Honeycomb, New Relic |
| [HyperDX](/drains/hyperdx) | `evlog/hyperdx` | `HYPERDX_API_KEY` | OTLP, cloud or self-hosted |
| [Sazabi](/drains/sazabi) | `evlog/sazabi` | `SAZABI_INTAKE_URL` | OTLP to a log stream; the URL is the credential |
| [Grafana Loki](/drains/loki) | `evlog/loki` | `LOKI_ENDPOINT` | A few labels, the whole event as JSON |
| [ClickHouse](/drains/clickhouse) | `evlog/clickhouse` | `CLICKHOUSE_ENDPOINT` | Rows you query with SQL |
| [File system](/drains/fs) | `evlog/fs` | None | NDJSON in `.evlog/logs`, for you and your agent |
| [Memory](/drains/memory) | `evlog/memory` | None | A ring buffer to assert on in tests |
| [NuxtHub](/drains/nuxthub) | `@evlog/nuxthub` | None | Events in your NuxtHub database, deleted on a schedule |
| [HTTP](/drains/http) | `evlog/http` | None | Browser logs posted to your server, then through the same drain |

A `create*Drain()` factory needs no argument when its variables are set, and the same names work in every framework. Each drain page lists its optional variables. Each setting is resolved in this order:

1. The option passed to the factory
2. `runtimeConfig.evlog.<name>`, on Nuxt and Nitro
3. `runtimeConfig.<name>`, on Nuxt and Nitro
4. The environment variable, with its `NUXT_` form read first

On Nuxt, the runtime config gives a setting a default that `NUXT_AXIOM_DATASET` overrides per deployment:

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['evlog/nuxt'],
  runtimeConfig: {
    axiom: { dataset: 'production-logs' },
  },
})
```

Do not declare a key as an empty placeholder there. `apiKey: ''` counts as set, and hides an `AXIOM_API_KEY` variable.

## When a drain cannot send

| Case | What happens |
| --- | --- |
| A required setting is missing | The drain logs which variable to set with `console.error`, and sends nothing |
| A request fails | An HTTP drain aborts the request after 5 seconds and retries a transient failure twice. Then it logs `[evlog/<name>] Failed to send events:` and drops the events |
| You call `sendTo*()` or `sendBatchTo*()` yourself | These helpers take a complete config, read nothing from the environment, and reject on failure, so a script or a test sees the error |

In the first two cases the request that produced the events is not affected. `timeout` and `retries` change the two defaults on every HTTP drain.

## Batch, retry, fan out

One HTTP call per event does not scale. Wrap a drain in the :term[pipeline]{of="pipeline"} and it buffers events, sends them in batches, and retries with backoff:

```typescript [evlog.config.ts]
import { defineEvlog, type DrainContext } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createDrainPipeline } from 'evlog/pipeline'

const pipeline = createDrainPipeline<DrainContext>({
  batch: { size: 50, intervalMs: 5000 },
  retry: { maxAttempts: 3 },
})

export default defineEvlog({
  service: 'my-app',
  drain: pipeline(createAxiomDrain()),
})
```

| Option | Default | What it does |
| --- | --- | --- |
| `batch.size` | `50` | Events per request |
| `batch.intervalMs` | `5000` | Longest wait before a partial batch is sent |
| `retry.maxAttempts` | `3` | Attempts per batch, backoff `exponential` by default |
| `maxBufferSize` | `1000` | Buffered events before the oldest are dropped |

To send to two destinations, write one drain that calls both, and wrap that: the two share one buffer and one retry budget. Inside it, call them with `Promise.allSettled`, so a slow or failing destination does not hold back the other. [Pipeline](/drains/pipeline) lists every option and what happens to a batch that fails.

A script has no request to end, so call `await drain.flush()` on the wrapped drain before the process exits, or the events still in the buffer are lost.

## Your own

A drain is a function that receives the batch. Each entry is a `DrainContext`: the `event`, the `request` it came from (`method`, `path`, `requestId`), and that request's `headers` without `authorization`, `cookie`, `set-cookie`, `x-api-key`, `x-auth-token` and `proxy-authorization`. Four pages cover what is not a destination:

| Page | Import | What it does |
| --- | --- | --- |
| [Custom drain](/extend/custom-drain) | `evlog/toolkit` | Write a drain for any backend, with the config, timeouts and retries the built-in drains use |
| [Pipeline](/drains/pipeline) | `evlog/pipeline` | Batch, retry and buffer any drain, and flush on shutdown and at request end |
| [Stream](/drains/stream) | `evlog/stream` | Subscribe to live events in-process or over a local SSE server |
| [Diagnostics channel](/extend/diagnostics-channel) | `evlog/diagnostics` | Publish events on `node:diagnostics_channel` for packages that do not import evlog, and for Tail Workers |
