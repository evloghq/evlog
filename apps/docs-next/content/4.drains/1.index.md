::

A drain is where events leave the process. You name it once in `evlog.config.ts`, and every route, job and script sends its events there. Your handlers never import it.

::drain-timeline
::

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'

export default defineEvlog({
  service: 'my-app',
  drain: createAxiomDrain(),
})
```

The drain runs fire-and-forget: the response does not wait for it, and a drain that throws cannot fail the request.

## Destinations

Every drain ships with the `evlog` package, under its own entry point, and reads its credentials from the environment when you pass none.

::drain-picker
::

Two more live outside that list: [HTTP](/drains/http) ships browser logs to your own server, where they go through the same drain, and [NuxtHub](/drains/nuxthub) stores events in your NuxtHub database.

## Batch, retry, fan out

One HTTP call per event does not scale. Wrap a drain in the :term[pipeline]{of="pipeline"} and it buffers events, sends them in batches, and retries with backoff:

```typescript [evlog.config.ts]
import { defineEvlog, type DrainContext } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createDrainPipeline } from 'evlog/pipeline'

const pipeline = createDrainPipeline<DrainContext>({
  batch: { size: 50, intervalMs: 5000 },
  retry: { maxAttempts: 3 },
})

export default defineEvlog({
  service: 'my-app',
  drain: pipeline(createAxiomDrain()),
})
```

| Option | Default | What it does |
| --- | --- | --- |
| `batch.size` | `50` | Events per request |
| `batch.intervalMs` | `5000` | Longest wait before a partial batch is sent |
| `retry.maxAttempts` | `3` | Attempts per batch, backoff `exponential` by default |
| `maxBufferSize` | `1000` | Buffered events before the oldest are dropped |

To send to two destinations, write one drain that calls both, and wrap that: the two share one buffer and one retry budget.
