[HyperDX](https://hyperdx.io) ingests OpenTelemetry. The drain encodes each wide event as one OTLP log record and sends it with your ingestion key.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createHyperDXDrain } from 'evlog/hyperdx'

export default defineEvlog({
  service: 'my-app',
  drain: createHyperDXDrain(),
})
```

## Credentials

```bash [.env]
HYPERDX_API_KEY=your-ingestion-key
```

The drain sends to `https://in-otel.hyperdx.io` by default. For a self-hosted HyperDX, set `HYPERDX_OTLP_ENDPOINT` to its OTLP HTTP base URL; evlog appends `/v1/logs`.

Copy the ingestion API key from your team's HyperDX dashboard. The drain sends it as the value of the `authorization` header, with no `Bearer` prefix, as [HyperDX's OpenTelemetry setup](https://hyperdx.io/docs/install/opentelemetry) documents. Without the key, the drain logs an error that names `HYPERDX_API_KEY` and sends nothing, on a self-hosted instance too.

## Cloud or self-hosted

HyperDX is open source, so the same drain targets a managed account and a cluster you run. Only the endpoint changes:

```bash [.env]
HYPERDX_OTLP_ENDPOINT=http://hyperdx.internal:4318
HYPERDX_API_KEY=your-key
```

Give the base URL, the value you would put in the `endpoint` of an `otlphttp` exporter, not the signal path. A self-hosted collector on the default OTLP HTTP port is `http://host:4318`.

## Options

| Option | Env | What it is |
| --- | --- | --- |
| `apiKey` | `HYPERDX_API_KEY` | The ingestion key, sent as the `authorization` header |
| `endpoint` | `HYPERDX_OTLP_ENDPOINT` | The OTLP HTTP base URL |
| `serviceName` | `HYPERDX_SERVICE_NAME`, `OTEL_SERVICE_NAME` | `service.name` on the resource. Defaults to the event's `service` |
| `resourceAttributes` | | Extra resource attributes |
| `recordShape` | | `'compact'` by default: a one-line body and dotted attributes. `'json'` sends the whole event as the body |
| `semanticConventions` | | `true` by default: also emits `http.request.method`, `url.path`, `exception.*` and the like |
| `timeout` | | Request timeout in ms, `5000` by default |
| `retries` | | Retries on a transient failure, `2` by default |

On Nuxt, each variable also reads with a `NUXT_` prefix, such as `NUXT_HYPERDX_API_KEY`.

`HYPERDX_SERVICE_NAME` wins over `OTEL_SERVICE_NAME`. Each option is read from the argument first, then on Nuxt and Nitro from runtime config under the `hyperdx` namespace, then from its environment variable. [Custom drain](/drains/custom#which-config-wins) has the full order.

To keep the 2.x output, set both shape options:

```typescript [evlog.config.ts]
createHyperDXDrain({
  apiKey: process.env.HYPERDX_API_KEY!,
  recordShape: 'json',
  semanticConventions: false,
})
```

## What is sent

The drain maps its options to the [OTLP drain](/drains/otlp)'s and sends through the same code: an OTLP `ExportLogsServiceRequest` as JSON, posted to `{endpoint}/v1/logs` with `Content-Type: application/json`. The [field mapping](/drains/otlp#how-fields-are-mapped), severity numbers, trace context and attribute types are the ones on that page.

Three things the OTLP drain does are not available here:

- The body is always JSON and never compressed. There is no `protocol` or `compression` option.
- The only header is `authorization`. There is no `headers` option.
- `OTEL_RESOURCE_ATTRIBUTES` and the `OTEL_EXPORTER_OTLP_*` variables are not read. Use `resourceAttributes`.

HyperDX's own collector example sets `compression: gzip` and also lists a gRPC endpoint on port 4317. The drain uses neither: it posts uncompressed JSON to the HTTP endpoint.

## When a request fails

A request is aborted after `timeout` milliseconds. A network error, a timeout, or a `408`, `429`, `502`, `503` or `504` response is retried up to `retries` times, with a wait that starts at 200 ms and doubles. Any other status fails on the first response.

The drain never throws into your request. It logs `[evlog/hyperdx] Failed to send events:` with the error, and those events are lost. The error starts with `OTLP API error:`, because the request goes through the OTLP sender. Wrap the drain in the [pipeline](/drains/pipeline#what-gets-retried) to batch events and retry a failed batch.

A `2xx` response that rejects some records is a failure the drain does not retry, as on the [OTLP drain](/drains/otlp#when-a-request-fails).

## Find the logs

Search in HyperDX filters on any field of the wide event: the level, the service, the path, your own attributes. Live tail streams incoming logs, and dashboards chart the same fields.

## Troubleshooting

| What you see | Cause and fix |
| --- | --- |
| `[evlog/hyperdx] Missing apiKey. Set HYPERDX_API_KEY, or pass to createHyperDXDrain()` | The variable is unset, or the server was not restarted after you added it |
| `401 Unauthorized`, or the ingest is rejected | The key is invalid or not allowed to ingest. Use the ingestion key, the value HyperDX shows for `authorization` in its OpenTelemetry examples |

## Send without the drain

`sendToHyperDX()` and `sendBatchToHyperDX()` post from your own code. They take the options above as their second argument, read nothing from the environment, and throw when the request fails:

```typescript [server/utils/hyperdx.ts]
import { sendToHyperDX, sendBatchToHyperDX } from 'evlog/hyperdx'

await sendToHyperDX(event, {
  apiKey: process.env.HYPERDX_API_KEY!,
})

await sendBatchToHyperDX(events, {
  apiKey: process.env.HYPERDX_API_KEY!,
  endpoint: 'https://in-otel.hyperdx.io',
})
```

`toHyperDXOTLPConfig(config)` returns the OTLP options the drain sends with, and `HYPERDX_DEFAULT_OTLP_HTTP_ENDPOINT` is the default endpoint.
