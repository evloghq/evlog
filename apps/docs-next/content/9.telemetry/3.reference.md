Every run sends the same event. You do not declare a schema per command, and you cannot add a field next to `command` or `durationMs`: your own data goes in `flags` and `custom`.

## The event

An event, abridged:

```jsonc
{
  "event": "run",
  "command": "sync",
  "durationMs": 412,
  "outcome": "success",
  "flags": { "dryRun": true, "output": "<set>" },
  "tool": { "name": "my-tool", "version": "1.0.0" },
  "env": {
    "node": "20.11",
    "ci": false,
    "provider": null,
    "tty": true,
    "agent": "cursor"   // std-env: cursor, claude, codex, … or null
  },
  "machineId": "ab3f…", // hashed; omitted in ephemeral CI
  "custom": { "itemsSynced": 42 }
}
```

The type is `RunEvent`, and these are all of its fields:

| Field | Type | What it holds |
| --- | --- | --- |
| `event` | `'run'` | Always `run` |
| `command` | `string` | The command name. Nested citty subcommands join with a space |
| `durationMs` | `number` | Run duration in milliseconds |
| `outcome` | `'success' \| 'error'` | `error` when the handler threw or called `telemetry.fail()` |
| `errorCode` | `string`, optional | The `code` of the thrown error, or the argument of `telemetry.fail()` |
| `flags` | object | The flags that were passed, sanitized |
| `tool.name`, `tool.version` | `string` | The `name` and `version` options |
| `env.node` | `string` | Node.js version |
| `env.ci` | `boolean` | Whether the run is in CI |
| `env.provider` | `string \| null` | The CI provider, when detected |
| `env.tty` | `boolean` | Whether the terminal is interactive |
| `env.agent` | `string \| null` | The AI coding agent, when detected: `cursor`, `claude`, `codex` |
| `env.os` | `string \| null` | `process.platform`: `darwin`, `linux`, `win32` |
| `env.arch` | `string \| null` | `process.arch`: `arm64`, `x64` |
| `env.environment` | `string` | The stage: `development`, `preview`, `production`, or your own value |
| `machineId` | `string`, optional | 16 hexadecimal characters, hashed from a random id stored on the machine. Omitted in CI |
| `custom` | object | Your fields, from `telemetry.set()` |
| `idempotencyKey` | `string` | 32 hexadecimal characters, hashed from `command`, `tool`, `machineId` and the timestamp cut to the second |
| `timestamp` | `string` | ISO 8601, taken when the run starts |

`flags` and `custom` are flat: each value is a boolean, a number or a string.

`env.environment` is the first of these that is set: `EVLOG_TELEMETRY_ENV`, `VERCEL_ENV`, the `environment` option, `NODE_ENV`, then `development`.

Two runs of one command by one machine within the same second share an `idempotencyKey`. In CI there is no `machineId`, so that holds across machines too.

## What is collected

Raw `argv` is never read. Flags come from the parser, and each value is recorded by its type:

| Value | Recorded as |
| --- | --- |
| Boolean, number | The value: `json: true`, `limit: 50` |
| String listed in `collect.flags` for that flag | The value: `format: "json"` |
| Any other string | `"<set>"`, exported as `FLAG_VALUE_SET` |
| Array, object | `true` |

```typescript [src/index.ts]
collect: {
  flags: { format: ['json', 'csv'] },           // --format json → "json"; --format yaml → "<set>"
  fields: { framework: ['nuxt', 'next'] },      // telemetry.set({ framework: 'nuxt' }) ok
}
```

Four kinds of parser noise are removed before the event is built, so `flags` holds what the user asked for and not what the parser filled in:

- Positionals: citty's `_` bucket, and every argument declared `type: 'positional'`.
- Undeclared flags: citty parses any `--name` it is given, so a flag the command's `args` does not declare is dropped, name included.
- Defaults: a flag still at its declared `default`.
- Kebab-case duplicates: `--min-score` arrives as both `minScore` and `min-score`. Only `minScore` is kept, and that is the name `collect.flags` uses.

A negation is still recorded: `--no-write` against `write: { default: true }` gives `write: false`.

`telemetry.set()` follows the same split. Numbers and booleans are always kept. A string is kept only when `collect.fields` lists that value for that key, and is dropped otherwise, without an error. Outside a `run()`, `telemetry.set()` and `telemetry.fail()` do nothing.

The `set()` on the handle returned by `createTelemetry()` is typed from `collect.fields`, so it autocompletes the declared keys and values. The ambient `telemetry.set()` accepts any numeric or boolean counter. Both write to the same `custom`.

## Options

`withTelemetry(command, options)`, `createTelemetry(options)` and `createGitHubActionsTelemetry(options)` take the same options:

| Option | Default | What it does |
| --- | --- | --- |
| `name` | required | The tool name. Names the config directory and the disclosure |
| `version` | required | The tool version |
| `bin` | `name` | The command people type, printed in the first-run notice |
| `endpoint` | none | The ingest URL. `EVLOG_TELEMETRY_ENDPOINT` replaces it |
| `environment` | none | A value for `env.environment`, such as `production` for a packaged CLI |
| `collect.flags` | none | Per flag, the string values recorded as they are |
| `collect.fields` | none | Per `custom` key, the string values accepted |
| `flushIntervalMs` | `900000`, `3600000` in CI | Time since the last successful send before `run()` sends again. `0` sends on every run |
| `flushThreshold` | `20` | Queue size that forces a send. At most `50` |
| `flushTimeoutMs` | `500` | Longest a send may take before it is abandoned |
| `maxBufferBytes` | `1048576` (1 MiB) | Outbox size past which the oldest events are dropped |
| `maxEventAgeMs` | `2592000000` (30 days) | Age past which a queued event is dropped |
| `sampling` | none | Declared for later. Every run is recorded today |

`createGitHubActionsTelemetry()` adds two:

| Option | Default | What it does |
| --- | --- | --- |
| `actionName` | `GITHUB_ACTION`, then `unknown` | The value of `custom.ghaAction` |
| `eventType` | `GITHUB_EVENT_NAME`, then `unknown` | The value of `custom.ghaEvent` |

Both values are cut to 128 characters.

A handle has four members:

| Member | What it does |
| --- | --- |
| `run(command, fn, opts?)` | Runs `fn` as one event and returns its result. An error is recorded and thrown again |
| `flush()` | Sends the whole backlog now, in batches of 50. Never throws |
| `set(fields)` | Sets `custom` fields on the active run |
| `enabled` | `false` when the user opted out. `run()` then calls `fn` and records nothing |

For a CLI that does not use citty, pass the parsed flags as `opts.flags` and they are sanitized as above. Add the argument definitions as `opts.args`, each a `{ type?, default? }`, to also drop undeclared flags, positionals and defaults.

## Environment variables

| Variable | Effect |
| --- | --- |
| `DO_NOT_TRACK` | `1` turns telemetry off. Checked first |
| `EVLOG_TELEMETRY` | `0` turns it off, `1` turns it on, over the saved preference |
| `EVLOG_TELEMETRY_DEBUG` | `1` prints each event to stderr, sends nothing and queues nothing |
| `EVLOG_TELEMETRY_ENDPOINT` | Replaces the `endpoint` option |
| `EVLOG_TELEMETRY_FLUSH_INTERVAL_MS` | Replaces `flushIntervalMs` |
| `EVLOG_TELEMETRY_FLUSH_THRESHOLD` | Replaces `flushThreshold` |
| `EVLOG_TELEMETRY_ENV` | Sets `env.environment`, over everything else |
| `EVLOG_TELEMETRY_MACHINE_ID` | When set in CI, a `machineId` is stored and sent there too |
| `XDG_CONFIG_HOME` | Base of the config directory, instead of `~/.config` |
| `NO_COLOR`, `FORCE_COLOR` | Turn the colors of the first-run notice off or on |

`DO_NOT_TRACK` and `EVLOG_TELEMETRY` read `true`, `yes` and `on` like `1`, and `false`, `no` and `off` like `0`, in any case.

## Extend the schema

The event has two owners. `@evlog/telemetry` owns the envelope, which is the same for every tool. You own what goes in `flags` and `custom`, declared once in `collect`:

```typescript [src/index.ts]
withTelemetry(command, {
  name: 'acme-cli',
  version: '2.1.0',
  endpoint: 'https://telemetry.acme.dev/api/ingest',
  collect: {
    flags: {
      format: ['json', 'yaml', 'table'],
      target: ['staging', 'production'],
    },
    fields: {
      product: ['cli', 'action', 'migrator'],
      plan: ['free', 'pro', 'enterprise'],
      framework: ['nuxt', 'next', 'remix'],
    },
  },
})
```

```typescript [src/commands/deploy.ts]
await t.run('deploy', async () => {
  const result = await deployServices()
  telemetry.set({
    servicesDeployed: result.count,   // number — always allowed
    rollbackUsed: false,              // boolean — always allowed
    framework: 'nuxt',                // string — allowed (in collect.fields)
    schemaVersion: 2,                 // number — version your custom shape
  })
})
```

The server is the second gate. Give [`parseIngestBody()`](/telemetry/ingest#validate-the-body) the same tool name and every `custom` key you set, and it removes the rest:

```typescript [app/api/telemetry/ingest/route.ts]
import { parseIngestBody } from '@evlog/telemetry/ingest'

const ALLOWED_CUSTOM = [
  'servicesDeployed', 'rollbackUsed', 'framework',
  'product', 'plan', 'schemaVersion',
  'ghaAction', 'ghaEvent',
] as const

export async function POST(req: Request) {
  const raw = await req.text()
  const events = parseIngestBody(raw, {
    allowedTools: ['acme-cli'],
    allowedCustomKeys: { 'acme-cli': ALLOWED_CUSTOM },
  })
  // dedupe on idempotencyKey, then persist
}
```

After validation, map the event to your own tables. The envelope is the wire format, and the columns are your choice:

```typescript [lib/telemetry-store.ts]
function toRow(event: RunEvent) {
  return {
    command: event.command,
    duration_ms: event.durationMs,
    outcome: event.outcome,
    tool_version: event.tool.version,
    format: event.flags.format,
    target: event.flags.target,
    services_deployed: event.custom.servicesDeployed,
    framework: event.custom.framework,
    plan: event.custom.plan,
    schema_version: event.custom.schemaVersion ?? 1,
    is_ci: event.env.ci,
    node: event.env.node,
    received_at: new Date(),
  }
}
```

When your counters change meaning, bump a numeric `schemaVersion` in `custom` and branch on it in the mapper:

```typescript [lib/telemetry-store.ts]
const version = (event.custom.schemaVersion as number | undefined) ?? 1
if (version === 1) return mapV1(event)
return mapV2(event)
```

When several tools post to one endpoint, give each its own list in `allowedCustomKeys`, keyed by `tool.name`, or prefix the keys per product (`acme_product`).

What the envelope does not do:

| Need | Answer | Workaround |
| --- | --- | --- |
| A new top-level field, such as `tenantId` | Not sent | A flat key in `custom`, or derive it on the server from `machineId` |
| Nested objects (`custom.user.plan`) | Flat records only | Flatten: `userPlan: 'pro'`, declared in `collect.fields` |
| Free-form strings: paths, emails | Blocked by design | Flags record `"<set>"`. Reduce the value to a number, a boolean or one of a declared set before `telemetry.set()` |
| A schema per command | One envelope per run | Set only the keys that matter in each command |
| A transform before the outbox | No hook | Map on the server |

If a value is safe to print in `TELEMETRY.md` and is a number, a boolean or one of a closed set of strings, it belongs in `collect` and `custom`. Anything else stays on the server.

## Disclosure

`generateDisclosure(toolName, collect?)` builds the disclosure from the envelope and your `collect`, so the text cannot drift from what the tool collects. Write it to a file and commit it with each release that changes `collect`:

```typescript [scripts/generate-disclosure.ts]
import { writeFile } from 'node:fs/promises'
import { generateDisclosure } from '@evlog/telemetry'

const { markdown } = generateDisclosure('my-tool', {
  flags: { format: ['json', 'csv'] },
})

await writeFile('TELEMETRY.md', markdown)
```

It returns `{ version, standard, extensions, markdown }`: the schema version `1`, the list of envelope fields, your allowlists as `{ flags, fields }`, and the rendered Markdown. The opt-out section of the Markdown names the command `evlog telemetry disable` whatever `toolName` is, so correct that line for your own tool.

`defineTelemetryCommands({ name, collect })` prints the same disclosure from `<tool> telemetry status`.

## Consent

Telemetry is on by default, with a notice on the first run. The first rule that applies decides:

1. `DO_NOT_TRACK=1` turns it off.
2. `EVLOG_TELEMETRY=0` turns it off, and `EVLOG_TELEMETRY=1` turns it on.
3. The saved preference, written by `telemetry disable` and `telemetry enable`, or by `disableTelemetry(name)` and `enableTelemetry(name)`.
4. Otherwise it is on.

Opting out with `telemetry disable` or `disableTelemetry()` deletes the outbox, so events that were queued and not yet sent never leave the machine. The run that opts out is not recorded.

The notice is printed to stderr once per tool, on the first run where stdout or stderr is a terminal and no preference is saved. It names the `telemetry status` and `telemetry disable` commands.

## The outbox

Everything is kept in `~/.config/<name>/telemetry`, or under `$XDG_CONFIG_HOME` when that is set:

| File | Holds |
| --- | --- |
| `outbox.ndjson` | The queued events, one JSON line each |
| `last-flush` | The time of the last successful send |
| `outbox.lock` | A lock held while the outbox is written |
| `preference.json` | The saved consent choice |
| `machine-id` | The random id that `machineId` is hashed from |
| `notice-shown` | A marker that the first-run notice was printed |

| Rule | Value |
| --- | --- |
| A `run()` sends when | The window has passed since the last successful send, or the queue has reached the threshold |
| A `run()` sends | One batch of at most 50 events |
| `flush()` sends | Every batch, until the outbox is empty or 500 ms have passed |
| Request timeout | 400 ms |
| Kept for a later run | `429`, `5xx`, a redirect, a network error, a timeout |
| Dropped | Any other `4xx` |
| Outbox over 1 MiB | The oldest events are dropped |
| Event older than 30 days | Dropped |
| Lock older than 30 seconds, or held by a dead process | Taken over |
| Lock still held after 5 tries, 25 ms apart | The write is skipped, and that event is lost |

A failure to read or write any of these files is swallowed: telemetry never throws into the command it measures.

## Exports

From `@evlog/telemetry`:

| Export | What it is |
| --- | --- |
| `withTelemetry(command, options)` | Wraps a citty command tree. One event per `run` handler |
| `createTelemetry(options)` | Returns a handle for scripts and other CLIs |
| `createGitHubActionsTelemetry(options)` | A handle that flushes after every run and adds `ghaAction` and `ghaEvent` |
| `telemetry.set(fields)` | Sets `custom` fields on the active run |
| `telemetry.fail(code?)` | Marks the active run as failed without throwing |
| `defineTelemetryCommands({ name, collect? })` | The citty subcommands `status`, `enable` and `disable` |
| `disableTelemetry(name)`, `enableTelemetry(name)` | Save the preference. Disabling deletes the outbox |
| `generateDisclosure(name, collect?)` | The disclosure, as data and as Markdown |
| `exampleRunEvent(overrides?)` | A complete sample `RunEvent`, for tests and snapshots |
| `parseIngestBody(raw, options)`, `IngestValidationError` | The server validator, also at `@evlog/telemetry/ingest` |
| `FLAG_VALUE_SET` | The string `<set>` |

The types are `RunEvent`, `RunOutcome`, `ToolInfo`, `EnvInfo`, `TelemetryOptions`, `TelemetryHandle`, `GitHubActionsTelemetryOptions`, `CollectConfig`, `CollectFlags`, `CollectFields`, `CustomFields`, `FlagDefinitions`, `TelemetryCliError`, `DisclosureDocument` and `IngestValidatorOptions`.

[Telemetry](/telemetry) shows the setup these options belong to, and [Ingest](/telemetry/ingest) the route that receives the event.
