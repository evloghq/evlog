Your CLI posts `{ events: [...] }` to a URL you own. This page builds that route: validate the body, store each event once, and answer with the status that tells the CLI what to do with its outbox.

`@evlog/telemetry/ingest` holds the validator alone, about 1.7 KB gzipped, so your API does not load the citty wiring.

## What you defend against

The ingest URL ships inside your package, where anyone can read it. An API key or an `Authorization` header baked into the CLI is just as readable, so neither is a barrier. Treat the endpoint as semi-public, like a browser analytics key, and defend on the server:

| Risk | Answer |
| --- | --- |
| Random bots | Validate the payload shape and answer `400` |
| Someone posting fake runs | Rate-limit by IP. The data is usage counters, not money |
| A forged `tool.name` | Allowlist your published tool names |
| Unexpected keys in `custom` | Keep only the keys you declared, the same list as `collect` on the CLI |
| Double counting on a retry | Dedupe on `idempotencyKey` when you store |
| Leaked user secrets | The CLI never reads raw `argv`, and sends only allowlisted flag values and declared fields |

That is the standard for client-side analytics: no real authentication, a validated payload, idempotent storage, a rate limit at the edge, and a payload with no personal data in it by design.

## Validate the body

`parseIngestBody(raw, options)` takes the raw request body and returns the validated events. Mirror the CLI config: the same tool name, and the custom keys you set with `telemetry.set()`.

```typescript [lib/telemetry-ingest.ts]
import { parseIngestBody } from '@evlog/telemetry/ingest'

export const ingestOptions = {
  allowedTools: ['my-tool'],
  allowedCustomKeys: {
    'my-tool': ['checksFailed', 'checksWarn', 'itemsSynced'],
  },
} as const

export function parseTelemetryBody(raw: string) {
  return parseIngestBody(raw, ingestOptions)
}
```

| Option | Default | What it does |
| --- | --- | --- |
| `allowedTools` | required | The `tool.name` values the endpoint accepts |
| `allowedCustomKeys` | none | Per tool name, the `custom` keys to keep |
| `maxBodyBytes` | `65536` (64 KiB) | Largest body, in UTF-8 bytes |
| `maxBatchSize` | `50` | Most events per body. The CLI never sends more than 50 |
| `maxCommandLength` | `256` | Longest `command` |
| `maxDurationMs` | `86400000` (24 hours) | Largest `durationMs` |

A tool with no entry in `allowedCustomKeys` gets an empty `custom`: every key is removed. A GitHub Action that should keep `ghaAction` and `ghaEvent` needs them in its list.

The function throws `IngestValidationError` on the first problem, and the message names it:

| Message | Cause |
| --- | --- |
| `payload too large` | Body over `maxBodyBytes` |
| `invalid json`, `invalid body` | Not JSON, or not an object |
| `invalid batch` | `events` missing, empty, or over `maxBatchSize` |
| `invalid event`, `invalid event type` | An entry is not an object, or `event` is not `run` |
| `unknown tool`, `invalid tool version` | `tool.name` not in `allowedTools`, or `tool.version` empty |
| `invalid command` | Empty, or over `maxCommandLength` |
| `invalid duration` | Not a finite number between `0` and `maxDurationMs` |
| `invalid outcome` | Not `success` or `error` |
| `missing idempotency key` | `idempotencyKey` empty |
| `invalid timestamp` | Not a UTC ISO 8601 string such as `2026-07-14T12:00:00.000Z` |
| `invalid error code` | `errorCode` present and not a non-empty string |
| `invalid flags`, `invalid custom` | Not a plain object |
| `invalid env`, `invalid env.<field>` | The `env` block or one of its fields has the wrong type |

One invalid event rejects the whole batch. In `flags` and `custom`, a value that is not a boolean, a number or a string is removed without an error. `env.os` and `env.arch` may be absent and come back as `null`. A `machineId` that is not a non-empty string is dropped.

## Wire the route

The contract is the same on any framework: read the raw body, validate, store, and answer `204` so the CLI clears its outbox.

::framework-tabs
```typescript [Nitro] server/api/telemetry/ingest.post.ts
import { defineHandler } from 'nitro/h3'
import { readRawBody, setResponseStatus } from 'h3'
import { IngestValidationError } from '@evlog/telemetry/ingest'
import { parseTelemetryBody } from '~/lib/telemetry-ingest'
import { storeRunEvents } from '~/lib/telemetry-store'

export default defineHandler(async (event) => {
  const raw = await readRawBody(event, 'utf8')
  if (!raw) {
    setResponseStatus(event, 400)
    return { error: 'empty body' }
  }

  try {
    const events = parseTelemetryBody(raw)
    await storeRunEvents(events)
    setResponseStatus(event, 204)
    return null
  } catch (err) {
    setResponseStatus(event, err instanceof IngestValidationError ? 400 : 500)
    return { error: 'invalid payload' }
  }
})
```
```typescript [Next.js App Router] app/api/telemetry/ingest/route.ts
import { IngestValidationError } from '@evlog/telemetry/ingest'
import { parseTelemetryBody } from '@/lib/telemetry-ingest'
import { storeRunEvents } from '@/lib/telemetry-store'

export async function POST(request: Request) {
  const raw = await request.text()
  try {
    const events = parseTelemetryBody(raw)
    await storeRunEvents(events)
    return new Response(null, { status: 204 })
  } catch (err) {
    const status = err instanceof IngestValidationError ? 400 : 500
    return Response.json({ error: 'invalid payload' }, { status })
  }
}
```
```typescript [Hono] src/routes/telemetry.ts
import { Hono } from 'hono'
import { IngestValidationError } from '@evlog/telemetry/ingest'
import { parseTelemetryBody } from '../lib/telemetry-ingest'
import { storeRunEvents } from '../lib/telemetry-store'

const app = new Hono()

app.post('/api/telemetry/ingest', async (c) => {
  const raw = await c.req.text()
  try {
    const events = parseTelemetryBody(raw)
    await storeRunEvents(events)
    return c.body(null, 204)
  } catch (err) {
    const status = err instanceof IngestValidationError ? 400 : 500
    return c.json({ error: 'invalid payload' }, status)
  }
})

export default app
```

## Store each event once

A retry or a backlog can post the same `idempotencyKey` twice. Upsert on it, or skip the duplicate, so the counts stay correct:

```typescript [lib/telemetry-store.ts]
import type { RunEvent } from '@evlog/telemetry'

export async function storeRunEvents(events: RunEvent[]): Promise<void> {
  for (const run of events) {
    await db.telemetryRun.upsert({
      where: { idempotencyKey: run.idempotencyKey },
      create: {
        tool: run.tool.name,
        version: run.tool.version,
        command: run.command,
        outcome: run.outcome,
        durationMs: run.durationMs,
        custom: run.custom,
        recordedAt: run.timestamp,
      },
      update: {},
    })
  }
}
```

The validated events are plain objects, so the same function can send them to a warehouse or a log backend instead of a table. [Reference](/telemetry/reference#the-event) lists every field.

## Answer with the right status

The CLI decides what to do with its outbox from your status code alone:

| You answer | The CLI |
| --- | --- |
| `204`, or any `2xx` | Removes the delivered events. Send it only once storage succeeded |
| `429`, `5xx` | Keeps the events and sends them again on a later run |
| `400`, or any other `4xx` | Drops the batch for good |

A `400` for a body that fails validation is right: the same bytes would fail again. A storage failure must be a `5xx`, or the events are lost. The routes above do both.

Put the rate limit where traffic enters, at the CDN, the API gateway or a middleware, keyed on the IP. The validator checks the shape of a payload, not how often one arrives. For tighter control, also count per `machineId` inside the handler.
