A checkout handler that logs five lines gives you five records to find and stitch together when it fails:

```typescript [Before: 5 log lines]
console.log('checkout started', { requestId })
console.log('user loaded', { userId: 'u_42' })
console.log('cart loaded', { items: 3, total: 2999 })
console.log('charging card', { provider: 'stripe' })
console.log('checkout done', { status: 200, ms: 182 })
```

With evlog the handler calls `log.set()` as it learns things, and one event is written when the response is sent, with the method, path, status, duration and request id added for you:

```json [Output]
{
  "level": "info",
  "service": "checkout",
  "method": "POST",
  "path": "/checkout",
  "status": 200,
  "durationMs": 182,
  "requestId": "4f1c…",
  "user": { "id": "u_42" },
  "cart": { "items": 3, "total": 2999 },
  "payment": { "provider": "stripe" }
}
```

Every field is a column you can query: `payment.provider = 'stripe' AND status >= 500`.

| | Line logs | One wide event |
| --- | --- | --- |
| Records per request | One per log call | One, emitted at the end |
| Context | Repeated on every line, or missing on some | Collected once, next to the outcome |
| Debugging a failure | Find every line for the request id, then rebuild the story | Read one event: inputs, outcome, error, duration |
| Volume | Grows with the number of calls | Fixed per request, then cut by [sampling](/events/sampling) |

This guide uses a plain `node:http` server, with no framework, so every step is visible. On Express, Fastify, Hono, NestJS or another framework, the [integration](/integrations) does the request part for you: follow [Installation](/start/installation) and the [quick start](/start/quick-start), then come back for service code, drains and the checklist.

## Set it up

Install the package and write the config. `npx evlog init` does both and checks the result:

```bash [Terminal]
pnpm add evlog
```

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'

export default defineEvlog({
  service: 'checkout',
})
```

Every option lives in this file: sampling, drains, enrichers, redaction. [Configuration](/reference/configuration) lists them.

## Emit one event per request

Without a framework, you create the request logger and emit it yourself, once, when the response is done. Listening to both `finish` and `close` covers a response that completes and a client that disconnects:

```typescript [src/server.ts]
import { randomUUID } from 'node:crypto'
import { createServer } from 'node:http'
import { createRequestLogger, initLogger, toLoggerConfig } from 'evlog'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

createServer((req, res) => {
  const log = createRequestLogger({
    method: req.method,
    path: new URL(req.url ?? '/', 'http://localhost').pathname,
    requestId: req.headers['x-request-id']?.toString() ?? randomUUID(),
  })

  let emitted = false
  const emit = () => {
    if (emitted) return
    emitted = true
    log.emit({ status: res.statusCode })
  }
  res.once('finish', emit)
  res.once('close', emit)

  log.set({ orderId: 'order-123', payment: { amount: 2999, currency: 'EUR' } })
  log.set({ payment: { chargeId: 'ch_123' }, outcome: 'paid' })

  res.statusCode = 200
  res.end(JSON.stringify({ orderId: 'order-123' }))
}).listen(3000)
```

Nested objects merge, so `payment` is filled in two calls. Send a request with `curl -X POST http://localhost:3000/checkout`. In development the event prints as a tree, and in production as one JSON line with `orderId`, `payment` and `outcome` next to the request fields.

Reusing an incoming `x-request-id` links the events of one request across services. The framework integrations do the same. For distributed traces, `createTraceContextEnricher()` adds the incoming `traceparent` to the event: see [Enrichers](/events/enrichers).

Log what you would want while debugging this operation: ids, outcomes, amounts, counts, timings. Leave out credentials and personal data you do not need. [Best practices](/reference/best-practices) lists what to keep out.

Work that finishes after the response cannot change the request's event, because the logger is sealed when it emits. Use `log.fork()` for background work, as [Events](/events#after-the-event-is-emitted) shows.

## Return an error that explains itself

`createError()` gives a failure a `status`, a `why`, a `fix` and a `link`. `log.error()` records it on the request's event, next to the context set before the failure, and `parseError()` reads the fields back to build the response:

```typescript [src/server.ts]
import { createError, parseError } from 'evlog'

// inside the request handler, after the finish and close listeners
try {
  throw createError({
    message: 'Payment declined',
    status: 402,
    why: 'The card issuer declined the charge',
    fix: 'Try another payment method',
    link: 'https://docs.example.com/payments/declined',
  })
}
catch (error) {
  log.error(error instanceof Error ? error : new Error(String(error)))
  const parsed = parseError(error)
  res.statusCode = parsed.status
  res.end(JSON.stringify({ message: parsed.message, why: parsed.why, fix: parsed.fix, link: parsed.link }))
}
```

The `finish` listener then emits an `error` event with `status: 402`, the context, and the error's message, `why`, `fix` and `link`. With a framework, the integration records a thrown error for you, and its [integration page](/integrations) shows how the response is built. [Errors](/errors) covers codes and catalogs.

## Send events to a backend

In development, events print to the terminal. In production, a [drain](/drains) sends them to a backend. Add it to the config and every handler uses it:

```typescript [evlog.config.ts]
import { defineEvlog, type DrainContext } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createDrainPipeline } from 'evlog/pipeline'

const pipeline = createDrainPipeline<DrainContext>({ batch: { size: 50 } })

export default defineEvlog({
  service: 'checkout',
  drain: pipeline(createAxiomDrain()),
})
```

`createAxiomDrain()` reads `AXIOM_API_KEY` and `AXIOM_DATASET`. The pipeline batches sends and retries failed batches. On Node.js, a pipeline that holds events flushes on `SIGTERM`, `SIGINT` and `beforeExit`. `process.exit()` and `SIGKILL` stop the process first, so call `await drain.flush()` before `process.exit()`. [Pipeline](/drains/pipeline#shutdown) has the deadlines.

## Before production

- **Sample by outcome.** Keep a share of successful `info` events, and `keep` rules so errors and slow requests always survive:

  ```typescript [evlog.config.ts]
  export default defineEvlog({
    service: 'checkout',
    sampling: { rates: { info: 10 }, keep: [{ status: 400 }, { duration: 1000 }] },
  })
  ```

- **Redact.** [Redaction](/events/redaction) is on by default in production. Add paths for fields specific to your domain.
- **Flush on exit.** Scripts, workers and serverless functions wait for pending delivery before the process stops. See [Standalone](/integrations/standalone) and [AWS Lambda](/integrations/aws-lambda).
- **Check the wiring.** [`evlog doctor`](/cli/doctor) says what is missing when nothing shows up, and [`evlog map`](/map) finds the handlers that still emit no event.

## Questions

**Can I keep `console.log` while I migrate?** Yes. evlog does not patch `console`, so existing calls keep working. Move one route at a time, and replace one-off messages with the [`log` API](/events/simple-logging) when you are ready.

**Does it slow down my app?** A request builds one object and serializes it once, and drains run after the event is emitted. [Performance](/reference/performance) has the numbers per call, and what to measure on your own path.

**How is this different from pino or winston?** They write a record per call. evlog's request logger collects fields through the request and writes one event with the outcome, error and duration on it. [Compare](/compare) covers each library.

**Does it work with OpenTelemetry?** The [OTLP drain](/drains/otlp) exports events to any collector, and the active span's `traceId` and `spanId` can go on the event. See [evlog and OpenTelemetry](/compare/opentelemetry).

To keep field names consistent across handlers, continue with [Typed fields](/events/typed-fields).
