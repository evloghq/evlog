By the time an app has 200 routes, 40 background jobs and a `console.log` in every file, adding structured logging means walking the whole codebase. Before the first request, it means adding one module. evlog is built for that first choice: the rest of the app inherits structured events, structured errors, typed catalogs, an audit trail and a drain pipeline that you do not build later.

Already shipping with pino or winston? The case is different, and [Compare](/compare) makes it library by library.

## Choose around the questions you ask your logs

A script that reports progress needs individual messages, and the [`log` API](/events/simple-logging) writes them. A checkout that crosses authentication, inventory and payment code is a different question: you want the whole operation. A [wide event](/events) lets each step add fields to the same event, so you filter failed checkouts by customer, payment provider or amount without joining separate lines first.

If your current logger already answers your questions, keep it. evlog pays off when you want context accumulation, request lifecycle handling and [structured errors](/errors) together.

As more people log, `orderId` in one handler becomes `orderID` in another. A shared type catches that in the editor:

```typescript [checkout.ts]
import { createLogger } from 'evlog'

type CheckoutContext = {
  orderId: string
  payment: { chargeId: string, amount: number }
  outcome: 'paid' | 'declined'
}

const log = createLogger<CheckoutContext>()
log.set({ orderId: 'order-123' })
log.set({ payment: { chargeId: 'ch_123', amount: 2999 } })
log.emit({ outcome: 'paid' })
```

An amount passed as a string, or an outcome outside the union, fails type checking in `set()` and `emit()`. Fields still arrive one call at a time: the type does not require every field before the event is emitted, and it does not validate incoming data. [Typed fields](/events/typed-fields) covers the framework setup.

## What you get on day one

One dependency, with no runtime dependencies of its own, and every part below uses the same `log` API:

| Part | What it does for you |
| --- | --- |
| [Redaction](/events/redaction) | Masks emails, card numbers, IPs, phone numbers, JWTs, bearer tokens, IBANs and provider credentials before the console and before any drain. On by default in production |
| [Structured errors](/errors) | Every error carries `why`, `fix` and `link` for your on-call, your client and a coding agent |
| [Wide events](/events) | One typed event per request, job or workflow, with every field the work touched |
| [Catalogs](/errors/catalogs) | `defineErrorCatalog` and `defineAuditCatalog` give refactor-safe codes and actions with autocomplete |
| [Sampling](/events/sampling) | Head sampling drops low-importance events by level, tail sampling keeps errors and slow requests |
| [Pipeline](/drains/pipeline) | Batching, retry with backoff and a bounded buffer around any drain |

The primitives are the part every modern logger has some version of. The parts around them handle problems you have not had yet:

- **You add AI to a route.** The [AI SDK integration](/extend/ai-sdk) puts tokens, tool calls, latency and cost on the request's event. With [Better Auth](/extend/better-auth), the same event names the signed-in user, so "which user spent $14 in one conversation" is one query.
- **Your stack spans several frameworks.** A Nuxt frontend, a Hono service and a Lambda webhook each get an [integration](/integrations) with the same `useLogger()`, `log.set()` and `createError()`, and the same drains behind them.
- **You want verbose logs in development only.** The [Vite plugin](/extend/vite) strips `log.debug()` from production builds and adds the source file and line to each log.
- **A user hits a bug in the browser.** [Browser events](/events/client) use the same `log` calls and post to your server, with the user attached.
- **You change vendors.** Your code emits to a drain, not to a vendor. Moving from stdout to Axiom, then adding Sentry, is a change to `evlog.config.ts`.

Fanning out to two backends is one config change, and no handler moves:

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { composeDrains } from 'evlog/toolkit'
import { createAxiomDrain } from 'evlog/axiom'
import { createSentryDrain } from 'evlog/sentry'

export default defineEvlog({
  service: 'my-app',
  drain: composeDrains([createAxiomDrain(), createSentryDrain()]),
})
```

`composeDrains` calls each drain with `Promise.allSettled`, so a slow Sentry does not hold back Axiom. [Drains](/drains) lists every destination, including the [file system](/drains/fs) for a self-hosted setup.

## Catalogs grow with the app

The smallest useful error catalog has two entries:

```typescript [src/errors.ts]
import { defineErrorCatalog } from 'evlog'

export const errors = defineErrorCatalog('billing', {
  PAYMENT_DECLINED: { status: 402, message: 'Payment declined' },
  INVOICE_NOT_FOUND: { status: 404, message: 'Invoice not found' },
})
```

Six months later it has thirty, `createError({ code })` autocompletes them, and it ships as a private package across a monorepo. The pattern does not change on the way. Audit actions grow the same way with `defineAuditCatalog`. See [Catalogs](/errors/catalogs).

## Context for coding agents

An agent is good at writing a handler and worse at debugging one. What it needs is context:

- A `createError({ message, why, fix, link })` is something it can read and explain, where `Error: failed` is not.
- One typed event per request is one record to reason about, not lines to grep.
- A catalog gives it `errors.PAYMENT_DECLINED` to pick from, so it does not invent codes.
- The [Skills](/skills) teach it to wire evlog and review logging the way these pages describe.

## Audit on day zero

GDPR export requests, SOC 2, HIPAA, PCI, or one incident review where someone asks who deleted that: every product meets one of them. Added on day 1000, an audit trail is a parallel system with its own schema, a backfill and actor identity rebuilt from headers. Added on day zero, it is `auditEnricher()` and a `log.audit({ action, actor, target })` call in the handlers that change state, on the events you already emit. [Audit](/audit) adds hash-chain integrity and keeps audit events past sampling.

## What "later" costs

Teams that start with `console.log` and add logging "when we need it" pay for it in four places:

- **Field names.** `userId`, `user_id`, `uid` or `actor.id`: once thirty services disagree, you write migration queries in your vendor.
- **Redaction.** Masking PII before the first log exists is a config line. After six months of logs, it is an incident.
- **The vendor.** Comparing Datadog, Axiom and Sentry while production is on fire is the worst time to compare them.
- **Error context.** Every `throw new Error('failed')` already written is one `why` and one `fix` your on-call does not get.

| When you adopt evlog | What it takes |
| --- | --- |
| Day 0 | Add the integration and `evlog.config.ts` |
| Day 30 | Switch the logger calls in a small app |
| Day 365 | Walk the codebase, settle field names, add audit and redaction: the cost of moving between any two structured loggers |

## Try it on one route

Start with one route or job and keep your existing logger everywhere else. A route on `console.log` next to a route on `log.set()` is a normal state during a migration. Use the events to investigate a real issue before you go further. [Simple logging](/events/simple-logging#adapt-existing-call-sites) maps `console.log`, pino, consola and winston calls to evlog, and when several records become one event, the queries that read them change too.

[Install evlog](/start/installation), or run `npx evlog init`, then follow the [quick start](/start/quick-start). For a server with no framework, [Structured logging in Node.js](/start/structured-logging-nodejs) goes end to end.
