`evlog init` does the setup the [installation guide](/start/installation) describes, in the project you are standing in.

```bash [Terminal]
npx evlog init
```

On a terminal it reads your project, asks what it cannot infer, shows the plan, and waits for your confirmation before it touches anything. The run goes through six steps:

1. Read the project with the same analysis [`evlog map`](/map) runs: the framework, the installed packages, the errors you repeat, the entry points with no audit trail. The offers come from that.
2. Install `evlog` with the package manager your lockfile implies, unless it is already there.
3. Register the integration for your framework.
4. Write `evlog.config.ts` with your service name and drains, plus batching, enrichers and sampling when you asked for them.
5. Add the evlog conventions to `AGENTS.md` and install the [skills](/skills), the same work as [`evlog agents`](/cli/agents), planned with the rest so you confirm once. Skills already installed are left for `npx skills update`.
6. Check the result with [`evlog doctor`](/cli/doctor), so the run ends on whether the setup works.

Every write is reported line by line, including the parts that were already in place.

## Flags

| Flag | What it does |
| --- | --- |
| `--yes`, `-y` | Skips every question and takes the defaults |
| `--framework <name>` | Overrides detection: `nuxt`, `nitro`, `next`, `tanstack-start`, `hono`, `express`, `fastify`, `effect`, `eve` |
| `--service <name>` | Service name on every wide event. Default: the one your `evlog.config.ts` sets, else your package name without its scope |
| `--drain <id>` | Development drain: `fs` (default) or `none` |
| `--prod-drain <a,b>` | Production drains, comma-separated. See [Drains](#drains) |
| `--extras <a,b>` | Comma-separated. See [Extras](#extras) |
| `--enrichers <a,b>` | `user-agent`, `geo`, `request-size`, `trace-context`. Default: all four, when the `enrichers` extra is on |
| `--sampling <id>` | `all`, `low`, `medium`, `high`, `very-high`. Default: `medium`, when the `sampling` extra is on |
| `--apps <a,b>` | Workspace packages to set up, by directory or package name. Monorepo root only |
| `--dry-run` | Prints the plan and the diff of each file it would change, and writes nothing |
| `--no-install` | Prints the install command and does not run the package manager |
| `--no-agents` | Skips the `AGENTS.md` block and the skills |
| `--no-agent-logs` | eve: hides the agent's `evlog__logs` tool |
| `--cwd <dir>` | Sets up another app in the workspace |
| `--json` | The plan and the result as JSON on stdout. Implies non-interactive |

An unknown `--framework`, `--drain`, `--prod-drain`, `--extras`, `--enrichers`, `--sampling` or `--apps` value stops the run with exit code `2`. It never falls back to a default, because a wrong drain set up without a word is worse than a failed command.

The run exits `1` when the package manager or the skills CLI fails. The files are written either way. It also exits `1` when a file cannot be written: the run stops there with `cli.WRITE_FAILED`, and the error names that file and the ones written before it, under `--json` too. Fix the path or its permissions and run `evlog init` again.

## Run it without prompts

`init` skips the prompts and takes every answer from flags and defaults in four cases:

| Condition | Why |
| --- | --- |
| `--yes` | You said so |
| `--json` | The payload is the contract, and prompts would sit in front of it |
| stdin or stdout is not a terminal | Piped, redirected, or spawned by a tool |
| `CI` is set to anything but `false` or `0` | A workflow runner has no keyboard |

```bash [Terminal]
evlog init --yes --prod-drain axiom,sentry --extras pipeline,enrichers
evlog init --yes --extras sampling --sampling high
evlog init --json --drain none          # plan and result as JSON, nothing to read
```

The flags express every choice the prompts can, so an agent reproduces what a person did and never waits on a keystroke.

## What it leaves alone

`init` appends to your files and never rewrites them:

- It patches a config file at the exact offsets of the node it adds to. Your comments, quote style and formatting survive, and nothing is reprinted from an AST.
- A file that already exists is reported as already present. There is no `--force`.
- Anything it cannot do safely becomes a manual step, with the snippet to paste and the reason it stopped. A `modules` key built from a variable is the common case.
- An `evlog.config.ts` you already have is read and never rewritten. A setting the run picked that your file lacks, a drain for instance, becomes a manual step. The service the file names, under `service` or `env.service`, becomes the default answer.
- When evlog already reaches the app through a wrapper package, `init` stops before any prompt or write.

A second run reports what is in place and writes nothing:

```text [Output]
· nuxt.config.ts already registers evlog/nuxt
· evlog.config.ts already exists
· .env.example already lists the adapter keys
```

`--dry-run` prints the diff of every file the run would create or change, against the file as it is now, plus the `package.json` change the install command would make:

```text [Output]
· would update nuxt.config.ts
   @@ -1,4 +1,4 @@
    export default defineNuxtConfig({
   -  modules: ['@nuxt/ui'],
   +  modules: ['@nuxt/ui', 'evlog/nuxt'],
      devtools: { enabled: true },
    })
```

The `package.json` diff lists each package at the tag it is installed from, `beta` or `latest`. The package manager writes the version that tag resolves to. With `--json`, the same diffs are in `preview`, one entry per file.

## The config it writes

Your answers land in one file at the root of the app, the same one the CLI reads. [`evlog config`](/cli/config) shows what applies.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createFsDrain } from 'evlog/fs'

/**
 * Settings for checkout, read by the app and by the evlog CLI.
 * https://evlog.dev/cli/config
 */
export default defineEvlog({
  service: 'checkout',
  // Local NDJSON under .evlog/logs, in development only.
  drain: process.env.NODE_ENV === 'production' ? undefined : createFsDrain(),
})
```

The framework files only point at it. Every framework branches on `process.env.NODE_ENV`, not `import.meta.dev`: Nitro inlines it as a literal in its production build, and `process.env` type-checks in a fresh Nuxt project before `nuxi prepare` has run.

## Drains

`init` asks two questions, one for development and one for production. `--drain` sets the development drain, `fs` or `none`. `--prod-drain` takes one or more hosted drains, and the same event goes to each.

| Id | Drain | Environment variables |
| --- | --- | --- |
| `fs` | Local files under `.evlog/logs`, the development default | none |
| `none` | Pretty console output only, development | none |
| `axiom` | Axiom | `AXIOM_DATASET`, `AXIOM_API_KEY` |
| `otlp` | Any OpenTelemetry collector | `OTEL_EXPORTER_OTLP_ENDPOINT`, and `OTEL_SERVICE_NAME` to override the service name |
| `posthog` | PostHog | `POSTHOG_API_KEY`, and `POSTHOG_HOST` when not on PostHog cloud |
| `sentry` | Sentry | `SENTRY_DSN` |
| `better-stack` | Better Stack | `BETTER_STACK_API_KEY` |
| `datadog` | Datadog | `DATADOG_API_KEY`, `DATADOG_SITE` |
| `hyperdx` | HyperDX | `HYPERDX_API_KEY` |
| `sazabi` | Sazabi | `SAZABI_INTAKE_URL` |
| `loki` | Grafana Loki | `LOKI_ENDPOINT` |
| `clickhouse` | ClickHouse | `CLICKHOUSE_ENDPOINT`, and the `evlog_events` table created first |

`init` never asks for a secret. It prints the variables each drain reads, lists them in `.env.example`, and leaves the values to you.

With one drain on each side, the generated config picks it in one line:

```typescript [evlog.config.ts]
export default defineEvlog({
  service: 'checkout',
  drain: process.env.NODE_ENV === 'production' ? createAxiomDrain() : createFsDrain(),
})
```

With several production drains it branches on the environment in one place:

```typescript [evlog.config.ts]
const drains = process.env.NODE_ENV === 'production'
  ? [pipeline(createAxiomDrain()), pipeline(createSentryDrain())]
  : [createFsDrain()]
```

The [file system drain](/drains/fs) is the only one gated to development. A drain that writes files writes them on whatever machine serves the request, and `init` does not turn that on in production for you. It writes to `.evlog/logs`, which `evlog doctor` and [`evlog logs`](/cli/logs) look for. On first write the drain puts a `.gitignore` inside `.evlog`, so the logs stay out of git. Batching wraps the network sends only, so a local write stays immediate.

An app set up by an earlier version of `init` has `server/plugins/evlog-drain.ts` and `evlog-enrich.ts`. They keep working, and the new config leaves `drain` or `enrich` out while they exist, so no event is sent twice.

## Extras

| Id | What you get | Offered when |
| --- | --- | --- |
| `enrichers` | The [enrichers](/events/enrichers) you pick with `--enrichers` | Always |
| `pipeline` | [Batching and retry](/drains/pipeline) in place of one HTTP call per request | A production drain was picked |
| `sampling` | A [sampling](/events/sampling) preset, set with `--sampling` | Always |
| `error-catalog` | A typed [error catalog](/errors/catalogs) seeded with the errors you already repeat | The scan found the same `createError` in more than one file |
| `audit-catalog` | Typed [audit](/audit) actions for the sensitive routes with no trail | `map` flagged sensitive entry points with no `log.audit()` |
| `ai` | Token usage, tool calls and cost on [AI SDK](/integrations/ai-sdk) generations | `ai` is a dependency |
| `better-auth` | The signed-in user on every event, through [Better Auth](/integrations/better-auth) | `better-auth` is a dependency |
| `vite` | The [Vite plugin](/integrations/vite) that strips `log.debug()` from production builds | The framework is TanStack Start |

An extra passed as a flag to a project that cannot use it is dropped and reported, not refused. `--extras vite,enrichers` therefore does the right thing across a monorepo of mixed apps.

### Sampling presets

| Id | Info | Warnings | For |
| --- | --- | --- | --- |
| `all` | everything | everything | The right answer until volume or cost says otherwise |
| `low` | 50% | 100% | A small app that has started to repeat itself |
| `medium` | 25% | 100% | Steady traffic with a bill worth watching |
| `high` | 10% | 100% | Info is most of what you are paying for |
| `very-high` | 1% | 50% | Trends rather than individual requests |

Errors are kept at 100% in every preset, and the generated config states it. `debug` never appears in the config, so debug events are kept in full: a level with no rate is not sampled.

```typescript [evlog.config.ts]
export default defineEvlog({
  service: 'shop',
  sampling: {
    rates: { info: 10, warn: 100, error: 100 },
  },
})
```

### Seeded catalogs

`error-catalog` writes the errors your code already repeats, with the text you already wrote:

```typescript [server/utils/errors.ts]
export const shopErrors = defineErrorCatalog('shop', {
  /** Currently written inline in server/api/checkout.post.ts, server/api/refund.post.ts */
  CARD_DECLINED: {
    status: 402,
    message: 'Card declined',
    why: 'The issuer refused it',
    fix: 'TODO: what they should do about it',
  },
})
```

`audit-catalog` works the same way and names one action per entry point `map` flagged as sensitive and untracked.

## What each framework gets

| Framework | What `init` writes | What stays yours |
| --- | --- | --- |
| Nuxt | `'evlog/nuxt'` added to `modules` in `nuxt.config.ts` | Nothing. `useLogger` and `parseError` are auto-imported, and `createError` is imported from `evlog` |
| Nitro | The import and the module call in `nitro.config.ts`, created when there is none | Nothing |
| Next.js | `instrumentation.ts` and `lib/evlog.ts`, under `src/` when your app lives there | Wrapping each route with `withEvlog()`. `init` prints the snippet |
| TanStack Start | The Nitro v3 config with `experimental.asyncContext` enabled | The `evlogErrorHandler` middleware on your root route |
| Hono | `src/evlog.ts`, or `evlog.ts` when there is no `src/`, exporting `evlogMiddleware` | `app.use(evlogMiddleware)` before your routes |
| Express | `src/evlog.ts` exporting `evlogMiddleware` from `evlog/express` | `app.use(evlogMiddleware)` before your routes |
| Fastify | `src/evlog.ts` re-exporting the `evlog` plugin next to `evlogOptions` | `await app.register(evlog, evlogOptions)` |
| Effect | `src/evlog.ts` exporting the `EvlogInit` and `EvlogRouter` layers | Providing the two layers to your server |
| eve | `agent/extensions/evlog.ts` and `agent/instrumentation/evlog.ts` in each agent | Nothing |

The Nuxt and Nitro modules find `evlog.config.ts` on their own, and options you pass to the module override it. On the other frameworks the generated file imports the config, with a path relative to the file `init` creates: `src/evlog.ts` imports `../evlog.config`.

On Nitro, `init` picks the subpath that matches your Nitro major and the evlog major installed: `evlog/nitro` for Nitro 3 and `evlog/nitro/v2` for `nitropack` on evlog 3, `evlog/nitro/v3` and `evlog/nitro` on evlog 2. On TanStack Start, `useRequest()` returns nothing without `experimental.asyncContext`, and the app would log no business context.

[Effect](/integrations/effect) is detected from the `effect` dependency, for Effect 4 apps served by `HttpRouter`. An app that also lists Next.js, Hono or another framework keeps that framework. An Effect 3 app (`@effect/platform`) is not detected, since `evlog/effect` needs Effect 4.

The Hono file shows the shape the middleware frameworks share:

```typescript [src/evlog.ts]
import { initLogger, toLoggerConfig, toMiddlewareOptions } from 'evlog'
import { evlog } from 'evlog/hono'
import config from '../evlog.config'

initLogger(toLoggerConfig(config))

/** Register once, before your routes: `app.use(evlogMiddleware)`. */
export const evlogMiddleware = evlog(toMiddlewareOptions(config))
```

## eve agents

`init` detects an [eve](/integrations/eve) agent from an `eve` dependency at 1.0 or later next to an agent directory: `agent/`, or `agents/<name>/agent/` in an agent workspace. It installs `evlog` and `@evlog/eve`, from the `beta` tag until evlog 3 is stable, and mounts the extension in each agent:

```typescript [agent/extensions/evlog.ts]
import evlog from '@evlog/eve'
import config from '../../evlog.config'

/** One wide event per agent turn, with the settings in evlog.config.ts. */
export default evlog(config)
```

It also writes `instrumentation/evlog.ts` in each agent, the same file as [`evlog setup eve`](/cli/setup), which puts each turn's trace and span ids on its event.

| Case | What `init` does |
| --- | --- |
| Agent workspace | One `evlog.config.ts` at the root and a mount in every member. Each mount sets its own `service`, the project's followed by the eve name: `agents/support/` in a project named `ops` reports as `ops-support`. A member with its own `package.json` is not part of the workspace |
| Agent inside a Next.js, Nuxt or other supported app | Sets up both from the same `evlog.config.ts`. The app keeps the service the config names, and the agent's mount sets `<service>-agent` |
| `--framework eve` or `--framework next` | Sets up only the agent, or only the app |
| A mount that sets no `service` | Left as it is, with the line to add printed |
| A file under `extensions/` that imports `@evlog/eve` | Counts as the mount, as `<name>.ts` or `<name>/extension.ts`. Under a name other than `evlog`, the report says the logs tool is `<name>__logs` |
| An `extensions/evlog.ts` or `instrumentation/evlog.ts` that does something else | Left alone, with the lines to add printed |
| An `evlog: {}` block in `nuxt.config.ts` | Stays where it is. It configures the Nuxt app only |
| An eve integration that sets `eveRoot` | Sets up the app and prints the `evlog init --cwd` that sets up the agent |
| `engines.node`, `.nvmrc` or `.node-version` allows a Node older than 24, or none says | Prints the `engines` line to add. eve 1.0 and `@evlog/eve` need Node 24 |
| eve before 1.0 | The agent is not set up. `init` says why and sets up the web app around it, if there is one |

`@evlog/eve` gives the agent an `evlog__logs` tool that reads its own wide events: a signed-in caller reads its own session, a schedule reads every turn, an anonymous caller reads nothing. Locally it reads `.evlog/logs`, which the development drain writes. An interactive run asks whether to keep the tool. `--no-agent-logs` hides it by writing `logs: { ...config.logs, access: () => false }` into the mount.

On Vercel the tool reads the project's runtime logs through a Vercel Connect connector, which `init` never picks for you. When the project is linked (`.vercel/project.json`), an interactive run lists the team's connectors that can read runtime logs and asks which to use, offers to create one, or skips. It writes the connector to `evlog.config.ts` as `logs: { vercel: { connector } }` and attaches it to the project the way `evlog setup vercel` does, after showing what the attachment grants. With `--yes`, `init` does not contact Vercel and points at `npx evlog setup vercel`.

## Monorepos

From a workspace root, `init` sets up the apps and leaves the root package alone. It lists the workspace packages that have a detectable framework and asks which to set up. Non-interactive runs set up all of them unless `--apps` names some:

```bash [Terminal]
evlog init                            # pick from the list
evlog init --yes --apps apps/web,apps/api
```

Each app keeps its own service name, taken from its `package.json`. Settings shared by every app belong in an `evlog.config.ts` at the workspace root. Each app's config then extends it and leaves out what the root already sets:

```typescript [apps/shop/evlog.config.ts]
import { defineEvlog } from 'evlog'
import base from '../../evlog.config'

export default defineEvlog({
  extends: base,
  service: 'shop',
})
```

A config extends one level. When the root config already extends a preset of its own, `init` writes nothing for the app and prints its settings as a manual step.
