The `evlog` executable ships with the `evlog` package. It runs apart from your app, on your machine or in CI, and needs no install of its own:

```bash [Terminal]
npx evlog <command>
```

The executable runs [`@evlog/cli`](https://npmjs.com/package/@evlog/cli) when it is installed and otherwise fetches it with the package manager that launched it, so `npx evlog init` works on a project that has nothing yet. A global `@evlog/cli` hands off to the copy the project installs, so a project always runs the version it pins. Install it as a dev dependency for a pinned run with no fetch, which is what CI wants:

::code-group
```bash [pnpm]
pnpm add -D @evlog/cli
```
```bash [bun]
bun add -d @evlog/cli
```
```bash [npm]
npm install --save-dev @evlog/cli
```
::

The CLI needs Node.js 22 or later, and evlog 2.31 or later or an evlog 3 beta next to it. When either is older, every command stops with a message naming the version it found and exits `1`. `@evlog/cli` has its own version line, `1.0.0-beta` next to evlog 3.

## Commands

| Command | What it does |
| --- | --- |
| [`evlog init`](/cli/init) | Installs evlog, registers the framework integration and writes `evlog.config.ts` with the drains you pick |
| [`evlog doctor`](/cli/doctor) | Checks that evlog is installed, resolvable, and writing logs where you expect |
| [`evlog map`](/map) | Scores every entry point on its logging and names the three to fix first |
| [`evlog logs`](/cli/logs) | Reads the events your app wrote: the latest, the failures, the slowest, or one request in full |
| [`evlog config`](/cli/config) | Shows the `evlog.config.ts` that applies here and where each setting comes from |
| [`evlog setup`](/cli/setup) | Lets `evlog logs` read a Vercel project's runtime logs, and puts trace ids on an eve agent's events |
| [`evlog agents`](/cli/agents) | Writes the evlog conventions into `AGENTS.md` and installs the skills |
| [`evlog telemetry`](/cli/telemetry) | Shows, enables or disables the CLI's own anonymous usage telemetry |
| [`evlog upgrade`](/start/upgrade) | Experimental. Shows what moving to the newest evlog major changes in your code |

`evlog upgrade` changes nothing on its own and exits `1` while anything is left to change. `--write` applies the fixes and bumps `evlog` in `package.json`, and then exits `1` only while a change that needs a person remains. It refuses to write over uncommitted changes unless you add `--force`. Its output can change in a 1.x release.

## Global flags

Every command accepts these:

| Flag | What it does |
| --- | --- |
| `--json` | Machine-readable JSON on stdout instead of the report |
| `--debug` | Prints a debug summary of the run and emits it as a wide event. Experimental |
| `--no-header` | Skips the branded header. `EVLOG_CLI_NO_HEADER=1` does the same |
| `--cwd <dir>` | Runs against another directory instead of the current one |
| `--help`, `-h` | Usage for the command, on stdout |
| `--version`, `-v` | Prints the CLI version and exits |

A flag the command does not declare, or a value flag with nothing after it, stops the run with exit code `2`. A mistyped gate never runs the command without the gate. Flags written before the command name are checked the same way, so `evlog --dry-run init` is refused and does not run `init` for real.

## Where the output goes

The report you read is written to stderr. Stdout is reserved for `--json`, so you can pipe a run into `jq` without the report in the way:

```bash [Terminal]
evlog map --json | jq '.map.score'
```

Without `--json`, a command writes nothing to stdout. `--help` and `--version` are the two exceptions, so `evlog --help | grep map` finds its line. Every `--json` report carries a `schemaVersion`, `2` today, which changes when the shape of a payload does, and an `environment`. That one is the CLI's own, `production` for a published install, and says nothing about your app.

Colour follows the stream the text is written to. It is dropped when that stream is not a terminal, when `NO_COLOR` is set, with `FORCE_COLOR=0`, and under `TERM=dumb`. `FORCE_COLOR=1` keeps it in captured output. The report lays itself out for the width it is given, so set `COLUMNS` to render at a fixed width.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | The command ran and nothing failed. Warnings do not fail a run |
| `1` | A check failed, a gate such as `--min-score` was not met, or the command stopped on an error |
| `2` | Usage error: an unknown command, an unknown flag, a flag with no value, or an invalid value |

A pipe replaces `$?` with the exit code of the last command in it, so `evlog map --min-score 90 | head` always looks successful. Use `set -o pipefail` when you pipe a gated run.

## Monorepos

`init`, `map` and `doctor` resolve the nearest `package.json` above the working directory and treat that package as the project. In a pnpm or npm workspace, running from `apps/web` scans `apps/web` and leaves the repo root alone.

`evlog map` scans one app at a time. From a bare workspace root, where there is no framework to detect, it stops with an error and prints no empty report:

```bash [Terminal]
cd apps/web && evlog map
# or
evlog map --cwd apps/web
```

From the same root, [`evlog init`](/cli/init) offers the apps to set up and [`evlog logs`](/cli/logs) reads every app that has logs.

## Debug a run

`--debug` prints what the command did: the steps it went through, the directory it resolved, and any findings. It emits the same information as an evlog wide event.

```bash [Terminal]
evlog map --debug
```

```text [Output]
── debug ────────────────────────────────
command  map
env      development
cwd      /Users/you/apps/web
steps    resolveProject → detectFramework → resolveEvlog → scan → writeMapFile → done
──────────────────────────────────────────
full event → --json --debug  (stderr)
```

Add `--json` to get the whole event on stderr in place of the summary. `EVLOG_CLI_DEBUG=1` does the same as the flag, for a CI job you cannot edit. The summary is for reading, not parsing: its fields can change in a 1.x release.
