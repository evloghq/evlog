Your logs say a request returned 502. A signal says it was Stripe, that a retry would have worked, and that it is not worth waking anyone. Your logs say a checkout returned 200. A signal says the customer left without an order.

```json [Wide Event]
{
  "method": "POST",
  "path": "/api/checkout",
  "status": 502,
  "error": { "name": "FetchError", "message": "request to https://api.stripe.com/... failed, reason: read ECONNRESET" },
  "signals": {
    "fault": { "value": "upstream", "confidence": 0.93 }
  }
}
```

`@evlog/signals` asks a decision model one question per matching event and writes the answer onto the event, with a confidence. `WHERE signals.fault.value = 'upstream' AND signals.fault.confidence > 0.9` is then a query like any other.

A signal is a question in English, attached to the events it applies to. When an event matches, the model reads it and answers with a probability for each option. There is no prompt to tune and no parser to write.

::signal-ask
::

## Ask your first question

```bash [Terminal]
pnpm add @evlog/signals ai
```

`ai` 7.0.130 or later is a peer dependency. A signal is a name, a predicate that picks the events it applies to, and the question:

```typescript [server/signals.ts]
import { defineSignal } from '@evlog/signals'

export const fault = defineSignal({
  name: 'fault',
  when: e => (e.status ?? 0) >= 400,
  ask: 'Who is responsible for this failure?',
  choice: {
    client: 'Bad input, expired session, client mistake',
    app: 'A bug or misconfiguration in our own code',
    upstream: 'A third-party dependency failed',
  },
})
```

The default model is `typesafe-ai/jev` through Vercel AI Gateway. Set `AI_GATEWAY_API_KEY`, or nothing on Vercel, where OIDC is picked up. The reference shows how to [pick another model](/signals/reference#pick-the-model).

The next failed request carries the column shown at the top of this page: `value` is the answer and `confidence` is its probability. Columns are written before the console line, so they show in the dev terminal, in platform logs such as Vercel, and in every [drain](/drains).

## Three kinds of answer

What you write decides the shape of the column, and the shape decides the query.

| You want to | You write | You get | Then |
| --- | --- | --- | --- |
| Flag events | `ask` | `value: boolean`, `confidence` | `WHERE signals.x.value = true`, or `keep` the event |
| Categorise events | `ask` and `choice` | `value` is one option name, `confidence` when the model gives one | `GROUP BY signals.x.value` |
| Rank events | `ask` and `score` | `value` is a level name, `score` between levels, `confidence` when the model gives one | `ORDER BY signals.x.score DESC` |

### Flag with a yes or no

`ask` alone is a yes or no question, and the model returns the probability of yes. The optional `criteria` tells the model what each answer looks like, which raises confidence on borderline events:

```typescript [server/signals.ts]
export const retryable = defineSignal({
  name: 'retryable',
  when: e => (e.status ?? 0) >= 500,
  ask: 'Would the same request most likely succeed if retried in a few seconds?',
  criteria: {
    true: 'Timeout, connection reset, rate limit, transient upstream error',
    false: 'Bug, bad data, missing resource',
  },
})
```

```json [Column]
"retryable": { "value": true, "confidence": 0.9 }
```

### Categorise with `choice`

`fault` above is a choice signal. Each option carries the description the model matches against, and `value` is one of the keys. Add an `unknown` option when the event may not carry the answer. Without it the model picks the least wrong of the others, and nothing tells you that your events are missing a field.

### Rank with `score`

Levels are ordered, lowest first. `value` is the most likely level and `score` is the probability-weighted position, so `severity.score > 1.5` reads as closer to `page` than to `watch`:

```typescript [server/signals.ts]
export const severity = defineSignal({
  name: 'severity',
  when: e => (e.status ?? 0) >= 500,
  ask: 'How urgent is this failure for the on-call engineer?',
  score: ['noise', 'watch', 'page'],
})
```

```json [Column]
"severity": { "value": "watch", "score": 1.2, "confidence": 0.6 }
```

Sort on `score` and bucket on `value`. `confidence` is the probability of the top level, so `0.6` here says the model was between `watch` and `page`. A model that answers without a distribution leaves `confidence` off choice and score columns.

## Scope every signal with `when`

`when` is a plain predicate and runs before anything else. No model call happens when it returns `false`, so `fault` costs nothing on the requests that succeed.

A signal sees the wide event in `enrich`, or the request context plus `status`, `path`, `method` and `durationMs` in `keep`. The fields evlog sets are typed. What your handlers logged with `log.set()` is there too, as `unknown`:

```typescript [server/signals.ts]
when: e => e.status === 200 && (e.payment as { provider?: string } | undefined)?.provider === 'stripe'
```

The model reads the event and the question, nothing else. Check three things before you ship a signal:

1. **The answer is in the event.** "Would a retry succeed" works because the error name and status are there. "Is this user about to churn" does not.
2. **The answer is one value.** "Was it slow, and was it our fault" is two signals.
3. **A rule could not do it.** `status >= 500` is a rule, and `when` alone answers it. "Transient or permanent" needs the model.

[Recipes](/signals/recipes) has twelve questions that pass.

## Keep what sampling would drop

Add `keep` to a signal, and a verdict that matches forces the event past [sampling](/events/sampling). Here are six requests under a production rule that keeps 0% of `info`. Sampling keeps the two errors, and three of the four 200s come back because a signal said so:

::signals-judge
::

A checkout that answered 200 and created no order is a normal success to every rule on its fields. This signal keeps it:

```typescript [server/signals.ts]
export const silentFailure = defineSignal({
  name: 'silent-failure',
  when: e => e.status === 200 && e.path === '/api/checkout',
  ask: 'Returned 200, but the customer did not get what they came for',
  keep: 0.8,
})
```

`keep: 0.8` keeps a yes with a confidence above 0.8. It is the short form of `keep: v => v.value && v.confidence > 0.8`. On a choice signal `v.value` is typed on the option names, so the compiler checks `v.value === 'app'`. A signal with `keep` needs a `when`.

`keep` only promotes. It never drops an event a sampling rule would have kept, so head sampling stays deterministic. The promoted event carries `kept: true` on the column, so you can count promoted events apart from sampled ones.

## What it costs

There are four prices, and each has a lever. All of them fail open: when a limit is reached, events flow through unjudged and nothing in the request path waits.

| Price | At the default | The lever |
| --- | --- | --- |
| Money | $0.042 per million input tokens, about $6 per 100k judged events | `when`, `cacheKey`, `state` |
| Rate | 1,200 calls per minute per account | `budget.perMinute`, `cacheKey` |
| Latency | Up to 2 s before a judged event drains, client unaffected | `timeoutMs`, a tight `when` |
| Egress | The whole event, before redaction for a `keep` signal | `state`, `providerOptions.gateway.zeroDataRetention` |

### Money

Jev bills input tokens only, at $0.042 per million at the time of writing. A 1.5k-token event is about $0.00006, so 100k judged events are about $6 and a million are about $60. In the demo run, 15 requests came to 14 calls, 1,569 input tokens, and $0.00007. Prices move, and the model page has the current figure.

The bill follows how many events reach the model. All signals due for one event share one call, so a second question on an event that is already judged is close to free:

::signal-batch
::

Three levers, in order:

- `when` keeps events away from the model.
- `cacheKey` reuses a verdict. An outage produces thousands of identical 502s, and a key on `path + error.name` makes them one call.
- `state` picks the fields the model reads. Six fields cost fewer tokens than the whole event.

### Rate

The account rate binds before money: 1,200 requests per minute per TypeSafe account, about 20 a second. `budget.perMinute` (default 600) caps one process, so with four instances on one account, set it to 300. When the budget is spent, events pass through unjudged and `stats().skipped` goes up. Three failed calls in a row pause the model calls for 30 s. The reference describes [how the budget is spent](/signals/reference#how-the-budget-is-spent) during a spike.

### Latency

A judged event reaches the console and your drain after the model's round trip, at most `timeoutMs` (default 2 s) per call. A `keep` signal also holds the sampling decision for that long. Two facts make the wait acceptable:

- The response is already sent. `keep` and `enrich` run after the request finishes, so the client never waits on the model.
- `durationMs` is measured before keep hooks run, so the judgment does not inflate your latency charts.

Put `keep` signals on narrow paths: `/api/checkout`, not every 200.

### Egress

The model reads what `state` returns. By default that is the whole wide event minus the `signals` columns. A signal judged in `enrich` reads the event after [redaction](/events/redaction), when redaction is on. A call made for a `keep` signal reads the request context before redaction runs. If your handlers log anything you would not paste into a third-party API, pick the fields:

```typescript [evlog.config.ts]
createSignals({
  signals,
  state: e => ({ status: e.status, path: e.path, durationMs: e.durationMs, error: e.error, payment: e.payment }),
  providerOptions: { gateway: { zeroDataRetention: true } },
})
```

`zeroDataRetention` is passed through to AI Gateway untouched. Inference runs in your process with your key. evlog holds no key and proxies nothing.

### What never happens

- A verdict is never prose. A column is a typed value with a probability, and nothing else is added to the event unless you set `stampModel`.
- A limit never fails a request. Budget spent, breaker open, state too large, model down: the event drains as it would have without signals, and a counter in [`stats()`](/signals/reference#stats) moves.

In tests, pass `evaluate` from `scriptedEvaluate()` in `@evlog/signals/testing` and no model is called. See [Testing](/signals/reference#testing).
