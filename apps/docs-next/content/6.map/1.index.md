You adopted evlog in the routes you touched last week. `evlog map` tells you about the other forty: which entry points have no wide event, no context, no structured error, and which of them move money or touch auth.

```bash [Terminal]
npx evlog map
```

```text [evlog map]
▀▀█ █▀▀   score /100              evlog-playground · Nuxt
  █ █▀█   ▰▰▰▰▰▰▰▰▰▰▰▰▰▰▰▱▱▱▱▱    29 entry points scanned
  ▀ ▀▀▀   good

FIX FIRST
1. ANY    /api/auth/:all* A — touches auth and logs nothing
2. GET    /api/test/catalog/payment-declined $ — moves money with no audit trail
3. POST   /api/auth/login A — missing log.audit

▲ 76 → 86 by fixing the 3 above
```

Run `evlog map <file>` on one of them to see the shape the rules expect, fix it, and run the map again. Run the command from the app's package: at a monorepo root with no framework of its own it stops and asks for an app directory or `--cwd`.

## What it reads

The scan reads your source with an AST and applies a versioned rule set: `useLogger()` and `log.set()` on every entry point, `createError({ why, fix })` where it throws, `log.audit()` where it moves money or touches auth. It does not run your handlers or watch traffic, so it works on an app that shipped three years ago and on a scaffold alike, and the same source with the same CLI version produces the same score on any machine.

That is also its limit: a high score says the recognized patterns are in place. It does not prove the logs reach your drain or hold enough context to explain a failure.

The framework is detected from `package.json` and config files. When several match, the most specific one wins and the report says which others matched. `--framework` overrides the choice. Each framework has its own way of finding entry points:

| Framework | What becomes an entry point |
| --- | --- |
| Nuxt | `server/api/**` (path prefixed `/api`, method from the filename suffix), `server/routes/**`, `server/middleware/**`, `server/tasks/**` as scheduled jobs, and pages under `app/pages/`, `pages/` or `src/pages/` |
| Nitro | `routes/**`, `api/**` (path prefixed `/api`), `middleware/**` |
| Next.js App Router | One API handler per HTTP method exported from `app/**/route.ts`, `app/**/page.tsx`, `middleware.ts`, and one server action per function exported from a `"use server"` file. `src/app/` and `src/middleware.ts` are read too |
| TanStack Start | `src/routes/**`: an API handler when the route declares server handlers or `createServerFn`, a page otherwise. `__root` files are skipped |
| Hono | `app.get('/path', handler)` registrations with a literal path, and `app.on(method, path, handler)` |
| Express | `app.get('/path', handler)` registrations on the app or on a `Router()` |
| Fastify | `app.get('/path', handler)` registrations and `app.route({ method, url, handler })` |
| Effect | `HttpRouter.add` and `HttpRouter.route` |
| eve | `agent/tools/**`, `agent/schedules/**` (TypeScript or Markdown) and `agent/channels/**`, plus the tools of each declared subagent |

A Next.js `route.ts` with no HTTP method export is listed once as `ANY`. An eve workspace is read from each `agents/<name>/agent/`, and its entry points carry the member's name (`support/lookup`). The report shows the HTTP method of an entry point, or its kind when it has none: `ANY`, `PAGE`, `MID`, `ACT` (server action), `CRON`, `WS`, `TOOL`, `SCHED`, `CHAN`.

What the scan does not see:

- **Your own wrappers.** A re-exported evlog helper counts, a helper wrapped in a function of your own (`withRequestLog(handler)`) does not. [Rules](/map/rules#how-evlog-helpers-are-recognized) lists what is recognized.
- **Other logging libraries.** The checks look for evlog calls, so a project that logs another way scores low even when its logs are useful. You can scan a project before installing evlog to plan the work.
- **Hono paths that are not literal.** A computed path and a controller-style handler (`app.get('/users', users.list)`) are not resolved, and `app.route('/api', users)` reports the child paths without `/api`.
- **Effect `HttpApi` endpoints**, whose path is declared apart from the handler.
- **eve's flat layout**, with agent files at the package root. A web app that runs its agent from another package with `eveRoot` is scored as the web app: run `evlog map` in the agent's package. eve skills, hooks and colocated `*.test.*` files are not entry points.
- **A file that does not parse.** The report warns `<file> failed to parse` and counts the file as one entry point that fails every check. `--verbose` prints every parser error. A [gated run](/map/ci#set-a-floor) stops instead.

## Read the report

The default report reads top down:

| Block | What it tells you |
| --- | --- |
| Score | The project score out of 100, its grade, and a row of blocks with one block per entry point, worst on the left. On a large project the row is sampled down to the terminal width |
| `COVERAGE` | The average score per area, for the areas the project has: API handlers, Pages, Agent tools, Middleware & jobs, Agent triggers, and Money & auth |
| `FIX FIRST` | At most three entry points, sensitive ones first, then worst score first, each with its file, line and the rule that failed |
| `THEN` | Every other gap, batched by fix: `add useLogger + log.set to /api/test/browser-ingest +4` is five entry points that need the same two lines |
| `GOING FURTHER` | [Opportunities](/map/rules#opportunities): features the project already uses that an entry point could use too. They never change the score |
| `✓ Already solid` | Entry points with nothing left to fix |
| `▲ 76 → 86` | The score you reach by fixing what is under `FIX FIRST` |

Money & auth groups every entry point flagged sensitive, so it overlaps the other areas, and it is marked `⚠` when it scores below 70. In `FIX FIRST`, `$` is money, `A` is auth and `@` is PII.

`--all` prints one row per entry point, worst first, grouped by directory, with one column per requirement:

```text [evlog map --all (trimmed)]
evlog-playground · Nuxt · 76/100 · 29 entry points, worst first

                                            log   ctx   err   audit catch fetch
server/
├─ api/auth/[...all].ts   ▰▰▱▱▱▱▱▱▱▱  20 A  ●     ●     ·     ●     ·     ·
├─ …i/auth/login.post.ts  ▰▰▰▰▰▰▰▰▱▱  75 A  ●     ●     ·     ●     ·     ·
└─ …st/wide-event.get.ts  ▰▰▰▰▰▰▰▰▰▰ 100    ●     ●     ·     ·     ·     ·

● covered   ● gap   ·  not applicable   $ money   A auth   @ pii
```

A `·` is a rule that does not apply, and a hollow `○` is a check you [disabled with a comment](/map/rules#disable-a-check).

Pass a file, a route, or `"METHOD /route"` to inspect one entry point:

```text [evlog map server/api/auth/login.post.ts]
POST   /api/auth/login A   ▰▰▰▰▰▰▰▰▱▱ 75/100
server/api/auth/login.post.ts · Nuxt

WHY THIS FILE IS SCANNED
▍ POST /api/auth/login — server handler

FLAGGED SENSITIVE BECAUSE
▍ auth: path says "auth"

CHECKS
✓ useLogger  wide event emitted per request
✓ log.set    context attached with log.set()
✗ log.audit  sensitive action with no audit trail  evlog.dev/use-cases/audit/overview

SUGGESTED SHAPE — Nuxt
│ export default defineEventHandler(async (event) => {
│   log.audit({
│     action: 'auth.login',
│     actor: { type: 'user', id: user.id },
│   })
│ })

▲ fixing this entry point: 75 → 100
```

The first two blocks say what the CLI thinks the file is and why it flagged it, so a wrong call is one line to spot. The suggested shape is composed from the rules that failed, in your framework's idiom, and the audit action is read off the route. A file that holds several entry points shows the first one and lists the others under `ALSO IN THIS FILE`.

## How the score is computed

Every entry point starts at 100 and loses the weight of each requirement it fails, down to 0.

| Requirement | Weight |
| --- | --- |
| `wide-event` | 40 |
| `audit` | 25 |
| `structured-errors` | 20 |
| `page-error-handling` | 20 |
| `context` | 15 |
| `error-handling` | 15 |

A rule that passes costs nothing, and neither does one that reports `n/a`, because it did not apply or you disabled it. Opportunities carry no weight. The weights add up to more than 100 on purpose: an entry point that fails everything lands at 0, and `wide-event` at 40 outweighs any pair of the smaller rules. [Rules](/map/rules) says what each one expects.

The login handler above fails `audit` alone, so it scores 75. `structured-errors` and `error-handling` are `n/a` there, since it throws nothing and catches nothing.

::map-score-climb
::

The project score is the average of the entry points, rounded, and weighted by what a blind spot costs:

| Entry point | Weight |
| --- | --- |
| Flagged money or auth | ×2 |
| Page | ×0.5 |
| Everything else | ×1 |

A page counts ×0.5 even when it is flagged, and exempt entry points are left out. With a sensitive handler at 75, a plain handler at 100 and a page at 50:

```text [Project score]
(75 × 2) + (100 × 1) + (50 × 0.5)   275
───────────────────────────────── = ───── = 79
        2 + 1 + 0.5                  3.5
```

| Score | Grade |
| --- | --- |
| 90 to 100 | `excellent` |
| 70 to 89 | `good` |
| 50 to 69 | `needs work` |
| 0 to 49 | `at risk` |

With no scorable entry point the report prints `--` and `nothing to scan`. `--json` still sets `map.score` to 100, next to `grade: "unscored"`, and an unscored run never passes `--min-score`. Check the detected framework and the entry point count before you read the number.

The score is made to be compared with itself. A 200-route app at 70 is in better shape than a 6-route app at 70, so compare two runs of one project.

### How an entry point is classified

Each entry point also gets a class, which the `summary` in `--json` counts:

| Class | When |
| --- | --- |
| `instrumented` | A handler that passes `wide-event` and `context`, an eve schedule or channel that passes `wide-event`, or a page that handles its fetch errors |
| `partial` | A handler that passes one of the two |
| `dark` | A handler that passes neither, or a page that swallows fetch errors |
| `exempt` | Nothing to instrument: evlog's own ingest endpoint, or a page that fetches nothing |

`dark` means the scan did not recognize evlog instrumentation. Read the code before you treat it as an absence of logs.

### What counts as sensitive

| Marker | Level | Flagged when |
| --- | --- | --- |
| `$` money | `high` | The handler imports `stripe`, `@stripe/stripe-js`, `paddle-sdk` or `@lemonsqueezy/lemonsqueezy.js`, or the path contains `checkout`, `payment`, `billing`, `invoice`, `refund`, `subscription`, `charge` or `payout` |
| `A` auth | `high` | The handler imports `better-auth`, `next-auth`, `lucia`, `@auth/core` or `@auth/nextjs`, or the path contains `auth`, `oauth`, `login`, `logout`, `signin`, `signup`, `register`, `password`, `token`, `session`, `mfa` or `otp` |
| `@` PII | `medium` | The handler names `email`, `phone`, `address`, `ssn` or `iban` and calls `create`, `update`, `insert` or `upsert` |

`high` doubles the entry point's weight and adds the `audit` requirement. `medium` only marks it in the report. Imports are read from the AST, subpaths included, so a comment that mentions `stripe` flags nothing. Path terms match whole words and allow a plural: `/api/authors` is not auth, `/api/refunds` is money.

## Flags

| Flag | Default | What it does |
| --- | --- | --- |
| `<entry>` | none | Inspects one entry point, by route path, `"METHOD /path"` or file path. One that matches nothing exits 2, and `evlog.map.json` is still written unless you pass `--no-write` |
| `--all` | off | Prints every entry point as a check matrix |
| `--min-score <n>` | off | Exits 1 when the project score is below `n`, a whole number from 0 to 100 |
| `--baseline [ref]` | off | Exits 1 on a [regression](/map/ci#catch-a-regression) against the committed map. Takes a path or `git:<ref>` |
| `--baseline-label <text>` | the ref | Names the baseline in the report and the annotations, for a map copied to a temporary file |
| `--framework <name>` | detected | Forces `nuxt`, `nitro`, `next`, `tanstack-start`, `hono`, `express`, `fastify`, `effect` or `eve` |
| `--no-write` | writes | Skips writing `evlog.map.json` |
| `--verbose` | off | Shows every parser error for a file that fails to parse, not only the first |
| `--cwd <dir>` | current | Scans another directory |
| `--json` | off | Prints the full map as JSON on stdout, the same as `--format json` |
| `--format <name>` | `human` | `human`, `json`, or `github` for [workflow annotations](/map/ci#annotate-the-diff) on stdout. `--json` with another format exits 2 |
| `--limit <n>` | `10` | The most annotations `--format github` emits, 1 or more. GitHub keeps ten per level per step |
| `--no-header` | off | Skips the branded header above the report |
| `--debug` | off | Writes a debug case file. Experimental |

`--min-score` and `--baseline` can be set once for the project in `evlog.config.ts`, as `map.minScore` and `map.baseline`, next to `map.rules` and `map.ignore`. The flag wins when both are set. [Config](/cli/config) has the four settings.

## The map file

Every run writes `evlog.map.json` to the project root: the score, the framework, the CLI version and rule-set version that wrote it, and every entry point with its checks, suggestions, sensitivity and score. It is the `map` object that `--json` prints, with the entry points sorted so two runs diff cleanly.

- **You do not gate, or you gate with `--min-score` only.** The file is a build artifact. Add it to `.gitignore`, or pass `--no-write`.
- **You gate with `--baseline`.** Track it like a lockfile: regenerate it with `evlog map`, review it in the diff, never edit it by hand. It changes on every run, since `generatedAt` does.

## Gate a pull request

Commit `evlog.map.json` once, then run `evlog map --baseline` on every pull request. A legacy app that starts at 34 and never regresses is in better shape than a new one at 80 that drifts. [CI](/map/ci) covers both gates, the exit codes and the GitHub Action that comments on the pull request.

::callout{icon="i-lucide-flask-conical" color="warning"}
The rule set is young, and a release that sharpens a rule can change a verdict on code you did not touch. Pin the CLI version in CI if you gate on the score.
::
