The Observability Score is the number `evlog map` prints: how many of your entry points emit a wide event, attach context, throw structured errors and audit what moves money or touches auth. [Map](/map#how-the-score-is-computed) has the weights and the grades. This page is the workflow around the number: read it, move it, and decide how far to trust it.

## Adopt it in an app already in production

The scan reads source, not traffic, so an app that shipped three years ago is scored the same way as a scaffold. You get the list before the next incident instead of during it:

1. Run `npx evlog map --no-write` from the app's package. Nothing is installed or deployed, and no agent watches a live process.
2. Read `FIX FIRST`. It holds at most three entry points, ranked by what they touch: money, auth and PII come before a health check.
3. Fix those three, running `npx evlog map <file>` on each to see the shape the rules expect. Nothing else on the list has to move yet.
4. Commit `evlog.map.json` and gate on it with [`--baseline`](/map/ci#catch-a-regression). From that commit on, a recognized regression needs a review.

A large codebase scores badly on its first run, and that number is not the point. A legacy app that starts at 34 and never regresses is in better shape than a new one at 80 that drifts down for a year.

## Fix one context gap

In a Next.js App Router app, this handler is wrapped for logging but adds nothing to its event. `@/lib/evlog` is the file you create with `createEvlog()`, as [Next.js](/integrations/next) shows:

```typescript [app/api/hello/route.ts]
import { withEvlog } from '@/lib/evlog'

export const GET = withEvlog(async (request: Request) => {
  const name = new URL(request.url).searchParams.get('name') ?? 'world'
  return Response.json({ message: `Hello ${name}` })
})
```

Inspect that file:

```bash [Terminal]
npx evlog map app/api/hello/route.ts --no-write
```

`wide-event` passes, since `withEvlog` emits one event per request. `context` fails with `no log.set() context accumulation`, which costs the route 15 points. Attach a decision the handler made, without recording the user's name:

```typescript [app/api/hello/route.ts]
import { useLogger, withEvlog } from '@/lib/evlog'

export const GET = withEvlog(async (request: Request) => {
  const log = useLogger()
  const name = new URL(request.url).searchParams.get('name') ?? 'world'
  log.set({ greeting: { personalized: name !== 'world' } })
  return Response.json({ message: `Hello ${name}` })
})
```

Run the same command again. `context` passes and the route moves from 85 to 100. In a larger app the project score moves by less, since it is a weighted average over every scored entry point.

A passing check says the pattern exists. Whether `greeting.personalized` is the field your next investigation needs is a judgement the scan cannot make, so read the event output too.

## Why a static score can gate a pull request

The same source, CLI version and framework adapter produce the same score on any machine, on every run. The scan applies a versioned rule set to an AST, so nothing depends on timing, traffic or environment:

- **No flaky gates.** A green `--min-score` means the recognized requirements cleared your floor. It never means the runner got lucky.
- **It ratchets.** `--baseline` compares against the committed `evlog.map.json` and fails on a requirement an existing entry point lost, the way a snapshot test fails. A refactor that drops a `log.set()` cannot pass a review that skips the diff.
- **It is reproducible.** The map file names the CLI and rule-set versions that wrote it, so anyone can regenerate a score from three weeks ago and cite it in a review.
- **It runs before traffic exists.** A gap is reported when the code is written, which is when it is cheapest to fix.

## What a high score does not prove

- **Runtime behavior.** Source patterns do not prove a handler runs, reaches its drain, or covers every error path. An entry point can score 100 and still emit an event with the wrong context.
- **Coverage of your whole app.** The scan sees the frameworks and entry point shapes its adapters recognize, listed on [Map](/map#what-it-reads). Logging through another library, or through a wrapper of your own, scores low even when the logs are useful. Use the score to plan evlog adoption, not to rank logging libraries.
- **Sensitivity.** Money and auth flags come from imports and route paths. The PII flag needs a field name such as `email` and a write call in the same handler. `evlog map <file>` prints the reason for each flag, so check it.
- **An empty scan.** With no scorable entry point, the report prints `--` and `nothing to scan`. `--json` still sets `map.score` to 100, next to `grade: "unscored"`, so read the grade and the entry point count, not the number.

Watch the `dark` count and the Money & auth row more than the headline. Those are where the next incident is hiding. Pair the score with runtime tests and with the [sampled events](/events/sampling) your app sends in production.

## Gate CI once the baseline is reviewed

Pin the CLI version, and keep `map.ignore` and `map.rules` in [`evlog.config.ts`](/cli/config), so a score only changes when your code does. A release that sharpens a rule can change a verdict on code you did not touch.

On a pull request, compare against the base branch rather than the working tree: a bare `--baseline` reads the `evlog.map.json` on disk, so a pull request that commits a regenerated map is compared with itself. A shallow checkout has no base branch, so fetch it first:

```bash [Terminal]
git fetch origin main
npx evlog map --baseline git:origin/main
```

The base branch needs a reviewed `evlog.map.json`. Without one, the command exits 1 with `No evlog.map.json in origin/main, and the ratchet needs a committed map`, which is a setup gap and not a regression.

`--baseline` does not track every field: removing one `log.set()` can leave another that still satisfies `context`, and a new dark entry point lowers the score without failing the gate. Add `--min-score` for a floor on the project score, knowing that an average can hide one weak route. [CI](/map/ci) covers both gates, the exit codes and the GitHub Action.
