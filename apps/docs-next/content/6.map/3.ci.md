A score you read once on your machine does not stop the next handler from shipping with no event. Two flags turn `evlog map` into a check a pull request has to pass: `--min-score` asks whether the app is good enough, and `--baseline` asks whether this pull request made it worse.

::map-pr-gate
::

Opportunities never affect the score, so neither gate can fail because the CLI suggested a feature. Only [requirements](/map/rules#requirements) fail a build.

## Set a floor

`--min-score <n>` prints a verdict under the report and exits 1 when the project score is below `n`:

```bash [Terminal]
evlog map --min-score 80
```

```text [Below the threshold]
 GATE  score 76 is below --min-score 90 — exit code 1
fix what is listed under FIX FIRST to pass · evlog.dev/cli/ci
```

```text [At or above it]
 GATE  score 76 meets --min-score 70 — exit code 0
```

The full report is printed either way, so a failed job says what to fix.

- The threshold is a whole number from 0 to 100. Anything else, such as a typo, a unit or an empty shell variable, stops the command with exit code 2. A misspelled flag such as `--min-scor 90` does the same.
- A run with nothing to score never meets a threshold. It exits 1.
- A file that does not parse stops a gated run with exit code 1 and `cli.MAP_PARSE_FAILED`, and leaves `evlog.map.json` as it was. Fix the file, or list it under `map.ignore` in [`evlog.config.ts`](/cli/config) when it is not app code.
- `map.minScore` in `evlog.config.ts` sets the floor for the project. The flag wins, and the verdict names the setting it came from.

Set the floor to today's score and raise it as you fix things. A floor of 90 on an app that scores 41 fails every pull request, and the team learns to ignore the job.

```bash [Terminal]
evlog map --json --no-write | jq '.map.score'
```

## Catch a regression

`--baseline` compares the fresh scan with the `evlog.map.json` you committed, per entry point and per check:

```bash [Terminal]
evlog map --baseline
```

```text [A regression]
 BASELINE  score 56 → 44 (-12) vs evlog.map.json

REGRESSED
✗ POST /api/checkout — useLogger no longer passes
   server/api/checkout.post.ts · evlog.dev/learn/wide-events
✗ POST /api/checkout — log.audit no longer passes
   server/api/checkout.post.ts · evlog.dev/use-cases/audit/overview

NEW AND DARK
⚠ GET /api/reports — added with no instrumentation
```

The unit is the requirement. A refactor that instruments one route and breaks another can leave the score where it was, and the comparison still reports the break.

| Change | Verdict |
| --- | --- |
| A requirement went from `pass` to `fail` | Fails the gate |
| A passing requirement was [disabled with a comment](/map/rules#disable-a-check) | Fails the gate |
| The score of the entry points that were already in the baseline dropped | Fails the gate |
| A new entry point was added with no instrumentation | Listed under `NEW AND DARK`, does not fail |
| An entry point was deleted | Counted as gone |
| A requirement went from `fail` to `pass` | Counted as fixed |

A new dark route lowers the project score and does not fail this gate. On an app that is not green yet, failing every pull request that adds an endpoint teaches the team to turn the job off. Run `--min-score` next to `--baseline` when you want a bar for new work.

The comparison reads a file your repository already contains: no network, no token, and a private repository gates like a public one.

### The map file is the ratchet

Commit `evlog.map.json`:

```bash [Terminal]
evlog map            # updates the file
git add evlog.map.json
```

A run that reports a regression exits 1 and does not rewrite the file. Rewriting it would lower the baseline to the worse state, and the same command run again would exit 0. To accept a drop, run `evlog map` without `--baseline` and commit the new map with the reason in the message.

### Choose what to compare against

| Value | Reads |
| --- | --- |
| `--baseline` | `evlog.map.json` in the working tree, then `git:HEAD` when there is no file on disk |
| `--baseline git:<ref>` | The copy committed at that ref |
| `--baseline <path>` | Any map file, relative to the project |

`map.baseline` in `evlog.config.ts` takes `true`, a path or `git:<ref>`. `--baseline-label <text>` renames the baseline in the report and the annotations, for a map copied to a temporary file.

A pull request that commits a regenerated map is compared with itself by a bare `--baseline`. Compare against the base branch instead. A default checkout fetches only the commit that triggered the run, so fetch the base first:

```bash [Terminal]
git fetch origin <base-branch>
npx evlog map --baseline git:origin/<base-branch>
```

`git:<ref>` reads only a file that was committed. When the base branch has no map, the command exits 1 with `No evlog.map.json in origin/<base-branch>, and the ratchet needs a committed map`. That is a setup gap, not a regression.

### How entry points are matched

An entry point is matched to its baseline entry by method and path. When a handler moves to another file in a pull request that adds a second handler with the same method and path, the comparison pairs it with the one that lost the most checks, then the most score. A move can therefore report a regression it did not cause. Read the report, then run without `--baseline` to accept it.

The comparison also does not track every field: removing one `log.set()` call can leave another that still satisfies `context`.

### When the rule set moves

`evlog.map.json` records the CLI version that wrote it and a rule-set version, which changes only when a rule's verdicts can change. When the committed rule-set version differs from the running one, `--baseline` refuses to compare and exits 2, because a tightened rule would show up as a regression on code the pull request did not touch.

```text [Output]
baseline was written by @evlog/cli 0.3.0, running @evlog/cli 0.4.1 (rule set 1 → 2)
regenerate the baseline: evlog map && git add evlog.map.json
```

A CLI release with no rule change keeps the rule-set version, so upgrading does not force a new baseline. A map written before version reporting has no version fields, and the CLI warns instead of failing.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | The score met the threshold, nothing regressed against the baseline, or neither gate was requested |
| `1` | The score is below `--min-score`, a regression against `--baseline`, a file a gated run could not parse, a baseline that could not be read, or a scan that could not run |
| `2` | A usage error: an unknown flag, a flag with no value, an invalid `--min-score`, `--framework`, `--format` or `--limit`, `--json` with another `--format`, an entry point to inspect that does not exist, or a baseline whose rule set does not match the running CLI |

::callout{icon="i-lucide-triangle-alert" color="neutral"}
A pipe replaces the exit code with the one of its last command, so `evlog map --min-score 90 | tee map.log` always looks green. Add `set -o pipefail` to the step.
::

## Run the GitHub Action

The [evlog action](https://github.com/evloghq/action) runs `evlog map`, scans the pull request's base branch to compare against, and reports where the review happens:

```yaml [.github/workflows/observability.yml]
name: Observability

on: pull_request

permissions:
  contents: read
  checks: write
  pull-requests: write

jobs:
  map:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: evloghq/action@v1
        with:
          min-score: 80
```

Nothing has to be committed and no token has to be created. On each run the action:

1. Runs `evlog map` on each package with a pinned `@evlog/cli`.
2. On a pull request, checks the base branch out next to the workspace, scans it with the same CLI, and compares.
3. Creates a check run named `evlog map` with one annotation per finding: the regressions, as failures, when there is a base, and every gap in `FIX FIRST` order, as warnings, when there is none.
4. Writes the report to the job summary, with every entry point and the result of each check.
5. Posts one comment on the pull request and edits it on every run.
6. Sets its outputs, then fails the step when a package regressed or scored under `min-score`, unless `gate` is `false`.

The comment opens on the score, then one line with the grade, the movement against the base, the number of regressions and a missed `min-score`. A failed gate lists each regression with the entry point, the check it lost and the score it cost. A passing run lists the checks that were fixed. Below that come the instrumented, partial and dark counts (one row per package in a monorepo) and up to five entry points to fix first. With no `min-score` set, the comment suggests one at today's score.

### Inputs

| Input | Default | What it does |
| --- | --- | --- |
| `command` | `map` | The CLI command to run. Only `map` |
| `version` | pinned per action release (`0.8.0` in 1.3.0) | The `@evlog/cli` version to run, or a full package spec. `latest` follows npm |
| `working-directory` | `.` | The project to scan, relative to the workspace |
| `packages` | none | One directory or glob per line (`apps/*`), each scanned as its own package |
| `baseline` | `auto` | `auto` scans the pull request base and compares against it. A path or `git:<ref>` is passed to the CLI. `none` turns the comparison off |
| `min-score` | none | Fails when a package scores below this number, 0 to 100 |
| `limit` | `10` | The most annotations per package when findings fall back to workflow commands. A check run has no cap |
| `gate` | `true` | `false` reports and sets the outputs without failing the step |
| `annotations` | `true` | Draws findings on the diff through the check run. Needs `checks: write` |
| `summary` | `true` | Writes the report to the job summary |
| `comment` | `true` | `true` posts one comment and keeps it updated. `on-failure` posts only when the gate failed, and updates an existing comment either way. `false` posts nothing. Needs `pull-requests: write` |
| `comment-key` | `default` | Keeps separate comments when the action runs more than once on a pull request |
| `telemetry` | `true` | `false` turns off telemetry for the action and its CLI scans. `DO_NOT_TRACK=1` and `EVLOG_TELEMETRY=0` do the same |
| `token` | the workflow token | The token for the check run and the comment. Pass an app token to post as your own bot |

On a push there is no base, so `baseline: auto` turns the comparison off and the run only reports. Pass `baseline: git:origin/main` to compare against a committed map. A package that does not exist on the base branch is new and has nothing to regress from.

### Outputs

| Output | What it is |
| --- | --- |
| `score` | The lowest package score |
| `delta` | The lowest score movement against the baseline. Empty without one |
| `regressions` | The number of checks that passed on the base and no longer do, every package together |
| `instrumented`, `partial`, `dark` | Entry point counts per class, every package together |
| `passed` | `true` when every package met the gate, whatever `gate` is set to |
| `results` | JSON, one entry per package: `name`, `framework`, `projectName`, `score`, `status`, `reasons`, `summary`, `delta`, `regressions`, `fixed` |

### Permissions

`contents: read` checks the code out. `checks: write` is for the check run and `pull-requests: write` for the comment. Without either, the action says so in a notice and the rest still runs: findings go out as workflow commands, capped at `limit` per package. Pull requests from forks get a read-only token, so they get those annotations and the job summary, with no check run and no comment.

## Annotate the diff

Without the action, `--format github` does the annotations from a `run:` step:

```yaml [.github/workflows/observability.yml]
      - uses: actions/setup-node@v5
        with:
          node-version: 22
      - run: npx evlog map --format github --min-score 80 --no-write
```

It writes [workflow commands](https://docs.github.com/en/actions/reference/workflow-commands-for-github-actions) to stdout, and the runner puts each finding on its line in the pull request. The report still goes to stderr and the exit code is the same, so both gates still fail the job. `--no-write` keeps the job from producing a map file nobody reads.

With `--baseline`, the findings are the regressions, as errors:

```text [With a baseline]
::error file=src/checkout.ts,line=12,title=evlog map%3A audit::has logger + context but no log.audit() — sensitive route needs audit trail
::error title=evlog map::score 74/100 (good): 18 instrumented, 2 partial, 9 dark; regressed against git:origin/main
```

Without one, they are every gap in `FIX FIRST` order, worst entry point first, as warnings. The list stops at `--limit`, and the closing notice says how many were left out:

```text [Without a baseline]
::warning file=src/payments.ts,line=3,title=evlog map%3A audit::has logger + context but no log.audit() — sensitive route needs audit trail
::warning file=src/health.ts,line=5,title=evlog map%3A wide-event::handler adds nothing to its request event — only method, path and status are recorded
::notice title=evlog map::score 76/100 (good): 19 instrumented, 2 partial, 8 dark; 13 more findings not shown
```

GitHub draws an annotation inline only when its line is part of the diff. The full list is under the job's Annotations on the Checks tab.

## Pin the CLI version

A release that sharpens a rule can fail a pull request for a reason its author cannot see in the diff.

Each action release pins the `@evlog/cli` it was tested with, so `@v1` does not follow npm, and upgrading the action is the pull request where a moved score is expected. When the action runs CLI 0.10 or later and the workflow has installed dependencies, a project that installs `@evlog/cli` runs its own version instead, on both sides of the comparison.

Without the action and without `@evlog/cli` installed, the `evlog` executable fetches the CLI on every run, so the job follows the latest release. Install it and let the lockfile hold it:

```bash [Terminal]
pnpm add -D @evlog/cli
```

```yaml [.github/workflows/observability.yml]
      - run: pnpm install --frozen-lockfile
      - run: pnpm evlog map --min-score 80 --no-write
```

## Read the JSON

`--json` writes the map to stdout. The report goes to stderr, so the two never mix.

```json [Shape]
{
  "schemaVersion": 2,
  "environment": "production",
  "map": {
    "version": 1,
    "generatedAt": "2026-07-25T18:42:10.114Z",
    "framework": "nuxt",
    "projectName": "evlog-playground",
    "score": 76,
    "routes": []
  },
  "summary": { "instrumented": 19, "partial": 2, "dark": 8, "exempt": 0, "suppressedChecks": 0 },
  "mapPath": "/path/to/app/evlog.map.json"
}
```

`mapPath` is `null` under `--no-write`. The payload also carries `grade`, `ignored` (entry points left out by `map.ignore`), `map.cliVersion`, `map.ruleSetVersion`, and a `baseline` object with the comparison when `--baseline` ran. Each entry in `map.routes` looks like this:

```json [One entry point]
{
  "framework": "nuxt",
  "kind": "api",
  "method": "POST",
  "path": "/api/auth/login",
  "file": "server/api/auth/login.post.ts",
  "handler": { "line": 1, "column": 0 },
  "id": "337325358269",
  "checks": {
    "wide-event": { "status": "pass" },
    "context": { "status": "pass" },
    "structured-errors": { "status": "n/a" },
    "error-handling": { "status": "n/a" },
    "audit": {
      "status": "fail",
      "message": "has logger + context but no log.audit() — sensitive route needs audit trail",
      "evidence": { "file": "server/api/auth/login.post.ts", "line": 1 }
    }
  },
  "suggestions": {},
  "sensitivity": { "level": "high", "reasons": ["auth: path says \"auth\""] },
  "event": { "fields": ["user.id", "auth.method"], "audit": [] },
  "score": 75
}
```

`checks` holds requirements and `suggestions` holds opportunities, in separate keys so a script cannot take a suggestion for a failure. A disabled check is `n/a` with `"suppressed": true`, and `summary.suppressedChecks` is the project total: watch it next to the score.

`event` is what the entry point's wide event carries, as the handler and the same-file helpers it calls spell it out: every path `log.set()` writes, dotted, and the literal `action` of each `log.audit()`. Context added in another file, a middleware or an enricher is not in it, and an entry point that sets nothing has no `event` key. Compare it between two scans to see which fields a change removes.

```bash [Terminal]
# every entry point with no event at all
evlog map --json --no-write \
  | jq -r '.map.routes[] | select(.checks["wide-event"].status == "fail") | .file'

# every failure as file:line — message
evlog map --json --no-write \
  | jq -r '.map.routes[].checks | to_entries[] | select(.value.status == "fail")
           | "\(.value.evidence.file):\(.value.evidence.line) — \(.value.message)"'

# fail a script when anything is dark
test "$(evlog map --json --no-write | jq '.summary.dark')" -eq 0

# how much of the score is disabled checks
evlog map --json --no-write | jq '.summary.suppressedChecks'
```

## Gate every package in a monorepo

`evlog map` scans one app at a time. The action takes one directory or glob per line and scans each as its own package, with its own row in the report:

```yaml [.github/workflows/observability.yml]
      - uses: evloghq/action@v1
        with:
          packages: |
            apps/*
            packages/api
          min-score: 70
```

With the CLI alone, a matrix does the same and lets each app carry its own threshold:

```yaml [.github/workflows/observability.yml]
jobs:
  map:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        include:
          - { app: apps/web, min: 80 }
          - { app: apps/admin, min: 60 }
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 22
      - run: npx evlog map --cwd ${{ matrix.app }} --min-score ${{ matrix.min }} --no-write
```
