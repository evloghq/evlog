`evlog map` printed a gap on one of your entry points and you want to know what it expects. It runs ten rules. Each has a stable id, and every finding carries the file and line it came from.

| | Requirements | Opportunities |
| --- | --- | --- |
| Effect on the score | Costs its weight when it fails | None |
| When it appears | Whenever it applies | Only when the project already uses the feature |
| In the report | `FIX FIRST` and `THEN` | `GOING FURTHER` |
| In the JSON | `checks` | `suggestions` |
| Can fail a CI gate | Yes | No |

A rule returns one of three statuses for an entry point:

| Status | Meaning |
| --- | --- |
| `pass` | The rule looked and found what it wanted |
| `fail` | The rule looked and did not. A requirement then costs its weight |
| `n/a` | The question does not apply here, or you [disabled the check](#disable-a-check) |

A handler that throws nothing is not asked whether its errors carry `why` and `fix`. It gets `n/a`, and its score is computed over the rules that applied.

::map-rules-matrix
::

The list will grow, and a release that sharpens a rule can change a verdict on code you did not touch. Compare scores from one CLI version only.

## Requirements

| Id | Column | Weight | Applies to | Passes with |
| --- | --- | --- | --- | --- |
| `wide-event` | `log` | 40 | Handlers, and an eve agent's schedules and channels | `useLogger()` |
| `context` | `ctx` | 15 | Handlers | `log.set()` |
| `structured-errors` | `err` | 20 | Handlers that throw or call `createError()` | `createError({ why, fix })` |
| `audit` | `audit` | 25 | Handlers flagged money or auth | `log.audit()` |
| `error-handling` | `catch` | 15 | Handlers with a `catch` | Logging or a rethrow in the `catch` |
| `page-error-handling` | `fetch` | 20 | Pages that fetch | Error handling on the fetch |

A handler is an API handler, a middleware, a scheduled job, a server action or an eve tool. The column is the header in `evlog map --all`.

### wide-event

Does this entry point emit a wide event? It passes when the handler resolves an evlog logger (`useLogger`, `createLogger`, `createRequestLogger`, `initLogger`) or runs inside an evlog wrapper (`withEvlog`, `withAudit`). In Nuxt that is `const log = useLogger(event)`, in Next.js `const log = useLogger()`.

The message depends on the framework. evlog's Nuxt and Nitro integrations emit an event for every request, so a failure there is an empty event:

```text [Nuxt / Nitro]
handler adds nothing to its request event — only method, path and status are recorded
```

```text [Next.js / TanStack Start]
no useLogger() — handler is a dark event
```

An eve agent passes through its mount: a file or a `<name>/extension.ts` in the agent's `extensions/` that imports or re-exports `@evlog/eve`, such as the one [`evlog init`](/cli/init) writes. The turn event lists every call, so the mount satisfies the rule for all of the agent's tools, schedules and channels. A declared subagent and each workspace member need a mount of their own. `wide-event` is the only check on a schedule or a channel, which run no code inside their turns.

```text [eve]
nothing records its runs — add @evlog/eve in the agent's extensions/
```

In a project without evlog installed, the message says to adopt evlog. [Events](/events) covers the wide event itself.

### context

Is request context attached? A logger with no `log.set()` emits a valid event that says nothing about the request. Only `set()` on a resolved evlog logger counts, and an unrelated `Map.set()` does not.

```typescript [Handler]
log.set({ user: { id }, order: { id, total } })
```

### structured-errors

Do thrown errors carry `why` and `fix`? The rule applies when the handler has a `throw` or a `createError()` call, and a `createError()` that is returned is checked too. The message names what is missing, `why`, `fix` or both:

```text [Messages]
throw new Error() — use createError({ why, fix })
createError() missing why and fix
createError() has why but missing fix
```

```typescript [Handler]
throw createError({
  status: 400,
  message: 'what the caller sees',
  why: 'what actually went wrong',
  fix: 'what to do about it',
  link: 'where to read more', // optional, not scored
})
```

[Errors](/errors) covers `createError`.

### audit

Does this sensitive entry point leave a trail? The rule applies where the [sensitivity classifier](/map#what-counts-as-sensitive) found money or auth, and reports `n/a` everywhere else. `log.audit()` satisfies it, through optional chaining too, so `log.audit?.deny()` counts.

The suggested action is read off the route: `/api/auth/login` suggests `auth.login` and `/api/orders/[id]/refund` suggests `orders.refund`.

```typescript [Handler]
log.audit({
  action: 'auth.login',
  actor: { type: 'user', id: user.id },
})
```

[Audit](/audit) covers the trail.

### error-handling

Is every caught error logged or rethrown? A `catch` counts as handled when it logs (`log.error`, `log.warn`, `log.set`, `log.audit`, `captureException`, or any `console` call), rethrows, or returns, in any branch. Two failures are reported apart:

```text [Messages]
empty catch block swallows errors
catch block swallows error without logging or rethrow
```

A handler with no `catch` is `n/a`: evlog's integrations hook the runtime's error channel, so an exception that escapes is recorded on the event with its status.

```typescript [Handler]
catch (error) {
  log.error(error)
}
```

### page-error-handling

Does this page survive its data fetch failing? This is the only rule for pages, and it applies to pages that fetch server-side: `fetch`, `$fetch`, `useFetch`, `useLazyFetch`, `useAsyncData`, `useLazyAsyncData`, `ofetch`, or a call on `axios`, `http` or `https`. It passes when the call sits inside a `try`, has a `.catch()` or an `onError` handler, or destructures an `error` binding from the fetch. An unrelated `try` elsewhere on the page does not count.

::framework-tabs
```vue [Nuxt]
<script setup lang="ts">
const { data, error } = await useFetch('/api/orders')
if (error.value) log.error(error.value)
</script>
```
```tsx [Next.js]
try {
  const orders = await getOrders()
} catch (error) {
  log.error(error)
}
```
::

[Lifecycle](/events/lifecycle) covers what happens when a request fails.

## Opportunities

Four rules suggest getting more out of a feature the project already uses. Adoption is confirmed against the AST, so a feature named in a comment does not count.

| Id | Fires when | Scope |
| --- | --- | --- |
| `error-catalog` | The project declares a catalog and the same inline error appears in two or more files | Per entry point |
| `audit-coverage` | The project records audit events, and this handler changes state without one | Per entry point |
| `ai-logging` | `ai` is a dependency and the AI SDK is called without `evlog/ai` | Once per project |
| `auth-identity` | `better-auth` is a dependency and `evlog/better-auth` is not installed | Once per project |

- **`error-catalog`** fires on duplication only, and the suggestion names a catalog you already have. See [error catalogs](/errors/catalogs).
- **`audit-coverage`** looks for `create`, `update`, `insert`, `upsert`, `delete` or `destroy` calls in a handler with no audit record. Entry points the `audit` requirement already covers are skipped. See [recording audit events](/audit/recording).
- **`ai-logging`** fires on `generateText`, `streamText`, `generateObject`, `streamObject`, `embed` and `embedMany`. Without [`evlog/ai`](/extend/ai-sdk) the event has no tokens, cost or model latency.
- **`auth-identity`** fires where auth is in play: the auth routes, or a handler that reads the session. [`evlog/better-auth`](/extend/better-auth) attaches the user and session to every event.

An `error-catalog` suggestion reads:

```text [Message]
"402 Card declined" is spelled out here and in 2 other files — one catalog entry would cover them
```

## Several entry points in one file

An Express, Hono or Fastify app registers many routes in one file, a Next.js `route.ts` exports one function per method, and a server actions file exports several actions. Each entry point gets its own verdict, read from the code it runs: its handler, plus every function, class and constant of the same file the handler names, followed from one to the next.

```typescript [src/index.ts]
function loadUser(id: string) {
  const log = useLogger()
  log.set({ user: { id } })
  return db.users.find(id)
}

app.get('/users/:id', (req, res) => res.json(loadUser(req.params.id)))

app.get('/health', (_req, res) => res.json({ ok: true }))
```

`GET /users/:id` passes `wide-event` and `context` through `loadUser`. `GET /health` fails both. Run `evlog map "GET /health"` to inspect one of them.

- The reading stops at the file. A helper imported from another file is not opened, so the context it sets is not credited to the handler that calls it.
- An import counts for the handlers that name it. `stripe` imported at the top of a routes file marks the routes that call it as money, not the health check next to them.
- A disable comment for the whole file covers every entry point in it.

## How evlog helpers are recognized

Every rule that looks for a logger checks that it is evlog's, from the AST. These count:

- **An import from evlog**: `import { useLogger } from 'evlog'`, subpaths included.
- **An auto-import**: in Nuxt and Nitro, evlog's module injects `useLogger` and `createEvlogError`, so a call with no import counts, unless the file declares the name itself.
- **A re-export from a local module**: `import { useLogger } from '@/lib/evlog'` counts when that module forwards evlog's export, as the [Next.js setup](/integrations/next) does. Exports destructured from a factory (`export const { useLogger } = createEvlog(...)`) are resolved too.
- **A re-export from a package**: `import { withEvlog } from '@acme/logger'` counts when `@acme/logger` is a dependency of the app, declares `evlog` in `dependencies` or `peerDependencies`, and forwards evlog's export from one of its `exports` entries. The map reads the installed package through `node_modules`, built output included. An app that reaches evlog only through such a package counts as having evlog installed.
- **An evlog wrapper**: `withEvlog` and `withAudit` instrument a handler that never names a logger.
- **The logger on the request**: `req.log` in Express, `request.evlog` and `request.log` in Fastify, `c.get('log')` in Hono, `event.context.log` in Nitro. `req.log` and `request.log` count when the app registers evlog's middleware, or when the call is one only evlog's logger answers: `set`, `audit` or `fork`.
- **In Effect**: `yield* EvlogLogger` and `yield* useLogger()`. `routerLayer()` anywhere in the sources makes every route emit an event.
- **In an eve tool**: `useLogger()` from `@evlog/eve/logger`.

These do not:

- **A local stub.** `function useLogger() { ... }` in your own file, or an import from `./my-logger` that does not forward evlog's export.
- **Fastify's own `request.log`.** `request.log.info()` in an app that never registers evlog's plugin is Fastify's logger.
- **evlog's `log` export.** `log.info()` is the [simple logging API](/events/simple-logging). It emits its own line and has no `set` or `audit`, so it does not satisfy `wide-event`.

## Disable a check

When a rule is wrong about your code, or right and you decided not to act, turn it off with a comment next to the code:

```typescript [server/api/health.get.ts]
// evlog-map-disable-next-line wide-event, context -- liveness probe, deliberately silent
export default defineEventHandler(() => ({ ok: true }))
```

| Directive | Covers |
| --- | --- |
| `// evlog-map-disable-next-line <ids>` | The line below the comment |
| `// evlog-map-disable-line <ids>` | The line the comment is on |
| `// evlog-map-disable <ids>` | The whole file, wherever the comment sits |

The ids are the ten above, separated by commas or spaces. A directive that names no id covers every rule, which suits a generated file. Block comments work the same way: `/* evlog-map-disable -- generated by the SDK */`. The text after `--` is your reason. It is optional, and the report prints it.

A disabled check becomes `n/a`, so it costs no points and `--min-score` stops failing on it. The rule still runs: a check that would have passed stays a `pass`, and one that never applied stays a plain `n/a`. The count of disabled checks is therefore the number of findings you chose not to see, and the report keeps it visible:

```text [evlog map]
○ 2 checks disabled by comment in 1 entry point
```

```text [evlog map <file>]
CHECKS
✓ log.set     context attached with log.set()
○ useLogger   disabled at line 1 — liveness probe, deliberately silent
```

In `--all` the cell is `○`. In the JSON the check carries `"suppressed": true` with `evidence` pointing at the comment, and `summary.suppressedChecks` is the project total. Under [`--baseline`](/map/ci#catch-a-regression), disabling a check that used to pass is a regression.

An id no rule answers to is reported above the report, and the check keeps failing:

```text [Warning]
⚠ server/api/probe.get.ts:1 disables "wide-evnt", which is not a check evlog map runs
```

To turn a check off for the whole project, set `map.rules` in [`evlog.config.ts`](/cli/config). Every check can be turned off except `wide-event` and `context`. `map.ignore` leaves whole entry points out, by file. The report says how many, and `--json` carries the count as `ignored`.

## Exempt entry points

evlog's own client-log ingest endpoint, a path or file with the segments `evlog/ingest` or `_evlog/ingest`, is not app code. Every rule reports `n/a` for it, it is never listed as something to fix, and the summary counts it as `exempt`, even when the file fails to parse. A page that fetches nothing is exempt too.

If `evlog map <file>` claims something you can see is untrue, [open an issue](https://github.com/evloghq/evlog/issues) with the entry point's output and the handler, and disable the check on that line in the meantime.
