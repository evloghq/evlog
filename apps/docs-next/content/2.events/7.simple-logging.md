A server starting, a cron tick, a warning in a utility function: some messages belong to no request and no job. For those, `log` works like the logger you already use. Each call emits one event straight away, through the same redaction and the same drain as a [wide event](/events).

```typescript [src/index.ts]
import { initLogger, log } from 'evlog'

initLogger({
  env: { service: 'my-app' },
})

log.info('auth', 'User logged in')
log.warn('cache', 'Cache miss for key user:42')
```

```bash [Output (Pretty)]
10:23:45.612 [auth] User logged in
10:23:45.613 [cache] Cache miss for key user:42
```

Call `initLogger()` once at startup. On Nuxt the module calls it for you and auto-imports `log`. `env.service` defaults to `'app'`.

`log` also works with no `initLogger()` call: every call prints with the defaults. That is fine for a scratch script. In production it means no redaction and no drain, so the first event prints a one-time warning that points at `initLogger({ drain })`.

## Two ways to call it

### A tag and a message

`log.info('auth', 'User logged in')` is the form above, made to be read in a terminal. When the message contains `%s`, `%d` or `%j` and more arguments follow, evlog formats it first, so call sites that come from pino or consola keep their printf style:

```typescript [src/index.ts]
log.info('auth', 'User %s logged in from %s', 'alice', '10.0.0.7')
log.info('payment', 'Retrying charge for order %d', 4091)
log.info('debug', 'Payload %j', { orderId: 4091, total: 9999 })
```

```bash [Output (Pretty)]
10:23:45.612 [auth] User alice logged in from 10.0.0.7
10:23:45.613 [payment] Retrying charge for order 4091
10:23:45.614 [debug] Payload {"orderId":4091,"total":9999}
```

| Specifier | Formats the argument as |
| --- | --- |
| `%s` | A string, objects and arrays as JSON |
| `%d` | A number, coerced with `Number()`, bigints as `10n` |
| `%j` | JSON, with a string fallback for values JSON cannot serialize |
| `%%` | A literal percent sign |

- Interpolation runs only when extra arguments are present. A message with a `%` and no arguments is logged unchanged.
- An unknown specifier, or one with no argument left, stays as written. Arguments left over are appended to the message, separated by spaces.
- When the first string contains a specifier, evlog reads it as the message and the call as untagged: `log.info('user %s logged in', 'alice')` prints `[log] user alice logged in`.
- Only the message is formatted. A field value in the object form is never read as a format string.

### An object

Pass an object for an event you want to query later:

```typescript [src/index.ts]
import { log } from 'evlog'

log.info({ action: 'user_login', userId: 42, method: 'oauth', provider: 'github' })
log.error({ action: 'sync_failed', source: 'postgres', target: 's3', error: 'connection_timeout' })
```

```bash [Output (Pretty)]
10:23:45.612 INFO [my-app]
  ├─ action: user_login
  ├─ userId: 42
  ├─ method: oauth
  └─ provider: github
```

`log.error()` and `log.fatal()` also take an `Error` directly. It lands on the event as `error`, with its name, message and stack.

Both call forms work in the browser with `evlog/client`. See [Browser events](/events/client).

## What reaches the drain

The object form always goes to the [drain](/drains) you gave `initLogger()`:

```typescript [src/index.ts]
import { initLogger, log } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'

initLogger({
  env: { service: 'my-app' },
  drain: createAxiomDrain(),
})

log.info({ action: 'deploy', version: '1.2.3', region: 'us-east-1' })
```

A tagged call depends on `pretty`. While `pretty` is on, the default in development, it prints its line and stops there: no drain, and no redaction of the message. With `pretty` off, the default in production, it becomes an event with `tag` and `message` and goes to the drain like the object form.

## Levels, and what each costs

| Level | Method | Use it for | Kept |
| --- | --- | --- | --- |
| `fatal` | `log.fatal()` | Failures the request or the process cannot recover from | Always, whatever the sampling rates |
| `error` | `log.error()` | Failures that need attention: API errors, timeouts, invalid state | 100% unless you set `sampling.rates.error` |
| `warn` | `log.warn()` | Unexpected but recoverable: a retry, a deprecation | `sampling.rates.warn`, 100% by default |
| `info` | `log.info()` | Normal operations: startup, shutdown, a completed action | `sampling.rates.info`, 100% by default |
| `debug` | `log.debug()` | Development details: SQL queries, intermediate state | `sampling.rates.debug`, 100% by default |
| `trace` | `log.trace()` | Finer detail than `debug` | Dropped unless you set `sampling.rates.trace` |

`minLevel` sets the lowest level `log` emits, `'debug'` by default. It applies to `log` only: wide events use `sampling.minLevel`, covered in [Sampling](/events/sampling).

The [Vite plugin](/integrations/vite) and the Nuxt module remove `log.debug()` calls from production builds. Their `strip` option lists the levels to remove, `['debug']` by default.

## Adapt existing call sites

Structured calls from pino and winston keep their shape. Calls from consola and `console.log` become a tag and a message, or an object:

::code-group
```typescript [pino]
import pino from 'pino'

const log = pino({ name: 'checkout' })

log.info({ event: 'checkout_started' })
log.info({ event: 'cart_loaded', items: 3, total: 9999 })
log.warn({ event: 'inventory_low', sku: 'SKU-42' })
log.error({ event: 'payment_failed', reason: 'card_declined' })
```
```typescript [winston]
import { createLogger, format, transports } from 'winston'

const log = createLogger({
  defaultMeta: { service: 'checkout' },
  format: format.json(),
  transports: [new transports.Console()],
})

log.info({ event: 'checkout_started' })
log.info({ event: 'cart_loaded', items: 3, total: 9999 })
log.warn({ event: 'inventory_low', sku: 'SKU-42' })
log.error({ event: 'payment_failed', reason: 'card_declined' })
```
```typescript [consola]
import { consola } from 'consola'

const log = consola.withTag('checkout')

log.info('Starting checkout')
log.info('cart loaded', { items: 3, total: 9999 })
log.warn('inventory low', { sku: 'SKU-42' })
log.error('payment failed', { reason: 'card_declined' })
```
```typescript [console.log]
console.log('[checkout] Starting checkout')
console.log('[checkout] cart loaded', { items: 3, total: 9999 })
console.warn('[checkout] inventory low', { sku: 'SKU-42' })
console.error('[checkout] payment failed', { reason: 'card_declined' })
```
```typescript [evlog]
import { initLogger, log } from 'evlog'

initLogger({ env: { service: 'checkout' } })

log.info({ event: 'checkout_started' })
log.info({ event: 'cart_loaded', items: 3, total: 9999 })
log.warn({ event: 'inventory_low', sku: 'SKU-42' })
log.error({ event: 'payment_failed', reason: 'card_declined' })
```
::

The drain, redaction, sampling, the level filter and the switch between pretty and JSON output all come from that one `initLogger()` call. [Compare](/compare) sets evlog next to each of these loggers, feature by feature.

To try evlog without a setup line, the default export is the same `log` object:

```typescript [src/index.ts]
import logger from 'evlog'

logger.info('checkout', 'Starting checkout')
logger.info({ event: 'checkout_started' })
```

Every call prints immediately. When you want a drain or redaction, add the `initLogger()` line and keep the same calls.

## Use it next to wide events

`log` and `createLogger()` share the drain, the redaction and the types, so you choose per call. Use `log` for a message that stands alone, and `createLogger()` for one event that covers a whole operation:

```typescript [scripts/sync-data.ts]
import { initLogger, log, createLogger } from 'evlog'

initLogger({ env: { service: 'sync-worker' } })

log.info('sync', 'Worker starting')

const run = createLogger({ source: 'postgres', target: 's3' })
try {
  const records = await fetchRecords()
  run.set({ found: records.length })

  for (const record of records) {
    await syncOne(record)
    log.debug({ event: 'record_synced', id: record.id })
  }

  run.set({ status: 'complete', synced: records.length })
} catch (err) {
  log.error({ event: 'sync_failed' })
  run.error(err as Error)
  throw err
} finally {
  run.emit()
}

log.info('sync', 'Worker finished')
```

The `log` calls give you a trail while the job runs, and `run` gives your dashboard one row per run.
