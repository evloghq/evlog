A logger accepts any field by default. Across a codebase that drifts: one route logs `user`, another `account`, a third `userId`, and a query on `user.plan` misses the other two. Pass an interface to the logger and the wrong key fails at compile time.

::typed-fields-intellisense
::

## Type the logger

Define an interface for the fields a route sets, and pass it as a generic:

```typescript [server/api/checkout.post.ts]
import { useLogger } from 'evlog'

interface CheckoutFields {
  user: { id: string; plan: string }
  cart: { items: number; total: number }
  action: string
}

export default defineEventHandler(async (event) => {
  const log = useLogger<CheckoutFields>(event)

  log.set({ user: { id: '123', plan: 'pro' } })  // OK
  log.set({ cart: { items: 3, total: 9999 } })    // OK
  log.set({ action: 'checkout' })                  // OK

  log.set({ account: '...' })                      // TS error
  log.set({ usr: { id: '123' } })                  // TS error

  return { success: true }
})
```

Every field is optional at every depth, because `log.set()` merges: `log.set({ user: { id: '123' } })` type-checks without `plan`. The type covers `set()`, the second argument of `log.error()`, `log.info()` and `log.warn()`, and what `getContext()` returns.

Without a generic, the logger accepts any field as before. Typing one route changes nothing for the others.

::callout{icon="i-lucide-triangle-alert" color="neutral"}
On Nuxt, `useLogger<T>` needs an explicit `import { useLogger } from 'evlog'`. The auto-imported function loses excess property checking through the generic, a TypeScript limitation, so `log.set({ typo: 'oops' })` is accepted without an error. Untyped calls can keep the auto-import.
::

## Fields evlog sets itself

Some fields belong to evlog and are accepted whatever your interface says. Leave them out of it:

| Field | Type | Set by |
| --- | --- | --- |
| `status` | `number` | The integration, from the response |
| `service` | `string` | The `routes` option, or `useLogger(event, 'payment-service')` |
| `operation` | `string` | `log.fork()`, with the label of the child event |
| `_parentRequestId` | `string` | `log.fork()`, with the `requestId` of the parent |
| `requestLogs` | `array` | `log.info()`, `log.warn()` and the other message methods |

```typescript [services/checkout.ts]
log.set({ status: 200 })    // OK - internal field
log.set({ service: 'api' }) // OK - internal field
```

## Every logger takes the generic

`useLogger<T>()` works the same in every framework integration. Loggers you create yourself take it too: `createLogger<T>()`, `createRequestLogger<T>()` and `createWorkersLogger<T>()`.

::framework-tabs
```typescript [Standalone]
import { createRequestLogger } from 'evlog'

interface MyFields {
  action: string
  userId: string
}

const log = createRequestLogger<MyFields>({
  method: 'POST',
  path: '/checkout',
})

log.set({ action: 'checkout', userId: '123' }) // OK
log.set({ unknown: true })                      // TS error
```
```typescript [Cloudflare Workers]
import { createWorkersLogger } from 'evlog/workers'

interface MyFields {
  action: string
}

const log = createWorkersLogger<MyFields>(request)
log.set({ action: 'process' }) // OK
```
::

## Shape the interfaces

Write one interface per domain, not one per route, and import it where the routes need it:

```typescript [server/types/log-fields.ts]
export interface AuthFields {
  user: { id: string; email: string; role: string }
  action: string
  mfaUsed: boolean
}

export interface PaymentFields {
  user: { id: string; plan: string }
  order: { id: string; total: number; currency: string }
  payment: { method: string; last4: string }
}
```

```typescript [server/api/auth/login.post.ts]
import { useLogger } from 'evlog'
import type { AuthFields } from '~/server/types/log-fields'

export default defineEventHandler(async (event) => {
  const log = useLogger<AuthFields>(event)
  log.set({ action: 'login', mfaUsed: true })
})
```

Keep each one to the fields those routes set. It does not need to mirror your data model: an interface with `user: FullUserProfile` and `order: CompleteOrder` describes fields most routes never set. [Best practices](/reference/best-practices) covers what belongs in an event and what to leave out.
