Logging every request gets expensive at scale, and most of those requests are identical successes. evlog samples in two tiers: head sampling drops a share of events by level, and tail sampling keeps an event once its outcome is known.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'

export default defineEvlog({
  service: 'my-app',
  sampling: {
    rates: { info: 10, warn: 50, debug: 0 },
    keep: [
      { status: 400 },
      { duration: 1000 },
      { path: '/api/payments/**' },
    ],
  },
})
```

With this config, a routine `200` has a 10% chance of being kept, and a `500`, a request over one second, or anything under `/api/payments/` is always kept:

```bash [What gets logged]
POST /api/users     200  45ms   → 10% chance (head sampling)
POST /api/users     500  45ms   → always kept (status >= 400)
GET  /api/products  200  2300ms → always kept (duration >= 1000)
```

## Head sampling

`rates` is a percentage from 0 to 100 per level. A level you leave out keeps everything, and `error` stays at 100 unless you set `error: 0` yourself. The draw is random: 10% keeps about one in ten, not exactly one in ten.

::head-sampling-plinko
::

## Tail sampling

`keep` runs after the request completes, when evlog knows the status, the duration and the path. `status` and `duration` match at or above the value, `path` is a glob, and any match keeps the event whatever head sampling decided.

::tail-sample-decision
::

For a rule the three conditions cannot express, such as keeping every event for an enterprise customer, pass a `keep` callback in the config. On Nuxt and Nitro, the `evlog:emit:keep` hook does the same.

## What sampling does not touch

Audit events are always kept: [Audit](/audit) marks them before sampling runs. A [signal](/signals) with `keep` can also carry an event past it, such as a `200` that created no order.
