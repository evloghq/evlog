Logging every request gets expensive at scale, and most of those requests are identical successes. evlog samples in two tiers: head sampling drops a share of events by level, and tail sampling keeps an event once its outcome is known.

::emits{step="rates"}
```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'

export default defineEvlog({
  service: 'my-app',
  sampling: {
    rates: { info: 10, warn: 50, debug: 0 },
    keep: [
      { status: 400 },
      { duration: 1000 },
      { path: '/api/payments/**' },
    ],
  },
})
```
::

With this config, a routine `200` has a 10% chance of being kept, and a `500`, a request over one second, or anything under `/api/payments/` is always kept:

```bash [What gets logged]
POST /api/users     200  45ms   → 10% chance (head sampling)
POST /api/users     500  45ms   → always kept (status >= 400)
GET  /api/products  200  2300ms → always kept (duration >= 1000)
```

## Head sampling

`rates` is a percentage from 0 to 100 per level. The draw is random: 10% keeps about one in ten, not exactly one in ten.

::head-sampling-plinko
::

| Level | Rate when you leave it out |
| --- | --- |
| `info`, `warn`, `debug` | 100 |
| `error` | 100, also when you set other levels. Only `error: 0`, or another rate you write yourself, drops errors |
| `trace` | 0. Set `rates.trace` to keep trace events |
| `fatal` | Always kept. It has no rate |

The same rates apply to [browser events](/events/client) that arrive on the Nuxt ingest route. Tail sampling does not apply to them, because a browser event has no status and no duration.

## Tail sampling

`keep` runs after the request completes, when evlog knows the status, the duration and the path. `status` and `duration` match at or above the value, `path` is a glob, and any match keeps the event whatever head sampling decided.

| Condition | Type | Keeps the event when |
| --- | --- | --- |
| `status` | `number` | The HTTP status is at or above the value. `400` covers every 4xx and 5xx |
| `duration` | `number` | The request took at least that many milliseconds |
| `path` | `string` | The request path matches the glob, such as `'/api/critical/**'` |

Tail sampling is checked first, and head sampling only draws when no rule matched. A request to `/api/payments/charge` that returns a `500` after two seconds is kept even with `info` at 1%.

## Your own keep rule

For a rule the three conditions cannot express, such as keeping every event for an enterprise customer, pass a `keep` callback in the config and set `ctx.shouldKeep`:

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'

export default defineEvlog({
  service: 'my-app',
  sampling: {
    rates: { info: 10 },
    keep: [{ status: 400 }],
  },
  keep(ctx) {
    if (ctx.context.user?.plan === 'enterprise') {
      ctx.shouldKeep = true
    }
  },
})
```

On Nuxt and Nitro, the `evlog:emit:keep` hook does the same from a server plugin:

::framework-tabs
```typescript [Nuxt] server/plugins/sampling.ts
export default defineNitroPlugin((nitroApp) => {
  nitroApp.hooks.hook('evlog:emit:keep', (ctx) => {
    if (ctx.context.user?.plan === 'enterprise') {
      ctx.shouldKeep = true
    }
  })
})
```
```typescript [Nitro] server/plugins/sampling.ts
import { definePlugin } from 'nitro'

export default definePlugin((nitroApp) => {
  nitroApp.hooks.hook('evlog:emit:keep', (ctx) => {
    if (ctx.context.user?.plan === 'enterprise') {
      ctx.shouldKeep = true
    }
  })
})
```
::

The callback receives:

| Field | Type | Description |
| --- | --- | --- |
| `status` | `number \| undefined` | HTTP response status |
| `duration` | `number \| undefined` | Request duration in milliseconds |
| `path` | `string \| undefined` | Request path |
| `method` | `string \| undefined` | HTTP method |
| `context` | `Record<string, unknown>` | Every field set with `log.set()` |
| `shouldKeep` | `boolean` | Set it to `true` to keep the event |

Only ever set `shouldKeep` to `true`. The `keep` rules are checked as well, so leaving it `false` drops nothing a rule would keep, and writing `false` cancels a `true` an earlier callback set.

The callback runs on every request an integration logs, before the event is built, and evlog waits for it. Keep it free of I/O. A logger you create yourself with `createLogger()` reads the `keep` rules and never calls the callback.

### Several rules, or a rule you reuse

`composeKeep` from `evlog/toolkit` runs several callbacks as one. Each runs in order, and one that throws is logged as `[evlog/compose-keep] keep failed` without stopping the others:

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { composeKeep } from 'evlog/toolkit'

export default defineEvlog({
  service: 'my-app',
  keep: composeKeep([
    (ctx) => {
      if (ctx.duration && ctx.duration > 2000) ctx.shouldKeep = true
    },
    (ctx) => {
      if (ctx.context.user?.plan === 'enterprise' && ctx.status && ctx.status >= 500) ctx.shouldKeep = true
    },
  ]),
})
```

A rule that ships with its own drain or enricher goes in a [plugin](/extend/plugins), which has a `keep` hook with the same context. Register it with `plugins: [keepEnterpriseErrors]`:

```typescript [src/keep-enterprise-errors.ts]
import { definePlugin } from 'evlog/toolkit'

export const keepEnterpriseErrors = definePlugin({
  name: 'keep-enterprise-errors',
  keep(ctx) {
    if (ctx.context.user?.plan === 'enterprise' && ctx.status >= 500) {
      ctx.shouldKeep = true
    }
  },
})
```

## Set a severity floor

Sampling controls volume, so a `keep` rule can bring back an `info` event that head sampling would drop. When info and debug wide events must never be written, as with a `LOG_LEVEL=warn` contract, set `sampling.minLevel`:

```typescript [server.ts]
initLogger({
  sampling: {
    minLevel: 'warn',
    keep: [{ duration: 1000 }],
  },
})
```

```bash [What gets logged]
GET  /api/products  200  2300ms  info   → dropped (below the floor, keep does not apply)
POST /api/checkout  200  120ms   warn   → kept
POST /api/users     500  45ms    error  → kept
```

- The floor accepts `trace`, `debug`, `info` or `warn`. It wins over the `keep` rules, the `keep` callback and the head rates, and a dropped event is neither enriched nor drained.
- It reads the event's level, which comes from a thrown error, `log.error()` and `log.warn()`, not from the response status. A handler that returns a `500` without throwing or calling `log.error()` emits an `info` event, which this floor drops.
- `error` and `fatal` events always pass it, and so do audit events. An `error` event still goes through head sampling, so `rates.error: 0` drops it.
- It covers request events and `createLogger()` events. The top-level `minLevel` is a different option, for the [`log` API](/events/simple-logging).
- It goes wherever `sampling` goes: `evlog.config.ts`, the Nuxt and Nitro `evlog` options, the Vite plugin, and Next.js `createEvlog()` or `createInstrumentation()`.

## Sample in production only

Sampling in development hides the events you are trying to read. On Nuxt, put `sampling` under `$production` in `nuxt.config.ts`:

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['evlog/nuxt'],
  evlog: {
    env: { service: 'my-app' },
  },
  $production: {
    evlog: {
      sampling: {
        rates: { info: 10, warn: 50, debug: 0 },
        keep: [
          { status: 400 },
          { duration: 1000 },
          { path: '/api/payments/**' },
          { path: '/api/auth/**' },
        ],
      },
    },
  },
})
```

On other frameworks, use your own environment check around the `sampling` option.

## What sampling does not touch

Audit events are always kept: [Audit](/audit) marks them before sampling runs. A [signal](/signals) with `keep` can also carry an event past it, such as a `200` that created no order.

`log.discard()` works the other way: it drops one event whatever the `keep` rules and the rates say, unless that event recorded an error. See [Events](/events#discard-an-event). [Lifecycle](/events/lifecycle) places sampling among the other stages.
