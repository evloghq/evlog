A click that did nothing, a page that failed to render, an error caught in a component: none of them reaches your server, so none of them is in your logs. `evlog/client` gives the browser the same `log` calls as the server. It prints to the console, and posts each event to your server when you turn the transport on.

::client-server-beacon
::

## Start it

Call `initLog()` once when the app starts. `log` then works in components, composables and event handlers.

::framework-tabs
```typescript [Nuxt] app/plugins/app-init.client.ts
export default defineNuxtPlugin((nuxtApp) => {
  nuxtApp.hook('app:created', () => {
    log.info({ action: 'app_init', path: window.location.pathname })
  })
})
```
```tsx [Next.js] app/providers.tsx
'use client'
import { useEffect } from 'react'
import { initLog, log } from 'evlog/client'

export function LogProvider({ children }: { children: React.ReactNode }) {
  useEffect(() => {
    initLog({ service: 'web' })
    log.info({ action: 'app_init', path: window.location.pathname })
  }, [])

  return <>{children}</>
}
```
```typescript [Any frontend] src/app.ts
import { initLog, log } from 'evlog/client'

initLog({ service: 'web' })
log.info({ action: 'app_init', path: window.location.pathname })
```
::

On Nuxt, the module already calls `initLog()` with the `evlog` options of `nuxt.config.ts`, and auto-imports `log`, `setIdentity`, `clearIdentity` and `setMinLevel`. Do not call `initLog()` yourself there: each call resets every option it is not given to its default. The Nuxt client service name is always `'client'`.

On Next.js, `EvlogProvider` from `evlog/next/client` calls `initLog()` for you, with the options below as props.

Outside a browser, every `log` call from `evlog/client` does nothing, so shared code can call it during server rendering.

## Two ways to call it

Pass an object for an event you want to query:

```typescript [pages/products.vue]
log.info({ action: 'page_view', path: '/products', referrer: document.referrer })
```

```bash [Browser console]
[web] info  { action: 'page_view', path: '/products', referrer: 'https://google.com' }
```

Pass a tag and a message for a line you want to read. The message takes the `%s`, `%d` and `%j` specifiers described in [Simple logging](/events/simple-logging#a-tag-and-a-message):

```typescript [composables/useCart.ts]
log.info('cart', 'Item %s added, cart total %d', 'SKU-42', 9999)
```

```bash [Browser console]
[cart] Item SKU-42 added, cart total 9999
```

Both forms have six levels: `log.fatal()`, `log.error()`, `log.warn()`, `log.info()`, `log.debug()` and `log.trace()`. `log.debug()` and `log.trace()` print with `console.log`, not `console.debug`, so the lines stay visible with the default DevTools filter. The event still carries `level: 'debug'` or `level: 'trace'`.

An `Error` is serialized the same way as on the server. `log.error(err)`, or an `Error` inside an object such as `log.error({ action: 'checkout', error })`, is logged with its `name`, `message` and `stack`, not as `{}`. With `pretty` on, the console receives the real `Error`, which DevTools lets you expand. The JSON console line and the transport receive the serialized form. See [Errors](/errors).

## Attach the user

`setIdentity()` merges its fields into every event until you clear it:

```typescript [composables/useAuth.ts]
import { setIdentity, clearIdentity, log } from 'evlog/client'

// After login
setIdentity({ userId: 'usr_123', plan: 'pro' })

log.info({ action: 'dashboard_view' })
// → { userId: 'usr_123', plan: 'pro', action: 'dashboard_view', ... }

// After logout
clearIdentity()
```

A second `setIdentity()` replaces the first. Put IDs in it, not emails, unless you mean to store them.

## Options

`initLog()` takes:

| Option | Default | What it does |
| --- | --- | --- |
| `enabled` | `true` | `false` turns every client `log` call into a no-op |
| `console` | `true` | `false` stops the console output. Events still go to the transport |
| `pretty` | `true`, `import.meta.dev` on Nuxt | Colored, formatted console output. `false` prints one JSON line per event |
| `minLevel` | `'debug'` | Lowest level that is printed and sent. Order: `trace` and `debug`, `info`, `warn`, `error`, `fatal` |
| `service` | `'client'` | Service name on every event |
| `transport.enabled` | `false` | Posts each event to your server |
| `transport.endpoint` | `'/api/_evlog/ingest'` | Where the events are posted |
| `transport.credentials` | `'same-origin'` | The `credentials` mode of the `fetch` call |

`minLevel` applies to the console and to the transport. To change it without a reload, for a debug toggle, call `setMinLevel('debug')` or `setMinLevel('warn')` from `evlog/client`.

## Send events to your server

Events stay in the browser console until you turn the transport on. It posts each event as one JSON object, with `fetch` and `keepalive: true`. It has no buffer, so nothing is batched and nothing is flushed when the page hides, and a failed request is ignored.

::framework-tabs
```typescript [Nuxt] nuxt.config.ts
export default defineNuxtConfig({
  modules: ['evlog/nuxt'],
  evlog: {
    transport: {
      enabled: true,
      endpoint: '/api/_evlog/ingest',
    },
  },
})
```
```tsx [Next.js] app/layout.tsx
import { EvlogProvider } from 'evlog/next/client'

export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <EvlogProvider service="web" transport={{ enabled: true, endpoint: '/api/_evlog/ingest' }}>
          {children}
        </EvlogProvider>
      </body>
    </html>
  )
}
```
```typescript [Any frontend] src/app.ts
import { initLog } from 'evlog/client'

initLog({
  service: 'web',
  transport: {
    enabled: true,
    endpoint: '/api/_evlog/ingest',
  },
})
```
::

### On Nuxt

Setting `evlog.transport.enabled` in `nuxt.config.ts` registers the ingest route and configures the client in one place. Turning the transport on in a client `initLog()` call alone does not register the route, and the requests fail silently.

The route does this to each event, in order:

1. Rejects a request whose `Origin` or `Referer` is not your own host with `403`, a body over 32 KB with `413`, and a body without a valid `timestamp` and `level` with `400`.
2. Replaces the client's `service` with the server's service and environment, and adds `source: 'client'`.
3. Applies the server's [redaction](/events/redaction) config.
4. Applies head [sampling](/events/sampling) with the server's rates. Tail sampling does not apply: a client event has no status and no duration.
5. Runs the `evlog:enrich` hook and your [enrichers](/events/enrichers), prints the event, and hands it to your [drain](/drains).

It answers `204`.

### On other frameworks

Create a POST route at the endpoint you configured. It receives one event object per request (`timestamp`, `level`, `service`, the identity fields and what you logged), not an array:

```typescript [app/api/_evlog/ingest/route.ts]
export async function POST(request: Request) {
  const body = await request.json()
  if (body === null || typeof body !== 'object' || Array.isArray(body)) {
    return Response.json({ error: 'expected one event object' }, { status: 400 })
  }
  return new Response(null, { status: 204 })
}
```

::callout{icon="i-lucide-triangle-alert" color="neutral"}
The ingest route has no authentication. The Nuxt origin check stops other websites, not a script that sets its own headers. Treat client events as untrusted input, and rate-limit the route where traffic enters, as [Ingest telemetry](/telemetry/ingest) does.
::

## Batch, retry and flush on hide

For higher volume, use the [HTTP drain](/drains/http): `createHttpLogDrain()` from `evlog/http`, with `log` from `evlog`. It sends batches of 25 events or every 2 seconds, retries a failed batch, and flushes with `sendBeacon` when the page becomes hidden.

```typescript [src/app.ts]
import { initLogger, log } from 'evlog'
import { createHttpLogDrain } from 'evlog/http'

const drain = createHttpLogDrain({
  drain: { endpoint: 'https://logs.example.com/v1/ingest' },
  pipeline: {
    batch: { size: 25, intervalMs: 2000 },
    retry: { maxAttempts: 2 },
  },
})

initLogger({ drain })
log.info({ action: 'app_init' })
```

It is a different logger from `evlog/client`, and the two do not share state:

- `initLog()`, `setIdentity()` and the client `minLevel` have no effect on it.
- It posts a JSON array, so it needs its own route, not the built-in ingest route, which accepts one object. [The server endpoint](/drains/http#the-server-endpoint) shows that route.
- Only object-form events reach it by default. In a browser `pretty` is on unless you turn it off, and a tagged call such as `log.info('tag', 'msg')` then only prints. Use the object form, or pass `pretty: false` to `initLogger()`.
- `sendBeacon` cannot send headers. If the endpoint needs an `Authorization` header, set `useBeacon: false` on `drain`.

evlog 3 removed the `evlog/browser` entry point. `createHttpDrain` and `createHttpLogDrain` are imported from `evlog/http`, as [Upgrade to v3](/start/upgrade#browser-entry-removed) explains.

## What to log from the browser

Log the action, the route and the outcome: a page view, a click that matters, a caught error. Leave out form values, tokens and request bodies. The browser prints what you log and the request body carries it, and only the Nuxt ingest route masks it afterwards. To keep debug lines out of both, raise `minLevel` to `'warn'`.
