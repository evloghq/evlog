A request that logs ten lines leaves you to stitch them back together during an incident. The same request as a :term[wide event]{of="wide-event"} is one record, with the user, the input, every step and the outcome as fields you can query.

::wide-event-collapse
::

## The shape it replaces

```typescript [src/jobs/sync.ts]
logger.info('Job started')
logger.info('User authenticated', { userId: user.id })
logger.info('Fetching data', { source: 'postgres' })
logger.info('Job finished', { duration: 234 })
```

Four lines, one correlation problem, and no line at all if the job throws between the second and the third. The wide event version accumulates the same facts and emits them together:

::emits{step="context"}
```typescript [src/jobs/sync.ts]
import { createLogger } from 'evlog'

const log = createLogger({ jobId: 'sync-001', queue: 'emails' })

log.set({ user: { id: user.id } })
log.set({ source: 'postgres', target: 's3' })
log.set({ records: { found: 1250, synced: 1250 } })
log.emit()
```
::

## Three ways to get a logger

| You are in | Use | Emits |
| --- | --- | --- |
| A route, with a framework integration | `useLogger(event)`, or the framework accessor (`c.get('log')`, `req.log`) | When the response ends |
| A script, job, queue worker or workflow | `createLogger(context)` | When you call `log.emit()` |
| An HTTP handler without an integration | `createRequestLogger({ method, path })` | When you call `log.emit()` |

For a one-off line that belongs to no unit of work, `log.info('tag', 'message')` still works, and prints straight away.

`createLogger()` and `createRequestLogger()` emit nothing until you call `log.emit()`, so call it in a `finally` block. `createRequestLogger()` is `createLogger()` with `method`, `path` and `requestId` filled in. `useLogger()` never creates a logger: it returns the one the integration attached to the request.

| Work | Logger | Page |
| --- | --- | --- |
| A CLI or one-shot script | `log.info()` for the steps, `createLogger()` for one summary event of the run | [Standalone](/integrations/standalone) |
| A background job, queue worker or cron | `createLogger({ jobId, queue })` per run | [Standalone](/integrations/standalone) |
| An AWS Lambda handler | `initLogger()` once at cold start, `createLogger()` per invocation | [AWS Lambda](/integrations/aws-lambda) |
| A Cloudflare Worker | The logger `withEvlog` passes to the handler, or `createWorkersLogger(request)` | [Cloudflare Workers](/integrations/cloudflare-workers) |
| A pipeline step | `createLogger({ step })` per stage, with its inputs and outputs | |
| An AI SDK call | The request logger, wrapped with `createAILogger(log)` | [AI SDK](/extend/ai-sdk) |
| A library or a shared workspace package | `createLogger()`, or a logger the caller passes in. Never `initLogger()`: the host app owns the config and the drain | [Standalone](/integrations/standalone) |
| A function called inside a request | `useLogger()`, so its fields land on the caller's event | [Integrations](/integrations) |

## What every event carries

The integration fills in what it knows: `method`, `path`, `status`, `duration` and `requestId` on a request, the `service` and `environment` on every event. You add the rest with `log.set()`, grouped into objects (`user`, `cart`, `payment`) rather than flat keys, so a query reads `user.plan = 'pro'`.

An error thrown during the work lands on the same event as `error`, with its `why` and `fix`. See [Errors](/errors).

evlog prints the event as a tree in development and as one JSON line in production, with nothing to configure. [Lifecycle](/events/lifecycle) follows it from the first `log.set()` to the drain.

```json [Production output]
{
  "level": "info",
  "method": "POST",
  "path": "/api/checkout",
  "status": 200,
  "duration": "234ms",
  "durationMs": 234,
  "user": { "id": 1, "plan": "pro" },
  "cart": { "items": 3, "total": 9999 },
  "payment": { "method": "card", "status": "success" }
}
```

## Design the event

A useful event answers four questions. The integration answers the first, and you add the other three:

| Layer | Answers | Example fields |
| --- | --- | --- |
| Operation | What ran | `method`, `path`, `requestId` on a request; `jobId`, `queue` on a job |
| Actor | Who triggered it | `user.id`, `user.plan`, `user.accountAge` |
| Business | What it touched | `cart.items`, `cart.total`, `shipping.country`, `coupon` |
| Outcome | How it ended | `status`, `duration`, `error`, set by evlog |

Name each group after the thing it describes. `log.set({ data: { id: 123 } })` tells the next reader nothing, `log.set({ order: { id: 123, status: 'pending' } })` does. Flat keys such as `userId`, `userEmail`, `cartTotal` drift into `uid` and `user_id` across a codebase, and a query on `user.id` misses them:

```typescript [services/checkout.ts]
log.set({
  user: { id: 1, email: 'a@b.com' },
  cart: { id: 2, total: 100 },
})
```

Call `log.set()` each time you learn something, not once at the end. A handler that throws halfway still emits every field set before the throw:

```typescript [server/api/checkout.post.ts]
const user = await getUser(event)
log.set({ user: { id: user.id, plan: user.plan } })

const cart = await getCart(user.id)
log.set({ cart: { items: cart.items.length, total: cart.total } })

const payment = await processPayment(cart)
log.set({ payment: { method: payment.method, status: payment.status } })
```

Log IDs rather than whole objects, and leave secrets out. [Redaction](/events/redaction) catches common shapes, and [Typed fields](/events/typed-fields) makes TypeScript reject a field name nobody agreed on. [Best practices](/reference/best-practices) lists recommended field groups and what to keep out.

You do not need a `try`/`catch` to record a failure. A thrown error lands on the event as `error`, with the status it carries, and the event is emitted at `level: 'error'`:

```bash [Output]
ERROR [checkout] POST /api/checkout 402 in 123ms
  ├─ error: Card declined
  │     Why: Issuer declined the charge
  │     Fix: Ask the customer to use another card
  ├─ user: id=1 plan=pro
  └─ cart: items=3 total=9999
```

## After the event is emitted

Emitting seals the logger, whether the integration emitted at the end of the response or you called `log.emit()`, and also when sampling dropped the event. A later `set()`, `error()`, `info()` or `warn()` does not reach the event: evlog ignores it and prints an `[evlog]` warning with the keys it dropped.

That matters for work that outlives the handler, such as a promise you did not await. `useLogger()` still returns the request's logger there, although its event is gone. Give that work its own event with `log.fork(label, fn)`:

```typescript [server/routes/checkout.post.ts]
import { evlog, useLogger } from 'evlog/express'

// Inside a route after evlog middleware:
const log = req.log
log.set({ order_dispatched: true })

log.fork('process_order', async () => {
  const child = useLogger()
  child.set({ inventory_checked: true })
})
```

When `fn` returns or throws, the forked logger emits a second event with `operation` set to the label and `_parentRequestId` set to the parent's `requestId`. The parent event can be emitted before the child's.

| Integration | Inside `fn` |
| --- | --- |
| Express, Fastify, NestJS, SvelteKit, React Router, Next.js `withEvlog`, Elysia, Hono, oRPC | `useLogger()` returns the forked logger |
| Nuxt, Nitro, TanStack Start, Cloudflare Workers `withEvlog` | `fn` receives the forked logger: `log.fork('label', async (child) => { child.set(...) })` |

A logger from `createLogger()` has no `fork()`.

`log.fork()` returns a promise that resolves once the child event has drained, and never rejects. Leave it unawaited for background work. Await it when the child carries a write that must land before the response, such as an [audit record](/audit/integrity). With `waitUntil` (Next.js, Cloudflare Workers, Vercel Edge), an unawaited fork is registered with it, so the runtime stays alive until the child drains.

A streaming response emits when its body finishes, not when the handler returns, on Next.js, Nuxt, Nitro, SvelteKit, Hono, React Router and oRPC. That is how [AI SDK](/extend/ai-sdk) fields land on the request's event.

## Set the level yourself

`log.error(err)` fills the `error` field with the error's name, message and stack, and raises the event to `level: 'error'`. To write the `error` field yourself, with a typed code or without a stack, raise the level with `log.setLevel()`:

```typescript
log.setLevel('error')
log.set({
  error: {
    code: 'PAYMENT_DECLINED',
    reason: 'insufficient_funds',
  },
})
```

`setLevel()` takes any level and wins over the one `log.error()` and `log.warn()` would set.

## Discard an event

A job that runs every minute and finds nothing to do has nothing to report, and one event per run buries the runs that did something. `log.discard()` drops that event before it is built, so nothing is printed, enriched or drained:

```typescript
const log = useLogger()
const expired = await sessions.deleteExpired()

if (expired === 0) {
  log.discard()
  return
}

log.set({ sessions: { expired } })
```

- `discard()` wins over `sampling.keep` and the head rates of [sampling](/events/sampling).
- A recorded failure is never discarded. If the same logger calls `log.error()` or `log.fatal()`, sets the level to `error` or `fatal`, or writes an [`audit()`](/audit) record, the event is emitted and skips head sampling, so `sampling.rates.error: 0` cannot hide it.
- The `sampling.minLevel` floor still reads the final level: a later `setLevel()` below the floor drops the event even after `log.error()`.
- Called after the event was emitted, it does nothing and prints an `[evlog]` warning.

[Effect](/integrations/effect) has the same rule for every run that does not fail: `withLogger(action, { emit: 'onError' })`.

## Questions

### How is a wide event different from a structured log?

Structured logging is the format: key-value fields, usually JSON, instead of free text. A wide event is a structured log with a scope. One unit of work produces one event, so the fields that would be spread over several lines sit on the same record and can be queried together. Stripe calls the same pattern [canonical log lines](https://stripe.com/blog/canonical-log-lines).

### Are wide events the same as traces?

No. A wide event is a log record, and a span is a timed operation inside a trace. evlog creates no spans and no metrics. The [trace context enricher](/events/enrichers#trace-context) attaches the incoming `traceparent` to the event, and the [OTLP drain](/drains/otlp) exports it next to the spans your stack already emits. See [evlog and OpenTelemetry](/compare/opentelemetry).

### Do wide events cost more to store?

Usually less. Logging line by line repeats the level, the timestamp and the request context on every line. On the checkout request measured in [Log cost](/reference/cost), one event is 56% fewer bytes and 75% fewer events than four lines. [Sampling](/events/sampling) cuts the volume further and still keeps every error and slow request.

### When does an integration emit?

When the response ends, including when the handler throws. On Next.js, `redirect()` and `notFound()` are rethrown without an event. A streaming response emits when its body finishes, on the integrations listed in [After the event is emitted](#after-the-event-is-emitted).
