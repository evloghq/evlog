A drain is a function that receives wide events and sends them somewhere. When no [built-in drain](/drains) covers your backend, you write one with the two factories every built-in drain is made of, both from `evlog/toolkit`:

| Your backend speaks | Use |
| --- | --- |
| HTTP: a REST or JSON ingest endpoint, a vendor `/v1/logs` | `defineHttpDrain` |
| Anything else: gRPC, a WebSocket, a vendor SDK, a queue, a raw socket | `defineDrain` |

## An HTTP drain

You write two functions and never call `fetch`. `resolve()` returns the config, or `null` to skip. `encode()` turns a batch of events into one request.

```typescript [lib/my-drain.ts]
import {
  defineHttpDrain,
  resolveAdapterConfig,
  type ConfigField,
} from 'evlog/toolkit'

interface MyServiceConfig {
  apiKey: string
  endpoint?: string
  timeout?: number
}

const FIELDS: ConfigField<MyServiceConfig>[] = [
  { key: 'apiKey', env: ['MYSERVICE_API_KEY'] },
  { key: 'endpoint', env: ['MYSERVICE_ENDPOINT'] },
  { key: 'timeout' },
]

export function createMyServiceDrain(overrides?: Partial<MyServiceConfig>) {
  return defineHttpDrain<MyServiceConfig>({
    name: 'myservice',
    resolve: async () => {
      const cfg = await resolveAdapterConfig<MyServiceConfig>('myservice', FIELDS, overrides)
      if (!cfg.apiKey) {
        console.error('[evlog/myservice] Missing apiKey')
        return null
      }
      return cfg as MyServiceConfig
    },
    encode: (events, cfg) => ({
      url: `${cfg.endpoint ?? 'https://api.myservice.com'}/v1/ingest`,
      headers: {
        'Content-Type': 'application/json',
        Authorization: `Bearer ${cfg.apiKey}`,
      },
      body: JSON.stringify(events),
    }),
  })
}
```

`defineHttpDrain` sends the request with a timeout, retries it, and adds the [identity headers](/drains/http#identity-headers). A failure is logged as `[evlog/myservice] Failed to send events:` and never thrown, so a backend that is down cannot fail a request.

| Field | Default | What it does |
| --- | --- | --- |
| `name` | required | The prefix in error logs and the value of `X-Evlog-Source` |
| `label` | `name` | The name that starts an HTTP error message, as in `Axiom API error: 400` |
| `resolve()` | required | Returns the config. `null` turns the drain into a no-op |
| `encode(events, config)` | required | Returns `{ url, headers, body }`, with `compression: 'gzip'` to compress the body. `null` skips the batch. You set `Content-Type` |
| `timeout` | `5000` | Milliseconds before a request is aborted |
| `retries` | `2` | Attempts after the first one, on network errors, timeouts, and `408`, `429`, `502`, `503`, `504` |
| `resolveTimeout(config)`, `resolveRetries(config)` | | Read either value from the resolved config under another key |
| `onResponse(response)` | | Inspects a 2xx response, to throw when it carries a partial failure |

A `timeout` or `retries` key on the resolved config wins over the one in this table. Retries back off from 200 ms, doubling, with jitter, and wait at least as long as a `Retry-After` header asks, up to 10 seconds. A longer `Retry-After` ends the call.

## Which config wins

`resolveAdapterConfig(namespace, fields, overrides)` gives your users the precedence the built-in drains have:

1. The `overrides` passed to your factory.
2. `runtimeConfig.evlog.<namespace>` on Nuxt and Nitro.
3. `runtimeConfig.<namespace>` on Nuxt and Nitro.
4. The environment variables listed in the field's `env`, in order.

A field with no `env` is never read from the environment. To support Nuxt's prefixed variables, list `NUXT_MYSERVICE_API_KEY` before `MYSERVICE_API_KEY` in `env`, and build your error messages with `formatPublicEnvKeys()`, which leaves the `NUXT_` names out.

Name fields the way the built-in drains do: `apiKey` for a bearer secret, `endpoint` for the base URL, `serviceName`, `timeout`.

## Wire it in

The factory returns a drain, so it goes where any drain goes:

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'
import { createMyServiceDrain } from './lib/my-drain'

export default defineEvlog({
  service: 'my-app',
  drain: createMyServiceDrain(),
})
```

An integration's `drain` option takes the same value, and so does the `evlog:drain` hook on Nuxt and Nitro:

```typescript [server/plugins/evlog-drain.ts]
import { createMyServiceDrain } from '../../lib/my-drain'

export default defineNitroPlugin((nitroApp) => {
  nitroApp.hooks.hook('evlog:drain', createMyServiceDrain())
})
```

The [drains overview](/drains#wire-it-into-your-framework) has the line for every framework: replace the built-in factory there with yours. In production, wrap the drain in the [pipeline](/drains/pipeline) so events are batched and a failed batch is retried.

## Filter or transform before sending

`encode()` receives the whole batch and the resolved config, so it is where you drop or reshape events:

```typescript [lib/my-drain.ts]
encode: (events, cfg) => {
  const filtered = events.filter(e => e.level === 'error' && e.path !== '/health')
  if (filtered.length === 0) return null

  const payload = filtered.map(e => ({
    ts: new Date(e.timestamp).getTime(),
    severity: e.level.toUpperCase(),
    attributes: { method: e.method, path: e.path, status: e.status, durationMs: e.durationMs },
  }))

  return {
    url: `${cfg.endpoint}/v1/push`,
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(payload),
  }
}
```

## A drain without HTTP

With `defineDrain` you own the transport. The toolkit still resolves the config, skips the batch when `resolve()` returns `null`, and isolates errors.

```typescript [lib/my-drain.ts]
import { defineDrain } from 'evlog/toolkit'

export const createCustomTransportDrain = () =>
  defineDrain<{ apiKey: string }>({
    name: 'custom',
    resolve: async () => ({ apiKey: process.env.MY_KEY! }),
    send: async (events, cfg) => {
      await myVendorSdk.publish(events, { token: cfg.apiKey })
    },
  })
```

Let `send` throw when delivery fails. Called directly, the drain catches the error and logs it with its name. Its `raw` variant rejects instead, and that is the one the pipeline calls, so its `retry` and `onDropped` see the failure. A `send` that swallows its own errors can never be retried. Timeouts and retries inside `send` are yours to write.

## What a drain receives

evlog calls a drain with one `DrainContext` per event, and the pipeline calls it with an array of them:

| Field | What it is |
| --- | --- |
| `event` | The wide event: `timestamp`, `level`, `service`, `environment`, then `version`, `commitHash`, `region`, `duration` and `durationMs` when known, and every field your code set |
| `request` | `method`, `path` and `requestId`, when the event comes from a request |
| `headers` | The request headers, with sensitive ones removed |

`encode()` and `send()` get `WideEvent[]` directly: the toolkit takes `event` out of each context.

## Toolkit helpers

| Export | What it does |
| --- | --- |
| `defineHttpDrain(spec)` | Builds an HTTP drain: retries, timeout, identity headers, error isolation |
| `defineDrain(spec)` | The same contract for a transport you own |
| `resolveAdapterConfig(ns, fields, overrides)` | Resolves config in the order above |
| `httpPost(opts)` | The POST helper under every built-in HTTP drain: timeout, retries, `Retry-After`, response bodies cut to 200 characters in error messages |
| `DrainDeliveryError` | The error `httpPost` throws, with `status`, `retryable`, `retryAfterMs` and `rejected`. Throw one with `retryable: false` to tell the pipeline not to retry |
| `composeDrains(drains)` | One drain that runs several concurrently and isolates each failure |
| `toTypedAttributeValue(value)` | Converts a value to the typed attribute shape Axiom and Sentry take |
| `toOtlpAttributeValue(value)` | Converts a value to an OTLP `AnyValue`, as the OTLP, HyperDX, Sazabi and PostHog drains do |
| `OTEL_SEVERITY_NUMBER`, `OTEL_SEVERITY_TEXT` | The OpenTelemetry severity for each evlog level |

## Publish it

A community drain is a small package: `src/drain.ts` exports the factory, the tests mock `fetch`, and `evlog` is a `peerDependency`. As a plain `dependency`, your package would install a second copy of evlog next to the app's.
