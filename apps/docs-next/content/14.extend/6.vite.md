::product-facts{entry="evlog/vite" status="stable"}
::

`evlog/vite` moves three chores to build time: it starts the logger, removes `log.debug()` calls from the production bundle, and can stamp each log with the file and line it came from. It works in any project built with Vite 7 or 8, such as SvelteKit, Hono, Express, Fastify or Elysia.

```typescript [vite.config.ts]
import { defineConfig } from 'vite'
import evlog from 'evlog/vite'

export default defineConfig({
  plugins: [
    evlog({
      service: 'my-api',
      environment: 'production',
    }),
  ],
})
```

With that, `log`, `createLogger()` and `createRequestLogger()` work without an `initLogger()` call, and `log.debug()` is gone from `vite build` output.

::vite-strip-build
::

On Nuxt you do not install this plugin. The [Nuxt module](/integrations/nuxt) takes `strip` and `sourceLocation` in `nuxt.config.ts` and runs the same transforms. There, `sourceLocation` defaults to `'dev'`:

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['evlog/nuxt'],
  evlog: {
    env: { service: 'my-app' },
    strip: ['debug'],           // Default
    sourceLocation: 'dev',      // Inject in dev only
  },
})
```

## Options

| Option | Type | Default | What it does |
| --- | --- | --- | --- |
| `service` | `string` | `'app'` | Service name on every event |
| `environment` | `string` | Detected | Environment name |
| `enabled` | `boolean` | `true` | Turns all logging on or off |
| `pretty` | `boolean` | `true` in development | Pretty prints events |
| `silent` | `boolean` | `false` | Suppresses console output |
| `sampling` | `object` | none | Head and tail [sampling](/events/sampling) |
| `minLevel` | `LogLevel` | `'debug'` | Lowest level the global `log` API prints. Request events are not affected |
| `stringify` | `boolean` | `true` | Emits JSON strings, or raw objects when `false` |
| `strip` | `LogLevel[]` | `['debug']` | Levels removed from production builds. `[]` turns stripping off |
| `sourceLocation` | `boolean \| 'dev'` | `false` | Injects `__source: 'file:line'` into log calls |
| `autoImports` | `boolean \| object` | `false` | Imports evlog symbols for you |
| `client` | `object` | none | Injects the browser logger into HTML pages |

## Start the logger at build time

The plugin serializes `service`, `environment`, `enabled`, `pretty`, `silent`, `sampling`, `minLevel` and `stringify` into the bundle through Vite's `define`, and evlog starts from them when it is first imported.

Only values that survive `JSON.stringify` travel this way. A `drain`, an `enrich` or `keep` callback and `plugins` are functions, so the plugin does not carry them: pass those to `initLogger()` or to your framework's middleware, as each [integration](/integrations) page shows.

## Strip log levels from the build

Stripping runs during `vite build` only, never in `vite dev`. It is a source transform: the call is deleted from the output, arguments included, so a stripped call costs nothing at run time.

```typescript [vite.config.ts]
evlog({
  service: 'my-api',
  // Default: strip debug logs in production builds
  // strip: ['debug'],

  // Strip debug and info in production:
  // strip: ['debug', 'info'],

  // Disable stripping:
  // strip: [],
})
```

The transform matches calls on an identifier named `log`, such as `log.debug(...)`. A call on another name, such as `req.log.debug(...)` or `logger.debug(...)`, stays. A stripped call used as an expression becomes `void 0`. `trace` is not in the default list: add it if you use it.

## Add the source location

`sourceLocation` adds the file path, relative to the Vite root, and the line number to every `log.<level>({ ... })` call that takes one object literal:

```typescript [vite.config.ts]
evlog({
  service: 'my-api',
  sourceLocation: true,      // Always inject
  // sourceLocation: 'dev',  // Only in development
})
```

A call that already has a `__source` key is left alone, and so is a call in the `log.info('tag', 'message')` form. With `true`, a production build embeds your source paths in the bundle, client code included, and the plugin prints a warning. `'dev'` limits it to `vite dev`.

## Auto-imports

Off by default. With `autoImports: true`, the plugin finds uses of `log`, `createEvlogError` and `parseError` in your code, adds the `import` statements, and writes an `auto-imports.d.ts` so TypeScript knows them:

```typescript [vite.config.ts]
evlog({
  service: 'my-api',
  autoImports: true,
})
```

Pass an object to change either part:

| Option | Default | What it does |
| --- | --- | --- |
| `imports` | `['log', 'createEvlogError', 'parseError']` | The symbols to import. `setIdentity` and `clearIdentity` come from `evlog/client`, anything else from `evlog` |
| `dts` | `'auto-imports.d.ts'` | Path of the generated declarations, relative to the Vite root. `false` writes none. When unset, the file goes in `src/` if that directory exists |

The auto-imported error constructor is `createEvlogError`, not `createError`: Nuxt, Nitro and h3 have a `createError` of their own. `createError` from `evlog` is still there when you import it yourself. A name you declare or import at the top of a file is never imported over.

## Browser logger

With `client`, the plugin prepends a module script to every HTML page that calls `initLog()` from `evlog/client`, so `log.info()` and `log.error()` work in browser code:

```typescript [vite.config.ts]
evlog({
  service: 'my-api',
  client: {
    console: false,
    transport: {
      enabled: true,
      endpoint: '/api/_evlog/ingest',
    },
  },
})
```

| Option | Default | What it does |
| --- | --- | --- |
| `service` | `'client'` | Service name on browser logs |
| `pretty` | `true` in `vite dev` | Pretty prints in the browser console |
| `console` | `true` | Prints to the browser console |
| `minLevel` | `'debug'` | Lowest level browser `log` calls emit |
| `transport.enabled` | `false` | Sends logs to your server |
| `transport.endpoint` | `'/api/_evlog/ingest'` | Where they are posted |
| `transport.credentials` | `'same-origin'` | The `fetch` credentials mode |

[Browser events](/events/client) covers the endpoint that receives them.

## Read evlog.config.ts

The plugin reads the `evlog.config.ts` the CLI, Nuxt and Nitro read. It looks for `evlog.config.ts`, `.mts`, `.js` and `.mjs` in the Vite root, then in each parent directory up to the workspace root, and takes the nearest one.

```typescript [evlog.config.ts]
import { defineEvlog } from 'evlog'

export default defineEvlog({
  service: 'my-api',
  pretty: false,
  sampling: { rates: { info: 10 }, keep: [{ status: 400 }] },
})
```

The file is the base, and the plugin options override it key by key:

```typescript [vite.config.ts]
evlog({
  environment: 'production', // the file keeps its service and pretty settings
})
```

Plugin options win on `service`, `environment`, `enabled`, `pretty`, `silent`, `minLevel`, `stringify` and on each key of `sampling`. The `sampling.keep` rules of both sides are kept. Those eight settings are the only ones read from the file. Its functions (`drain`, `enrich`, `keep`, `plugins`) are not injected and do not run in the build.

A file with a syntax or import error fails the build with its path in the message. Without a file, only the plugin options apply.

## Vite versions

The plugin supports Vite 7 and 8. On Vite 8, which builds with Rolldown, the transform hooks declare a native `filter` and `moduleType`, so a file that cannot contain a log call is skipped on the Rust side, before it reaches JavaScript. A Vite version that ignores the filter falls back to the same check inside the plugin.
