When your framework has no `evlog/<framework>` entry point, you write the integration yourself. `evlog/toolkit` exports the building blocks the built-in integrations are made of, so what you write is the part specific to your framework: where the request is, where the logger goes, and when the response ends.

The toolkit is in beta. Every built-in integration runs on it, and its surface can still change.

| You have | Use | From |
| --- | --- | --- |
| An HTTP framework with a middleware or hook around each request | [`defineFrameworkIntegration()`](#write-the-manifest) | `evlog/toolkit` |
| A lifecycle with no request context to read from | [`createMiddlewareLogger()`](#without-a-manifest) | `evlog/toolkit` |
| A job, a queue message, a CLI run | [`createLogger()`](#outside-http) | `evlog` |

An integration owes its users the contract every built-in one keeps: an `evlog()` middleware that takes `BaseEvlogOptions`, the logger on the framework's own request object, `useLogger()` for the code underneath the handler, and `log.fork()` for background work.

## Write the manifest

A manifest says how to read the request and where to attach the logger. `defineFrameworkIntegration` returns a `start()` function that does the rest:

```typescript [my-framework-evlog.ts]
import type { IncomingMessage, ServerResponse } from 'node:http'
import {
  defineFrameworkIntegration,
  type BaseEvlogOptions,
} from 'evlog/toolkit'
import { createLoggerStorage } from 'evlog/toolkit/storage'
import type { RequestLogger } from 'evlog'

export type MyFrameworkEvlogOptions = BaseEvlogOptions

const { storage, useLogger } = createLoggerStorage(
  'middleware context. Make sure the evlog middleware is registered before your routes.',
  'my-framework',
)

export { useLogger }

const integration = defineFrameworkIntegration<IncomingMessage>({
  name: 'my-framework',
  extractRequest: (req) => ({
    method: req.method || 'GET',
    path: req.url || '/',
    headers: req.headers,
    requestId: typeof req.headers['x-request-id'] === 'string'
      ? req.headers['x-request-id']
      : undefined,
  }),
  attachLogger: (req, logger) => {
    (req as IncomingMessage & { log: RequestLogger }).log = logger
  },
  storage,
})

export function evlog(options: MyFrameworkEvlogOptions = {}) {
  return async (req: IncomingMessage, res: ServerResponse, next: () => Promise<void>) => {
    const { skipped, finish, runWith } = integration.start(req, options)
    if (skipped) {
      await next()
      return
    }
    try {
      await runWith(() => next())
      await finish({ status: res.statusCode })
    } catch (error) {
      await finish({ error: error as Error })
      throw error
    }
  }
}
```

That middleware has route filtering, per-route service names, tail sampling, redaction, enrichers, drains, plugin hooks, error capture, the request duration and `log.fork()`.

| Manifest key | What it does |
| --- | --- |
| `name` | A stable identifier, used in error messages |
| `extractRequest(ctx)` | Returns `{ method, path, headers?, requestId? }`. `headers` is a Web `Headers` object or a Node header record |
| `attachLogger(ctx, logger)` | Puts the logger where handlers read it, such as `req.log` |
| `storage` | The `AsyncLocalStorage` behind `useLogger()`. When set, the logger gets `log.fork()` |
| `forkLifecycle` | `{ onChildEnter, onChildExit }`, called around each forked child. `onChildExit` runs after the child's event has drained |
| `extractWaitUntil(ctx)` | Returns the platform's `waitUntil` when it lives on the framework context |

On each request, `integration.start(ctx, options)`:

1. Calls `extractRequest`, and removes sensitive headers such as `authorization` and `cookie` from what enrichers and drains see.
2. Generates a `requestId` when `extractRequest` returns none.
3. Creates the request logger, or returns `skipped: true` when `include` and `exclude` filter the route out or logging is off.
4. Calls `attachLogger`, with `log.fork()` attached when `storage` is set.

It returns:

| Key | What it is |
| --- | --- |
| `logger` | The request logger |
| `skipped` | `true` when evlog does not log this request. Call the next handler and return |
| `runWith(fn)` | Runs `fn` inside `storage`, so `useLogger()` resolves in everything it calls. Without `storage`, it calls `fn` directly |
| `finish({ status?, error?, durationMs? })` | Ends the request: sets the status or records the error, runs tail sampling, emits, redacts, enriches and drains. `durationMs` replaces the measured time |
| `finishResponse(response, { status? })` | The same for a Fetch `Response`. See [streaming responses](#streaming-responses) |
| `middlewareOptions` | The options the logger was created with, for `attachForkToLogger` |

`createLoggerStorage(hint, id)` comes from `evlog/toolkit/storage`, not from `evlog/toolkit`: the main entry stays free of `node:async_hooks` so it runs on edge runtimes. `hint` ends the error message `useLogger()` throws outside a request. `id` names the storage slot, so two copies of evlog in one process share it: pass one of your own.

## Options your users pass

`BaseEvlogOptions` is the option type of every integration: `include`, `exclude` and `routes` to filter and name routes, `drain`, `enrich` and `keep`, `redact`, `plugins`, and the `waitUntil` hook described below. They behave as in [`evlog.config.ts`](/reference/configuration). Extend the type when your framework needs more.

`toMiddlewareOptions(config)` from `evlog` turns an `evlog.config.ts` into these options, the way the [Hono page](/integrations/hono) uses it.

## Without a manifest

When there is no context object to extract from, call `createMiddlewareLogger` yourself. `@evlog/eve` does this to emit one event per agent turn:

```typescript
import { createMiddlewareLogger, extractSafeNodeHeaders } from 'evlog/toolkit'

const { logger, finish, skipped } = createMiddlewareLogger({
  method,
  path,
  requestId,
  headers: extractSafeNodeHeaders(rawHeaders),
  ...options,
})
```

You get the same pipeline and the same `finish` and `finishResponse`. Three things become yours: running the handler inside `storage.run(logger, fn)`, attaching `log.fork()` with `attachForkToLogger(storage, logger, middlewareOptions)` before the request finishes, and calling `finish`.

## Streaming responses

A handler that returns a server-sent event stream returns before the stream is done, and fields set while it streams would miss the event. For a framework that hands you a Fetch `Response`, call `finishResponse(response)` in place of `finish({ status })` and return what it resolves to. A plain response is finished at once. A response with a `text/event-stream` or `application/x-ndjson` content type, chunked transfer encoding, or the AI SDK UI stream header is wrapped, and the event is emitted when its body ends or fails.

## Workers and edge

On Cloudflare Workers and Vercel Edge, the runtime can stop as soon as the response is returned. Pass the platform's `waitUntil`: enrichers still run before the response, and the drain is registered with `waitUntil` so it finishes afterwards. [`evlog/workers`](/integrations/cloudflare-workers) and the Nitro plugin do the same.

With a manifest, declare where the hook lives:

```typescript
const integration = defineFrameworkIntegration<WorkerContext>({
  name: 'my-framework',
  extractRequest: (ctx) => ({ /* … */ }),
  attachLogger: (ctx, logger) => { /* … */ },
  extractWaitUntil: ctx => ctx.executionCtx.waitUntil.bind(ctx.executionCtx),
})
```

Without one, pass it per request:

```typescript
import { waitUntil } from '@vercel/functions'

const { logger, finish, skipped } = createMiddlewareLogger({
  method,
  path,
  requestId,
  headers: extractSafeNodeHeaders(rawHeaders),
  waitUntil, // or ctx.waitUntil.bind(ctx) on Cloudflare
  ...options,
})
```

A `waitUntil` in the options passed to `integration.start()` wins over `extractWaitUntil`. With neither, the manifest path uses the Vercel Functions request context when there is one. Otherwise `finish` awaits the drain, which is right for a long-running Node.js server.

`log.fork()` uses the same hook. It registers the child's lifetime with `waitUntil` when it is called, while the handler is still in scope, so a fork nobody awaits still drains before the runtime stops.

## Outside HTTP

A queue worker, a CLI or a cron job needs no middleware. Create a logger per unit of work with `createLogger` from `evlog`, and emit it yourself:

```typescript [worker.ts]
import { createLogger } from 'evlog'

async function processJob(job: Job) {
  const log = createLogger({ job: { id: job.id, queue: job.queue } })

  try {
    await runJob(job)
  } catch (err) {
    log.error(err as Error)
    throw err
  } finally {
    log.emit()
  }
}
```

The event goes to the drain `initLogger()` registered, with the [identity headers](/drains/http#identity-headers) every drain request carries. [Standalone](/integrations/standalone) covers this path, and when to use `createRequestLogger` instead.

## Toolkit exports for integrations

| Export | What it does |
| --- | --- |
| `defineFrameworkIntegration(spec)` | The manifest factory |
| `createMiddlewareLogger(options)` | The request lifecycle underneath it. Returns `{ logger, finish, finishResponse, skipped }`, the `MiddlewareLoggerResult` type |
| `BaseEvlogOptions` | The option type every integration accepts |
| `createLoggerStorage(hint, id?)` | Returns `{ storage, useLogger }`. From `evlog/toolkit/storage` |
| `attachForkToLogger(storage, parent, options, lifecycle?)` | Adds `log.fork(label, fn)` to a logger and returns it. The manifest calls it for you. `log.fork()` returns a promise that resolves once the child's event has drained |
| `forkBackgroundLogger(options)` | The function behind `log.fork()`, for a lifecycle that has no storage |
| `extractSafeHeaders(headers)` | Copies a Web `Headers` object without the sensitive headers |
| `extractSafeNodeHeaders(headers)` | The same for a Node header record |
| `extractErrorStatus(error)` | The HTTP status an error carries, `500` when it has none |
| `shouldDeferEmitForResponse(response)` | Whether `finishResponse` waits for this response's body |
| `defineEvlog(config)` | One config object for `initLogger` and the middleware options |
| `definePlugin(plugin)` | A plugin with any of `setup`, `enrich`, `drain`, `keep`, `onRequestStart`, `onRequestFinish`, `onClientLog`, `extendLogger` |
| `composeEnrichers`, `composeDrains`, `composeKeep`, `composePlugins` | Combine several extensions into one |
| `onErrorCreated(listener)` | Called with every `EvlogError` as it is built |

Types such as `RequestLogger`, `DrainContext`, `EnrichContext`, `WideEvent` and `TailSamplingContext` come from `evlog`. The toolkit also holds the factories for a [custom drain](/extend/custom-drain) and for [enrichers](/events/enrichers).

## Read a built-in one

Every built-in integration is a manifest plus the glue its framework needs, in one file each under [`packages/evlog/src`](https://github.com/evloghq/evlog/tree/main/packages/evlog/src):

- [Express](https://github.com/evloghq/evlog/blob/main/packages/evlog/src/express/index.ts) is the shortest: a manifest, storage, and Node's response events.
- [Hono](https://github.com/evloghq/evlog/blob/main/packages/evlog/src/hono/index.ts) shows `finishResponse` and `extractWaitUntil` on a Fetch framework.
- [Fastify](https://github.com/evloghq/evlog/blob/main/packages/evlog/src/fastify/index.ts) calls `start()` in one hook and `finish()` in another.
- [Elysia](https://github.com/evloghq/evlog/blob/main/packages/evlog/src/elysia/index.ts) scopes the storage by hand, with `forkLifecycle`.
- [NestJS](https://github.com/evloghq/evlog/blob/main/packages/evlog/src/nestjs/index.ts) is a module that registers the middleware on every route.
- [SvelteKit](https://github.com/evloghq/evlog/blob/main/packages/evlog/src/sveltekit/index.ts) runs in the `handle` hook, with the platform's `waitUntil`.

If you build an integration for a framework evlog does not ship, [open a pull request](https://github.com/evloghq/evlog/pulls).
