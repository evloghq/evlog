A logger that writes a line per step sends the same request context over and over: every line carries its own level, timestamp, host and request bindings. evlog emits one event per request, so that context is written once. Price the difference against your own traffic:

::log-cost-calculator
::

## Where the byte counts come from

Both shapes are the same checkout request, serialized through the real libraries.

::code-group
```typescript [evlog, 1 event of 322 B]
const log = createLogger({ method: 'POST', path: '/api/checkout', requestId: 'req_abc' })
log.set({ user: { id: 'usr_123', plan: 'pro' } })
log.set({ cart: { items: 3, total: 9999 } })
log.set({ payment: { method: 'card', last4: '4242' } })
log.emit({ status: 200 })
```

```typescript [pino, 4 lines of 736 B]
const child = pinoLogger.child({ method: 'POST', path: '/api/checkout', requestId: 'req_abc' })
child.info({ user: { id: 'usr_123', plan: 'pro' } }, 'user context')
child.info({ cart: { items: 3, total: 9999 } }, 'cart context')
child.info({ payment: { method: 'card', last4: '4242' } }, 'payment context')
child.info({ status: 200 }, 'request complete')
```
::

| | Events | Bytes |
| --- | ---: | ---: |
| pino, 4 lines | 4 | 736 |
| evlog, 1 event | 1 | 322 |
| Difference | 75% fewer | 56% fewer |

The two numbers differ because one event removes the duplicated envelope and keeps the payload. pino writes `level`, `time`, `pid`, `hostname`, `method`, `path` and `requestId` four times and evlog writes them once, and the four `msg` strings disappear. The fields you set are written once either way.

Your ratio is not this ratio. A handler that logs two lines saves less, and one that repeats a large `user` object on every line saves more.

## Which number moves your bill

Providers meter logs in one of two ways, and that decides which saving you collect.

| Metered by | Saving you collect | Providers |
| --- | --- | --- |
| Gigabytes ingested | The 56% byte figure | Grafana Cloud, Sentry, PostHog, Better Stack, Axiom |
| Gigabytes and indexed events | The 75% event figure, on the indexing line | Datadog |

Per-gigabyte billing is the common case, so most teams collect the byte saving. Datadog bills ingestion per gigabyte and indexing per million events, and the indexing line is the larger of the two at the rates the calculator starts from, so the event count is what moves that bill.

The rates are list prices read on 14 August 2026, before free tiers, committed-use discounts and retention add-ons. Vendors change pricing, which is why every rate is an input in the calculator.

## Sampling moves both columns

The calculator applies sampling to both shapes. Any logger can drop records by level or sample in its transport, so applying it to evlog alone would credit evlog with a saving that is not its own. Pull the slider down and both bills fall together while the gap between them holds.

Sampling is still the larger lever. One event per request is a floor that consolidation cannot go under. [Sampling](/events/sampling) has no such floor: head sampling drops events by level at emit time, and tail sampling force-keeps errors and slow requests through a rule that discards the rest.

What evlog changes is the unit sampling works on. Dropping a line loses part of a request. Dropping an event loses a whole request, and keeping an event keeps all of it.

## Ask it from your editor

The same calculation is a tool on the [docs MCP server](/skills#mcp-server) at `https://www.evlog.dev/mcp`, so a connected agent can answer it directly:

```text [MCP tool call]
estimate-log-cost({ requestsPerMonth: 10000000, linesPerRequest: 4, provider: "datadog" })
```

It returns both shapes, the saving, and the basis it used: the measured byte counts, the rates it applied and the date they were read. Pass `perGb` and `perMillionIndexed` to price a provider that is not in the list, or to correct one whose pricing has moved.
