The [comparison suite](https://github.com/evloghq/evlog/blob/v3/packages/evlog/bench/comparison/vs-alternatives.bench.ts) gives every logger the same work: build the record, serialize it to one JSON line, and write that line to the same no-op stream.

Microseconds per call, lower is better. Median of three runs, `NODE_ENV=production`, on an Apple M4 Pro with evlog 3 (beta), pino 10.4, LogLayer 9.4 over pino, LogTape 2.4 and winston 3.19, on Node.js 24.22:

| Work | evlog | pino | LogLayer | LogTape | winston |
| --- | ---: | ---: | ---: | ---: | ---: |
| One record, 5 fields | 0.67 | 0.59 | 0.98 | 3.14 | 2.84 |
| One request record | 1.22 | 1.02 | 1.80 | 4.09 | 5.18 |
| A request record with an error | 1.99 | 1.80 | 2.61 | 5.71 | 4.65 |
| Redact two paths in a request record | 3.15 | 1.40 | | | |

## Where evlog is slower, and why

- **A request record, against pino.** evlog creates a request logger, checks every `set()` payload for `Error` objects so they are logged with their name, message and stack, and calls the drain through a promise so a failing drain cannot break the request.
- **Redacting paths, against pino.** evlog copies the whole event and checks every key against the paths. pino only visits the paths you configure.

## What a microbenchmark does not tell you

An event-construction measurement is not the cost of a request, and it is not a delivery guarantee. Moving from ten lines per request to one event changes how many records you write, not the cost of each one. To price your own path:

1. Run a representative handler with `enabled: false` as the baseline.
2. Turn on the redaction, enrichers and output you deploy.
3. Exercise successes, errors and the largest context you expect, and record latency distributions, not only throughput.
4. Include batching, retries and shutdown, and confirm the records reach the destination.
