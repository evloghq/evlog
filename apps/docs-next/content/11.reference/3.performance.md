The [comparison suite](https://github.com/evloghq/evlog/blob/v3/packages/evlog/bench/comparison/vs-alternatives.bench.ts) gives every logger the same work: build the record, serialize it to one JSON line, and write that line to the same no-op stream.

Microseconds per call, lower is better. Median of three runs, `NODE_ENV=production`, on an Apple M4 Pro with evlog 3 (beta), pino 10.4, LogLayer 9.4 over pino, LogTape 2.4 and winston 3.19, on Node.js 24.22:

| Work | evlog | pino | LogLayer | LogTape | winston |
| --- | ---: | ---: | ---: | ---: | ---: |
| One record, 5 fields | 0.67 | 0.59 | 0.98 | 3.14 | 2.84 |
| One request record | 1.22 | 1.02 | 1.80 | 4.09 | 5.18 |
| A request record with an error | 1.99 | 1.80 | 2.61 | 5.71 | 4.65 |
| Redact two paths in a request record | 3.15 | 1.40 | | | |

The same rows on Node.js 26.7:

| Work | evlog | pino | LogLayer | LogTape | winston |
| --- | ---: | ---: | ---: | ---: | ---: |
| One record, 5 fields | 0.57 | 0.62 | 1.03 | 3.31 | 3.20 |
| One request record | 0.98 | 0.84 | 1.71 | 4.57 | 5.64 |
| A request record with an error | 1.21 | 2.25 | 3.21 | 6.13 | 4.64 |
| Redact two paths in a request record | 3.36 | 1.21 | | | |

Every minimum was within 5% of its median, except winston's, within 11%. On these rows evlog is 2.3 to 5.8 times faster than LogTape and winston, and 1.3 to 2.7 times faster than LogLayer over pino. Against pino it ranges from 1.2 times slower to 1.9 times faster, depending on the row and the Node.js version. consola, with a reporter that serializes its log object, takes 0.57 µs for one record on Node.js 24, and has no equivalent for the other rows.

## Where evlog is slower, and why

- **A request record, against pino.** evlog creates a request logger, checks every `set()` payload for `Error` objects so they are logged with their name, message and stack, and calls the drain through a promise so a failing drain cannot break the request.
- **Redacting paths, against pino.** evlog copies the whole event and checks every key against the paths. pino only visits the paths you configure. evlog's default redaction in production, which also masks emails, card numbers and the other built-in patterns in every string, takes 3.17 µs for the same request on Node.js 24. No other logger here scans values by default, so that row has no counterpart.

## When another logger fits better

A [pino transport](https://github.com/pinojs/pino/blob/main/docs/transports.md) can run in a worker thread, so delivery leaves the calling thread, while pino still serializes the record on it. Winston formats and transports, or a consola reporter, may already produce the exact output your app needs, and keeping that configuration can cost less than porting it. These rows do not show evlog winning every workload. Measure throughput and latency with your destination, payloads and delivery policy, including queued work and the final flush, not only the time to enqueue an event.

## What a microbenchmark does not tell you

An event-construction measurement is not the cost of a request, and it is not a delivery guarantee. Moving from ten lines per request to one event changes how many records you write, not the cost of each one. To price your own path:

1. Run a representative handler with `enabled: false` as the baseline.
2. Turn on the redaction, enrichers and output you deploy.
3. Exercise successes, errors and the largest context you expect, and record latency distributions, not only throughput.
4. Include batching, retries and shutdown, and confirm the records reach the destination.

Do not add the means of unrelated microbenchmarks and call the sum a request cost. Work overlaps, takes different branches or runs in the background, and network delivery and backend indexing need their own measurements.

## Bundle size

An entry point's emitted file is not the size of the bundle that imports it: shared chunks and the exports you select change the result. The server core, `evlog/http`, the integrations and the drains also target different uses, so a server bundle says nothing about which browser logger is smaller. Build the entry points you plan to import and measure that bundle. To compare with another library, keep the bundler, target, minification, compression, versions and imported features the same.

## evlog 2 and evlog 3

`log.set()` runs 1.7 to 2.9 times faster in evlog 3 than in 2.36.0, and `emit` 1.4 to 2.2 times faster. The latest evlog 2 already has the gains made since 2.32.0: requests about 2.5 times cheaper, an install half the size, serverless functions released milliseconds after their request, and a drain that stops retrying a backend that rejects a batch or asks it to wait.

| Measurement | 2.32.0 | 2.36.0 | 2.37.0 | evlog 3 |
| --- | ---: | ---: | ---: | ---: |
| Request without a drain | 23.8 µs | 9.4 µs | 10.0 µs | 8.4 µs |
| Request with a drain pipeline | 25.3 µs | 9.7 µs | 11.2 µs | 9.3 µs |
| Serverless request | 26.2 µs | 10.9 µs | 12.2 µs | 10.8 µs |
| `bench/core` suite, geometric mean against 2.36.0 | not run | 1× | 0.99× | 1.22× |
| CPU at 5,000 requests/s with `waitUntil` | 29% | 20% | 21% | 20% |
| Serverless function kept alive after its request, p99 at 2,000 requests/s | 9.8 s | 9.9 s | 11 ms | 12 ms |
| Same, p50, when the backend takes 300 ms | 6.2 s | 6.2 s | 0.66 s | 0.66 s |
| Shutdown flush when the backend answers 400 | 15 s | 15 s | 38 ms | 36 ms |
| Install size | 1.98 MB | 0.93 MB | 0.97 MB | 0.93 MB |

Three paths do more work in evlog 3:

- **Redaction** also checks values for credentials, and costs 10 to 13% more than in 2.36.0.
- **A serverless app whose backend is down** uses about 8% of a core at 1,000 requests/s against 3%, because each request end sends the events the pipeline holds before the function freezes.
- **`evlog/pipeline`** grows from 2.0 kB to 7.0 kB gzip, to carry the retry rules, drop reporting and request-end flush.

These numbers come from a 4-core Intel Xeon at 2.90 GHz on Linux with Node.js 26.13.1, on November 21, 2026. 2.32.0 and 2.36.0 come from npm, 2.37.0 is `main` at [`104923e1`](https://github.com/evloghq/evlog/commit/104923e1), and evlog 3 is the `v3` branch at [`268ff9ab`](https://github.com/evloghq/evlog/commit/268ff9ab), which is newer than `3.0.0-beta.3`. A request row is the time per request over 200,000 sequential requests that set fields and finish, without the handler's own work. Each load scenario ran twice. The `bench/core`, `log.set()`, `emit` and redaction figures come from a run earlier the same day, before the pipeline changes in [#1212](https://github.com/evloghq/evlog/pull/1212), which do not touch the logger.

## Reproduce the numbers

This section is for checking the numbers above, so its commands run in a checkout of the [evlog repository](https://github.com/evloghq/evlog/tree/v3/packages/evlog/bench), not in your app. Each suite answers one question:

| Suite | What it measures |
| --- | --- |
| `bench/core/` | How context size, merging, emission and errors change the cost of building an event. Redaction is off |
| `bench/core/production.bench.ts` | One emit with the redaction a production process turns on by default |
| `bench/comparison/` | Each logger writing the same JSON line to the same stream |
| `bench/load/` | Whole requests, with and without a drain pipeline, against published releases |

From `packages/evlog`, with dependencies installed, run a suite once instead of in watch mode:

```bash [Terminal]
pnpm exec vitest bench --run --project evlog bench/comparison/
pnpm exec vitest bench --run --project evlog bench/core/
pnpm exec tsx bench/scripts/size.ts
```

Vitest writes the results to `bench/results.json`. To compare a published release with your checkout:

```bash [Terminal]
npm pack evlog@2.36.0 && mkdir -p /tmp/evlog-2.36.0 && tar xzf evlog-2.36.0.tgz -C /tmp/evlog-2.36.0
pnpm --filter evlog build
pnpm bench:load --pkg 2.36.0=/tmp/evlog-2.36.0/package --pkg head=. --repeat 2
```

Read a suite's setup before you read its result: silent output, a disabled drain and reused fixtures change the work included. When you publish a run, record the commit, the dependency versions, the runtime, CPU and OS, the warmup and measurement settings, the payload, the redaction and the destination, and say whether the number measures construction, serialization, queued delivery or completed delivery.
