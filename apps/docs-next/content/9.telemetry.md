A CLI runs on someone else's machine, so you cannot read its logs. `@evlog/telemetry` applies the wide event to it: one command run is one event, with the command name, sanitized flags, duration and outcome, and nothing from raw `argv`.

```bash [Terminal]
pnpm add @evlog/telemetry
```

```typescript [scripts/migrate.ts]
import { createTelemetry, telemetry } from '@evlog/telemetry'

const t = createTelemetry({ name: 'my-migrator', version: '2.0.0' })

await t.run('migrate', async () => {
  const rows = await migrateBatch()
  telemetry.set({ rowsMigrated: rows.length, batchSize: 500 })
})
```

`telemetry.set()` takes numbers and booleans by default. A string flag value is recorded as `"<set>"` unless you declare it in `collect`.

## From the user's machine to your backend

```text
CLI → @evlog/telemetry → outbox.ndjson → POST /ingest → validate → store
```

1. The run appends one event to `~/.config/<tool>/telemetry/outbox.ndjson`, after checking consent.
2. On flush, the backlog is posted to your ingest endpoint.
3. Your endpoint validates it with `parseIngestBody()` from `@evlog/telemetry/ingest`, which allowlists tools and custom keys.
4. A `2xx` removes the delivered events from the outbox.

Nothing is sent until you set an endpoint, in the config or as `EVLOG_TELEMETRY_ENDPOINT`. A short CI job or an offline machine sends its backlog on the next run.

## Entry points

| You ship | Use |
| --- | --- |
| A citty CLI | `withTelemetry()` around the root command |
| A script or migrator | `createTelemetry()` and `t.run()` |
| A GitHub Action | `createGitHubActionsTelemetry()`, which adds `GITHUB_ACTION` and `GITHUB_EVENT_NAME` only |

`generateDisclosure()` writes `TELEMETRY.md` from the runtime config, so the disclosure you commit cannot drift from what you collect.

The package is standalone: about 8.6 KB gzipped, with `citty` and `std-env` as its only dependencies, and no dependency on `evlog`.
