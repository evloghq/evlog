An action reaches the audit trail in one of three ways: you call `log.audit()` inside a request, `audit()` outside one, or you wrap the function with `withAudit()` and evlog records the outcome for you. Every symbol on this page is imported from `evlog`.

| You have | Use | The event |
| --- | --- | --- |
| A request logger | `log.audit(fields)` | The request's wide event, with an `audit` field |
| A refused action | `log.audit.deny(reason, fields)` | The same, with `outcome: 'denied'` |
| A job, a script, a CLI | `audit(fields)` | A one-shot event of its own |
| A function that is the action | `withAudit(options, fn)` | A one-shot event per call, outcome resolved from the result |

## In a request

`log.audit()` sets the `audit` field on the request's wide event and marks the event to be kept past sampling:

```typescript [server/api/invoices/refund.post.ts]
log.audit({
  action: 'invoice.refund',
  actor: { type: 'user', id: user.id },
  target: { type: 'invoice', id: 'inv_889' },
  outcome: 'success',
})
```

The method is on the request logger of each integration:

Every other integration hands you the same logger through its own accessor, listed on its [integration](/integrations) page. Outside a request, call [`audit()`](#outside-a-request).

`log.audit()` accepts `action`, `actor`, `target`, `outcome`, `reason`, `changes`, `causationId`, `correlationId` and `version`. `outcome` defaults to `'success'` and `version` to `1`. [The audit field](/audit#the-audit-field) describes each one.

`log.set({ audit: { ... } })` writes the same field and the event is kept too, but nothing is defaulted. It is the only way to set `context` or `idempotencyKey` yourself.

A wide event holds one `audit` field. A second `log.audit()` on the same logger merges into the first, so an action that needs its own record goes in `log.fork()` or through `audit()`. After the event is emitted, `log.audit()` does nothing and prints a warning. An audit event survives `log.discard()`.

`log.audit.deny(reason, fields)` takes the same fields without `outcome` and `reason`. Call it on the negative branch of every authorization check, as in [Record a denial](/audit#record-a-denial).

## Outside a request

A cron task or a queue worker has no request logger. `audit()` creates a logger, sets the field and emits at once:

```typescript [scripts/cleanup.ts]
import { audit } from 'evlog'

audit({
  action: 'cron.cleanup',
  actor: { type: 'system', id: 'cron' },
  target: { type: 'job', id: 'cleanup-stale-sessions' },
  outcome: 'success',
})
```

It returns the emitted event, or `null` when logging is disabled. There is no request to read, so the event has no `requestId`, `ip` or `userAgent`. `target` accepts extra keys, which is where a job id, a queue name or a run id goes.

```json [Logged event (trimmed)]
{
  "audit": {
    "action": "cron.cleanup",
    "actor": { "type": "system", "id": "cron" },
    "target": { "type": "job", "id": "cleanup-stale-sessions" },
    "outcome": "success",
    "version": 1,
    "idempotencyKey": "9f2c4e1a7b3d5f60a8c1e2d4b6f80a13"
  }
}
```

## Wrap the function

A refund, a deletion or a role change is one function whose result is the outcome. Wrap it and the call cannot be forgotten:

```typescript [server/utils/refund.ts]
import { withAudit, AuditDeniedError } from 'evlog'

const refundInvoice = withAudit(
  { action: 'invoice.refund', target: input => ({ type: 'invoice', id: input.id }) },
  async (input: { id: string }, ctx) => {
    if (!ctx.actor) throw new AuditDeniedError('Anonymous refund denied')
    return await db.invoices.refund(input.id)
  },
)

await refundInvoice({ id: 'inv_889' }, {
  actor: { type: 'user', id: user.id },
  correlationId: requestId,
})
```

| The function | `outcome` | `reason` |
| --- | --- | --- |
| Returns | `success` | None |
| Throws `AuditDeniedError`, or an error whose `status` or `statusCode` is `403` | `denied` | The error message |
| Throws anything else | `failure` | The error message |

The error is thrown again in both cases. `target` is an object or a function of the input. The second argument of the wrapped function carries `actor`, which is required, and optionally `causationId` and `correlationId`.

`withAudit()` emits through `audit()`, so the record is its own event and not a field on the request's event. Pass the request id as `correlationId` to join the two. Keep a manual `log.audit()` when the audit is one decision among several in a handler, or when it must be recorded before the action completes, such as "user requested deletion".

## Name your actions

`defineAuditAction` fixes the action name and the target type in one place, so call sites carry no string to mistype:

```typescript [src/audit.ts]
import { defineAuditAction } from 'evlog'

const refund = defineAuditAction('invoice.refund', { target: 'invoice' })

log.audit(refund({
  actor: { type: 'user', id: user.id },
  target: { id: 'inv_889' }, // type inferred as 'invoice'
  outcome: 'success',
}))
```

Past a handful of actions, group them in a catalog. It follows the convention of [error catalogs](/errors/catalogs): `UPPER_SNAKE_CASE` keys under a prefix, and the recorded `action` is `prefix.KEY`.

::code-group
```typescript [audit/billing.ts]
import { defineAuditCatalog } from 'evlog'

export const billingAudit = defineAuditCatalog('billing', {
  INVOICE_REFUND: {
    target: 'invoice',
    severity: 'high',
    requiresChanges: true,
    description: 'Refund an invoice to the customer',
    redactPaths: ['cardNumber'],
  },
  INVOICE_CREATE:      { target: 'invoice' },
  INVOICE_VOID:        { target: 'invoice', severity: 'high', requiresReason: true },
  SUBSCRIPTION_CANCEL: { target: 'subscription', severity: 'high' },
})
```
```typescript [server/api/refund.post.ts]
import { billingAudit } from '~/audit/billing'

log.audit(billingAudit.INVOICE_REFUND({
  actor: { type: 'user', id: user.id },
  target: { id: 'inv_889' }, // type inferred as 'invoice'
  outcome: 'success',
}))
```
::

Both functions take the same options per action:

| Option | Type | Purpose |
| --- | --- | --- |
| `target` | `string` | `target.type` filled in when the call site gives a target without one |
| `description` | `string` | A label for docs, alert rules and review tooling |
| `severity` | `'low' \| 'medium' \| 'high' \| 'critical'` | Alerting and review priority |
| `requiresChanges` | `boolean` | States that callers should attach `changes` |
| `requiresReason` | `boolean` | States that callers should attach `reason` |
| `redactPaths` | `string[]` | The paths to pass to `auditDiff()` for this action |

Only `target` changes the event. The other five are metadata, readable on each factory next to `action`, and evlog enforces none of them:

```typescript [server/api/refund.post.ts]
billingAudit.INVOICE_REFUND.action           // 'billing.INVOICE_REFUND' (literal type)
billingAudit.INVOICE_REFUND.target           // 'invoice'
billingAudit.INVOICE_REFUND.severity         // 'high'
billingAudit.INVOICE_REFUND.requiresChanges // true
billingAudit.INVOICE_REFUND.redactPaths      // ['cardNumber']
billingAudit._actions                        // readonly ['billing.INVOICE_REFUND', ...]
```

A catalog also exposes `_prefix`. The two forms mix in one codebase: `defineAuditAction` for a one-off action whose full name you write yourself, a catalog for each bounded context such as `billing` or `auth`.

To get the union of every action as the `AuditAction` type, register each catalog once:

```typescript [evlog.d.ts]
import type { billingAudit } from './audit/billing'

declare module 'evlog' {
  interface RegisteredAuditCatalogs {
    billing: typeof billingAudit
  }
}
```

## Record what changed

For an action that mutates a record, `auditDiff()` compares the two versions and returns the value for `changes`:

```typescript [server/api/users/update.post.ts]
import { auditDiff } from 'evlog'

const before = await db.users.byId(id)
const after = await db.users.update(id, patch)

log.audit({
  action: 'user.update',
  actor: { type: 'user', id: actorId },
  target: { type: 'user', id },
  outcome: 'success',
  changes: auditDiff(before, after, { redactPaths: ['password', 'token'] }),
})
```

The result is `{ patch }`, a list of `{ op, path, value }` entries where `op` is `add`, `remove` or `replace` and `path` is a JSON Pointer such as `/role`. A `remove` has no `value`. Nested objects are compared key by key, and `Date`, `RegExp`, `Set` and `Map` values by content.

| Option | Default | What it does |
| --- | --- | --- |
| `redactPaths` | none | Paths whose value is replaced, in the syntax of [`redact.paths`](/events/redaction#narrow-it-or-extend-it) |
| `replacement` | `'[REDACTED]'` | The text that replaces a redacted value |
| `includeBefore` | `false` | Adds the redacted `before` snapshot next to the patch |
| `includeAfter` | `false` | Adds the redacted `after` snapshot next to the patch |

Diff the fields that carry meaning, not the whole database row. Strip computed columns, password hashes, internal flags and large JSON blobs first: a status going from `paid` to `refunded` is an audit fact, a `lastModified` timestamp ticking is noise.
