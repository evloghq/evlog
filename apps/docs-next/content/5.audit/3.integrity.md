An audit event on your main drain is one row among millions, sampled, purged and editable like the rest. Four things make it evidence: request context on every event, a drain of its own, a guarantee that sampling never drops it, and a signature. Each is one function from `evlog`, and each is optional.

```typescript [evlog.config.ts]
import { auditEnricher, auditOnly, defineEvlog, signed } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createFsDrain } from 'evlog/fs'
import { composeDrains } from 'evlog/toolkit'

export default defineEvlog({
  service: 'my-app',
  enrich: auditEnricher(),
  drain: composeDrains([
    createAxiomDrain(),
    auditOnly(
      signed(createFsDrain({ dir: '.audit' }), { strategy: 'hash-chain' }),
      { await: true },
    ),
  ]),
})
```

This is the setup from [Audit](/audit#turn-it-on), written for any framework. `composeDrains` runs both drains at once and isolates their failures, so an Axiom outage does not stop the audit write.

## Add the request context

`auditEnricher()` runs on events that carry `audit` and leaves every other event alone. It fills `audit.context`:

| Field | Read from |
| --- | --- |
| `requestId` | The request id evlog assigned |
| `traceId` | `traceId` on the event |
| `ip` | The first address in `x-forwarded-for`, or `x-real-ip` |
| `userAgent` | `user-agent` |
| `tenantId` | Your `tenantId` function |

Without it `audit.context` stays empty, and an incident responder needs at least the request id and the IP to place a recorded action.

```typescript [server/plugins/evlog.ts]
nitro.hooks.hook('evlog:enrich', auditEnricher({
  tenantId: ctx => ctx.event.tenant as string | undefined,
  bridge: { getSession: async ctx => readSessionActor(ctx.headers) },
}))
```

| Option | Default | What it does |
| --- | --- | --- |
| `tenantId` | none | A function of the enrich context that returns the tenant id |
| `bridge.getSession` | none | Returns the actor of the current session. Used only when the event has no `actor` |
| `overwrite` | `false` | Replaces context fields that are already set |

If your context comes from somewhere else, write [your own enricher](/events/enrichers#your-own) in its place.

## Give audit events their own drain

`auditOnly(drain)` forwards an event to the drain only when it has an `audit` field. It wraps any drain, including one you wrote. Three reasons to separate the two streams:

- Cost: audit volume is small next to product events, so a long retention on that dataset alone stays cheap.
- Permissions: the audit dataset can be read-only for engineers and write-only for the app.
- Retention: audit trails are kept for seven years or more, and product logs rarely outlive 90 days.

By default the wrapped drain is called and not awaited, like any drain. With `{ await: true }` the drain step that carries the audit event finishes only when the write has landed:

```typescript [evlog.config.ts]
auditOnly(createFsDrain({ dir: '.audit' }), { await: true })
```

It costs one awaited drain call per request that records an audit. Without it, a crash between the emit and the flush leaves an action that happened and no row that says so. On runtimes with `waitUntil` (Next.js, Cloudflare Workers, Vercel Edge), that step runs after the response and the runtime stays alive until the write lands. An audit recorded inside `log.fork()` is drained by the child event, so `await log.fork(...)` when the write must land before the handler returns.

## Kept past sampling

Any event with an `audit` field skips every rule that drops events: head [sampling](/events/sampling) rates, the `sampling.minLevel` floor, and `log.discard()`. There is no option to turn this off, and nothing to configure to get it. Do not sample or summarize audit events downstream either.

## Sign the events

`signed(drain, options)` adds integrity fields to each audit event before the wrapped drain receives it. Events without `audit` pass through unsigned.

| Strategy | Adds | Detects |
| --- | --- | --- |
| `hmac` | `audit.signature`, an HMAC of the event | An edit to that event |
| `hash-chain` | `audit.prevHash` and `audit.hash` | An edit, and also a deleted or reordered event |

::hash-chain-tamper
::

With `hmac`, each event is signed on its own with your secret. Editing a row breaks that row and no other:

```typescript [evlog.config.ts]
signed(drain, { strategy: 'hmac', secret: process.env.AUDIT_SECRET! })
```

With `hash-chain`, each event's hash covers the hash before it, so removing a row breaks the chain from that point on. The chain head is kept in memory unless you give it a store:

```typescript [evlog.config.ts]
import fs from 'node:fs/promises'

signed(drain, {
  strategy: 'hash-chain',
  state: {
    load: () => fs.readFile('.audit/head', 'utf8').catch(() => null),
    save: (h) => fs.writeFile('.audit/head', h),
  },
})
```

::callout{icon="i-lucide-triangle-alert" color="neutral"}
Without `state`, the chain starts over each time the process starts, and two instances write two unrelated chains. Pass `state` backed by a file, Redis or Postgres for any chain that must outlive one process.
::

| Option | Strategy | Default | What it does |
| --- | --- | --- | --- |
| `secret` | `hmac` | required | The signing key |
| `state.load` | `hash-chain` | none | Returns the last hash, or `null` on the first run. Called once, before the first audit event |
| `state.save` | `hash-chain` | none | Stores the new hash. Called after each audit event |
| `algorithm` | both | `'sha256'` | `'sha256'` or `'sha512'` |

A chained drain handles one event at a time, in order, and awaits the wrapped drain. If signing or the write fails, it prints `[evlog/audit] signed drain failed` and moves on to the next event. `signed()` needs Web Crypto (`globalThis.crypto.subtle`), which Node, Bun, Deno, browsers and Cloudflare Workers provide.

Signing detects tampering. It does not prevent it: someone with write access to the store can still delete the file or the table, and the chain shows that events are missing. If the store is already append-only (S3 Object Lock, a Postgres table with immutable rows, BigQuery append-only tables), `signed()` adds latency and no protection.

evlog ships no command that verifies a chain. Comparing each `prevHash` with the `hash` of the event before it finds a deleted or reordered event. Finding an edit inside one event means recomputing its hash, and evlog does not export the serialization it hashes.

Rotate an HMAC secret once a year. Store a key id next to the signature, for example by extending `AuditFields` with `keyId` through `declare module 'evlog'`, so a verifier looks the key up by id and events signed with the previous secret stay verifiable.

## Redact what an audit event carries

Audit events go through the same [redaction](/events/redaction) as every event. `auditRedactPreset` is a stricter list of paths to add to yours:

```typescript [evlog.config.ts]
import { auditRedactPreset, defineEvlog } from 'evlog'

export default defineEvlog({
  service: 'my-app',
  redact: {
    paths: [
      ...(auditRedactPreset.paths ?? []),
    ],
  },
})
```

The preset names `authorization`, `cookie`, `set-cookie`, `password`, `passwordHash`, `token`, `apiKey`, `secret`, `accessToken`, `refreshToken`, `cardNumber`, `cvv` and `ssn`. Each matches that key at any depth, including inside `audit.changes.before` and `audit.changes.after`. The email and card patterns keep masking partially, so the trail stays readable.

A `changes.patch` entry holds its value under the key `value`, which no path names. Redact it at the source, with the `redactPaths` option of [`auditDiff()`](/audit/recording#record-what-changed).

## Erasure requests

An append-only trail collides with the right to be forgotten in GDPR. The pattern that keeps both:

1. Keep audit rows immutable.
2. Encrypt the personal fields with one key per actor, held outside the audit store.
3. To forget a user, delete their key. The row stays, the chain stays valid, and the personal data is unreadable.

evlog has no helper for this. The encryption happens in your code, before `log.audit()`.

## Retention

evlog does not enforce a retention window. The store does:

| Drain | Mechanism |
| --- | --- |
| [File system](/drains/fs) | `maxFiles` on `createFsDrain` deletes the oldest files |
| Postgres | A scheduled `DELETE FROM audit_events WHERE timestamp < now() - interval '7 years'` |
| Axiom, Datadog, Loki | The retention policy of the dataset, set in the platform |
| S3 Object Lock | Lifecycle rules and an Object Lock retention period |

Write the window down in your security policy. An auditor checks the written rule.

## What this covers

SOC 2, HIPAA, GDPR and PCI ask an audit trail the same questions: who, what, when, from where, with which outcome, and how you know nobody changed it.

| Question | Answered by |
| --- | --- |
| Who, what, with which outcome | `actor`, `action`, `target`, `outcome`, `reason` on [the audit field](/audit#the-audit-field) |
| When | `timestamp` on the event |
| From where | `audit.context`, from `auditEnricher()` |
| Was every action recorded | Audit events skip sampling, and `await: true` closes the crash window |
| Was it changed afterwards | `signed()` makes an edit or a deletion detectable |

What evlog leaves to you:

- Preventing deletion. That takes an append-only store.
- Verifying the chain. No verifier ships today.
- Retention and erasure, which belong to the store and to your code.
- Coverage. An action nobody calls `log.audit()` for is not in the trail. Record denials as well as successes, and jobs as well as routes.
- The written policy an auditor reads first.
