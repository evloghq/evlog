An auditor asks who refunded invoice 1842, and who tried to without permission. A request log answers how a request behaved. An audit event answers who tried to do what, and whether it was allowed.

::emits{step="allowed"}
```typescript [route:POST /api/invoices/refund]
log.audit({
  action: 'invoice.refund',
  actor: { type: 'user', id: user.id, email: user.email },
  target: { type: 'invoice', id: invoice.id },
  outcome: 'success',
  reason: 'Customer requested refund',
})
```
::

An audit event is a wide event with a reserved `audit` field. Drains, enrichers and redaction apply to it as they do to any event, so there is no second logging library and no parallel pipeline. [Sampling](/events/sampling) is the one exception: an event that carries `audit` is always kept.

::audit-force-keep
::

`log.audit()` is on the logger every integration hands you: `useLogger()`, `c.get('log')`, `req.log`. A job or a script has no request, and calls the standalone `audit()` instead. [Recording](/audit/recording) covers both, with the typed catalog and the diff helper.

## Turn it on

`log.audit()` needs no setup: the event goes wherever your events already go. Two additions turn it into an audit trail, an enricher that records where the request came from and a second drain that receives only audit events and signs them.

```typescript [server/plugins/evlog.ts]
import { auditEnricher, auditOnly, signed } from 'evlog'
import { createAxiomDrain } from 'evlog/axiom'
import { createFsDrain } from 'evlog/fs'

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('evlog:enrich', auditEnricher())
  nitro.hooks.hook('evlog:drain', createAxiomDrain())
  nitro.hooks.hook('evlog:drain', auditOnly(
    signed(createFsDrain({ dir: '.audit' }), { strategy: 'hash-chain' }),
    { await: true },
  ))
})
```

| Piece | What it does |
| --- | --- |
| `auditEnricher()` | Adds the request id, trace id, IP and user agent to `audit.context` |
| `auditOnly(drain)` | Sends only audit events to that drain. `{ await: true }` waits for the write instead of firing it and moving on |
| `signed(drain, { strategy })` | Chains each event to the previous one (`hash-chain`) or signs it with a secret (`hmac`), so an edit or a deletion is detectable |

The main drain keeps audit events next to the rest of your events, so your dashboards and queries cover them. The signed drain is the copy that still holds the chain when the main store has an outage, gets purged, or loses a row.

::audit-dual-sink
::

The `evlog:*` hooks exist on Nuxt and Nitro. [Integrity](/audit/integrity) has the wiring for the other frameworks, and the options of each piece.

## Record a denial

The action that was refused is the one an auditor asks about first, and the one most teams forget to log:

::emits{step="denied"}
```typescript [route:POST /api/invoices/refund]
if (!user.canRefund(invoice)) {
  log.audit.deny('Insufficient permissions', {
    action: 'invoice.refund',
    actor: { type: 'user', id: user.id },
    target: { type: 'invoice', id: invoice.id },
  })
  throw createError({ status: 403, message: 'Forbidden' })
}
```
::

`log.audit.deny(reason, fields)` is `log.audit()` with `outcome: 'denied'` and the reason filled in.

## The audit field

`audit` is typed as `AuditFields` on every wide event. In a store that holds all your events, `audit IS NOT NULL` selects the audit trail.

| Field | Type | Set by | What it holds |
| --- | --- | --- | --- |
| `action` | `string` | You | What was attempted, such as `invoice.refund` |
| `actor` | object | You | Who attempted it |
| `target` | `{ type, id, ...extra }` | You | The resource. Extra keys are allowed |
| `outcome` | `'success' \| 'failure' \| 'denied'` | You | How it ended. `log.audit()` defaults to `success` |
| `reason` | `string` | You | Why, in words. Expected on a denial |
| `changes` | `{ before?, after?, patch? }` | You | What changed, from [`auditDiff()`](/audit/recording#record-what-changed) |
| `causationId` | `string` | You | Id of the action that caused this one |
| `correlationId` | `string` | You | Id shared by every action of one operation |
| `version` | `number` | evlog | Schema version of the field, `1` |
| `idempotencyKey` | `string` | evlog | A stable key for the event, derived when it is emitted |
| `context` | object | `auditEnricher()` | `requestId`, `traceId`, `ip`, `userAgent`, `tenantId` |
| `signature` | `string` | `signed()` with `hmac` | HMAC of the event |
| `prevHash`, `hash` | `string` | `signed()` with `hash-chain` | Hash of the previous event, and of this one |

`action`, `actor.type` and `actor.id` are the minimum. An `audit` object without them gets no `idempotencyKey`.

### Say who acted

`actor` takes a `type`, an `id`, and optionally `displayName` and `email`.

| `actor.type` | Use it for |
| --- | --- |
| `user` | A person authenticated through your normal auth flow |
| `system` | Cron jobs, queue workers, scheduled tasks, background processes |
| `api` | A call from another service, authenticated by a token |
| `agent` | An AI tool call. `model`, `tools`, `reason` and `promptId` describe it, as in [the AI SDK integration](/extend/ai-sdk) |

Record the real actor. A synthetic `user` on a job that no person triggered is the fastest way to fail an audit review. `actor.id` is the stable id of the user or the system, never a session id: sessions correlate through `context.requestId` and `context.traceId`.

### Record how it ended

| `outcome` | Meaning |
| --- | --- |
| `success` | The action completed as requested |
| `failure` | The action was attempted and failed: a downstream error, a race |
| `denied` | An authorization check refused the action |

`failure` and `denied` are different facts. A run of denials signals probing or a misconfigured permission.

### Name the action

Write `action` as `noun.verb`: `invoice.refund`, `user.invite`, `apiKey.revoke`. Use the past tense when the action already happened (`invoice.refunded`). Alert rules query on `action`, so a typo is a missed alert. Keep the names in one file, or in a [typed catalog](/audit/recording#name-your-actions) once there are more than a handful.

### Make a retry safe

evlog derives `idempotencyKey` when the event is emitted: 32 hexadecimal characters hashed from `action`, the actor's `type` and `id`, the target's `type` and `id`, `outcome`, and the timestamp cut to the second. A drain that retries a write sends the same key, so make it the primary key of your audit table and the duplicate collapses on `ON CONFLICT DO NOTHING`. The same actor repeating the same action on the same target within one second also gets one key.

### Tie an action to its cause

Set `correlationId` on every audit event of one operation, such as a request that triggers a refund, an email and a webhook. Most teams use the request id. `causationId` is the id of the audit event that caused this one. Fill it only when one user action triggers a chain of internal ones.
