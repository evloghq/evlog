You adopted evlog in the routes you touched last week. `evlog map` tells you about the other forty: which entry points have no wide event, no context, no structured error, and which of them move money or touch auth.

```bash [Terminal]
pnpm dlx evlog map
```

Run `evlog map <file>` on one of them to see the shape the rules expect, fix it, and run the map again.

## What it reads

The scan reads your source with an AST and applies a versioned rule set: `useLogger()` and `log.set()` on every entry point, `createError({ why, fix })` where it throws, `log.audit()` where it moves money or touches auth. It does not run your handlers or watch traffic, so it works on an app that shipped three years ago and on a scaffold alike, and the same source with the same CLI version produces the same score on any machine.

That is also its limit: a high score says the recognized patterns are in place. It does not prove the logs reach your drain or hold enough context to explain a failure.

Supported today: Nuxt, Nitro, Next.js App Router, TanStack Start, Hono, Express and Fastify.

## Gate it in CI

| Flag | The question it answers |
| --- | --- |
| `--min-score <n>` | Is the app good enough? Exits 1 below the threshold |
| `--baseline` | Did this pull request make it worse? Compares with the committed `evlog.map.json` and fails on a regression |
| `--json --no-write` | Structured output for an agent or a script, without touching the baseline |

Commit `evlog.map.json` once, then run `evlog map --baseline` on every pull request. A legacy app that starts at 34 and never regresses is in better shape than a new one at 80 that drifts.

::callout{icon="i-lucide-flask-conical" color="warning"}
The rule set is young, and a release that sharpens a rule can change a verdict on code you did not touch. Pin the CLI version in CI if you gate on the score.
::
