`throw new Error('Payment failed')` tells you that something broke. It does not say whether the card was declined or your Stripe key expired, and it says nothing to the user. A structured error carries both:

::code-group
```typescript [route:POST /api/checkout]
import { createError } from 'evlog'

throw createError({
  message: 'Payment failed',
  status: 402,
  why: 'Card declined by issuer',
  fix: 'Try a different payment method',
  link: 'https://docs.example.com/payments/declined',
})
```
```json [Response]
{
  "status": 402,
  "message": "Payment failed",
  "data": {
    "why": "Card declined by issuer",
    "fix": "Try a different payment method",
    "link": "https://docs.example.com/payments/declined"
  }
}
```
::

The error lands on the wide event of the request that threw it, with `why`, `fix` and `link` at the top of `error`, next to the context the request had already collected.

## The fields

| Field | Required | What it is for |
| --- | --- | --- |
| `message` | Yes | What happened, in words a user can read |
| `status` | No | The HTTP status. Leave it unset outside HTTP: an HTTP boundary answers 500 when it is missing |
| `why` | No | The technical reason, for whoever debugs it |
| `fix` | No | What to do about it |
| `link` | No | A page that explains it |
| `cause` | No | The error you are wrapping |
| `internal` | No | Fields for the logs only, never sent in the HTTP response |
| `data` | No | Your own payload, sent in the response and logged under `error.data` |

## Read it on the client

`parseError()` takes whatever your fetch threw and gives back the same fields:

```typescript [composables/useCheckout.ts]
import { parseError } from 'evlog'

try {
  await $fetch('/api/checkout', { method: 'POST', body: cart })
} catch (err) {
  const error = parseError(err)
  toast.add({ title: error.message, description: error.why, color: 'error' })
}
```

## Errors outside HTTP

A job, a cron task or an agent turn has no status to return. In evlog 3, `status` is optional and an error without one logs no `status` field at all, so a failed export does not show up as a `500` on your dashboards.
