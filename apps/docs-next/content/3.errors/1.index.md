`throw new Error('Payment failed')` tells you that something broke. It does not say whether the card was declined or your Stripe key expired, and it says nothing to the user. A structured error carries both:

::emits{step="error"}
:::code-group
```typescript [route:POST /api/checkout]
import { createError } from 'evlog'

throw createError({
  message: 'Payment failed',
  status: 402,
  why: 'Card declined by issuer',
  fix: 'Try a different payment method',
  link: 'https://docs.example.com/payments/declined',
})
```
```json [Response]
{
  "status": 402,
  "message": "Payment failed",
  "data": {
    "why": "Card declined by issuer",
    "fix": "Try a different payment method",
    "link": "https://docs.example.com/payments/declined"
  }
}
```
:::
::

The error lands on the wide event of the request that threw it, with `why`, `fix` and `link` at the top of `error`, next to the context the request had already collected.

## The fields

| Field | Required | What it is for |
| --- | --- | --- |
| `message` | Yes | What happened, in words a user can read |
| `code` | No | A stable identifier that clients and dashboards branch on, such as `PAYMENT_DECLINED` |
| `status` | No | The HTTP status. Leave it unset outside HTTP: an HTTP boundary answers 500 when it is missing |
| `why` | No | The technical reason, for whoever debugs it |
| `fix` | No | What to do about it |
| `link` | No | A page that explains it |
| `cause` | No | The error you are wrapping |
| `internal` | No | Fields for the logs only, never sent in the HTTP response |
| `data` | No | Your own payload, sent in the response and logged under `error.data` |

`createError()` returns an `EvlogError`, a subclass of `Error`: throw it, reject with it, or pass it to `log.error()`. A string is shorthand for the message alone, as in `createError('Something went wrong')`.

- `createEvlogError` is the same function, for files where a framework owns the name `createError`. On Nuxt the auto-imported `createError` is Nuxt's and drops `why`, `fix` and `link`, so import evlog's from `evlog` or call the auto-imported `createEvlogError`.
- `EvlogError.isEvlogError(error)` tells you whether a caught value is one. Unlike `instanceof`, it matches an error created by a second copy of evlog in `node_modules`.
- The status is `error.status` and the text is `error.message`. evlog 3 removed `statusCode`, `statusText` and `statusMessage`: see [Error status fields](/start/upgrade#error-status-fields).

### Say why it broke and what to do

`message`, `why`, `fix` and `link` all travel to the client, so write them for the person who reads them. `fix: 'Try again'` gives the user nothing to act on. `why: 'File exceeds maximum size (10MB)'` with `fix: 'Reduce the file size or compress the image before uploading'` does.

Leave `fix` out when the user cannot act. The status says who can:

| Status | When | What to write |
| --- | --- | --- |
| `400` | The client sent something it can correct | A `fix` that names the correction: `Please enter a valid email address` |
| `401` | The request needs authentication | A `fix` and a `link` to the sign-in page |
| `404` | The resource does not exist | The `message` alone is enough |
| `500` | The server failed | A `why` such as `Database connection timeout`, and no `fix` |

### A payload for the client

`why`, `fix` and `link` are strings a person reads. When the client needs values it branches on, such as an order id, a retry deadline or a list of invalid fields, pass them as `data`:

```typescript
throw createError({
  code: 'PAYMENT_DECLINED',
  message: 'Payment could not be completed',
  status: 402,
  fix: 'Try another payment method',
  data: {
    orderId: 'ord_8x2k',
    retryAfter: 30,
  },
})
```

The response body's `data` object holds the payload next to `code`, `why`, `fix` and `link`, and `error.data` on the server returns the same merged object. Those four keys win on a collision, so `data: { code: 'x' }` never overwrites the `code` you passed. h3's `createError` uses the same field, and evlog's Nitro error handler forwards it for h3 errors too.

### Context that stays on the server

`internal` is for what logs, drains and support tools need and a client must never see:

```typescript
throw createError({
  message: 'Payment could not be completed',
  status: 402,
  why: 'Your card was declined',
  fix: 'Try another payment method',
  internal: {
    correlationId: 'pay_8x2k',
    processorCode: 'insufficient_funds',
    rawIssuerResponse: '…', // never sent to the client
  },
})
```

- The response bodies evlog writes, and `toJSON()`, leave `internal` out.
- `parseError()` never returns it. On the server, the thrown error still carries it on `raw`.
- The wide event includes it as `error.internal` once the error is recorded.

Read it as `error.internal`. A debugger shows it under a symbol key: evlog stores it non-enumerable, so `JSON.stringify(error)` never exposes it.

### Wrap the error you caught

Pass the original as `cause`. The event logs it under `error.cause`, and `toJSON()` keeps only its `name` and `message`:

```typescript [services/checkout.ts]
import { createError } from 'evlog'

try {
  await stripe.charges.create(charge)
} catch (err) {
  throw createError({
    message: 'Payment processing failed',
    status: 500,
    why: 'Stripe API returned an error',
    cause: err, // Original error preserved
  })
}
```

## From the throw to the response

Throw the error inside a handler. It lands on the request's event, which sets the event's `level` to `error`, and the response takes the error's `status`. An error with no `status` answers 500. That default belongs to the HTTP boundary, not to the error: see [Status is optional](/start/upgrade#status-is-optional).

Who writes the body depends on the framework:

| Framework | Response body |
| --- | --- |
| Nuxt, Nitro, SvelteKit | evlog's error handler writes `url`, `status`, `message`, `error: true` and `data` ([Nitro and Nuxt error body](/start/upgrade#nitro-and-nuxt-error-body)) |
| Next.js | `withEvlog()` answers with `error.toJSON()`: `name`, `message`, `status`, `data`, and the `name` and `message` of the cause |
| [Hono](/integrations/hono#when-a-handler-throws), [Fastify](/integrations/fastify#errors) | You write it in the framework's error handler, from the fields `parseError()` returns |
| [Express](/integrations/express#errors) | The same, in the error middleware, where you also record the error with `req.log.error(err)` |

Each [integration](/integrations) page shows its handler.

## What the event records

`log.error(err)` serializes the error into the event's `error` field. The server and the browser share the serializer.

- The logged error has `name`, `message` and `stack`, then `code`, `status`, `data`, `internal`, `why`, `fix`, `link` and `cause` when they are set. A cycle is logged as `'[Circular]'`.
- `code`, `why`, `fix` and `link` are logged on any error that carries them, not only on an `EvlogError`. `status` is read from `status`, then from h3's `statusCode`.
- A logged `EvlogError` carries `code`, `why`, `fix` and `link` once, at the top of `error`. `error.data` is only the payload you passed, and it is absent when you passed none ([Logged error guidance](/start/upgrade#logged-error-guidance)).
- An `Error` anywhere inside a `log.*({ ... })` event is serialized the same way. On the server `log.set()` does it too. The browser logger has no `log.set()`: see [Client logging](/events/client).
- An object that is not an `Error` and defines its own `toJSON` is kept as it is, so that method decides how it is written out.
- The request logger's `error()` also takes a string, which it wraps in an `Error`, and a second argument of fields to merge into the event.

### A second error replaces the first

An event has one `error` field. A second `log.error()` on the same logger replaces every field the first one wrote, so the event describes the last error only. Fields you put on `error` yourself with `log.set()`, or through the second argument of `error()`, stay. To keep both failures, record the earlier one under its own key, which serializes it the same way:

```typescript
log.set({ stockSync: { error: orderErrors.STOCK_SYNC_FAILED() } })
```

evlog 2 merged the two errors. [A second error replaces the first](/start/upgrade#a-second-error-replaces-the-first) has the difference.

### Errors h3 wraps

When you pass a caught error to h3's `createError(err)`, h3 keeps it as `cause` and takes over its message and stack. evlog logs the pair once: the original error, with the wrapper's `status` and `data` added. The message, stack and `cause` are not repeated.

When you pass an options object, as in `createError({ statusCode: 402, message: 'Payment could not be completed' })`, h3 keeps that object as `cause`. evlog drops it when every field in it is already on the error, so the logged error keeps `status: 402` and has no `cause`.

### An error with its own `toJSON`

For a custom `Error` that defines `toJSON`, that method decides how `data` and `internal` are logged:

- A key `toJSON` leaves out, or sets to `undefined`, is not logged.
- A value `toJSON` rewrites is logged as rewritten, not raw.

`name`, `message`, `stack`, `code`, `status`, `why`, `fix` and `link` are read from the error itself, whatever `toJSON` returns.

::code-group
```typescript [server/utils/payment-error.ts]
class PaymentError extends Error {
  constructor(message: string, readonly data: { orderId: string, cardNumber: string }) {
    super(message)
  }

  toJSON() {
    return { name: this.name, message: this.message, data: { orderId: this.data.orderId, cardNumber: '[REDACTED]' } }
  }
}

log.error(new PaymentError('Card declined', { orderId: 'ord_1', cardNumber: '4242424242424242' }))
```
```json [Logged error (trimmed)]
{
  "name": "Error",
  "message": "Card declined",
  "data": { "orderId": "ord_1", "cardNumber": "[REDACTED]" }
}
```
::

`toJSON` covers only the error that defines it. To mask a value wherever it appears in an event, use [redaction](/events/redaction). `EvlogError` is the exception: its `toJSON` shapes the HTTP response and leaves `internal` out, and the log keeps `internal`.

## Record an error and still respond

Some failures should not fail the request, such as a receipt email that did not send after the order was saved. Catch the error, pass it to the request logger's `error()`, and return your normal response:

```typescript [server/api/orders.post.ts]
import { orderErrors } from '~/errors/orders'

export default defineEventHandler(async (event) => {
  const log = useLogger(event)
  const order = await createOrder(event)
  log.set({ order: { id: order.id } })

  try {
    await sendReceipt(order)
  }
  catch (error) {
    log.error(orderErrors.RECEIPT_EMAIL_FAILED({ cause: error }))
  }

  return order
})
```

The request still emits one wide event. Its `level` is `error`, so [sampling](/events/sampling) applies the `error` rate, 100% by default, and its `status` is the one you answered with:

```json [Logged event (trimmed)]
{
  "level": "error",
  "status": 200,
  "order": { "id": "ord_1" },
  "error": {
    "name": "EvlogError",
    "message": "Receipt email not sent",
    "code": "orders.RECEIPT_EMAIL_FAILED",
    "why": "The email provider timed out",
    "cause": { "name": "Error", "message": "ETIMEDOUT" }
  }
}
```

## Errors outside HTTP

A job, a cron task or an agent turn has no status to return. In evlog 3, `status` is optional and an error without one logs no `status` field at all, so a failed export does not show up as a `500` on your dashboards.

Create the error as a value and record it with `log.error()`. Nothing is thrown, so the work keeps running:

```typescript [jobs/export.ts]
import { createError, log } from 'evlog'

const err = createError({
  message: 'Export job stalled',
  why: 'No progress for 5 minutes',
  fix: 'Retry the job',
})

log.error(err) // recorded on the wide event, the job carries on
```

```json [Logged event (trimmed)]
{
  "level": "error",
  "error": {
    "name": "EvlogError",
    "message": "Export job stalled",
    "why": "No progress for 5 minutes",
    "fix": "Retry the job"
  }
}
```

## Read it on the client

`parseError()` takes whatever your fetch threw and gives back the same fields:

```typescript [composables/useCheckout.ts]
import { parseError } from 'evlog'

try {
  await $fetch('/api/checkout', { method: 'POST', body: cart })
} catch (err) {
  const error = parseError(err)
  toast.add({ title: error.message, description: error.why, color: 'error' })
}
```

| Field | Type | What it holds |
| --- | --- | --- |
| `message` | `string` | The error's message. `An error occurred` when a response body has none |
| `status` | `number` | The HTTP status, `500` when the error has none |
| `code` | `string` | The `code` of the error, or the `code` of a Node-style error such as `ENOENT` or `ECONNRESET` |
| `why`, `fix`, `link` | `string` | The guidance, absent when the error has none |
| `data` | `object` | The response's `data`: your payload merged with `code`, `why`, `fix` and `link`. Absent when there is no payload |
| `raw` | `unknown` | The value you passed in, for debugging |

It accepts an ofetch `FetchError`, an `EvlogError` caught on the server, an h3 error and any other `Error`. A value that is not an error becomes `{ message: String(value), status: 500 }`. `internal` never appears in the result. Read your payload from `data`:

```typescript
const { data } = parseError(error)
if (typeof data?.retryAfter === 'number') scheduleRetry(data.retryAfter)
```

### Branch on the code

A `message` changes with the copy, and many failures share a status. Branch on `code`, which you control:

::structured-error-branching
::

```typescript [composables/useCheckout.ts]
import { parseError } from 'evlog'

try {
  await $fetch('/api/checkout', { method: 'POST', body: cart })
} catch (err) {
  const error = parseError(err)

  switch (error.code) {
    case 'PAYMENT_DECLINED':
      return showRetryWithDifferentCard()
    case 'CART_EXPIRED':
      return rebuildCart()
    default:
      return toast.add({ title: error.message, color: 'error' })
  }
}
```

The same `code` is on the wide event as `error.code`, so a dashboard groups and alerts on it without parsing messages.

## In the dev terminal

With `pretty` on, the default in development, a failed request prints as a wide event with the `error` block first and the request context under it. The block shows the message, the file and line of the throw with a code snippet, then `Code`, `Why`, `Fix`, `More` for the link, `Caused by`, and the stack with its `node_modules` frames counted and hidden.

On Nuxt and Nitro, the framework prints its own `[request error]` overlay for the same failure. `dev` picks which of the two you see:

| `dev` | evlog prints | Nitro overlay |
| --- | --- | --- |
| `'evlog'`, the default in pretty dev | The full error block | Hidden |
| `'nitro'` | The message and its guidance, with no location or stack | Shown, with Nitro's Youch stack |
| `'both'` | The full error block | Shown |
| `{ frameworkOverlay: false }` with `pretty: false` | JSON lines | Hidden |

The object form takes `frameworkOverlay`, `false` by default in pretty dev and `true` otherwise, and `prettyError`:

| `prettyError` option | Default | What it does |
| --- | --- | --- |
| `detail` | `'full'`, or `'guidance'` when the overlay is shown | `'guidance'` prints `Code`, `Why`, `Fix`, `More` and `Caused by` with no location, snippet or stack |
| `snippet` | `true` in pretty dev with `detail: 'full'` | Prints the source lines around the throw |
| `stackDepth` | `2` when `compact`, otherwise `3` | App frames listed after the throw site. `0` when `detail` is `'guidance'` |
| `compact` | `true` in pretty dev | One line of context around the snippet instead of two |

[Configuration](/reference/configuration) lists `dev` with the other logger options.
