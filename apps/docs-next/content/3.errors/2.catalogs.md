The third time you write `createError({ status: 404, message: 'User not found' })`, the message, the status and the code have already started to drift. A catalog defines each error once:

```typescript [src/errors.ts]
import { defineErrorCatalog } from 'evlog'

export const errors = defineErrorCatalog('app', {
  USER_NOT_FOUND: { status: 404, message: 'User not found' },
  FORBIDDEN: { status: 403, message: 'Forbidden' },
  VALIDATION_FAILED: {
    status: 400,
    message: ({ field }: { field: string }) => `Invalid ${field}`,
  },
})
```

Each key becomes a factory. Throw it with the parameters its message needs:

```typescript [route:GET /api/users]
throw errors.USER_NOT_FOUND()
throw errors.VALIDATION_FAILED({ field: 'email' })
```

The error's `code` is `${prefix}.${KEY}`, here `app.USER_NOT_FOUND`. That string is what reaches the HTTP response, the wide event and your dashboards, so keep the convention across services and a code from one is recognizable in another.

## Conventions

| | Convention | Example |
| --- | --- | --- |
| Key | `UPPER_SNAKE_CASE` | `PAYMENT_DECLINED` |
| Prefix | `lower.dot.case`, can nest | `billing`, `billing.payment` |
| Code | `${prefix}.${KEY}` | `billing.PAYMENT_DECLINED` |
| One catalog | One bounded context, one prefix, one file | `errors/billing.ts` |

## Autocomplete on the code

Register the catalogs once, and `createError({ code })` and `parseError(err).code` complete the codes you defined:

```typescript [src/errors/index.ts]
declare module 'evlog' {
  interface RegisteredErrorCatalogs {
    billing: typeof billingErrors
  }
}
```

The augmentation is type-only: there is nothing to initialize at runtime. In tests, compare against `billingErrors.PAYMENT_DECLINED.code` instead of a string, so a rename fails type-checking instead of silently passing.

Audit actions have the same shape, with `defineAuditCatalog`. See [Audit](/audit).
