The third time you write `createError({ status: 404, message: 'User not found' })`, the message, the status and the code have already started to drift. A catalog defines each error once:

::emits{step="catalog"}
```typescript [src/errors.ts]
import { defineErrorCatalog } from 'evlog'

export const errors = defineErrorCatalog('app', {
  USER_NOT_FOUND: { status: 404, message: 'User not found' },
  FORBIDDEN: { status: 403, message: 'Forbidden' },
  VALIDATION_FAILED: {
    status: 400,
    message: ({ field }: { field: string }) => `Invalid ${field}`,
  },
})
```

Each key becomes a factory. Throw it with the parameters its message needs:

```typescript [route:GET /api/users]
throw errors.USER_NOT_FOUND()
throw errors.VALIDATION_FAILED({ field: 'email' })
```
::

The error's `code` is `${prefix}.${KEY}`, here `app.USER_NOT_FOUND`. That string is what reaches the HTTP response, the wide event and your dashboards, so keep the convention across services and a code from one is recognizable in another.

## Conventions

| | Convention | Example |
| --- | --- | --- |
| Key | `UPPER_SNAKE_CASE` | `PAYMENT_DECLINED` |
| Prefix | `lower.dot.case`, can nest | `billing`, `billing.payment` |
| Code | `${prefix}.${KEY}` | `billing.PAYMENT_DECLINED` |
| One catalog | One bounded context, one prefix, one file | `errors/billing.ts` |

The key keeps its casing in the code. The layout changes with the size of the app, and the API does not:

| Size | Layout |
| --- | --- |
| Small | One `src/errors.ts` with one catalog |
| Medium | One file per domain in `src/errors/` (`billing.ts`, `auth.ts`, `user.ts`), and an `index.ts` that re-exports them and holds the type registration |
| Large | One catalog per sub-domain, with a nested prefix: `defineErrorCatalog('billing.payment', { DECLINED: ... })` gives `billing.payment.DECLINED` |
| Monorepo | [One npm package](#ship-a-catalog-as-a-package) per bounded context, each owning its prefix |

## What an entry takes

`defineErrorCatalog(prefix, map)` takes the prefix and a map of entries. Only `message` is required:

| Option | Type | What it does |
| --- | --- | --- |
| `message` | `string` or `(params) => string` | What happened. A function makes its params required and typed at the call site |
| `status` | `number` | The HTTP status. Leave it out for an error that never becomes a response |
| `why` | `string` | The technical reason |
| `fix` | `string` | What to do about it |
| `link` | `string` | A page that explains it |
| `internal` | `Record<string, unknown>` | Server-only context, merged with the `internal` of each call |
| `tags` | `readonly string[]` | Labels for your own grouping. They stay on the factory: not on the error, the response or the event |

A catalog with every kind of entry, used in the examples below:

```typescript [errors/billing.ts]
import { defineErrorCatalog } from 'evlog'

export const billingErrors = defineErrorCatalog('billing', {
  CART_EMPTY: {
    status: 400,
    message: 'Cart is empty',
  },
  PAYMENT_DECLINED: {
    status: 402,
    message: 'Card declined',
    why: 'Issuer declined the charge',
    fix: 'Try a different payment method',
    link: 'https://docs.example.com/errors/billing.payment_declined',
  },
  INSUFFICIENT_FUNDS: {
    status: 402,
    message: ({ available, required }: { available: number, required: number }) =>
      `Insufficient funds: $${available} available, $${required} required`,
    fix: 'Add funds and retry',
  },
})
```

## What a call can change

A factory returns an `EvlogError` with the entry's defaults applied, so everything on [Errors](/errors) holds for it. The call can override some of them:

```typescript
// Catalog default:
// message: 'Card declined'
// internal: { category: 'gateway' }

throw billingErrors.PAYMENT_DECLINED({
  message: 'Custom message for this specific call',
  internal: { stripeRef: 'ch_x', category: 'gateway-overridden' },
  cause: stripeErr,
})

// Resulting EvlogError:
// - message: 'Custom message for this specific call' (override)
// - status: 402 (catalog default)
// - why: 'Issuer declined the charge' (catalog default)
// - internal: { category: 'gateway-overridden', stripeRef: 'ch_x' }
```

- A call can override `message`, `status`, `why`, `fix` and `link`, and pass a `cause`.
- `internal` is shallow-merged with the entry's, and the call wins on a shared key.
- `code` cannot be overridden. The catalog owns it, because dashboards, alerts and client code branch on it.
- A factory takes no `data`. For a client payload, call `createError()` with the entry's `code`.
- When `message` is a function, its params are required and type-checked: `errors.VALIDATION_FAILED()` does not compile.

## On the event

A catalog error is logged like any other structured error, with the entry's `code` at `error.code`. An entry without a `status` logs none, which is what a job, an agent turn or a CLI script wants. Call the factory to get the error as a value and record it with `log.error()`:

```typescript [jobs/export.ts]
import { defineErrorCatalog, log } from 'evlog'

const jobs = defineErrorCatalog('job', {
  EXPORT_STALLED: {
    message: 'Export job stalled',
    why: 'No progress for 5 minutes',
    fix: 'Retry the job',
  },
})

log.error(jobs.EXPORT_STALLED()) // recorded on the wide event, the job carries on
```

```json [Logged event (trimmed)]
{
  "level": "error",
  "error": {
    "name": "EvlogError",
    "message": "Export job stalled",
    "code": "job.EXPORT_STALLED",
    "why": "No progress for 5 minutes",
    "fix": "Retry the job"
  }
}
```

An HTTP boundary answers 500 for an error that reaches it without a `status`. Inside a request, the request logger records a catalog error the same way and the handler still returns: see [Record an error and still respond](/errors#record-an-error-and-still-respond).

## Read the catalog

Each factory exposes its entry as read-only properties: `code`, `status`, `message`, `why`, `fix`, `link`, `tags` and `internal`. The catalog adds `_prefix` and `_codes`, both non-enumerable, so `Object.keys(billingErrors)` returns the entry names only:

```typescript
billingErrors.PAYMENT_DECLINED.code   // 'billing.PAYMENT_DECLINED'
billingErrors.PAYMENT_DECLINED.status // 402
billingErrors._codes
// readonly [
//   'billing.CART_EMPTY',
//   'billing.PAYMENT_DECLINED',
//   'billing.INSUFFICIENT_FUNDS',
// ]
```

## One error without a catalog

`defineError(code, entry)` builds a single factory. It takes the same entry and returns the same factory, and you write the full code yourself. Use it for an error that belongs to no domain, such as a rate limit:

```typescript [src/errors/index.ts]
import { defineError, defineErrorCatalog } from 'evlog'

export const billingErrors = defineErrorCatalog('billing', {
  PAYMENT_DECLINED: { status: 402, message: 'Card declined' },
})

export const rateLimited = defineError('app.RATE_LIMITED', {
  status: 429,
  message: ({ retryAfter }: { retryAfter: number }) =>
    `Rate limited: retry in ${retryAfter}s`,
})

// Both look identical at the call site:
throw billingErrors.PAYMENT_DECLINED()
throw rateLimited({ retryAfter: 30 })
```

## Autocomplete on the code

Register the catalogs once, and `createError({ code })` and `parseError(err).code` complete the codes you defined:

```typescript [src/errors/index.ts]
declare module 'evlog' {
  interface RegisteredErrorCatalogs {
    billing: typeof billingErrors
  }
}
```

The augmentation is type-only: there is nothing to initialize at runtime. In tests, compare against `billingErrors.PAYMENT_DECLINED.code` instead of a string, so a rename fails type-checking instead of silently passing.

The registry key is a name you choose. evlog reads the codes from each registered catalog and exports their union as `ErrorCode`:

```typescript
import type { ErrorCode } from 'evlog'

const validCode: ErrorCode = 'billing.PAYMENT_DECLINED' // OK
const invalidCode: ErrorCode = 'billing.NOPE' // type error once the catalog is registered
```

What the registration does and does not do:

- `createError({ code })` and `parseError(err).code` complete the registered codes and still accept any string, so a typo there compiles. Only a value typed `ErrorCode` rejects it.
- With no catalog registered, `ErrorCode` is `never` and `code` is a plain `string`.
- TypeScript merges `declare module 'evlog'` blocks across files. Put one at the bottom of a single catalog file, in `src/errors/index.ts` for a folder, or in each package's `src/index.ts`.
- Give each catalog its own key. A second declaration of the same key with another catalog is a type error.
- If nothing completes, the file with the augmentation is not in the TypeScript program: check the `include` of `tsconfig.json`.
- Keep the augmentation out of `*.test.ts`. When the main `tsconfig.json` includes the tests, it applies to the whole codebase.

## Ship a catalog as a package

A catalog is plain TypeScript with `evlog` as a peer dependency (`"evlog": "^3.0.0"`). Put the augmentation in the same file as the catalog, so the build emits it into the published `.d.ts`:

```typescript [packages/errors-billing/src/index.ts]
import { defineErrorCatalog } from 'evlog'

export const billingErrors = defineErrorCatalog('billing', {
  PAYMENT_DECLINED: {
    status: 402,
    message: 'Card declined',
    why: 'Issuer declined the charge',
    fix: 'Try a different payment method',
    link: 'https://docs.example.com/errors/billing.payment_declined',
  },
  // ...
})

declare module 'evlog' {
  interface RegisteredErrorCatalogs {
    billing: typeof billingErrors
  }
}
```

An app that imports `@acme/errors-billing` gets the factories and the completion with no setup of its own. Adding an entry is a minor release that consumers pick up through a normal upgrade.

Keep one prefix per package: `@acme/errors-billing` owns `billing.*`, `@acme/errors-auth` owns `auth.*`. Nothing checks this at runtime. Two catalogs with the same prefix and key produce the same code, and no reader of the event can tell them apart.

## API

Everything is exported from `evlog`.

| Symbol | Kind | What it is |
| --- | --- | --- |
| `defineErrorCatalog(prefix, map)` | function | Typed error factories under one prefix |
| `defineError(code, entry)` | function | One error factory, with the code you write |
| `ErrorCatalogEntry` | type | The options of one entry |
| `ErrorCode` | type | The union of every registered code |
| `RegisteredErrorCatalogs` | interface | The registry you augment |

Audit actions have the same shape, with `defineAuditCatalog`, `defineAuditAction`, `RegisteredAuditCatalogs` and the `AuditAction` type. See [Name your actions](/audit/recording#name-your-actions).
